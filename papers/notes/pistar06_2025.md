# pistar06_2025 — π*0.6: a VLA That Learns From Experience (Physical Intelligence, arXiv 2025)

sources: papers/md/pistar06_2025.md [sha256 9f4f5a30] ; code/md/pistar06_2025.md [commit 215abfb2]

## One-line contribution
RECAP: an offline-RL recipe that conditions a flow-matching VLA (π0*.6, built on π0.6/π0.5) on a
binarized advantage indicator from a learned value function, so the same architecture can be
trained from demonstrations, autonomous rollouts, and human corrections without policy-gradient
machinery (§IV–V).

## Setting
- hand(s): none — end-effector is a parallel-jaw gripper only; no multi-fingered/dexterous hand appears anywhere in the paper or the released code (see Evaluation block below).
- arm: "static bimanual system with two 6 DoF arms with parallel jaw grippers" (Fig. 5 caption); pre-training additionally uses "many different robots"/"multiple robot platforms" (§V-A, §V-D) but none are named or itemized in the paper text. Code repo (openpi, code/md lines 892-948) ships policies for ALOHA (bimanual, grippers, state dim 14), DROID (single Franka arm, parallel gripper), and LIBERO (sim, gripper) — all non-dexterous.
- simulator / physics: none — all results are real-robot; no sim is used for the RECAP experiments.
- observation: "camera images X, the robot's configuration q" plus language prompt ℓ and metadata s (§V-A, model equation for πθ). For the bimanual rig: "joint and gripper positions, as well as images from three cameras: a base camera mounted between the arms, and a wrist-mounted camera on each arm" (Fig. 5).
- action space: action chunks a_{t:t+H} = "joint angles and gripper commands at 50 Hz" (§V-A); exact chunk length H is not stated numerically anywhere in the parsed paper or code text.
- objects / data: task objects are t-shirts/shorts/11 clothing types, a commercial espresso machine, and flattened cardboard box sheets (§VI-A); no object-count table given.

## Method
- paradigm: VLA + offline RL (advantage-conditioned policy extraction), iterated over deployment cycles; base model is a flow-matching VLA (π0.6, descended from π0.5) trained with the Knowledge Insulation (KI) recipe [73].
- backbone VLM: "The base VLM is Gemma 3 [78] 4B model" (§V-A, listing π0.6's improvements over π0.5). The value function uses "the same architecture as the VLA policy, but with a smaller VLM backbone" — "a smaller 670M parameter VLM backbone that is also initialized from Gemma 3" (§IV-A, §V-C).
- action head: "a separate 'action expert' — a dedicated set of weights (860M parameters) that are trained with flow matching specifically for action generation, but can attend to the activations in the rest of the model" (§V-A). Training also predicts discretized actions via the FAST tokenizer [77] under the KI recipe, with a stop-gradient so the flow-matching expert doesn't affect the rest of the model. Code confirms flow-matching is the shipped action head: "in this repository, we currently only support the flow matching head for both π0.5 training and inference" (code/md README).
- reward or loss:
  - Value function target (§IV-A / Eq. 1, text-described since the rendered equation block was stripped by the PDF→md conversion): a distributional value function p_φ(V | o_t, ℓ) over B=201 discretized bins, trained by "minimizing the cross-entropy H over the trajectories in the current dataset D" against the discretized empirical return R_t^B. Continuous value extracted as V^π_ref(o_t,ℓ) = Σ_b p_φ(V=b|o_t) v(b).
  - Reward definition (§V-C, equation not text-recoverable): sparse, episode-level success label converted so the value function equals "the (negative) number of steps until successful completion," with "C_fail a large constant... chosen so as to ensure that failed episodes have low values" for failed episodes; values normalized to (−1, 0) per task by max episode length.
  - Advantage: A^π(o_t,a_t) = Σ_{t'=t}^{t+N-1} r_{t'} + V^π(o_{t+N}) − V^π(o_t), an N-step estimate (§III); post-training uses N=50 lookahead, pre-training uses N=T (whole episode) "since it allows us to calculate the advantage values on-the-fly during pre-training using a single inference call to the value function" (Appendix F).
  - Improvement indicator: I_t follows a delta distribution with "a task dependent improvement threshold ε_ℓ" (§IV-B). Policy objective (Eq. 3, text around it, equation itself not text-recoverable) is described as: "the real training objective combines likelihoods for the discrete values with the flow matching objective for the continuous values," i.e. minimizing the negative log-likelihood of log π_θ(a_t:t+H | I_t, o_t, ℓ) with advantage values A^π_ref(o_t,a_t,ℓ) from the value function and α a "tradeoff hyperparameter." Human corrections are forced to I_t = True: "we found it useful to force I_t = True (i.e., positive) for actions provided as human corrections during autonomous rollouts" (§IV-B).
  - Advantage-conditioning dropout: "we randomly drop out the conditioning on the advantage indicator 30% of the time" to enable CFG-style inference (Appendix F).
  - Advantage threshold ε_ℓ: pre-training sets it "such that approximately 30% of the demonstration data has positive advantage (as calculated on a random sample of 10k datapoints)"; fine-tuning sets it "such that approximately 40% of the evaluation rollouts in each iteration have positive advantage," except T-shirt/shorts folding, tightened to ~10% positive (Appendix F).
  - Relation to CFGRL/classifier-free guidance: for β=1, π̂(a|o) = π_ref(a|I,o); β>1 obtainable at test time via CFG using conditional/unconditional heads (Appendix E), with the paper using "β ∈ [1.5, 2.5] where useful."
- key trick(s): advantage conditioning replaces policy-gradient extraction so an end-to-end flow-matching VLA can be trained with plain supervised (KL/NLL) losses on all off-policy data at once, sidestepping the intractable log-likelihood of flow/diffusion action heads that blocks standard policy gradients (§IV-B); iterated "offline" RL loop (collect → retrain value fn → retrain policy) rather than online RL (§V-D, Algorithm 1); finetuning the value function and policy from the pre-trained checkpoint each iteration rather than from the previous iteration's checkpoint, "to avoid drift over multiple iterations" (§V-D).

## Contact / penetration handling
Not addressed. The paper never mentions interpenetration, contact solvers, or a physics simulator of any kind; all training/eval is on real hardware with sparse, human-rated episode success labels, not contact-based metrics.

## Evaluation
- metrics (exact definitions): "Throughput measures the number of successful task executions per hour... Success rate measures the proportion of episodes that succeed, and is derived from human-provided annotations. Raters are asked to judge the episode with respect to multiple quality metrics, and we aggregate these quality indicators into a success label" (§VI-C).
- per-task success criteria (§VI-A, quoted): Laundry (t-shirt/shorts) — "fold[ed] and stacked in the top right corner of the table within 200 seconds"; Laundry (diverse, scored on button-up shirt) — "correctly folded and placed on a stack on the table within 500 seconds"; Laundry (targeted failure removal) — "folded correctly with the collar always facing up within 200 seconds"; Cafe (double espresso) — "completing all steps within 200 seconds without critical mistakes (such as dropping the portafilter or spilling the coffee)"; Box assembly — "going from a flattened to an assembled and stacked box in under 600 seconds."
- headline numbers: reported only as bar charts (Figs. 7-10; no numeric table in the parsed text), so exact per-condition percentages beyond those stated in prose are not extractable here. Prose numbers that are stated exactly: "On all of the tasks except diverse laundry, the success rate of the final π0*.6 model is in the 90%+ range" (§VI-C.1); box assembly "achieves a success rate of about 90% both for folding the box and labeling it in the allocated time limit of 600 seconds" (§VI-C.2); T-shirt/shorts folding over 2 RECAP iterations shows "an overall 50% improvement in throughput," box assembly shows "a 2× improvement in throughput" after iteration 2 (§VI-C.2); failure-mode-removal ablation on the strict-criteria laundry task: "applying RECAP in this setting for two iterations (collecting 600 trajectories in each iteration) results in a policy that succeeds 97% of the time" (§VI-C.4, Fig. 12).
- data volumes behind these numbers (Appendix F, exact counts as stated): T-shirt/shorts — "300 episodes across 4 robot stations for reporting eval performance," and for the 2-iteration RL-only ablation "300 trajectories on four robots in each iteration" (main text §VI-C.2); diverse laundry — "450 evaluation episodes and 287 correction episodes"; failure-mode-removal ablation — "∼1000 autonomous and 280 + 378 correction episodes spread over 3 robots"; box assembly — "600 demonstrations and 360 correction episodes in each iteration, using 3 robots in total" (matches main text's "600 autonomous trials and 360 trials with interventions in each iteration," §VI-C.2); cafe — "single iteration and collect 429 correction episodes as well as 414 autonomous episodes."
- pretraining data: "tens of thousands of hours of demonstrations from numerous tasks and a variety of different robots" (§IV); code md README independently states the openpi base checkpoints are "pre-trained on 10k+ hours of robot data" (code/md, Base Models table) — note this is the released base-model figure, not necessarily π0*.6's own pretraining hour count, which the paper itself does not give as a number.
- baselines beaten: pre-trained π0.5; pre-trained π0.6 (no advantage indicator, supervised); RL-pretrained π0*.6 (RL-pretrained but no target-task data); π0*.6 offline-RL+SFT (demo-only finetune, advantage fixed True); AWR (advantage-weighted regression on the same value function); a PPO variant ("DPPO/FPO"-style with an SPO-style trust region, Appendix D). RECAP's π0*.6 "achieves by far the highest throughput for the laundry task compared to AWR and PPO" (Fig. 11 caption); no exact PPO/AWR numbers given in text beyond this qualitative claim.
- real robot? Yes — all reported numbers are real-robot (no sim results at all). Robot: the bimanual 6-DoF-arm + parallel-jaw-gripper rig of Fig. 5, plus a factory deployment rig for box assembly and a professional espresso machine setup for cafe; trial/episode counts as listed above per task.

## Reproducibility
Code released: yes, the general openpi framework (pi0/pi0-FAST/pi0.5, flow-matching action head, ALOHA/DROID/LIBERO policy adapters, training scripts) is public at github.com/Physical-Intelligence/openpi, commit 215abfb2 as parsed here. Checkpoints released: base pi0/pi0-FAST/pi0.5 checkpoints and several fine-tuned "expert" checkpoints (ALOHA-towel, ALOHA-tupperware, ALOHA-pen-uncap, DROID, DROID-FAST, LIBERO) are listed with `gs://openpi-assets` paths (code/md Model Checkpoints tables). Not released in this repo: the RECAP-specific pieces described in the paper — the π0*.6 advantage-conditioning input, the distributional value function (§IV-A), the RECAP training loop (Algorithm 1), and the espresso/laundry/box-assembly task checkpoints and datasets themselves are not present in the parsed code/md (the file tree and Python signatures show only the base pi0/pi0.5/FAST models and the ALOHA/DROID/LIBERO example policies, code/md lines 336-1190). So none of the paper's Figs. 7-12 numbers can be reproduced from this repo as parsed; only the underlying flow-matching VLA architecture and its generic fine-tuning recipe can be.

## Limitations stated by the authors
From §VII (Discussion, no separate Limitations section): "our system is not fully autonomous: it relies on human labeling and effort for reward feedback, interventions, and episode resets"; exploration is "relatively naïve... largely greedy, relying on stochasticity in the policy and human interventions to explore new solutions"; RECAP "performs iterated 'offline' updates (i.e., it collects a batch of data, retrains the model, and repeats), rather than running a fully online RL loop where the policy and value function are updated in real time as data is collected," a choice "made... out of convenience."
