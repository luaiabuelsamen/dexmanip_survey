## One-line contribution
AnyTeleop is a modular, camera-agnostic (RGB or RGB-D, single or multi-camera) teleoperation server that detects hand pose with MediaPipe + a multi-camera detection-fusion scheme, retargets it to arbitrary dexterous hands via a keypoint-vector optimization (the open-sourced "dex-retargeting" library), and drives the arm with GPU-accelerated collision-free motion generation (CuRobo) — shown to beat both a floating-hand teleoperation baseline and an RL baseline on downstream imitation learning (Table III) and to match or beat a hardware-specific baseline system on 10 real XArm6+Allegro tasks (Table IV).

## Setting
- operator interface: vision-based, camera only — no glove, no VR headset, no exoskeleton. Supports "RGB or RGB-D data from one or multiple cameras" (Sec. IV); finger keypoints come from MediaPipe (RGB-only, 21 hand-knuckle 3D keypoints in wrist frame + 2D image keypoints, runs real-time on CPU); global wrist pose comes either from PnP using RGB-D depth values, or, RGB-only, from an added neural network predicting weak-perspective scale (following FrankMocap [50]) which "has a larger error than depth camera, but it is still sufficient for many downstream teleoperation tasks" (Sec. IV-A). Multi-camera detection fusion (Sec. IV-B) auto-calibrates relative camera rotations from the first N=50 frames of hand motion (treating the hand as "a natural marker") and picks, frame by frame, the camera whose SMPL-X-predicted hand-shape-parameter error (vs. a per-operator reference from the first 50 frames) is lowest, as a proxy confidence score.
- robot hand(s) controlled: demonstrated across multiple embodiments — Allegro hand (XArm6-Allegro real-robot comparison, Table IV; also the SAPIEN sim IL experiments' arm-hand/floating-hand variants), Shadow hand (Kuka-Shadow in the collaborative handover demo, Fig. 5), Schunk hand (UR10-Schunk in the same demo), and a D-Claw (Fig. 1, cited as an example of retargeting "to a different morphology" requiring manually specified keypoint-vector mappings). The open-sourced dex_retargeting configs additionally ship for Ability Hand, Inspire Hand, LEAP Hand, Panda Gripper, and Schunk SVH Hand (code/md, configs/teleop/*.yml) — beyond what the paper itself evaluates.
- retargeting formulation (Sec. IV-C, "Hand Pose Retargeting", quoted): "This process is often formulated as an optimization problem [42, 16], where the difference between the keypoint vectors of the human and robot hand is minimized. The optimization can be defined as follows: "min_qt Σ_{i=0}^N ||α*vi_t − fi(qt)||^2 + β||qt − qt−1||^2, s.t. ql ≤ qt ≤ qu" (Eq. 1; recovered by OCR from papers/md/anyteleop_2023.ocr.md; OCR text is noisier than the layout parse, symbols may be imperfect) where qt represents the joint positions of the robot hand at time step t, vt^i is the i-th keypoint vector for human hand computed from the detected finger keypoints, fi(qt) is the i-th forward kinematics function which takes the robot hand joint positions qt as input and computes the i-th keypoint vector for the robot hand, ql and qu are the lower and upper limits of the joint position, α is a scaling factor to account for hand size difference. An additional penalty term with weight β is included to improve temporal smoothness." Correspondence is over per-fingertip keypoint *vectors* (origin-to-tip, human vs. robot forward kinematics), not raw joint angles — same family as dexpilot_2020's fingertip-vector cost, generalized to arbitrary target morphologies: "When retargeting to a different morphology, such as a Dclaw in Figure 1, we need to specify the keypoint vectors mapping between the robot and human fingers manually." Joint limits ARE explicitly handled as constraints (ql, qu terms in the optimization). Collision handling for the hand itself is not described in this optimization (it "only considers the robot hand" — no object or environment term); for the arm, self/environment collision-avoidance is delegated downstream to the CuRobo motion-generation module (Sec. IV-D), not to the hand retargeting cost. Code confirms the shipped Allegro-hand vector-retargeting config: `target_task_link_names: [link_15.0_tip, link_11.0_tip, link_7.0_tip, link_3.0_tip]` (the four fingertips), `scaling_factor: 1.6` (the α term), `low_pass_alpha: 0.2` (temporal filter, the low-pass-filtering realization of the β smoothness term) (code/md, configs/teleop/allegro_hand_{left,right}.yml); a distinct `type: DexPilot` config variant is also shipped per hand, implementing dexpilot_2020's specific fingertip-pair-projection formulation as an alternative retargeting type within the same library.
- end-to-end latency: not reported as a single end-to-end number; instead per-module profiling (Table II, RTX 3090 desktop / RTX 2070 laptop, all modules run on one machine simultaneously): Hand Pose (RGB) 26±5 ms (desktop) / 34±5 ms (laptop); Hand Pose (RGB-D) 27±5 / 35±5 ms; Fusion 1±0 / 1±0 ms; Retargeting 9±7 / 10±9 ms; Motion 8±3 / 11±5 ms. Designed module frequencies: hand pose/fusion/retargeting at 25 Hz (detection-limited), motion generation ideally at 120 Hz ("we found it difficult to achieve this throughput when running all these modules on the same computer" on one machine — recommended fix is splitting modules across machines).
- cost of the rig: not stated as a dollar figure anywhere in the parsed text — only camera/GPU hardware is described (single RealSense camera for the real-robot comparison, Sec. VI-B), no BoM or total system cost.
- data rate / demonstrations per hour: not reported as a throughput number. What is reported: fixed demonstration counts per task — "50 demonstration trajectories for each task" (both baseline and AnyTeleop, SAPIEN IL experiment, Sec. VII-A) and "we run each task ten times for AnyTeleop" (real-robot comparison, Sec. VI-B) — no elapsed-collection-time or demos/hour figure is given for either.
- task(s) demonstrations were used for: (1) downstream imitation learning in SAPIEN simulation via DAPG [46] on three tasks — Relocate, Flip Mug, Open Door — each in floating-hand and arm-hand variants (Table III); (2) direct real-robot teleoperation replication of 10 manipulation tasks from Robotic Telekinesis [54] on an XArm6+Allegro rig with a single RealSense camera (Pickup Box Object, Pickup Fabric Toy, Box Rotation, Scissor Pickup, Cup Stack, Two Cup Stacking, Pouring Cubes onto Plate, Cup Into Plate, Open Drawer, Open Drawer and Pickup Object; Table IV, Fig. 4); (3) a collaborative human-to-robot handover demo (qualitative, Sec. VII-B, Fig. 5) with two remote operators.

## Evaluation
- exact success criterion: for the SAPIEN IL tasks, success metrics are deferred to the baseline paper ("More details about the success metrics can be found in [43]", Sec. VII-A) — not restated numerically here. For the real-robot replication (Table IV), success is binary per-trial task completion, matching [54]'s protocol; no further numeric threshold given.
- number of eval episodes/seeds: SAPIEN IL — "we train policies with three different random seeds. For each policy, we evaluate it on 100 trials" (Sec. VII-A, Table III caption: "success rate is computed from 100 trials"). Real-robot — 10 trials/task for AnyTeleop, matching [54]'s own reported 10-trial baseline numbers (Sec. VI-B, "we run each task ten times for AnyTeleop... For the baseline method, we directly use the results reported in their paper").
- headline numbers (with table): Table III (SAPIEN, IL via DAPG, 100 trials, mean±std over 3 seeds) — Arm-Hand Relocate: AnyTeleop-collected-data 70.0±9.8 vs. RL 33.7±29.3 vs. baseline-collected-data 40.3±36.7; Arm-Hand Open Door: 79.7±15.5 (ours) vs. 34.7±31.7 (RL) vs. 51.3±30.7 (baseline); Floating-Hand Flip Mug is the one exception where the baseline-collected data wins: 51.3±34.7 (baseline) vs. 47.3±28.3 (ours) vs. 33.7±15.0 (RL). Table IV (real robot, 10 trials/task) — AnyTeleop beats or ties Telekinesis [54] on all 10 tasks: e.g. Two Cup Stacking 0.7 vs. 0.3, Cup Into Plate 1.0 vs. 0.8, Open Drawer and Pickup Object 0.9 vs. 0.6; tied at 0.6 (Box Rotation) and 0.7 (Pouring Cubes onto Plate); overall "AnyTeleop can get a higher success rate of 8/10 tasks and the same success rate on 2/10."
- baselines beaten: Robotic Telekinesis [54] (real-robot teleoperation comparison, and as the SAPIEN IL demonstration-collection baseline), a pure-RL baseline [44] with the same dense reward as [54] (SAPIEN IL comparison, no demonstrations).
- real robot? Yes — XArm6 + Allegro hand, single RealSense camera, 10 trials/task across the 10 replicated Telekinesis tasks (Table IV); qualitative-only real-robot collaborative handover demo (Kuka-Shadow / UR10-Schunk, Fig. 5, no trial count reported).
- attributed advantage over the baseline (quoted, Sec. VII-A): "our system has two benefits that contribute to better performance in imitation learning: (i) The collected trajectory is more smooth... (ii) Different from the baseline, our system explicitly supports teleoperation with arm-hand system and guarantees no self-collision. On the contrary, the baseline system utilizes retargeting to generate joint trajectory for robot arm, which may lead to several self-collision for robot arm."

## Limitations / failure modes stated by the authors (Sec. VIII, quoted)
- "loss of tracking during fast human hand motion, which triggers a pause and re-detection process" — workaround: instruct the operator to slow down.
- "unreliable hand pose when the hand is in self-occlusion" — workaround: "incorporating multiple cameras for tasks that require significant hand rotation."

## Notes for the survey
- Feeds: the retargeting-formulation comparison table directly alongside dexpilot_2020 — this paper's dex_retargeting library literally ships DexPilot's fingertip-pair-projection cost as one of two selectable optimizer types (`type: DexPilot` vs. `type: vector`), so the survey should present AnyTeleop's "vector" optimizer as a generalization of DexPilot's formulation (per-fingertip keypoint-vector matching to arbitrary target morphologies, with explicit joint-limit constraints ql/qu that DexPilot's paper does not mention) rather than a wholly separate approach.
- This paper's retargeting cost has been recovered by OCR (see above): min_qt Σ_{i=0}^N ||α*vi_t − fi(qt)||^2 + β||qt − qt−1||^2, s.t. ql ≤ qt ≤ qu (Eq. 1, papers/md/anyteleop_2023.ocr.md). dexpilot_2020's cost function, which was also an unrecovered image in that paper's layout parse, has since been recovered by OCR as well (see papers/notes/dexpilot_2020.md), so the two retargeting costs can now be compared as written rather than through prose descriptions.
- Contact/penetration handling: explicitly scoped OUT of the hand retargeting module ("this module only considers the robot hand") — no hand-object interpenetration or self-collision term at all in the retargeting cost; self-collision avoidance is claimed only for the arm, via the downstream CuRobo motion planner, not the hand. Flag this as a second data point (with dexpilot_2020) that early-generation optimization-based retargeters treat collision/penetration as entirely out of scope for the hand itself.
- Cost-of-rig and demos/hour: neither is stated in this paper (mark "not stated" in the survey table) — only per-module latency (Table II) and fixed per-task demonstration counts (50 sim / 10 real) are given, with no elapsed collection time to derive a rate.
