## One-line contribution
MJPC: an open-source, real-time predictive-control framework built on MuJoCo that exposes three shooting-based planners (iLQG, Gradient Descent, and a new zero-order "Predictive Sampling" baseline) behind a shared cost-authoring API and interactive GUI, and shows Predictive Sampling solving in-hand cube reorientation with a Shadow Hand "from scratch, in real time" with no learning (abstract; Sec. 4.2).

## Setting
- hand(s): Shadow Hand [Tuffield and Elias, 2003], sourced from MuJoCo Menagerie (Sec. 4.2 "Hand" example). No arm (in-hand task, hand presumably fixed-base — not stated explicitly). Single-handed. Not applicable: no bimanual or human-hand-tracking setting for this task; the repo's separate "Bimanual manipulation" example (README "Example tasks") is a different, unparsed task.
- simulator / physics: MuJoCo [Todorov et al., 2012], via MJPC's own C++ planning/rollout API (Sec. 3.1). No fixed sim timestep or contact-solver parameters are given anywhere in the parsed paper or code md for this task; the paper only states that MuJoCo affords "faster-than-realtime simulation of high-dimensional systems with many contacts" and that the 27-DoF humanoid "can be simulated 4000 times faster than realtime on a single CPU thread" (Sec. 3.1) — a general engine claim, not a per-task setting.
- #envs: not applicable in the RL sense — Predictive Sampling parallelises N candidate rollouts per planning step (N=10 for the Hand task, Table 1, App. B) rather than training environments; this is planning-time parallelism, evaluated once online, not a training population.
- observation: not applicable as a learned-policy observation vector — the planner reads the true simulator state x directly ("Measure the current state x", Algorithm 1) with no perception or state-estimation model discussed for the Hand task.
- action space: joint controls u parameterised as a time-indexed spline over P=6 knots for the Hand task (Table 1, App. B), evaluated with one of three interpolants (zero-order hold, piecewise-linear, cubic Hermite; Sec. 3.3); the spline compresses the control sequence before the sampling/optimisation step. Replanning happens continuously and asynchronously from simulation (Algorithm 1); total planning time per update is stated only in aggregate across all examples: "between 1 and 20 milliseconds" (Sec. 4.2), no per-task breakout for Hand.
- objects / data: single cube, goal specified as a target orientation set interactively by the user in the GUI (Sec. 4.2). No dataset, no human demonstration or motion-capture reference — not applicable: "the target orientation can be set by the researcher in real-time" (Sec. 4.2), the task is authored directly as a cost function, not learned or retargeted from any human data.

## Method
- paradigm: model-based predictive control (online trajectory optimisation), not RL/IL. No training phase, no learned policy or value function for the Hand result reported (Sec. 4.2, 5.1).
- algorithm: **Predictive Sampling** (Algorithm 4, Sec. 3.4) — a derivative-free, sampling-based shooting method run in the asynchronous predictive-control loop (Algorithm 1): at each planning iteration, draw N-1 noisy candidate spline-parameter vectors θ_i ~ N(θ̄, σ²I) around the current nominal θ̄ (plus the nominal itself, total N candidates), roll out all N candidates in parallel from the measured state x₀ using MuJoCo forward simulation, evaluate each rollout's total cost J, and set the new nominal to the argmin candidate; the agent continuously reads the current action off the nominal spline while the planner re-plans in a separate, faster loop (Algorithm 1; Algorithm 5 in App. C gives the same loop as pseudocode). The paper frames it as "MPPI with infinite temperature", "CEM with a non-adaptive distribution", or "trivial random search" (Sec. 5.1) — deliberately not novel, offered as a simplicity/performance lower bound that "turned out to be surprisingly competitive" with iLQG and Gradient Descent (abstract, Sec. 5.1).
- planner settings for the Hand task (Table 1, App. B): spline knots P=6, rollouts N=10, horizon T=25 (timesteps, units not stated — likely planning steps not seconds), sampling noise σ=0.1.
- iLQG and Gradient Descent (Sec. 3.4, Algorithms 2-3) are the two derivative-based alternatives MJPC also implements, using MuJoCo's finite-difference Jacobians (Sec. 3.2 "Derivatives"); the Hand headline result is attributed to Predictive Sampling, not these.
- key trick(s): (a) risk-sensitive exponential cost transformation ρ(l; R) (Sec. 3.2) generalising the base quadratic-form cost, with R=0 (risk-neutral) as MJPC's default — no evidence this was used for the Hand task specifically (R is a global per-task GUI-exposed parameter; App. B does not print a task-specific R for Hand). (b) spline-compressed control representation to shrink the search space for sampling/gradient planners (Sec. 3.3). (c) asynchronous agent/planner loop letting simulation be slowed down to trade off against planner compute on slower hardware (Sec. 1, Algorithm 1).

## Reward / objective block (cost, not reward — see HOWTO_METHOD block C)
MJPC optimises a finite-horizon cost, not a trained RL reward; the "base cost" form (Sec. 3.2, eq. 4) is c = Σ_{i=1..M} w_i · n_i(r_i), a sum of M weighted, twice-differentiable norm terms n_i of residuals r_i "that are small when the task is solved," optionally passed through the risk transform ρ(l; R).
- Hand objective (App. B, "This task comprises M = 3 cost terms"): only two of the three terms survive the parse intact —
  - Term 1: r1 = "cube orientation minus goal orientation"; n1 = quadratic; w1 = 3.
  - Term 2: r2 = "cube linear velocity"; n2 = quadratic; w2 = 10.
  - Term 0: header present, residual/norm/weight text lost to flattening — not stated (see parse caveat above). By analogy to the Humanoid task's Term 0 (a position-tracking residual) it is plausibly a cube-position term, but this is not asserted as fact.
  - No tolerance in metres or radians is given for any Hand term — the paper reports raw weighted quadratic costs, not a threshold-based success criterion (see Evaluation below).
- Code: the C++ residual implementing these terms (in the repo's `shadow_reorient` task directory) is not present in code/md/mjpc_2022.md — code/md for this key contains only unrelated Python task files (merge_panda_robotiq.py, mjx/tasks/bimanual/handover.py, mjx/tasks/insert.py, mjx/tasks/instruction.py), none of which implement the Hand/cube task. **Reward block cannot be cross-checked against code for this key — flagged as thin.**

## Contact / penetration handling (block D)
Not addressed as a named concept anywhere in the parsed paper or code for the Hand task. The only contact-adjacent statements are general MuJoCo-engine claims: "MuJoCo affords faster-than-realtime simulation of high-dimensional systems with many contacts" (Sec. 3.1), and a footnote using penetration purely as an illustration of shooting vs. direct trajectory-optimisation methods — "consider the physical scenario of a free rigid box lying flat on a plane under gravity, and then consider the non-physical scenario of the same box hovering above the plane or penetrating it by a few microns" (Sec. 2, footnote 2) — this is a discussion of why shooting methods only ever produce physically-realisable (non-penetrating, in the sense of "obeying the simulator's own contact resolution") trajectories, not a measured or penalised interpenetration metric. No contact solver softness/stiffness parameters are given in the parsed paper or code for this key. Hand-object interpenetration between the Shadow Hand and the cube is neither measured nor penalised as a distinct cost term; whatever the MuJoCo contact solver enforces implicitly (unstated parameters) is the only thing preventing penetration.

## Evaluation
- metrics (exact definitions): none stated as a threshold-based success/failure criterion for the Hand task. The paper reports only qualitative outcomes ("performs in-hand manipulation of a cube to a desired orientation", Sec. 4.2) and aggregate planning-time numbers ("total planning time for a single update is between 1 and 20 milliseconds", Sec. 4.2, across all three highlighted examples, not broken out per task).
- failure definition: not stated. There is no rollout-termination or failure criterion described for the Hand task (e.g. no dropped-cube or max-reorientation-time cutoff mentioned) — evaluation is continuous, cost-based, and demonstrated via video/GUI rather than a numeric benchmark table.
- headline numbers: none numeric beyond the two Table-1 hyperparameters and the "1-20 ms" planning-time range; the paper explicitly defers to the accompanying video ("dpmd.ai/mjpc") for judging the Hand behaviour (Sec. 4).
- object tracked position only, or position + orientation: orientation only for the printed terms (Term 1 = cube orientation vs. goal orientation); a plausible cube-position term (Term 0) is present but its content is lost in the parse, so position tracking cannot be confirmed from this source. Cube linear velocity (Term 2) is also costed.
- baselines beaten: none quantitatively — the comparison is qualitative and rhetorical: Predictive Sampling "turned out to be surprisingly competitive with the more established algorithms" (abstract) relative to iLQG and Gradient Descent, with no numeric table for the Hand task specifically. The paper claims in-hand reorientation "has not previously been solved from scratch, in real time" to the authors' knowledge (Sec. 4.2) but does not name or re-run a specific prior baseline for this task.
- real robot? none — all results are in simulation (Sec. 4.2 examples run "in simulation on a single CPU"); Sec. 5.3 "Hardware" discusses transfer to real robots only as future work, not a result.
- hardware / compute: experiments run on a Lenovo ThinkStation P920, 48 GB RAM, Intel Xeon Gold 6154 72-core CPU, with additional experiments on an Apple MacBook Pro (2021), 16 GB RAM, M1 Pro CPU (App. D) — not broken out per task.

## Limitations stated by the authors (Sec. 5.3)
- "Can only control what MuJoCo can simulate" — and specifically only what can be simulated much faster than real time; very-high-DoF systems (fluid, cloth, soft bodies) are out of reach.
- "Myopic": fixed planning horizon T with no mechanism to see past it; suggested (not implemented here) fixes are learned policies, learned value functions to bound the rollout, or a high-level agent setting the cost function hierarchically.
- Hardware deployment is largely future work: state estimation for free-moving, contact-rich systems (as opposed to fixed-base manipulators with static objects) is called "the difficult and interesting case" and "remains to be seen".
- Predictive Sampling itself is explicitly not claimed as a good algorithm — "we are introducing Predictive Sampling not because it is good, but because it is not good. It is the simplest possible sampling-based shooting method, and therefore establishes a lower bound for performance baselines" (Sec. 5.1).

## Quotable claims (verbatim, with section)
- "In-hand reorientation—a high-DoF system with complex contact dynamics—is considered difficult to solve [Chen et al., 2022] and to the best of our knowledge has not previously been solved from scratch, in real time." (Sec. 4.2)
- "for all of the examples, the total planning time for a single update is between 1 and 20 milliseconds." (Sec. 4.2)
- "Predictive Sampling was designed as an elementary baseline, mostly for its pedagogical value, but turned out to be surprisingly competitive with the more established algorithms." (abstract)
- "The goal is not to find the minimum, but to remain in the basin-of-attraction of the minimum." (Sec. 5.1)
- "one can only control what can be simulated much faster than real time." (Sec. 5.3)

## Notes for the survey
- Feeds: the model-based/planning counterpoint to every RL tracker in this batch — a hand-object contact task (cube reorientation) solved with zero learning, zero human demonstration data, and zero retargeting, purely by authoring a cost and sampling around it in real time. Useful for framing why RL trackers' "reference tracking" reward shape (position/orientation residuals with quadratic or exponential norms) is not itself novel — MJPC's base cost form (Sec. 3.2) is structurally the same weighted-residual pattern used by, e.g., dexmachina_2025's r_pos/r_rot exponential terms, just optimised online instead of by a trained policy.
- Sharpest contrast for the survey's interpenetration section: MJPC neither measures nor penalises hand-object interpenetration anywhere in the parsed source, and the one place penetration is mentioned at all is a footnote about trajectory-optimisation semantics, not a task metric — a clean "not addressed" data point against papers that build contact-graph or matched-contact rewards (e.g. physhoi_2023, dexmachina_2025).
- Caution: the Hand-task reward block is unusually thin — one of three cost terms lost to PDF flattening, and no code confirmation available at all for this key. Any survey table entry for mjpc_2022's Hand-task cost should carry a footnote pointing to this gap rather than presenting 2/3 terms as the complete objective.
- No failure definition, no eval-episode count, and no numeric success rate exist for this task in the parsed source; the survey should not attribute a "success rate" to MJPC's Hand demo — the paper's own evidence is qualitative/video-based.
