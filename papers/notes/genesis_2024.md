# genesis_2024 — Genesis: A Generative and Universal Physics Engine for Robotics and Beyond (Genesis Authors / Genesis-Embodied-AI, software release, 2024)

source: repository only, no paper — sources: code/md/genesis_2024.md [c27875eb] (no papers/md file exists for this key: bib `pdf_url`/`arxiv` are null, and `papers/md/genesis_2024.md` does not exist)

## One-line contribution
A unified, multi-material GPU physics engine ("Genesis World") coupling Rigid, FEM, MPM, Particle (PBD/SPH), a libuipc-based IPC solver, an explicit coupler, and a SAP (semi-analytic-primal-style) coupling path in one scene/state, with three interchangeable rendering backends and a Python-to-multi-backend (CUDA/ROCm/Metal/Vulkan/x86/ARM64) compiler called Quadrants (README).

## Setting
- hand(s) shipped as assets: **Shadow Hand** appears as a named example asset — `examples/rigid/ik_shadow_hand.py` (inverse kinematics on the Shadow Hand) and `examples/sensors/surface_distance_shadowhand.py` (a surface-distance tactile-style sensor demo on the Shadow Hand) (code/md, Python-signatures section, and the "Simulation Interface" example gallery). No other dexterous hand (Allegro/LEAP/XHand) was found in the parsed README example gallery or file-tree excerpt; Franka (a parallel-jaw-gripper arm) is the other manipulator repeatedly used in examples (`franka_cube.py`, `single_franka_envs.py`, `grasp_env.py`, `diffik_controller.py`).
- simulator / physics: layered stack — Simulation Interface (asset parsing for URDF/MJCF/OBJ/GLB/USD, entity accessors, controllers, sensors, parallel/heterogeneous environments, built-in GUI) → Physics (the multi-solver engine) → Render (Nyx in-house renderer, Luisa DSL ray tracer, or Pyrender rasterizer, all as pluggable camera-sensor backends) → Compiler (Quadrants, a fork of Taichi as of June 2025, lowering Python kernels to CUDA/ROCm/Metal/Vulkan/x86/ARM64, and carrying "Genesis's autodiff, GPU graphs, and fastcache machinery") (README, "What is Genesis World?").

## Physics block
- solver / contact model: the rigid-body solver is a dedicated `ConstraintSolver` (`genesis/engine/solvers/rigid/constraint/solver.py`) with `add_equality_constraints`, `add_inequality_constraints`, `resolve`, and a separate `noslip()` post-pass — i.e. an equality/inequality-constraint-based rigid solver with an explicit no-slip correction step, architecturally similar to MuJoCo's own solver+noslip design (and the README explicitly lists MuJoCo as "Reference for rigid body dynamics" among its acknowledged influences). Supporting modules confirm a line-search-based Newton-style iterative resolve (`linesearch.py`) and constraint-island decomposition for parallelism (`island.py`); `backward.py` in the same constraint package indicates the rigid contact solve has a differentiable (adjoint/backward) path (also confirmed by `tests/grad/test_rigid_constraints.py`).
- supported materials (multi-solver coupling, from the README's "Physics" catalogue and its acknowledged reference implementations): **Rigid** bodies (reference: MuJoCo for dynamics, libccd for collision detection); **FEM** (deformables, e.g. `fem_hard_and_soft_constraint.py`); **MPM** (elastoplastic/granular materials, e.g. sand-wheel coupling, reference: FluidLab); **Particle-based PBD** (cloth, liquid; reference: "Ten Minute Physics" / PBF3D) and **SPH** (liquid; reference: SPH_Taichi); **libuipc** (an IPC — Incremental Potential Contact — solver, used for cloth/robot-teleop and cut/deformable examples); an **explicit coupler** bridging solvers (cloth-on-rigid, rigid+MPM attachment, SPH+MPM, water-wheel, "cut dragon"); and **SAP** coupling (Franka-grasp-rigid-cube example, `sap_coupling/`), i.e. a semi-analytic-primal-style compliant-contact path distinct from the main rigid solver, used specifically for grasp-coupling scenes.
- integrator: not stated explicitly in the parsed README text (no named integrator scheme, e.g. semi-implicit Euler vs. implicit, is given); the `ConstraintSolver`'s `resolve`/`noslip`/`linesearch` structure implies an iterative Newton-type per-step solve, consistent with a MuJoCo-like architecture, but this is inferred from module names, not stated as fact.
- differentiability: yes, and load-bearing to the architecture — Quadrants (the Taichi-derived compiler) explicitly "carries Genesis's autodiff, GPU graphs, and fastcache machinery" (README), and the rigid constraint solver has a dedicated `backward.py` plus gradient tests (`tests/grad/test_rigid_constraints.py`).
- claimed throughput from the README: **none stated**. No FPS, steps/sec, or "Nx faster" figure appears anywhere in the parsed README (Overview, Catalogue, Installation, License/Acknowledgments, Citation sections); a `fps_tracker()` method exists in `genesis/engine/simulator.py` (code/md) confirming the engine measures its own FPS at runtime, but no benchmark number from that tracker is quoted in the README text captured here. (Note: any "tens of millions of FPS" or similarly large throughput figure sometimes associated with Genesis in secondary sources is not present in this parsed README snapshot and must not be attributed to this source.)
- GPU or CPU: both, via the Quadrants compiler backends — CUDA and AMD ROCm (GPU, NVIDIA and AMD), Apple Metal/MPS (GPU, Apple Silicon), Vulkan, and CPU targets x86 and ARM64 (README, "What is Genesis World?" and "Quick Installation": separate pip/uv install paths are given for "NVIDIA GPU (CUDA 12.6 as an example)," "CPU only (Linux/Windows)," and "Apple Silicon (Metal/MPS)").
