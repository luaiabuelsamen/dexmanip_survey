# newton_2025 — Newton: An open-source, GPU-accelerated physics simulation engine built upon NVIDIA Warp (NVIDIA, Google DeepMind, Disney Research; Linux Foundation project, software release, 2025)

source: repository only, no paper — sources: code/md/newton_2025.md [ecc03b49] (no papers/md file exists for this key: bib `pdf_url`/`arxiv` are null, and `papers/md/newton_2025.md` does not exist)

## One-line contribution
A Linux-Foundation, community-built GPU physics engine on NVIDIA Warp that extends/generalizes Warp's deprecated `warp.sim` module and integrates MuJoCo Warp (MJWarp) as its primary backend, adding OpenUSD support, differentiability, and multiple pluggable solver back-ends under one API (README).

## Setting
- hand(s) shipped as assets: **Allegro Hand** ships as a first-class example — `newton/examples/robot/example_robot_allegro_hand.py`, runnable via `python -m newton.examples robot_allegro_hand` (README, "Examples"). No other dexterous hand (Shadow/LEAP/XHand) was found in the parsed README example gallery; other examples are non-hand robots (quadrupeds/ANYmal, cloth, drones, etc., inferred from `asv/benchmarks/simulation/bench_anymal.py`, `bench_cable.py`, `bench_cloth.py`, `example_cloth_style3d.py`).
- simulator / physics: requires Python 3.10+, Linux (x86-64/aarch64), Windows (x86-64), or macOS (CPU-only); NVIDIA GPU (Maxwell or newer), driver 545+/CUDA 12, "no local CUDA Toolkit installation required" (README, "Requirements").

## Physics block
- solver(s): Newton is explicitly multi-solver, not single-backend. Confirmed solver classes/modules from the code manifest: **SolverMuJoCo** (wraps MJWarp; `EqType` is now "a deprecated alias for `SolverMuJoCo.EqType`", i.e. MuJoCo-style equality-constraint types are first-class); **SolverKamino** (its own subpackage `newton/_src/solvers/kamino/`, configured via `PADMMSolverConfig`, `DVISolverConfig`, and `ForwardKinematicsSolverConfig` — i.e. a Proximal-ADMM and a Dual-Variational-Inequality contact solver, distinct from MuJoCo's); an **XPBD** solver (`test_solver_xpbd.py`, `test_solver_xpbd_tetrahedra.py`, `bench_quadruped_xpbd.py`, `CpuXPBDQuadruped` — "XPBD rigid-body quadruped — exercises XPBD solver, contacts, articulations"); a **VBD** (Vertex Block Descent) solver for cloth/deformables (`test_solver_vbd.py`, `test_solver_vbd_proxy_full_surface.py`); and a **Style3D** cloth solver (`test_solver_style3d.py`, `example_cloth_style3d.py`). An `IKSolver` (inverse kinematics, LM and L-BFGS backends, `newton/_src/sim/ik/`) is separate from the dynamics solvers.
- integrator / contact model: inherited per-backend — when using `SolverMuJoCo`, contact/constraint semantics are MuJoCo's own soft-constraint (`solref`/`solimp`-style) model as ported by MJWarp (see `mujoco_warp_2025` note); when using `SolverKamino`, the model is ADMM/DVI-based (proximal/variational-inequality contact resolution, distinct from MuJoCo's formulation); XPBD and VBD use position-based-dynamics-style constraint projection rather than a force-level complementarity solve.
- differentiability: explicitly a design goal — "Newton emphasizes GPU-based computation, OpenUSD support, differentiability, and user-defined extensibility" (README, "Newton"). A dedicated test file `newton/_src/sim/tests/test_differentiable_contacts.py` (name inferred from the file listing) confirms at least one solver path is tested for differentiable contacts, though which solver(s) support it is not stated in the parsed README text itself.
- supported materials: rigid articulated bodies (the primary use case, e.g. Allegro hand, ANYmal quadruped), cloth (Style3D, VBD-based examples), and cable/rod dynamics (`newton/_src/sim/rod.py`, `bench_cable.py`); no FEM/MPM/SPH solver is named in the parsed manifest (contrast `genesis_2024`, which has all of those).
- GPU or CPU: GPU-primary (NVIDIA Maxwell+, driver 545+/CUDA 12) but explicitly cross-platform at reduced capability — "macOS runs on CPU" only (README, "Requirements"); a `bench_cpu.py` benchmark file and a `test_fast_dr_legs_solver_does_not_import_torch` test suggest a maintained CPU-only code path for at least the "fast" domain-randomization-legs benchmark.
- claimed throughput from the README: none — no FPS, steps/sec, or speedup number appears anywhere in the parsed README (Requirements/Quickstart/Examples sections). The only performance-adjacent artifacts are an ASV (airspeed velocity) benchmark suite (`asv/benchmarks/simulation/*.py`, tracking metrics like `solver_niter_mean`/`solver_niter_max` for Kamino, per `bench_kamino.py`) and nightly CI benchmark workflows, neither of which publishes a number in the parsed text.

## Notes for the survey
- Newton is architecturally the "engine of engines" in this batch: it does not replace MJWarp's contact model but wraps it as one interchangeable solver (`SolverMuJoCo`) alongside ADMM/DVI (Kamino), XPBD, and VBD — the survey's physics-comparison table should list Newton's contact model as "solver-dependent" rather than assign it a single row, and cross-reference `mujoco_warp_2025` for the MuJoCo-backend case.
- The presence of `test_differentiable_contacts.py` is the only positive evidence in this corpus that a *Newton* solver (likely Kamino, given its ADMM/proximal formulation) supports differentiable contacts, in contrast to MJWarp's own README, which states differentiability "is not yet available" as of the parsed commit — this distinction (Newton-via-Kamino may be differentiable even where Newton-via-MJWarp is not) is worth flagging explicitly if the survey claims "Newton is differentiable."
- Allegro Hand is the one confirmed dexterous-hand asset; no throughput number could be found for it or any other scene in the parsed README, so any FPS/steps-per-sec claim about Newton must be sourced elsewhere (e.g. the nightly CI dashboards, not fetched here) or left as "not stated."
- Code md provenance: `code/md/newton_2025.md` (117,884 chars, the largest non-tactile manifest in this batch) is README + pruned file tree + ~75 Python files' signatures; solver *behavior* above is inferred from class/config/test names (e.g. `PADMMSolverConfig`, `DVISolverConfig`, `SolverMuJoCo.EqType`), not from reading solver-loop source code, so algorithmic details (iteration counts, convergence criteria) are not stated and should be verified against the live repo before being quoted as fact.
