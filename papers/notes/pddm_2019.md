# pddm_2019 — Deep Dynamics Models for Learning Dexterous Manipulation (Nagabandi, Konolige, Levine, Kumar; CoRL 2019)

sources: papers/md/pddm_2019.md [sha256 a9da82c3] ; code/md/pddm_2019.md [commit 06b88cdb]

## One-line contribution
PDDM: online MPC (a filtering + reward-weighted-refinement, MPPI-style trajectory optimizer) over an ensemble
of learned feed-forward dynamics models, with no policy network and no policy-gradient training; shown on a
simulated task suite and on a real 24-DoF Shadow Hand (Sec 3, Sec 4.4).

## Setting
- hand(s): 9-DoF three-fingered D'Claw hand [5] (valve turning); 24-DoF anthropomorphic Shadow Hand (in-hand
  reorientation, handwriting, Baoding balls). Real-world: Shadow Hand only (Sec 4.4). Not bimanual. arm: none
  for manipulation; a 7-DoF Franka-Emika arm only runs the automated Baoding-ball reset ("pre-preprogrammed
  7-DoF Franka-Emika arm to use its parallel jaw gripper to pick them up and return them to the Shadow
  Hand's palm", Sec 4.4) — it never manipulates the task object.
- simulator / physics: MuJoCo [32] (Sec 4.1); README requires "mujoco (v1.5)", `sim_robot.py` supports two
  backends ("mujoco_py - MuJoCo v1.50" or "dm_control - MuJoCo v2.00"). Contact/solver settings: not stated.
  Timestep `dt` (Table 2): Valve Turning 0.15 s, In-hand Reorientation 0.1 s, Baoding Balls 0.1 s (Handwriting
  cell blank in the flattened table). Parallel envs: not stated — Alg. 1 collects `R` rollouts sequentially
  per iteration (App. A); the only parallelism is `N` candidate action sequences (200–700, Table 1) sampled
  through the model at plan time. GPU / wall-clock training time: not stated beyond data-hours (below).
- observation: state-based, built explicitly in each env's `_get_obs` (code/md). Baoding
  (`baoding_env.py`): `robot_pos`(24)+`object1_pos`(3)+`object1_velp`(3)+`object2_pos`(3)+`object2_velp`(3)+
  `target1_pos`(2)+`target2_pos`(2) = 40, matching Table 2's dim(s)=40. Cube/reorientation (`cube_env.py`):
  `robot_pos`(24)+`object_position`(3)+`object_orientation`(3)+`object_velp`(3)+`object_velr`(3)+
  `desired_orientation`(3) = 39 by the code's own comments — but Table 2 states dim(s)=46 for In-hand
  Reorientation. **Mismatch, not reconciled by either source.** DClaw/valve (`dclaw_turn_env.py`):
  `hand_qp`(n_jnt)+`hand_qv`(n_jnt)+`lid_qp`+`lid_qv`+`goal`, consistent with Table 2's dim(s)=21 at n_jnt=9.
  Both `_get_obs` calls pass `robot_noise_ratio=0, object_noise_ratio=0` — no observation noise in the
  released code path. Handwriting's observation is not in the released code (no `handwriting` env dir).
- action space: joint position targets, "we normalize the action spaces to [−1, 1]" (App. B). Real-robot
  control: planner commands the hand at 10 Hz, "communicated via a 0-order hold to the low-level position
  controller that operates at 1kHz" (Sec 4.4).
- objects / data: no offline dataset, no demonstrations — "our method is sample efficient without requiring
  any expert demonstrations" (Sec 2). Data is collected online by the MPC rollouts (Algorithm 1). Sim tasks
  used "1-2 hours worth of data," real-world "2-4 hours worth of data" (Sec 4.1); Baoding in sim solved with
  "100,000 data points, or 2.7 hours worth of data" (Sec 4.3).

## Method
- paradigm: model-based RL — **not** a policy-gradient or actor-critic method. There is no trained policy
  network; action selection is online planning (MPC) with a learned ensemble dynamics model, replanned every
  step (Sec 3.1, 3.4).
- algorithm: dynamics model is an ensemble of `M` feed-forward networks, "2 fully-connected hidden layers of
  size 500 with relu nonlinearities and a final fully-connected output layer," trained with MSE and Adam, lr
  0.001, batch size 500 (App. B). Each member differs only by "a different random initialization θi0 and use
  different batches of data Di at each train step" (Sec 3.2) — no bootstrap resampling. The planner ("PDDM")
  is the last of three gradient-free optimizers in Sec 3.3: random shooting → iterative CEM → "Filtering and
  Reward-Weighted Refinement," an MPPI-style ([28, 16]) update over time-correlated action samples with
  reward-weighting γ and filtering coefficient β; Alg. 1 line 7: `PDDMMPC(st, {fθ0...fθM}, H, N, r, γ, β)`.
  Planner-over-model MBRL, not PPO/SAC/any policy-gradient algorithm.
- teacher-student / distillation: none — not applicable.
- domain randomization: not stated (no randomized-quantity list found in either source).
- key trick(s): mean-across-ensemble reward drives planning (Sec 3.4); action-sequence filtering for
  smoothness (Sec 3.3); replanning every step "to mitigate some model inaccuracies by preventing accumulating
  model error" (Sec 3.4). Ablations (Fig. 4, Sec 4.2): larger architecture helps; ensembles help most early
  in training; warmstart vs. random re-init makes little difference; horizon `H` has a sweet spot (too short
  → greedy, too long → compounding error); γ has a sweet spot (too soft → no movement, too hard → drops).

## Method — Reward / cost block (planner cost, not an RL reward function)
Verbatim from Table 2 (App. B), "Reward r(s, a)" column:
- Valve Turning: `−10|valveθ − targetθ| + 1(|valveθ − targetθ| < 0.25) + 10∗1(|valveθ − targetθ| < 0.1)`
- In-hand Reorientation: `−7||cuberpy − targetrpy|| − 1000·1(isdrop)`
- Handwriting: `−100||tipxy − targetxy|| ; −20||tipz|| ; −10·1(forwardtipping > 0)` (three rows, one task,
  in Table 2 — no code available to cross-check, see below)
- Baoding Balls: `−5||objectsxyz − targetsxyz|| − 500·1(isdrop)`

From code (`get_reward`, code/md):
- `dclaw_turn_env.py`: `r_target_dist = -10*screw_dist` (screw_dist = abs `angle_difference(screw_pos,
  target_pos)`), `bonus_small = 1 if screw_dist<0.25 else 0`, `bonus_big = 10 if screw_dist<0.1 else 0`,
  `r_total = r_target_dist + bonus_small + bonus_big`. **Matches Table 2 exactly.**
- `cube_env.py`: `ori_dist = -7*angle_diffs` (`angle_diffs = norm(obj_orientation - desired_orientation)`),
  `drop_penalty = -1000*is_fall` (`is_fall` when `obj_height < -0.1`), `r_total = ori_dist + drop_penalty`.
  **Matches Table 2 exactly.**
- `baoding_env.py`: `r_total = 5*pos_dist_1 + 5*pos_dist_2 + drop_penalty + wrist_angle`, `drop_penalty =
  -500*is_fall` (`is_fall` from `obj{1,2}_pos[:,2] < height_threshold=0.06`), plus `wrist_angle =
  -10*wrist_too_high` when wrist angle exceeds `wrist_threshold=0.15`. **Mismatch:** code's extra
  `-10*wrist_too_high` term is absent from Table 2's printed Baoding formula.
- Handwriting: no `pddm/envs/handwriting/` exists in the repo and no reward body is in code/md — the Table 2
  formula above is paper-only, unverifiable against code.

## Contact / penetration handling
Not addressed. Neither source uses "penetration" or any interpenetration metric. Failure/termination is
judged purely by object height thresholds: Baoding `height_threshold=0.06` m, cube `obj_height < -0.1`
(code, `get_reward`). Contact solver parameters are not given.

## Evaluation
- metrics (exact definitions where given): "NormalizedTaskReward" (Fig. 4, 5 y-axes) and "TaskReward" (Fig.
  6, 8), not otherwise defined beyond the Table 2 reward formulas; "TrackingMeanError (mm) of Pencil Tip" is
  the Handwriting metric (Fig. 7 y-axis). Each env exposes a `get_score` method (code/md signatures) but its
  body is not in code/md, so a success definition distinct from the planning reward is **not stated**.
- headline numbers: Baoding balls solved with "100,000 data points, or 2.7 hours worth of data," PDDM the
  only method to succeed (Sec 4.3, Fig. 8). In-hand reorientation: PDDM best on both 2- and 8-goal-angle
  variants; SAC "actually attaining a higher final reward" than PDDM on 2 goals but failing on 8 (Fig. 6).
  Handwriting: PDDM, SAC, NPG all solve the single fixed trajectory; "only PDDM succeeds" on arbitrary
  trajectories (Fig. 7).
- baselines beaten (Sec 4.3): Nagabandi et al. [20] (deterministic NN + random-shooting MPC), PETS [27],
  NPG [33] (model-free), SAC [34] (model-free), MBPO [35] (hybrid). Re-run vs. quoted: not stated.
- real robot? Yes — 24-DoF Shadow Hand, Baoding balls only (not valve/cube/handwriting), "trained entirely
  with real-world experience, without any simulation or prior knowledge of the system" (Sec 4.4). Success
  criterion: "the episode terminates if the specific task horizon of 10 seconds has elapsed or if the hand
  drops either ball" — success = completing the commanded 90° or 180° rotation within 10 s without a drop.
  Results (Fig. 9, Sec 4.4): "a success rate of about 100%" for 90° after "under 2 hours of real-world
  training," and "about 54% on the challenging 180° rotation task." Trial count behind these %: not stated.

## Grasp pose and manipulation mode
PDDM is not a grasp-pose generator: no separate learned/sampled grasp module exists; joint targets at every
timestep are the direct output of MPC planning against the learned dynamics model. This is continuous
in-hand manipulation (finger-gaiting), not discrete grasp-then-lift — valve turning is a fixed-object 1-DoF
rotation, while cube reorientation and Baoding balls involve free-floating objects requiring "careful
stabilization strategies as well as re-grasping strategies" (Sec 4.1) that emerge from planning against the
reward, not a separate grasp-synthesis step. Initial reset pose: set by each env's `do_reset`/`reset_model`
(signatures in code/md, bodies not shown) — exact reset distribution not stated.

## Object / task set (exact names, Sec 4.1, Table 2)
Four tasks: **Valve Turning** (D'Claw 9-DoF hand turns a 1-DoF valve to a random target in [−π, π]);
**In-hand Reorientation** (24-DoF hand reorients a free-floating cube to arbitrary goals — evaluated with 2
goal angles [left/right 90°] and 8 goal angles [90° and 45° left/right/up/down], Sec 4.3); **Handwriting**
(fixed base, pencil-tip tracking; single fixed trajectory vs. training on arbitrary trajectories then testing
on the fixed one); **Baoding Balls** (two free-floating balls rotated around the palm, counter-clockwise by
default, "repurposed, without additional training" for clockwise rotation, single-ball relocation, and
hand-posing, Sec 4.3).

## Limitations stated by the authors
Sec 5 frames these as future work, implying current gaps: "studying methods for planning at different levels
of abstraction in order to succeed at sparse-reward or long-horizon tasks," and "studying the effective
integration of additional sensing modalities such as vision and touch." Sec 4.4: the real-world task "is
substantially more challenging than its simulated counterpart," gains slowing once the policy "must learn the
more complex transition of transferring control of a Baoding ball from the pinky to the thumb." Real-world
state comes from a learned camera tracker with "average tracking errors of 5 mm and latency of 20 ms"
(App. C) — an unmodeled error source in the real-robot numbers.
