# artigrasp_2023 — ArtiGrasp: Physically Plausible Synthesis of Bi-Manual Dexterous Grasping and Articulation (Zhang et al., 3DV 2024)

sources: papers/md/artigrasp_2023.md [fb69acf2] ; code/md/artigrasp_2023.md [92fb3078]

## One-line contribution
Per-hand PPO policies on simulated MANO hands in RaiSim that grasp, relocate and articulate ARCTIC's two-part objects from a single static hand-pose reference, trained with a two-phase curriculum (fixed-base single-hand, then free-base two-hand); 0.50 task success vs 0.11 for a D-Grasp adaptation (Table 3).

## Setting
- hand(s): "controllable MANO hand models [53] with mean shape following [16]. The models have 51 DoFs each and are represented by the local hand pose q in R^45 and global pose T in R^6" (Sec. 4); code: `hand_model_r: "rhand_mano.urdf"`, `hand_model_l: "lhand_mano.urdf"` (general_two/cfgs/cfg_reg.yaml). No arm; floating wrist. Bimanual, one policy per hand.
- simulator / physics: RaiSim [34] (Sec. 6.1); "Simulation timestep 2.5e-3 s", "Simulation steps per action 4" (Table 6) = 100 Hz control; code `simulation_dt: 0.0025`, `control_dt: 0.01`, `num_envs: 21`, `num_threads: 32`, `max_time: 4.0` (general_two cfg). "physics simulation speed scales roughly quadratically with the number of contacts in the environment" (Sec. 4.4). Training: "a single Nvidia RTX 6000 GPU and 128 CPU cores ... roughly three days" (Sec. 6.1).
- observation (Sec. 4.2): hand features H = (q, q_dot, f, T_dot~) — joint rotations, velocities, "net contact forces of each link of the hand", wrist linear/angular velocity in object-relative frame; object features O = (Omega~, Omega_dot~, I_art) with the 7-DoF articulated pose and velocity wrist-relative, and I_art = (q~_ax, q~_art, l_art, m_art, m_base): articulation-axis direction, wrist-to-axis direction and distance, part masses; goal features G = (g~_q, g~_x, g_c, g_a): joint-angle error to reference, joint-position error, "[c | c - c]" target contacts and binary-contact difference, and articulation-angle error.
- action space: "PD-control targets, from which torques tau are computed" (Sec. 4); code `finger_action_std: 0.015`, `rot_action_std: 0.01`, `wrist_dim: 6`.
- objects / data: ARCTIC meshes "split into a base and an articulation part with a single connecting joint" (Sec. 4); 8 objects after excluding scissors, capsule machine and phone (App. B.1); "745 hand pose references for 8 objects ... train/test split of 488/257" (App. B.1); one reference per interaction, chosen by heuristics: grasping if base velocity exceeds eps_v, articulation if the angle changes (App. B.2). Image-based references: 60 from validation subject s05 via the ARCTIC regressor (App. B.5).

## Method
- paradigm: RL; PPO [54] following D-Grasp's implementation (App. A). Table 6: epochs 1e4, steps per epoch 6e5, 300 env steps per episode, batch 2000, 20 updates per epoch, gamma 0.996, lambda_GAE 0.95, clip 0.2, lr 5e-4, 2 x 128 hidden, entropy 0.0.
- reward (Sec. 4.3; the equations were dropped by the converter, so only the text descriptions survive): r = r_im + r_task. r_im contains the pose reward r_p ("joint position error is the weighted sum of the distances between target and current positions x and x of every joint, and the joint angle error measures the L2-norm of the differences between the target and current finger joint (and wrist) angles", weights w_px^i and w_pq), the contact reward r_c ("a relative contact term, which corresponds to the fraction of target contacts c the hand has achieved, and a contact impulse term, which encourages the amount of force f applied on desired contact joints, capped by a factor proportional to the object's weight m_o", weights w_cc, w_cf) and a regulariser r_reg on "the linear and angular velocities of the hand and object". r_task = "opening the object to a target articulation angle and avoiding the movement of the object base from its initial pose", weights w_tq, w_tx.
- weights (Table 6): w_px 3.0, w_px,fingertip 12.0, w_pq 0.2, w_cc 1.5, w_cf 1.5, w_rh 0.5, w_ro 0.2, w_tq 1.5, w_tx 0.2, lambda 5.0 (lambda is not defined in the extracted text; presumably the impulse cap factor).
- code: the reward body is C++ (raisimGymTorch env, not in the code md, which lists Python signatures only: `get_reward_info` -> `self.wrapper.rewardInfoLeft()`). The coefficients in `raisimGymTorch/raisimGymTorch/env/envs/general_two/cfgs/cfg_reg.yaml` are: pos_reward 3.0, pose_reward 0.2, contact_reward 1.5, impulse_reward 1.5, obj_angle_reward_ 1.5, obj_pos_reward_ 0.2 ("distance to initial position"), rel_obj_vel_reward_ -0.5 ("object velocity in wrist frame"), torque -0.0, body_vel_reward_ -0.5, body_qvel_reward_ -0.2, obj_avel_reward_ -0.5 ("angular vel of the joint"), obj_vel_reward_ -0.5, obj_qvel_reward_ -0.3. Match: w_px, w_pq, w_cc, w_cf, w_tq, w_tx. Mismatch: the paper's two regulariser weights (w_rh 0.5, w_ro 0.2) are five separate velocity penalties in code (-0.5, -0.2, -0.5, -0.5, -0.3), and the fingertip weight 12.0 and lambda 5.0 do not appear in the yaml. Phase-1 config `envs/left_fixed/cfgs/cfg_reg.yaml` uses contact_reward 2.0, impulse_reward 2.0, obj_angle_reward_ 0.0, body_qvel_reward_ -0.2 (body_vel commented out), i.e. the weights differ between curriculum phases and Table 6 reports only one set.
- no explicit penetration term: penetration is left to the simulator; "This allows our method to learn motions that adhere to physical plausibility, ensuring no object interpenetration" (Sec. 1).
- key trick(s): two-phase curriculum — phase 1 "fix the objects to the table surface and train each hand separately in its own physics environment", phase 2 free base and "the hands are both simulated in the same environment" (Sec. 4.4; code envs `left_fixed`, `multi_obj_arti`, then `general_two`); articulation features I_art; sequence composition by heuristics (release, retract along object-centre-to-wrist, interpolate to pre-grasp, articulate) with D-Grasp's motion-synthesis module for relocation (Sec. 5).

## Evaluation
- metrics (Sec. 6.1, verbatim): "Grasp Success Rate (Suc. G): A grasp is defined as success if the object is lifted higher than 0.1m and does not fall until the sequence terminates." "Position Error (PE): The mean position error between the object's final and target 3D position in meters." "Angle Error (AE): ... geodesic distance in radian." "Articulation Success Rate (Suc. A): An articulation is defined as success if the hand can articulate the object for more than 0.3 rad and the articulated part does not slip until sequence termination." "Articulation Angle Error (AAE)" in radian. "Simulated Distance (SD): As articulation should not move the object base, we report average displacement of the object base in meters." "Task Success Rate (Suc. T): We deem a task as success if the PE < 0.05m, the AE < 0.2rad, and the AAE < 0.5rad."
- interpenetration: "We omit the interpenetration metric since all of our baselines include a physics simulation which exhibits no interpenetration." (Sec. 6.1). No penetration number is reported anywhere in the paper.
- protocol: grasping on 30 sampled 6D targets per reference (x,y in [-0.15, 0.15] m, z in [0.15, 0.45] m, orientation noise +-0.3 rad); articulation on 5 targets {0.5, 0.75, 1.0, 1.25, 1.5} rad (App. B.3); composed task ~7500 trials, target base in x,y [-0.1, -0.05] m, yaw +-0.4 rad, articulation in [0.5, 0.6] rad (App. B.4).
- headline numbers:
  - Table 2 (Suc. G / PE / AE | Suc. A / AAE / SD): PD+IK 0.13 / 1.20 / 1.50 | 0.28 / 0.80 / 0.39; D-Grasp 0.72 / 0.12 / 0.62 | 0.22 / 0.93 / 0.49; Ours 0.71 / 0.13 / 0.69 | 0.55 / 0.57 / 0.01.
  - Table 3 (composed task, Suc. T / PE / AE / AAE): D-Grasp 0.11 / 0.05 / 0.15 / 0.66; Ours 0.50 / 0.03 / 0.10 / 0.41.
  - Table 4 (image-reconstructed references, s05): D-Grasp 0.60 / 0.16 / 0.78 | 0.20 / 1.07 / 0.63; Ours 0.64 / 0.16 / 0.80 | 0.54 / 0.55 / 0.01; Ours* (mocap refs) 0.67 / 0.14 / 0.95 | 0.54 / 0.53 / 0.01.
  - Table 5 (ablations): w/o curriculum 0.74 / 0.13 / 0.65 | 0.36 / 0.77 / 0.02; w/o cooperation 0.21 / 0.32 / 1.43 | 0.48 / 0.65 / 0.02; w/o art. features 0.67 / 0.15 / 0.73 | 0.48 / 0.67 / 0.01; Ours 0.71 / 0.13 / 0.69 | 0.55 / 0.57 / 0.01.
  - Unseen object: "about 15% performance drop" on a single left-out object (Sec. 6.2, no table).
- baselines beaten: D-Grasp [16] (articulation and composed task; grasping is a tie: 0.71 vs 0.72), PD+IK.
- real robot? No.

## Limitations stated by the authors
- "it sometimes generates unnatural poses caused by noisy hand pose references and the trade-off between the task and imitation reward" (Sec. 7); "especially the index finger is often poorly labeled in the data, which translates to our policies" (App. C.2).
- Three ARCTIC objects excluded: scissors ("requires in-hand manipulation"), phone and capsule machine ("very small and thin articulation parts which cannot be modeled with our method currently") (App. B.1).
- Generalisation to unseen objects only a "proof-of-concept" on one object (Sec. 6.2); planning between phases is heuristic (App. C.1).

## Quotable claims (verbatim, with section)
- "This allows our method to learn motions that adhere to physical plausibility, ensuring no object interpenetration and that object articulation results from stable hand-object contacts and forces." (Sec. 1)
- "We omit the interpenetration metric since all of our baselines include a physics simulation which exhibits no interpenetration." (Sec. 6.1)
- "Despite reconstruction noise such as handobject interpenetration, our method can retain comparable performance as in the experiment with hand pose references from motion capture." (Sec. 6.3)
- "physics simulation speed scales roughly quadratically with the number of contacts in the environment" (Sec. 4.4)

## Notes for the survey
- Feeds: two-hand physics-based synthesis from ARCTIC; curriculum from single-hand fixed-base to shared free-base; the "simulator guarantees no interpenetration" stance (contrast with the DexTrack audit in the parent repo, where 1-2 mm holds were measured in Isaac Gym; RaiSim's contact solver is not the same, and no penetration measurement is reported here).
- Reward equations are missing from the markdown; the yaml coefficients are the only machine-readable form of the objective, and they disagree in structure with Table 6's regulariser weights (see Method).
- Code needs a RaiSim licence ("you need to get a valid, free license for the RaiSim physics simulation", README); repository licence file not in the md. URDFs for ARCTIC objects live in this repo (`rsc/arctic`), which the ARCTIC README lists as a third-party resource.
- Corpus usage of ArtiGrasp (grep -l -i): arctic_2022, bidexgrasp_2026, bidexhd_2024, bimangrasp_2024, dexmachina_2025, dextrack_2025, gigahands_2024, maniptrans_2025, taco_2024.
