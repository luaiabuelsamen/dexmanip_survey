# physics_engine_comparison_2015 — Simulation Tools for Model-Based Robotics: Comparison of Bullet, Havok, MuJoCo, ODE and PhysX (Erez, Tassa, Todorov, ICRA 2015)

sources: papers/md/physics_engine_comparison_2015.md [sha256 30decb48] ; no code

## One-line contribution
A common-interface benchmark (same XML model, same PD grasp controller, ported to each engine's native API) comparing MuJoCo, Bullet, ODE, PhysX and Havok on raw speed, numerical self-consistency, energy/momentum conservation, and a grasp-stability test; conclusion: "each engine performs best on the type of system it was designed and optimized for: MuJoCo wins the robotics-related tests, while the gaming engines win the gaming-related tests without a clear leader among them" (Abstract).

## Setting
- hand(s): "A 35-DOF robotic arm, modeled after the Shadow Hand robot, grasping a capsule using fixed spring-dampers" (Sec. IV-A, "Grasping"). No DoF breakdown between arm and hand is given; spring-damper PD gains for the grip: "Set-points for the spring correspond to a clenched-fist configuration. Spring-damper parameters are respectively K = 0.4 Nm/rad and B = 0.005 Nms/rad." No other hand is used.
- arm: the same 35-DOF Shadow-Hand-modeled arm/hand system; no separate arm model. single/bimanual: single.
- simulator / physics: five engines compared side by side via a shared model (parsed once from MJCF, replicated via each engine's API): MuJoCo, Bullet (plus an experimental Featherstone/"BulletMB" articulated variant), ODE, PhysX, Havok. Models restricted to a common feature subset: hinge joints only (plus a free joint for floating bodies), sphere/capsule collision geometry plus a ground plane (no boxes or meshes), Coulomb friction only (no restitution or rolling friction), and forces limited to gravity, joint constraints, actuation torques, and joint stiffness/damping (Sec. II).
- observation / action space: state (position + orientation + linear/angular velocity of every rigid body) recorded uniformly across engines (Sec. II); action = joint torques via a PD controller with constant reference positions for the grasp task (Sec. III).
- objects / data: four synthetic model systems (Sec. IV-A): **Grasping** (35-DOF Shadow-Hand-like arm + capsule object); **Humanoid** (25-DOF, falls and wiggles under sinusoidal open-loop torques); **Planar Chain** (5-DOF, 5 bodies, 5 frictionless hinges, energy/angular-momentum conserving); **27 Capsules** (27x6=162 DOF, randomly oriented capsules falling onto the floor, a gaming-style stacking scenario). Large-scale variant: N=(25,50,75,...,250) capsules for the sparse-solver scaling test (Sec. V).

## Physics
- **Contact model**: soft/rigid varies by engine, but the comparison framework itself restricts contacts to Coulomb friction between spheres/capsules and a ground plane only — "excluding features like restitution and rolling friction" (Sec. II). MuJoCo's contact model is the soft-convex one from mujoco_2012/mujoco_convex_contact_2014 (not re-derived here); the paper treats the other engines' contact models as given by their native LCP/impulse solvers, not re-specified numerically.
- **Solver / iteration counts**: only ODE's is given a number — "We used 50 iterations [of ODE's iterative LCP solver], which Stevens et al. [22] found to be necessary to achieve comparable accuracy to Bullet and DART" (Appendix, ODE). ODE's exact solver was tried and rejected: "We were unable to run stable simulations with the exact solver ... This may be because we are testing contact configurations where the underlying LCPs become harder to solve exactly. Therefore we only report results using the iterative solver." No iteration counts are given for Bullet, PhysX, or Havok's internal solvers. MuJoCo is run in two integrator configurations — semi-implicit Euler and 4th-order Runge-Kutta (the RK order is MuJoCo's own accuracy knob, described as "sub-dividing the timestep in Runge-Kutta fashion," Sec. III) — plus, in Sec. V only, a comparison of MuJoCo's "(still experimental) sparse solver" against "the dense solver used in the rest of the paper."
- **Differentiable contacts**: not discussed; the paper predates the differentiable-simulation literature and makes no differentiability claim for any engine.
- **Default timestep / substeps**: no single "default" — the whole point of the paper is a timestep sweep. Consistency test: "running the simulation at many different values of the timestep h, from 1/64 msec to 32 msec increasing by a factor of 2" (Sec. IV-C), using an engine-specific reference trajectory generated at "very small h, in our case 1/64 msec" (Sec. III). Large-scale sparse-solver test (Sec. V): fixed 10 msec timestep, Euler integration, 10 sec simulated.
- **Friction model**: Coulomb friction only, uniformly imposed across engines by the comparison framework (Sec. II, "Contact"); no per-engine friction-cone/pyramid detail is given for the non-MuJoCo engines.
- **Penetration handling / exposure**: the framework computes "features such as momentum, energy, joint dislocation, joint limit violation and **contact penetration**" from the recorded rigid-body state (Sec. II) — i.e., penetration is measured/exposed as a derived quantity in this benchmark's own instrumentation, uniformly across all five engines, though the paper does not report numeric penetration-depth values in the results (the grasp test instead reports the qualitative pass/fail "object still in hand" outcome per timestep). How each native engine internally resolves penetration (soft vs. hard) is not itemized per engine beyond noting MuJoCo's joint-coordinate, non-Cartesian representation and its accuracy edge.
- **GPU or CPU**: CPU only, single machine for all: "All tests were performed on an i7-3930K processor running Windows 8.1. We used high-resolution timers to time the main step function of each engine" (Sec. IV-B).
- **Throughput** (Fig. 3, second column, "thousand evaluations/sec (kHz)", i7-3930K, single core, all values verbatim from the flattened figure text):
  - Grasp: Bullet 2.9e-4, Havok 3.7e-3, MuJoCo Euler 6.5e-2, ODE 6e-1, PhysX 3e0 (units/scale ambiguous in the flattened OCR — these appear to be the y-axis accuracy-plot values interleaved with the speed legend in the same figure block; the note flags this ambiguity explicitly, see below).
  - Humanoid: Bullet 4.8, Havok 5, MuJoCo Euler 14.5, ODE 9.1, PhysX 3.8 (kHz).
  - Planar Chain: Bullet 22.8, BulletMB 81.4, Havok 23.8, MuJoCo Euler 243.2, ODE 36, PhysX 6.4 (kHz).
  - 27 Capsules: Bullet 4.4, Havok 6.2, MuJoCo Euler 3.6, ODE 23.7, PhysX 5.2 (kHz).
  - AMBIGUITY FLAG: Fig. 3's OCR/markdown flattening interleaves the per-system legend values with axis labels and accuracy-plot numbers (e.g., the Grasp row's numbers look like accuracy/discrepancy values, not the humanoid/chain/capsule rows' kHz-scale numbers, which are self-consistent with "thousand evaluations/sec"). Treat the Humanoid, Planar Chain, and 27-Capsules kHz figures above as reasonably reliable (consistent order of magnitude and internally consistent with prose: "MuJoCo is the fastest engine ... sometimes by a wide margin" on robotics systems, "ODE wins by a large margin" on capsules, "MuJoCo is the slowest" on capsules — Sec. IV-B); do NOT trust the Grasp-row numeric values quoted above as raw kHz without checking the original figure.
  - Prose qualitative summary (Sec. IV-B): "on systems relevant to robotics, MuJoCo is the fastest engine in the comparison, sometimes by a wide margin. In the gaming scenario however (i.e. the capsule test) ODE wins by a large margin, while MuJoCo is the slowest." BulletMB (articulated Bullet) on the Planar Chain: "3 times slower than MuJoCo" but "still outperforms all the engines that use Cartesian coordinates by a significant margin."
  - Large-scale sparse-solver scaling (Sec. V, Fig. 5, N=25..250 capsules, 10 sec sim, 10 msec Euler timestep): "the sparse solver has linear scaling, and for the largest system it is 76 times faster than the dense solver — whose scaling is between quadratic and cubic." "MuJoCo's sparse solver in this setting is about 2 times slower than gaming engines, however it does have linear scaling." No absolute wall-clock numbers given in text; Fig. 5's numeric axis values did not survive parsing.
- **Robot hands shipped as assets**: none as reusable assets — the "Shadow-Hand-modeled" 35-DOF arm+hand is this paper's own custom XML test model, built once in MJCF and replicated via each engine's own API (Sec. II); it is not described as a distributable/released asset.

## Evaluation
- metrics: (1) raw CPU speed in evaluations/sec (Fig. 3 col. 2); (2) self-consistency = deviation from a very-small-timestep reference trajectory, averaged over "10 trajectory pieces," measured as a speed-accuracy Pareto curve (Fig. 1-3 col. 3; Sec. III, IV-C); (3) energy and linear/angular momentum drift on energy/momentum-conserving variants ("astronaut" = humanoid with gravity/ground disabled; planar chain) (Fig. 4, Sec. IV-E); (4) grasp stability = "the largest timestep h for which the object remains in the hand during the entire simulation" (Sec. III, IV-D).
- headline numbers: **Grasp-stability table (Sec. IV-D, exact)**: Bullet 1/32 ms, MuJoCo Euler 16 ms, MuJoCo RK 16 ms, ODE 1/4 ms, PhysX 2 ms (Havok excluded — "we currently have no working PD controller for Havok, and it is therefore excluded from the grasping test," Appendix). MuJoCo holds the grasp at a timestep 8x larger than PhysX (the next best) and 64x larger than ODE. See Throughput above for raw-speed and consistency figures.
- baselines beaten: MuJoCo beats all four other engines on robotics-relevant speed and consistency, and on grasp-stability timestep; ODE and the Cartesian engines beat MuJoCo on raw speed for the disconnected-body (27-capsule) gaming scenario, and Cartesian engines (Bullet, ODE, PhysX, Havok) beat MuJoCo's joint-coordinate representation specifically on **linear momentum conservation** at large timesteps: "Constant linear momentum means that the system state remains on a manifold which is a linear subspace in Cartesian coordinates ... Indeed, the Cartesian engines are actually more accurate with larger time steps ... even [MuJoCo's RK integrator] cannot compete with Cartesian engines on this test" (Sec. IV-E). ODE's semi-implicit Coriolis-force integration also wins the angular-momentum "astronaut" test despite Euler integration (Sec. IV-E).
- real robot? no — all four systems are synthetic/simulated only.

## Full comparison table's conclusions (as requested)
Consolidating Sec. IV-B through V and the Summary (Sec. VI) system-by-system:
- **Grasping** (robotics-relevant, hardest test): MuJoCo (Euler and RK, tied) holds the grasp at up to 16 ms; PhysX a "distant second" at 2 ms; ODE at 0.25 ms; Bullet at 0.03 ms; Havok untested (no working PD controller). "All engines manage to complete the test at small timesteps... But as the timestep increases they effectively simulate a different physics model which can no longer hold the object." Consistency: "Note the grasp model where ODE and Bullet have partial speed-accuracy curves. This is because for larger timesteps they go unstable on this system."
- **Humanoid** (robotics-relevant): MuJoCo fastest and most consistent; among the least consistent were "PhysX and Havok — which is interesting because they are probably the most heavily optimized gaming engines in our comparison. This result confirms the common knowledge that gaming optimizations do not target accuracy but rather stability."
- **Planar Chain** (energy/momentum-conserving, no contact): "The largest difference is seen for the planar chain, where the test is won not so much by the engine but by the RK integrator" — RK-MuJoCo dominant by orders of magnitude on consistency; BulletMB (articulated) is 3x slower than MuJoCo but beats the Cartesian engines significantly.
- **27 Capsules** (gaming-relevant, no robotics analog): ODE fastest by a large margin, MuJoCo slowest in raw speed, but "MuJoCo outperforms all other engines by orders of magnitude [in consistency] ... even on the capsule test where it is the slowest [in speed]."
- **Energy/momentum conservation** ("astronaut" humanoid, planar chain, Fig. 4): RK integration wins energy conservation "by orders of magnitude, as it should"; ODE's semi-implicit Coriolis-force handling wins angular momentum "despite using Euler integration"; Cartesian engines win linear-momentum conservation at large timesteps because the conserved manifold is linear in Cartesian coordinates but curved in joint coordinates.
- **Large-N scaling** (Sec. V, capsules, joint- vs. Cartesian-coordinate scaling): MuJoCo's sparse solver scales linearly and is 76x faster than its own dense solver at N=250, but is still "about 2 times slower than gaming engines" at that scale — the paper attributes the gaming engines' scaling advantage to Cartesian coordinates avoiding the dense "Hessian" A = J M^-1 J^T that arises even from sparse M and J in joint coordinates, requiring "elaborate indexing machinery" to route around.
- **Bottom line (Sec. VI, verbatim synthesis)**: "None of the engines being compared was uniformly better than all others. MuJoCo was both the fastest and the most accurate on constrained systems relevant to robotics, and was capable of stable grasping at a much larger time step. On systems composed of many disconnected bodies it was the slowest in terms of raw CPU speed (while ODE was the fastest), however it remained the most accurate overall."

## Limitations stated by the authors
- Model feature set deliberately restricted (hinge joints only, sphere/capsule collision only, Coulomb friction only, no body-level damping/joint friction) — "we are not testing every engine-specific feature, even if some of the omitted features may offer an advantage for robotics applications" (Sec. II).
- Author conflict of interest disclosed: "we are the developers of the MuJoCo engine which is included in the comparisons ... a secondary goal of this paper is to identify the strengths and weaknesses of MuJoCo" (Sec. I).
- Bullet's Featherstone/articulated mode "is not yet fully debugged and exhibits unexpected behavior in some simulations, so we were able to use this new functionality only in tests without contact" (Appendix).
- PhysX's articulation API "does not offer a direct way to compute joint angles" so PhysX articulation results are excluded (Appendix).
- Havok has no working PD controller in this framework and is excluded from the grasp test entirely (Appendix).
- ODE's exact LCP solver was unstable in their tests; only the 50-iteration approximate solver is reported, "in contrast to the experience of others" (Appendix).
- Consistency measurement is heuristic, not exact, near chaotic regimes: "once the state deviates from the reference, further deviations may actually be physically correct (especially if the system is near-chaotic). So we should measure deviations over small integration intervals" (Sec. III).
- Grasp-timestep measurements are only accurate to a factor of 2 because tested timesteps are log-spaced (Sec. IV-D).
- "It is an open question whether this [grasp] model system can be tuned to work better in the gaming engines" (Sec. IV-D).
- MuJoCo's sparse solver is explicitly called "still experimental" (Sec. V).

## Notes for the survey (which sections this feeds; contradictions with other notes)
- Physics-engine background / motivation section: the canonical "why MuJoCo dominates dexterous-hand RL" citation — the grasp-stability table (16 ms vs. 2 ms vs. 0.25 ms vs. 0.03 ms) is the single strongest, most citable number in this batch for "MuJoCo's soft-contact + joint-coordinate formulation holds a grasp at far larger timesteps than gaming engines."
- Flag the Fig. 3 OCR ambiguity for the Grasp-row raw-speed numbers explicitly if this table is reused in the survey — re-verify against the original PDF figure before quoting the Grasp row's kHz values; the Humanoid/Chain/Capsule rows are corroborated by consistent prose and are safer to quote.
- Contrast with mujoco_convex_contact_2014: that paper's "penetration is a controlled, mass-independent, critically-damped state variable" claim is indirectly validated here by MuJoCo's outsized grasp-stability timestep — large timesteps are tolerable specifically because penetration is absorbed softly rather than causing instability, matching this paper's framing ("they effectively simulate a different physics model which can no longer hold the object" for the LCP-based engines going unstable at similar timesteps).
- No GPU, no batching, no differentiability — 2015, single-core CPU, one seed per config (10 trajectory pieces averaged for consistency, not repeated random seeds) — do not conflate with later GPU-parallel throughput numbers (isaacgym_2021, brax_2021, maniskill2_2023, mujoco_playground_2025) which use entirely different protocols (batched env-steps/sec vs. single-instance evaluations/sec).
- No hand asset ships from this paper; the Shadow-Hand-modeled grasp system is a one-off, non-distributed test rig — do not cite this as a source of a reusable Shadow Hand model.
