# robopianist_2023 — RoboPianist: Dexterous Piano Playing with Deep Reinforcement Learning (Zakka et al., CoRL 2023)

sources: papers/md/robopianist_2023.md [43aa10df] ; code/md/robopianist_2023.md [0d9736c6]

## One-line contribution
A MuJoCo benchmark, ROBOPIANIST, of two Shadow Dexterous Hands playing a full-size 88-key piano from a 150-song MIDI corpus (`REPERTOIRE-150`), where a DroQ (regularized SAC) agent trained with human-prior-shaped rewards (fingering labels, key-press shaping, energy penalty, lookahead) reaches an average F1 of 0.79 on a 12-song evaluation suite, nearly double an MPC (Predictive Sampling) baseline's 0.43, while multi-song RL and multitask BC both fail to generalize zero-shot to held-out songs (Abstract, Sec. 3-5).

## Setting
- hand(s): **two Shadow Dexterous Hand** models ("Shadow Hand E3M5" per the code's `ShadowHand` class docstring) from MuJoCo Menagerie, "designed to closely reproduce the kinematics of the human hand" (Sec. 3). DoF is not given as a single number in the parsed paper text; the action is 45-dimensional total for both hands plus sustain pedal (see Action space below), and the code exposes a configurable `reduced_action_space` and `forearm_dofs` option (constrains DoF not present in the human hand, e.g. an opposable little finger, and reduces thumb joint range — Sec. 4.4). Vendor: Shadow Robot Company (cited as [37] in the paper; not independently confirmed by name in the parsed text beyond "Shadow Dexterous Hand").
- arm: forearms are present as a small number of additional Cartesian DoF (see observation table: "Forearm Cartesian position," 6 values = 3 per hand), not a full manipulator arm — the hands are mounted with limited forearm translation, not a 6/7-DoF arm.
- bimanual: yes — both hands play simultaneously, and one explicit reward term (`forearm_reward` in code, not in the paper's Table 2) penalizes forearm-forearm collisions between the two hands.
- simulator / physics: **MuJoCo** (cited [34, 35], version not stated in the parsed text). Physics timestep is **not explicitly stated for the RL agent** in the main text, but the MPC baseline (App. F) states "a physics time step of 0.005 seconds," and the main text states actions are converted to torques "using PD controllers running at 500Hz" (Sec. 3) — consistent with a 0.002s physics substep cadence implied by 500Hz, though the paper does not directly equate the two. Contact model: not stated (MuJoCo default not specified). Number of parallel envs: not applicable — this is a single-environment, non-vectorized JAX RL codebase per App. D ("Computing infrastructure").
- control rate: **agent predicts target joint angles at 20Hz**; these targets are tracked by PD controllers running at 500Hz (Sec. 3). Sec. 5.3 additionally sweeps control timestep (0.01/0.025/0.05/0.1 s ↔ 100/40/20/10 Hz) against lookahead horizon L, finding 20Hz (0.05s) a "sweet spot": "at 100Hz, the MDP becomes too long-horizon, which complicates exploration, and at 10Hz, the discretization of the MIDI file becomes too coarse."
- number of parallel envs: n/a (see above).
- GPU and wall-clock: Google Cloud `n1-highmem-64` (Intel Xeon E5-2696V3, 32 cores @ 2.3GHz, 416GB RAM, **4 Tesla K80 GPUs**); "Each 'run'... took an average of 5 hrs wall clock time," with up to 8 runs performed in parallel (App. D, "Computing infrastructure and experiment running time"). MPC baseline ran on a 2021 M1 Max MacBook Pro, 64GB RAM (App. F).

## Learning block
- paradigm: **RL** (model-free, off-policy actor-critic) for the specialist and multi-task-RL experiments; a separate **BC** (behavior cloning, MSE regression) experiment distills specialist RL policies into a multitask policy (Sec. 5.2, "Multitask Behavioral Cloning") — this is a genuine RL→BC distillation pipeline, though not framed by the authors as "teacher-student"; the BC student is trained on 100 collected trajectories per song (2 held out for validation) with a feed-forward MLP predicting expert actions from state+goal via MSE loss.
- algorithm and implementation: **DroQ** [42], "one of several regularized variants of the widely-used Soft-Actor-Critic algorithm" — "a regularized variant of clipped double Q-learning" using dropout (rate 0.01) + layer normalization in each of 3 critic MLP layers (256 hidden units, ReLU); actor is a tanh-diagonal-Gaussian, also a 3-layer 256-unit MLP; Xavier weight init, zero bias init; codebase implemented in JAX (App. D, "Network architecture"). Comparison baseline: **online MPC (Predictive Sampling)**, a derivative-free sampling-based planner using the MJPC implementation (Howell et al.), N=10 candidates/iteration sampled from a Gaussian (nominal mean, σ=0.05) around a cubic-spline (spline dimension 2) action-sequence representation, planning horizon 0.2s, planning timestep 0.01s, physics timestep 0.005s, run at one-tenth real-time speed "to give the planner adequate search time" (App. F). No teacher-student/privileged→vision distillation in the RL agent itself — same (proprioceptive + goal) observations at train and eval; the RL→BC step is the only distillation-like step, and it is privileged-free (both use the same state+goal inputs).
- observation vector, item by item (Table 1, verbatim): Hand and forearm joints (rad, size 52); Forearm Cartesian position (m, size 6); Piano key joints (rad, size 88); Active fingers (discrete, size L·10); Piano key goal state (discrete, size L·88) — where L is the lookahead horizon (stacked future goal states).
- action space: **45-dimensional**, "target joint angles for the hand with an additional scalar value for the sustain pedal" (Sec. 3) — i.e. position targets, not torques or a residual; predicted at 20Hz and converted to torques by PD controllers at 500Hz. Sec. 4.4 ("Constraining the action space") explores a reduced action space by disabling non-human-hand DoF (e.g. opposable little finger) and narrowing the thumb's joint range — this speeds up learning, though "with additional training time, the full action space eventually achieves similar F1 performance."
- domain randomization: not a sim-to-real randomization study; the code exposes an `augmentations` and `randomize_hand_positions` constructor argument on `PianoWithShadowHands` (code/md, `piano_with_shadow_hands.py` `__init__` signature), but the specific randomization ranges are not detailed in the parsed paper text — treat as **not stated** for exact ranges. This is a sim-only benchmark; no real-world deployment is attempted.

## Reward / objective block — quoted from paper AND code (with an explicit mismatch)
**Paper (Sec. 4.2, App. B, Table 2, verbatim):**
| Reward | Formula | Weight | Explanation |
|---|---|---|---|
| Key Press | 0.5·g(‖k_s−k_g‖₂) + 0.5·(1−**1**{false positive}) | 1 | "Press the right keys and only the right keys" |
| Energy Penalty | |τ_joints|ᵀ|v_joints| | −5e-3 | "Minimize energy expenditure" |
| Finger Close to Key | g(‖p_f−p_k‖₂) | 1 | "Shaped reward to bring fingers to key" |
"g is a function that transforms the distances to rewards in the [0,1] range" (the `dm_control` `tolerance` function). "The total reward at a given time step is a weighted sum over the aforementioned components" (Sec. 4.2). App. D additionally names a `discount factor` of 0.99 as a training hyperparameter (Table 3), separately ablated in Sec. 5.3 over [0.84, 0.99], finding 0.84-0.92 optimal and noting agents trained with high discounts (0.96, 0.99) become overly conservative ("opting to skip entire note sub-segments").

**Code (`robopianist/suite/tasks/piano_with_shadow_hands.py`, `PianoWithShadowHands._set_rewards`, quoted verbatim):**
```python
def _set_rewards(self) -> None:
    self._reward_fn = composite_reward.CompositeReward(
        key_press_reward=self._compute_key_press_reward,
        sustain_reward=self._compute_sustain_reward,
        energy_reward=self._compute_energy_reward,
    )
    if not self._disable_fingering_reward:
        self._reward_fn.add("fingering_reward", self._compute_fingering_reward)
    else:
        print('Fingering is unavailable. OT fingering reward is used.')
        self._reward_fn.add("ot_fingering_reward", self._compute_ot_fingering_reward)
    if not self._disable_forearm_reward:
        self._reward_fn.add("forearm_reward", self._compute_forearm_reward)
```
`_compute_key_press_reward` matches the paper's Table 2 formula almost exactly (0.5·mean(tolerance(...)) for correct keys + 0.5·(1 − any false-positive activation)). `_compute_fingering_reward` matches g(‖p_f−p_k‖₂) via the `tolerance` function with `bounds=(0, _FINGER_CLOSE_ENOUGH_TO_KEY)`. `_compute_energy_reward` implements the paper's `|τ|ᵀ|v|` formula via `power = hand.observables.actuators_power(physics)` and `rew -= self._energy_penalty_coef * np.sum(power)` (i.e. power = τ·v, consistent, with `energy_penalty_coef` as a constructor argument rather than a hardcoded −5e-3).
**Mismatches (paper vs. code), explicit:**
1. The code's `CompositeReward` sums **five** terms by default (`key_press_reward`, `sustain_reward`, `energy_reward`, `fingering_reward`, `forearm_reward`) — the paper's Table 2 documents only **three** (Key Press, Energy Penalty, Finger Close to Key). `sustain_reward` (rewards correctly timing the sustain pedal via the same `tolerance` mechanism) and `forearm_reward` (flat 0.5 if the two forearms' collision geoms don't intersect, else 0.0 — "Reward for not colliding the forearms") are present in the released code but **not documented anywhere in the paper's reward table or Appendix B text**.
2. The code contains a second fingering-reward variant, `_compute_ot_fingering_reward`, whose docstring is `"""OT reward calculation from RP1M https://arxiv.org/abs/2408.11048"""` — this cites a **later (2024) paper** (RP1M, confirmed as a corpus entry `rp1m_2024` that itself cites RoboPianist) and uses `scipy.optimize.linear_sum_assignment` to solve an optimal-transport-style fingertip-to-key assignment instead of the paper's fixed per-note fingering-label assignment. This is a **post-publication code addition**, not part of the original CoRL 2023 paper's method, and must not be attributed to the paper text.
3. App. B's formula listing gives explicit numeric weights (1, −5e-3, 1); the code's `CompositeReward.compute` (per its signature) appears to sum terms without additional per-term weight multipliers beyond what's baked into each `_compute_*` method's own internal scaling (e.g. energy's `energy_penalty_coef`) — the exact top-level weighting logic inside `CompositeReward.compute`'s body was not captured in code/md (only the class's method signatures were extracted for `composite_reward.py`), so whether the code applies the paper's stated 1/−5e-3/1 weights exactly, or via a different configuration path, is **not independently verifiable from the parsed code** — flag rather than assert equivalence.

## Contact / penetration handling
Partially addressed, but only for a specific collision pair, not general interpenetration: the code's `forearm_reward` explicitly checks `collision_utils.has_collision(physics, right_hand_root_geoms, left_hand_root_geoms)` and zeroes the reward component if the two forearms collide — a binary collision-avoidance shaping term, not a continuous penetration-depth or contact-force penalty, and it is **absent from the paper's own reward description** (see mismatch #1 above). The paper's Table 2 "Finger Close to Key" and "Key Press" terms use unsigned Euclidean distances and joint-position tolerances, not any interpenetration or contact-force measure — finger-key contact itself is measured purely by the piano key's joint position (whether the key is sufficiently depressed), not by a hand-object mesh penetration check. `PianoTask.__init__` (code/md, `base.py`) exposes a `primitive_fingertip_collisions` constructor flag, suggesting an alternate (simplified) fingertip collision geometry mode exists, but its effect is not detailed in the parsed text.

## Evaluation block
- exact success criterion: not a binary success/failure threshold — evaluated continuously via **precision, recall, and F1** computed by comparing per-timestep piano-key on/off state against the MIDI ground truth, averaged across all timesteps (Sec. 3, "Musical evaluation"): "precision measures how good the agent is at not hitting any of the 'off' keys, while recall measures how good the agent is at hitting the 'on' keys... F1... ranges from 0... to 1 (perfect precision and recall)." F1 is the paper's primary reported metric.
- number of eval episodes/seeds: specialist policies trained 5M samples, 3 seeds (Sec. 4, general design-consideration experiments); F1 evaluated "every 10K training steps for 1 episode (no stochasticity in the environment)" — deterministic evaluation, mean-of-policy-output rollout, 1 rollout/evaluation since the environment is fixed (App. D, "Training and evaluation").
- sim vs real: **sim only** — no real-robot deployment anywhere in this paper.
- real-robot trial counts: n/a.
- headline numbers: **ROBOPIANIST-ETUDE-12** (Sec. 5.1, Fig. 4): mean F1 **0.79** (ROBOPIANIST/DroQ) vs **0.43** (MPC/Predictive Sampling) — "our method uses 5 million samples to train for each song using the same set of hyperparameters." Per-song F1 values are shown only as a bar chart (Fig. 4) across 12 named pieces (Piano Sonata D845, Bagatelle Op.3 No.4, Partita No.26, French Suite No.5, Waltz Op.64 No.1, Piano Sonata K279, French Suite No.1, Piano Sonata No.21, Kreisleriana Op.16 No.8, Golliwogg's Cakewalk, Piano Sonata No.23, French Suite No.5) — individual per-song numeric values were not extracted as text (chart only); the 0.79/0.43 averages are the only exact headline numbers in the parsed text.
- **Multi-song RL** (Sec. 5.2, Fig. 5): F1 on the shared training song (Für Elise) drops "from roughly 0.7 F1 for 1 song (i.e., the specialist) to almost 0 F1 for 16 songs" as more songs are added to one policy; zero-shot test F1 on ROBOPIANIST-ETUDE-12 stays low (~0.044-0.060 range per the chart) regardless of pre-training-task count — "multitask RL training fails to positively transfer on the test set regardless of the size of the pre-training tasks."
- **Multitask BC** (Sec. 5.2, Fig. 6): trained on 100 collected trajectories/song (2 held out for val) from `REPERTOIRE-150`, tested zero-shot on `ETUDE-12`; test F1 improves as training-song count increases from 1→64 (higher generalization than RL) "but zero-shot performance on ROBOPIANIST-ETUDE-12 falls far below the performance achieved by the specialist policy." Larger hidden dimension (1024 vs 64-512) improves training-song F1 but risks overfitting with too few songs.
- **Lookahead × control-timestep sweep** (Sec. 5.3, Fig. 7): F1 grid over control timestep {0.01,0.025,0.05,0.1}s × lookahead {0,1,5,10,20}: best cell 0.64 at (timestep=0.05, lookahead=10); worst reported cell 0.08 at (timestep=0.01, lookahead=0); 20Hz (0.05s) control is called "a sweet spot," with 100Hz (0.01s) "drastically reducing the final score."
- baselines: MPC (Predictive Sampling via MJPC, App. F) is the sole quantitative baseline reported in the main comparison (Fig. 4); it was re-implemented/re-run by the authors (not merely quoted), using a cost function of `c_total = c_key + c_finger` (energy/control costs were tried and disabled because "they decreased performance").
- baselines beaten: yes, RoboPianist/DroQ beats the MPC baseline by a wide margin (0.79 vs 0.43 mean F1) on the 12-song evaluation suite.
- real robot?: none.

## Reproducibility
Code, MIDI dataset tooling, and hand/piano models are released: repo (commit 0d9736c6) with `robopianist/suite/tasks/piano_with_shadow_hands.py`, `robopianist/suite/composite_reward.py`, `robopianist/models/hands/shadow_hand.py`, `examples/piano_with_shadow_hands_env.py`, `examples/self_actuated_piano_env.py`, plus tests (`piano_with_shadow_hands_test.py`, `shadow_hand_test.py`). Table 3 (App. D) gives the full RL hyperparameter list: ADAM optimizer (lr 3e-4, β=(0.9,0.999)), critic/actor each 256 hidden units × 3 layers ReLU, dropout 0.01 (critic only), discount 0.99, minibatch 256, replay-buffer capacity 1M, seed steps 5000, critic-target EMA momentum 0.005, actor log-std bounds [−20,2], learnable entropy temperature (init 1.0), 5M total training steps. **Licence, verbatim (code/md README): "All other code is licensed under an Apache-2.0 License." MuJoCo Menagerie's own licence applies to the hand/robot models (linked separately), and "The PIG dataset cannot be redistributed on GitHub due to licensing restrictions"** — i.e. the MIDI fingering-label dataset underlying `REPERTOIRE-150` must be obtained and preprocessed separately by the user, it is not bundled. A "Works that have used RoboPianist" section lists at least one downstream paper (Hu et al., "Privileged Sensing Scaffolds Reinforcement Learning").

## Limitations stated by the authors
"While ROBOPIANIST produces agents that push the boundaries of bi-manual dexterous control, it does so in a simplified simulation of the real world. For example, the velocity of a note, which modulates the strength of the key press, is ignored in the current reward formulation. Thus, the dynamic markings of the composition are ignored. Furthermore, our RL training approach can be considered wasteful, in that we learn by attempting to play the entire piece at the start of every episode, rather than focusing on the parts of the song that need more practicing. Finally, our results highlight the challenges of multitask learning especially in the RL setting." (Sec. 6, "Limitations").

## Quotable claims (verbatim, with section)
- "When we remove this prior and only reward the agent for the key press, the agent's F1 stays at zero and no substantial learning progress is made." (Sec. 4.1, on fingering-label reward shaping)
- "giving a constant penalty regardless of the number of false positives was crucial for learning; otherwise, the agent would become too conservative and hover above the keyboard without pressing any keys." (Sec. 4.2)
- "multitask RL training fails to positively transfer on the test set regardless of the size of the pre-training tasks." (Sec. 5.2)
- "A control frequency of 20Hz (0.05 seconds) is a sweet spot, with notably 100Hz (0.01 seconds) drastically reducing the final score." (Sec. 5.3)

## Notes for the survey

- The paper vs. code reward-term mismatch (5 code terms vs 3 documented paper terms, plus a later OT-fingering-reward citing a 2024 follow-up paper RP1M) is a concrete, well-evidenced instance of "paper documents a simplified version of what the shipped code actually runs" — cite this note's code block directly if the survey discusses reproducibility gaps between published reward formulas and released implementations.
