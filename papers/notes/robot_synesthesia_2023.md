# robot_synesthesia_2023 — Robot Synesthesia: In-Hand Manipulation with Visuotactile Sensing (Yuan et al., ICRA 2024)

sources: papers/md/robot_synesthesia_2023.md [sha256 31f8ee6b] ; no code

## One-line contribution
Fuses camera and tactile-sensor point clouds into one unified 3D point cloud ("Robot Synesthesia") fed to a distilled visuotactile student policy for in-hand object rotation, trained via a PPO teacher → BC/DAgger student pipeline in Isaac Gym and transferred zero-shot to a real Allegro Hand (Abstract; §IV.B–C).

## Setting
- hand(s): 16-DOF Allegro Hand, fitted with 16 Force-Sensing Resistors (FSR) as binary tactile sensors on palm and finger links (§III.A). Arm: XArm6 robot arm (§III.A, Fig. 2). Single hand only; bimanual: not mentioned.
- simulator / physics: Isaac Gym [62] (§III.A). Physics engine beyond "rigid body physics simulator" not specified; sim timestep not stated; control frequency stated as **10Hz, consistent in both simulated and real environments** (§III.A). Number of parallel training envs: not stated. GPU used / wall-clock training time: not stated anywhere in the text.
- observation: teacher (privileged, low-dim state): joint position $q_t\in\mathbb{R}^{16}$, binary tactile signal $o_t$, rotation axis $k\in S^2$, previous position target $\hat q_t$, object position $x_t\in\mathbb{R}^3$, object velocity $v_t\in\mathbb{R}^3$, angular velocity $w_t\in\mathbb{R}^3$, and object shape-feature embedding $f\in\mathbb{R}^{32}$ from a pretrained PointNet encoder (§IV.C.1). Student (deployable): joint position, binary tactile signal, rotation axis, previous position target (stacked with 3 historical states), plus camera point cloud $P^c_t$, augmented (proprioceptive-mesh) point cloud $P^a_t$, and the proposed tactile point cloud $P^{touch}_t$, each point tagged with a one-hot vector marking its source before concatenation (§IV.A.1, §IV.C.2). All point clouds are transformed into the hand-palm frame before being fed to the network (§IV.A.3).
- action space: relative joint position command $a_t\in\mathbb{R}^{16}$; a PD controller drives the hand toward $\hat q_{t+1}=\hat q_t+\hat a_t$, with an exponential moving average $\hat a_t=\eta a_t+(1-\eta)\hat a_{t-1}$, $\eta=0.8$ (§IV.A.2). Control rate 10Hz (§III.A).
- objects / data: no demonstration dataset — pure RL + on-policy distillation. Sim objects: an artificial four-way wheel wrench, two identical balls, and a training set of artificial objects of "common geometries" (cuboids, cylinders, polygons, etc.) for the three-axis task (§III.B, §V.A.1, Fig. 5). Real-world test objects: cubes and "other daily objects of distinct sizes and shapes," used only to test generalization, not for training (§V.A.1, Fig. 5).

## Method
- paradigm: RL (teacher) → teacher-student distillation via Behavior Cloning + DAgger (student) (§IV.C). No goal-conditioned demonstrations used.
- algorithm: Proximal Policy Optimization (PPO) [64] for the teacher; MLP policy/value nets stacking the current state with 3 historical states (§IV.C.1). Student uses PointNet [3] as point-cloud encoder, latent vector concatenated with other inputs into an MLP, first pre-trained with BC on a teacher dataset $D$ of "5120 k transitions" (exact magnitude ambiguous in the OCR'd text — could be 5120·k or 5,120,000; quoted as printed), then fine-tuned with DAgger [65] (§IV.C.2). Which PPO/RL codebase is not stated.
- teacher-student / privileged information: the teacher is privileged with ground-truth object position, velocity, angular velocity, and a pretrained shape-feature embedding $f\in\mathbb{R}^{32}$ (constant per object) — none of which the student observes; the student instead receives only point clouds and tactile/proprioceptive signals (§IV.C.1–2).
- reward or loss — quoted verbatim (§IV.A.3, eq. 1):
  > "$r_t = c_1 r_{rot} + c_2 r_{vel} + c_3 r_{dist} + c_4 r_{torq} + c_5 r_{work} + c_6 r_{ctrl}$."
  Term definitions, quoted/paraphrased as given: "$r_{rot}$ rewards the object's rotation angle. $r_{vel}$ penalizes the object's linear velocity to discourage motions that translate the object. $r_{dist}$ is a decreasing function regarding the distance between the object and the fingertips, encouraging the fingers to approach the object in hand and interact with it. $r_{torq}$ penalizes large torques, $r_{work}$ penalizes the work of the controller, and $r_{ctrl}$ penalizes the control error between command targets and real robot motion." Plus: "We additionally implement a large penalty when the object falls off the hand." The weights $c_1,\ldots,c_6$ are stated only as "tuned hyper-parameters" — **no numeric values are given anywhere in the text**. Discount factor $\gamma$ is likewise only a symbol, never a number. No reward-function code exists in this repo to cross-check (no code source).
- key trick(s): the unified "Synesthesia" tactile point cloud (see below); one-hot point-source tags so vision/augmented/tactile points share one input tensor; action EMA smoothing ($\eta=0.8$); early episode termination when the object falls, "to facilitate efficient training" (§IV.A).

## Tactile-visual point cloud construction (Robot Synesthesia) — §IV.B, §III.A
- Camera point cloud $P^c_t\in\mathbb{R}^{N_c\times3}$: generated from a Microsoft Azure Kinect depth image placed beside the hand, in both sim and real (§III.A). $N_c=512$ (§IV.A.3, after eq. 1).
- Augmented point cloud $P^a_t$: sampled from the robot's own mesh at its current proprioceptive pose, "to model the spatial relationship between the hand and the object" (§III.A). Size $N_a = 8\, n_{link}$, with $n_{link}=21$ links on the hand (§IV.A.3) — i.e. 168 points.
- Tactile point cloud $P^{touch}_t$: "for each tactile sensor on the hand that detects a signal (i.e., $o_{t,i}=1$), we sample points on the sensor's meshes to create a tactile-based point cloud" (§IV.B). Size given as $N_t = 8\, n_{touch}$, where $n_{touch}\in\{0,\ldots,16\}$ is the number of currently triggered FSR sensors (§IV.A.3) — so this cloud is empty except where contact is detected. Note: the state definition in §IV.A.1 writes $P^{touch}_t\in\mathbb{R}^{N_a\times3}$ (same $N_a$ symbol as the augmented cloud), which conflicts with the later $N_t=8n_{touch}$ formula in §IV.A.3 — likely an OCR/typo inconsistency in the source; flagging rather than resolving it.
- Fusion: all three clouds are concatenated at the input level (not at the feature level) after each point is tagged with a one-hot source vector, and the whole cloud is transformed into the hand-palm frame before being passed to a single PointNet encoder (§IV.A.3, §IV.B, Fig. 3 caption).
- Qualitative check (§V.E): visualizing which points PointNet's max-pool keeps, "our policy uses 42.7% of tactile-based points on average and the rest points are mainly from the tips or edges of fingers and the palm."

## Contact / penetration handling
Not addressed. The word "penetrat*" does not appear anywhere in the paper. Contact is only used as a binary tactile signal (FSR reading thresholded at $\theta_{th}$, §III.A) for reward ($r_{dist}$, proximity-based) and observation; there is no interpenetration penalty, measurement, or stated contact-solver configuration.

## Evaluation
- metrics (quoted, §V.A.2, "suggested by [41]"):
  1. "**Cumulative Rotation Reward (CRR)** is the reward our agent obtains in an episode. We use it to evaluate the rotation capability of a policy in the simulation."
  2. "**Cumulative Rotation Angle (CRA)** is the angle (by rounds) the object rotates along the axis in an episode. We use it to evaluate a policy in the real."
  3. "**Time-to-Fall (TTF/Duration)** is the length of an episode (by seconds). TTF varies when the object falls off before the maximal episode length."
  No binary success threshold (metres/radians/seconds) is defined anywhere; success is read off these continuous metrics.
- eval protocol: sim policies "tested for 500 episodes... Each trial lasts 50 seconds" (Table I/II captions), each policy "averaged over 3 policies trained on 3 seeds" (Table I caption). Real-world: "tested for 5 episodes. Each trial lasts 60 seconds" (Table III caption).
- headline numbers:
  - Table I (sim, RL teacher, 3 seeds × 500 eval episodes): Ours beats PS and Visual RL on all 5 tasks, e.g. 4-way wrench CRR 1011.1±329.9 (Ours) vs 440.7±590.3 (PS) vs 10.9±2.2 (Visual RL); TTF 47.5±0.4 (Ours) vs 22.6±18.5 (PS) vs 8.1±3.2 (Visual RL) [Table I].
  - Table II (sim, distilled student, modality ablation, 500 episodes): full "Touch+Cam+Aug+Syn" wins 3/5 tasks on CRR (4-way wrench 504.0, double balls 407.7, multi-object z-axis 1035.0) but loses to "Touch+Cam+Aug" on multi-object x-axis (881.1 vs 846.9) and to "Cam+Aug" on multi-object y-axis (743.5 vs 686.8) [Table II].
  - Table III (real robot, CRA/TTF, 5 episodes, 60s trials): "Touch+Cam+Aug+Syn" (the full Synesthesia model) is best or tied-best on 4/5 tasks, e.g. 4-way wrench 1.5/43.0 vs next-best 0.25/60.0 for all other conditions; double balls 22.9/36.6 (best); multi-object y-axis is the one exception where "Touch+Cam+Aug" (no Syn) wins, 1.4/28.3 vs 0.9/29.3 [Table III]. Paper's stated takeaway: "the advantage of integrating vision and touch becomes more significant when deployed to the real world" and "these results highlight the low domain gap of our proposed tactile point cloud representation" (§V.D).
- baselines beaten: Stage I (RL): "Partially-observable-State (PS/Non-visual RL)" [42] (proprioception + contact only) and "Visual RL" (visuotactile, trained via RL from scratch, no distillation) — both beaten on all 5 tasks (Table I, §V.B). Stage II/real (distillation ablation): Touch-only, Cam+Aug (no touch), Touch+Cam+Aug (no Synesthesia term) — the full Touch+Cam+Aug+Syn model wins most but not all tasks (Tables II–III).
- real robot: Allegro Hand + XArm6, FSR tactile sensors, Azure Kinect camera; zero-shot sim-to-real transfer, "without any fine-tuning" (§V.D); 5 episodes per task per condition, 60 s per trial (Table III).

## Limitations stated by the authors
No dedicated "Limitations" section. From Conclusion (§VI): "Future work may encompass goal-conditioned object rotation tasks and the integration of optical tactile sensors" — implying the current system is not goal-conditioned and uses only binary FSR tactile sensing, not optical tactile sensors (e.g. DIGIT/GelSight, discussed only as related work in §II). Related Work also notes the tactile signal is binarized "to abridge the Sim-to-Real gap" (§III.A), i.e. a deliberate loss of tactile resolution rather than a stated shortcoming.

## Quotable claims (verbatim, with section)
- "we propose Robot Synesthesia, a novel point cloudbased tactile representation inspired by human tactile-visual synesthesia" (Abstract).
- "This approach treats the combined visual and tactile data as a single input to the policy network. This innovative design, which we term Robot Synesthesia, enriches the contextual understanding for both modalities and encodes the sensory data into a cohesive 3D space." (§II, Visuotactile Manipulation).
- "our policy uses 42.7% of tactile-based points on average and the rest points are mainly from the tips or edges of fingers and the palm." (§V.E).
- "A rudimentary concatenation of tactile signals and the extracted features of point clouds could increase the challenge for the policy to comprehend their underlying relationship." (§V.D).
