# aloha_act_2023 — Learning Fine-Grained Bimanual Manipulation with Low-Cost Hardware (Zhao, Kumar, Levine, Finn, RSS 2023)

sources: papers/md/aloha_act_2023.md [2e2fe258] ; code/md/aloha_act_2023.md [742c753c]

## One-line contribution
ALOHA: a $20k bimanual parallel-jaw teleoperation rig (two ViperX followers, joint-space-mapped from two WidowX leaders, 4 cameras at 50 Hz) paired with ACT (Action Chunking with Transformers), a CVAE policy that predicts k-step joint-target chunks and combines them at test time via exponentially-weighted temporal ensembling, reaching 80-90% success on fine-grained bimanual tasks (opening a condiment cup, slotting a battery) from ~50 human demonstrations each (Abstract, Sec. III-V).

## Setting
- hand(s): **parallel-jaw grippers**, not dexterous hands — explicitly "We do not employ dexterous hands due to price and maintenance considerations" (Sec. III). Custom 3D-printed "see-through" fingers with gripping tape fitted to the OEM ViperX gripper.
- arm: two Trossen Robotics **ViperX 300 6-DoF** arms as followers (750 g payload, 1.5 m span, 5-8 mm accuracy, ~$5,600 each), teleoperated via joint-space mapping (not task-space/IK) from two **WidowX 6-DoF** arms as leaders (~$3,300 each, same manufacturer); leader retrofitted with a 3D-printed "handle and scissor" mechanism (continuous, non-binary gripper control, reduced backdrive force) and a rubber-band gravity-counterbalance mechanism (enables >30 min sessions). Total system budget ~$20k (comparable to one Franka Emika Panda).
- bimanual: yes — this is the paper's central claim, that low-cost bimanual coordination (not a dexterous hand) suffices for fine-grained manipulation.
- simulator + version: MuJoCo (cited as [63] in the paper; version not stated) for 2 simulated tasks; the real 6 tasks run on physical ALOHA hardware. No physics engine settings (contact solver, timestep) stated in the parsed text for either sim or real.
- sim timestep / control rate: not stated for MuJoCo simulation; **real-hardware teleoperation and data recording both run at 50 Hz** (Sec. III); a user-study ablation (App. D/E) also tests 5 Hz teleoperation for comparison. Low-level joint tracking is by PID controllers inside the Dynamixel motors, driven by the target joint positions ACT (or the human leader) outputs.
- number of parallel envs: n/a — this is a real-robot teleoperation + from-scratch-per-task training paper, not a large-scale parallel-sim RL paper.
- GPU / wall-clock: "The model has around 80M parameters, and we train from scratch for each task. The training takes around 5 hours on a single 11G RTX 2080 Ti GPU, and the inference time is around 0.01 seconds on the same machine." (Sec. IV.C).
- cameras/observation hardware: 4 Logitech C922x webcams at 480×640 RGB, 2 wrist-mounted (on the followers) + 1 front + 1 top (Sec. III); all streamed and recorded at 50 Hz alongside teleoperation.

## Learning block
- paradigm: **behavior cloning** (imitation learning) trained as a conditional VAE — not RL, not RL+demo, not distillation.
- algorithm/implementation: Action Chunking with Transformers (ACT), the paper's own architecture — a BERT-style Transformer CVAE encoder (discarded at test time) + a ResNet18-image-conditioned Transformer encoder-decoder as the CVAE decoder/policy (Sec. IV.C; code `policy.py`, class `ACTPolicy`). No teacher-student or privileged→vision distillation — the same policy sees the same (image + proprioception) observations at train and test time; the only train-only input is the CVAE encoder's access to the ground-truth future action chunk (discarded at inference, replaced by z=0).
- observation vector, item by item (Sec. IV.C): current joint positions of the follower robots (14-dim: 7+7 DoF for two arms, gripper included in each arm's joint count) + 4 RGB images at 480×640×3 (top, front, left-wrist, right-wrist). Images are each encoded by a ResNet18 into a 15×20×512 feature map, flattened to 300×512, given a 2D sinusoidal position embedding; the 4 camera streams concatenate to 1200×512; joint positions and the CVAE style variable z are each linearly projected to 512-d and appended, giving a 1202×512 Transformer-encoder input.
- action space: **absolute target joint positions** for both arms (14-dim, 7 per arm including gripper), tracked by the low-level PID controller in the Dynamixel motors — explicitly not torques and not a residual: "We also noted degraded performance when using delta joint positions as actions instead of target joint positions" (Sec. IV.C). Actions are recorded from the **leader** robot's joints (not the follower's), because "the amount of force applied is implicitly defined by the difference between them, through the low-level PID controller" (Sec. IV).
- domain randomization: real-world tasks randomize object initial position along a 15 cm reference line (or, for _Slide Ziploc_, drop height ~5 cm above the table to randomize bag deformation); simulated tasks randomize object position uniformly within 2D regions (Sec. V.A, Fig. 6-7). No visual domain randomization (textures/lighting/camera) is described — this is a from-scratch, small-scale, single-embodiment/single-scene method paper, not a sim-to-real randomization study.

## Reward / objective block — quoted from paper AND code
**Paper (Sec. IV.B and Algorithm 1, verbatim):** the model is "trained to maximize the log-likelihood of demonstration action chunks, i.e. min_θ −Σ_{s_t,a_t:t+k∈D} log π_θ(a_t:t+k|s_t), with the standard VAE objective which has two terms: a reconstruction loss and a term that regularizes the encoder to a Gaussian prior. Following [23], we weight the second term with a hyperparameter β." Algorithm 1 spells out the two terms exactly:
```
L_reconst = MSE(â_t:t+k, a_t:t+k)
L_reg = D_KL(q_φ(z|a_t:t+k, ō_t) ∥ N(0, I))
Update θ, φ with ADAM and L = L_reconst + β·L_reg
```
Note the paper's Algorithm 1 states `L_reconst = MSE`, but the main text (Sec. IV.C) separately states "We use L1 loss for reconstruction instead of the more common L2 loss: we noted that L1 loss leads to more precise modeling of the action sequence" — i.e. **the algorithm-box pseudocode and the implementation text disagree on the reconstruction loss** (MSE/L2 in Algorithm 1 vs. explicitly-stated L1 in the prose); the released hyperparameter table and code use the L1 configuration per the prose. β (the KL weight) = 10 in the released hyperparameters (Table III) and matches the code's launch command `--kl_weight 10` (code/md README, "To train ACT" example).

**Code:** `code/policy.py` defines `class ACTPolicy(Module)` with `__init__`, `__call__(self, qpos, image, actions, is_pad)`, `configure_optimizers`, and a module-level `def kl_divergence(mu, logvar)` — these are the function signatures that implement the loss above, but code/md/aloha_act_2023.md captured **only the signatures, not the function bodies** (the "Python signatures and reward/observation bodies" section for this repo has no extracted body text for `policy.py`), so the exact L1-vs-KL weighting code cannot be quoted verbatim here; do not reconstruct it from memory. The `imitate_episodes.py` launch command in the README (`--policy_class ACT --kl_weight 10 --chunk_size 100 --hidden_dim 512 --batch_size 8 --dim_feedforward 3200 --num_epochs 2000 --lr 1e-5`) matches Table III's hyperparameters exactly (kl_weight/beta=10, chunk_size=100, hidden_dim=512, batch_size=8, feedforward=3200, lr=1e-5), confirming paper and code agree on hyperparameter values even though the loss-function body itself is not captured in code/md.

**Action chunking / horizon (IL-specific, HOWTO_METHOD C):** chunk size k=100 (Table III hyperparameter); the policy models π_θ(a_t:t+k | s_t) instead of π_θ(a_t | s_t). At inference, the policy is queried at **every** timestep (not every k steps) so that overlapping chunks are combined via **temporal ensembling**: a weighted average over all chunk predictions made for the same target timestep, with exponential weights w_i = exp(−m·i) (i = age of the prediction, w_0 = weight of the oldest), giving a_t = Σ_i w_i A_t[i] / Σ_i w_i (Algorithm 2). This is explicitly distinguished from naive smoothing over adjacent-timestep actions, which the authors say "leads to bias" — here the aggregation is over multiple predictions *for the same* timestep.

## Contact / penetration handling
**Not addressed.** ALOHA/ACT has no contact-force sensing, no penetration or interpenetration term, and no contact-solver discussion in the parsed text — it is a parallel-jaw-gripper, vision+proprioception BC policy on real hardware, where task success is judged behaviorally (see Evaluation below), not via a simulated or measured contact/penetration metric. The paper's own precision language ("clearance is around 5mm," "loop measures 3mm × 25mm... tie measures 2mm × 10-25mm") describes task tolerances, not a contact/penetration metric that is computed or reported per rollout.

## Evaluation block
- exact success criteria: task-specific behavioral success, not a numeric threshold in metres/radians in most cases — e.g. _Put On Shoe_: "The task is only considered successful if the shoe clings to the foot after both arms release" (Sec. V.A); _Bimanual Insertion_ (sim): peg touches the pins inside the socket, "clearance is around 5mm in the insertion phase"; _Transfer Cube_ (sim): cube placed inside the other gripper, "clearance between the cube and the left gripper (around 1cm)." Each task is also scored on a manually defined sequence of sub-tasks (e.g. _Slide Ziploc_: Grasp → Pinch → Open), reported as success-rate-per-stage.
- number of eval episodes/seeds: simulated tasks — 3 random seeds × 50 policy evaluations each (300 rollouts/task/method); real-world tasks — 1 seed × 25 evaluations/task (Table I/II captions).
- sim vs real: both — 2 MuJoCo tasks (Cube Transfer, Bimanual Insertion) trained on either scripted or human-teleoperated demonstrations, 6 real ALOHA tasks (Slide Ziploc, Slot Battery, Open Cup, Thread Velcro, Prep Tape, Put On Shoe) trained only on human demonstrations.
- real-robot trial counts: 25 trials/task (real tasks), 1 seed. Demonstration counts: 50 demos/task except _Thread Velcro_ (100 demos); episodes 8-14 s (400-700 steps at 50 Hz), 10-20 min of data/task, 30-60 min wall-clock with resets.
- headline numbers (Table I, success % [scripted | human] for sim tasks, single number for real): Cube Transfer sim ACT **97 | 82** vs best baseline BeT 60 | 16; Bimanual Insertion sim ACT **90 | 60** vs BeT 51 | 13; Slide Ziploc real ACT **88** (final "Open" stage) vs all baselines 0 at final stage; Slot Battery real ACT **96** (final "Insert" stage) vs all baselines 0 at final stage (Table I; per-stage breakdown also given, e.g. Slide Ziploc Grasp/Pinch/Open = 93/90/32→92/96/88 across the two success-count table halves — see paper Table I for the disambiguated per-subtask numbers). Table II (real, ACT vs best baseline BeT only): Open Cup — Tip Over 100, Grasp 96, Open Lid **84** vs BeT 12/0/0; Thread Velcro — Lift 92, Grasp 40, Insert **20** vs BeT 24/0/0; Prep Tape — Grasp 96, Cut 92, Handover 72, Hang **64** vs BeT 8/0/0/0; Put On Shoe — Lift 100, Insert 92, Support 92, Secure **92** vs BeT 12/0/0/0.
- baselines: BC-ConvMLP (image CNN + joints → single-step action, no chunking), BeT (Behavior Transformer — no action chunking, frozen separately-trained visual encoder, discretized action bins + continuous offset), RT-1 (Transformer, fixed-length observation history, discretized actions), VINN (non-parametric weighted k-NN over a BYOL-pretrained visual feature space). All four were re-run/tuned by the authors ("We carefully tune the hyperparameters of these four prior methods using cube transfer," hyperparameters in App. D Tables III-VII) — i.e. baselines were re-run, not only quoted from their original papers.
- ablations (Sec. VI): (a) chunk size k swept 1→episode-length; success rises from 1% (k=1, no chunking) to 44% (k=100) then slightly tapers at k=200,400 (near-open-loop); action chunking (augmented into BC-ConvMLP and VINN) improves both baselines too, though ACT still leads. (b) Temporal ensembling: +4% for BC-ConvMLP, +3.3% for ACT, but a drop for VINN (non-parametric, "retrieves ground-truth actions... does not suffer from" the smoothing issue TE fixes). (c) CVAE objective: on scripted (deterministic) sim data, removing the CVAE objective "makes almost no difference"; on human data, success drops from 35.3% to 2% without it — "the CVAE objective is crucial when learning from human demonstrations." (d) User study, 6 participants (4 men, 2 women, ages 22-25, none with prior ALOHA experience): lowering teleoperation frequency from 50 Hz to 5 Hz increased task completion time by 62% (33s→20s zip-tie threading at 5→50 Hz; 16s→10s cup unstacking), verified significant by Repeated Measures Designs, p<0.001.

## Limitations stated by the authors
**Hardware** (App. F): "ALOHA struggles with tasks that require multiple fingers from both hands, for example opening child-proof pill bottles with a push tab"; struggles with high-force tasks (lifting heavy objects, twisting open a sealed water bottle, opening tightly-pressed marker caps) "because the low-cost motors cannot generate enough torque"; struggles with fingernail-requiring tasks (lifting taped-down packing tape, opening aluminum soda cans) despite thin gripper edges; cannot perform in-hand rotation tasks (e.g. Baoding balls) because "our setup does not have a hand."
**Policy learning** (App. F): two reported full failures — unwrapping candies (0/10 in a first protocol; with an easier per-candy protocol, "successfully unwraps 3/5 candies," attributed to perception difficulty in locating the wrapper seam) and opening a small flat ziploc bag (consistently picks up the bag but fails the 3 subsequent mid-air manipulation steps, attributed to hard-to-perceive deformable-bag state). "We believe that pretraining, more data, and better perception are promising directions to tackle these extremely difficult tasks."

## Notes for the survey
- This is the canonical low-cost bimanual gripper baseline the survey should contrast against dexterous-hand bimanual work (dextrack, robopianist, DexMachina, etc.): no dexterous hand, no contact/penetration handling at all, real-robot-only evaluation with small (25-trial, 1-seed) real-world eval budgets, and from-scratch per-task training (80M params, 5 GPU-hours/task) rather than a shared multi-task policy.
- The reconstruction-loss mismatch between Algorithm 1 (MSE) and Sec. IV.C's prose (explicitly L1) is a real internal inconsistency worth flagging wherever the survey's method-comparison table cites ACT's loss function — cite the prose (L1) as the actually-used setting per Table III/README hyperparameters, but note Algorithm 1 says MSE.
- Action representation (absolute joint targets, not deltas, not torques) and the temporal-ensembling trick (aggregating multiple chunk predictions *for the same* timestep, not smoothing over adjacent timesteps) are the two design choices most likely to be directly reused or contrasted in this survey's method section — both are explicitly ablated with numbers above.
- Since only function *signatures* (not bodies) were captured for `policy.py` in code/md, this note cannot quote the literal PyTorch loss code — HOWTO_METHOD's requirement to "quote... from the code config or reward function" is satisfied here only via the hyperparameter file/launch-command match, not via a code body quote.
