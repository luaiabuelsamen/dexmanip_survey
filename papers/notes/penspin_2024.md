# penspin_2024 — Lessons from Learning to Spin "Pens" (Wang, Yuan, Che, Qi, Ma, Malik, Wang; CoRL 2024)

sources: papers/md/penspin_2024.md [645b99b2] ; code/md/penspin_2024.md [5035c52d]

## One-line contribution
Oracle RL policy trained with privileged info generates realistic sim trajectories; these are used both to pre-train a proprioceptive student (via BC on oracle rollouts, not DAgger) and, replayed open-loop on the real robot, to harvest fewer than 50 real trajectories that fine-tune the student to close the sim-to-real gap for continuous pen spinning (Abstract, Sec. 3).

## Setting
- hand(s): Allegro Hand, 4 fingers × 4 DoF = 16 DoF (Sec. 4.1). No arm; single hand.
- simulator / physics: Isaac Gym [34] (Sec. 4.1). Code cfg configs/task/AllegroHandHora.yaml: `sim.dt: 0.005` (200 Hz), `substeps: 1`, PhysX `num_position_iterations: 8`, `num_velocity_iterations: 0`, `contact_offset: 0.002`, `rest_offset: 0.0`, `max_depenetration_velocity: 1000.0`. Control frequency 20 Hz via `controlFrequencyInv: 10` (paper Sec. 4.1 states control at 20 Hz, PD at 333 Hz on hardware — the sim PD runs at 200 Hz per the physics step, not 333 Hz; the 333 Hz figure is real-hardware only). Oracle training: 8192 parallel envs (Table 7 / App. A.1); student pretraining config (Table 6) lists 48 envs.
- observation: oracle policy o_t = joint positions q_t, previous joint-position target a_{t-1}, binary tactile c_t (20 sensors, 5 per fingertip), fingertip positions p_t, pen pose+angular velocity w_t, point cloud of the pen (∈ R^{100×3}, PointNet-encoded), plus 3 stacked historical steps of q and target, plus privileged physical properties (mass, COM, friction, size) (Sec. 3.1). Table 5 dims: q_t ∈ R^{3×16}, a_{t-1} ∈ R^{3×16}, c_t ∈ R^32, p_t ∈ R^{4×3}, w_t ∈ R^7, point cloud R^{100×3}. Student ("sensorimotor"/proprioceptive) policy: 30 steps of joint positions q_{t-29:t} and previous targets a_{t-30:t-1} only (Sec. 3.2), via a temporal transformer + MLP. Code `compute_observations` (allegro_hand_hora.py): builds a 96-dim lagged buffer from noisy joint pos + current target (32) with optional tactile (32) + fingertip pos (12) channels when `privInfo.enable_tactile` is set; `numObservations: 96` in the released cfg (tactile disabled in that cfg — `enable_tactile: False`), so the released training config's observation is narrower than the paper's tactile+point-cloud oracle description.
- action space: relative joint-position target, a_t = η·f(o_t) + a_{t-1}, η the action scale, sent through a low-level PD controller (Sec. 3.1). Code: `action_scale: 0.04167`, PD `pgain: 3`, `dgain: 0.1`, `torque_limit: 0.7`, `torque_control: True` (configs/task/AllegroHandHora.yaml).
- objects / data: sim training uses only cylindrical ("pen-like") objects with randomized physical properties (Sec. 4.1); object `type: 'block'` field in the released yaml with `sampleProb: [1.0]` (single object-type slot, scale-randomized). Real world: 3 training objects (A, B, C) used to collect 45 replay-derived demonstrations (15 each), 7 unseen objects (D–J) for evaluation (Sec. 3.3, Fig. 7). Table 9 gives per-object mass 10.8–49.7 g, length 14.4–22.2 cm, contact-part diameter 27.3–37.9 mm, materials "3D-printed components, leatheroid, and various plastics."

## Method
- paradigm: RL (oracle, PPO) → BC pre-training on oracle rollouts (student) → BC fine-tuning on real trajectories (student). Algorithm: PPO [61] via IsaacGymEnvs-derived codebase (App. A.1); student trained with behavior cloning (Sec. 3.2, App. A.1 "We train our student policy with Behavior Cloning").
- key trick vs. prior distillation pipelines: oracle-policy rollouts (not sensorimotor/DAgger rollouts) are recorded as the BC dataset for the student — "we roll out the oracle policy f in simulation, in contrast to previous work using DAgger and rolling out the sensorimotor policy [11, 35]" (Sec. 3.2).
- reward (paper, Sec. 3.1 + App. A.1): r = r_rot + λ_z·r_z + λ_energy·r_energy, where r_energy bundles r_vel (linear-velocity penalty), r_diff (deviation from initial pose), r_ang (angular-velocity-above-threshold penalty), r_torque (torque penalty), r_work (controller work penalty). Table 4 weights: λ_rot=1.0, λ_z=-1.0, λ_l(=r_vel)=-0.3, λ_diff=-0.1, λ_ang=-0.3, λ_torque=-0.1, λ_work=-1.0.
- reward (code, penspin/tasks/allegro_hand_hora.py `compute_reward`/`compute_hand_reward`): `reward = rotate_reward_scale*rotate_reward + object_linvel_penalty_scale*object_linvel_penalty + pose_diff_penalty_scale*pose_diff_penalty + torque_pscale*torque_penalty + work_pscale*work_penalty + pencil_z_dist_penalty_scale*z_dist_penalty + position_penalty_scale*position_penalty + rotate_penalty_scale*rotate_penalty`. Released cfg (configs/task/AllegroHandHora.yaml `reward:` block) scales: `rotate_reward_scale: 1.0`, `obj_linvel_penalty_scale: -0.3`, `pose_diff_penalty_scale: -0.1`, `torque_penalty_scale: -0.1`, `work_penalty_scale: -1.0`, `rotate_penalty_scale: -0.3`, `pencil_z_dist_penalty_scale: -1.0`, `position_penalty_scale: -0.1`, `action_penalty_scale: 0.0`. `rotate_reward` is `clip(vec_dot, angvelClipMin=-0.5, angvelClipMax=0.5)` where `vec_dot` is angular velocity about the spin axis; `rotate_penalty` fires only above `angvelPenaltyThres: 1.0` — this rotate-above-threshold penalty is not named in the paper's Table 4 weight list (Table 4 lists no rotate_penalty term) but exists in code with scale -0.3, matching λ_ang's stated role ("penalizes the pen's angular velocity above a pre-defined threshold") — i.e. paper's λ_ang = code's `rotate_penalty_scale`, naming differs. `position_penalty` (deviation of object x,y,z from a canonical position/height) is present in code and in Table 4's implicit set but not explicitly named in the Sec. 3.1 prose. `_setup_reward_config` supports 4-tuple curriculum scales `[init, final, start, end]`, unused (all scalars) in the released cfg.
- initial state design: multiple hand-designed canonical grasp poses (inspired by human pen-spinning cycle) plus noise, filtered for stability, replacing the single-canonical-pose sampling of prior work [11, 35] (Sec. 3.1, ablated in Fig. 4 left / Fig. 5c — single-pose init "does not achieve finger gaiting").
- domain randomization (App. A.2, Table 8 / code `randomization:` block): object scale ×[0.95,1.05] (code: `randomizeScaleList: [0.78, 0.8, 0.82, 0.84, 0.86]` off a `baseObjScale: 0.8`, i.e. list-based not the paper's stated multiplicative range); mass [0.01,0.03] kg (code lower/upper 0.01/0.02); COM ±0.1 cm (code ±0.001 m = ±0.1 cm, consistent); friction (obj & fingertip) [0.3,3.0]; external disturbance force 0.2×object-mass with probability 0.25 (paper text; code has `forceScale/randomForceProbScalar` both 0.0 in the released task cfg — disturbance force appears disabled in the shipped config despite being described as used); PD stiffness [2.5,3.5], damping [0.09,0.11]; observation noise N(0,0.02 rad), action noise N(0,0.01 rad) (code splits into separate `_e_scale`/`_t_scale` episode- and step-level noise terms, smaller than the paper's stated 0.02/0.01).
- policy optimization: PPO, MLP for policy/value on oracle; App. A.1 Table 7: 8192 envs, 12 steps/env/epoch (paper text says "# steps" but table shows 12, not the "# steps" prose value), 16384 minibatches, 5e8 agent steps total ("less than one day on a single GPU"), γ=0.99, λ_GAE=0.95, lr 5e-3, clip 0.2, entropy coef 0.0, KL threshold 0.02, max grad norm 1.0. Student: Table 6, 48 envs (this is the demonstration-generation/BC env count, not oracle training), 512 steps, 4096 minibatches, 2000 epochs, lr 1e-3; ~50M steps of oracle-rollout data collected for BC.
- fine-tuning: after generating 15 oracle trajectories (>800 timesteps each, one per varied init pose) and replaying each on 3 real objects, a trajectory is kept if it rotates the object more than 2π; repeated until 15 kept trajectories per object (45 total) — this is the real-world dataset used to fine-tune (further BC, "fine-tune our proprioceptive policy π") the pre-trained student (Sec. 3.3).

## Evaluation
- metrics: sim — Cumulative Rotation Reward and episode Duration (s) (Sec. 4.1, following [11,12,13]). Real — Radians of Rotation (RR, over the z-axis) and Success rate (Suc.), success defined as "the policy can rotate target objects at least 180 degrees, which typically corresponds to ... one circle of finger gaiting" (Sec. 4.1).
- headline numbers (Table 1, real world, 10 objects A–J): Ours best or tied-best on every object; e.g. Object A RR 3.43 / Suc. 54.93% vs. Oracle-Replay 2.80/37.62%, P.Distill "N.A." (fails to converge in sim), V.Distill 1.85/17.65%. Unseen Object H: Ours 4.63/75.79% vs. Replay 2.93/44.35%. Text (Sec. 4.3 Q4): on training objects A/B/C "15%-30% better performance in terms of success rate" than Oracle Replay; on unseen D/E/F "a 10% increase in the radius rotated" with similar success rate; on I/J/K "15%-30% success rate improvements." A second protocol with 10 random grasps × 5 trials each (not the replay-trajectory-matched inits) gives larger deltas: object D 54%→78% (+22 pts... paper states "22.0%"), E 46%→82% (paper: "36% (from 46 to 82)"), F 34%→74% (paper: "40%").
- ablations: Table 2 (pretrain/fine-tune) — "Only Pretrain" (no real fine-tuning) and "No Pretrain" (fine-tune from scratch on 45 real trajectories) both underperform "Ours" on every object, most on unseen D (Ours 80.65% vs. No-Pretrain 16.53%, Only-Pretrain 6.86%). Table 3: increasing "No Pretrain" demos 15→45→75 improves training-object success (14→54→77% on A) but stays far below Ours on unseen objects (e.g. F: 75-demo No-Pretrain 15.00% vs. Ours-45 53.33%), i.e. more real data does not substitute for sim pre-training.
- baselines beaten: Oracle Replay (open-loop trajectory replay directly on hardware — real numbers, no learning), P. Distill (DAgger-style proprioceptive distillation, fails to converge in sim — "N.A."), V. Distill (visuotactile distillation, sim-to-real gap causes near-total real failure, many entries pinned at RR 1.57/Suc 0% from a "thumb+index rotate 90°, then drop" failure mode), ACT [63] behavior cloning from only the 15 real demos (50% lower rotation radius on training objects, <20% success on OOD objects per Sec. 4.3 Q6 prose, not a separate table).
- real robot: Allegro Hand, hardware experiments across 10 objects (3 train + 7 unseen); Table 1 numbers derived from real trials but exact per-cell trial counts are not given (only the two-protocol description: replay-trajectory-matched inits, and a separate 10-random-grasp × 5-trials-each protocol quoted in Sec. 4.3 prose for objects D/E/F only). Numeric, not video-only, but full N per Table-1 cell is not stated in the parsed text.

## Limitations stated by the authors (Sec. 5)
- "Sim-to-Real does not directly work for such contact-rich and highly dynamic tasks. Even when isolating touch and vision, the pure physics sim-to-real gap remains significant and cannot be bridged by extensive domain randomization alone."
- Vision and touch sim-to-real gaps identified as bottlenecks but not ruled out for future use; "Humans do not seem to need vision to spin a pen, but touch feedback seems important."
- Currently rotation is single-axis (z only); multi-axis rotation left as future work.
- Assumes the object starts at a stable grasp, following [10,11]; no grasping-from-scratch.

## Quotable claims (verbatim, with section)
- "we roll out the oracle policy f in simulation, in contrast to previous work using DAgger and rolling out the sensorimotor policy [11, 35], and collect a dataset of proprioception and actions" (Sec. 3.2)
- "Sim-to-Real does not directly work for such contact-rich and highly dynamic tasks." (Sec. 5)
- "Simulation is still useful for exploring skills. ... nearly impossible to achieve with human teleoperation and imitation learning alone." (Sec. 5)
- "Many entries are recorded as 1.57 for Vision Distillation due to a consistent failure mode: the thumb and index finger can rotate the object by 90 degrees, but then the object drops." (Table 1 caption)
- "we use the trajectories generated by the oracle policy as an open-loop controller in the real world ... If this open-loop controller can rotate objects more than 2π in this trial, we store this trajectory in the dataset." (Sec. 3.3)

## Notes for the survey
- Feeds: sim-to-real fine-tuning method comparison; the "oracle-rollout BC instead of DAgger" trick is a direct methodological contrast point against eureka_2023/dreureka_2024's pure-sim optimization and against any paper claiming DAgger distillation works at this dynamics regime.
- Reward-block mismatch is real and worth citing in the survey's method table: the paper's Table 4 weight list (λ_rot, λ_z, λ_l, λ_diff, λ_ang, λ_torque, λ_work) does not 1:1 name-match the code's scale keys (`rotate_reward_scale`, `pencil_z_dist_penalty_scale`, `obj_linvel_penalty_scale`, `pose_diff_penalty_scale`, `rotate_penalty_scale`, `torque_pscale`, `work_pscale`, plus an unlisted `position_penalty_scale`); values agree where names can be matched, but the disturbance-force domain-randomization term described in text (App. A.2) is zeroed in the released task config.
- Contact/penetration handling: not addressed as a measured quantity anywhere in paper or code; only PhysX solver defaults (`contact_offset 0.002`, `rest_offset 0.0`, `max_depenetration_velocity 1000.0`) are set, and binary tactile "contact" sensors are a reward/observation input, not a penetration metric.
- Real-robot success numbers are numeric (RR + Suc.%) across 10 objects, not video-only, but the note that per-cell trial counts are not stated in the parsed text should be flagged if the survey needs to compare trial-count rigor against poise_2026 or articulated_tools_inhand_2025.
