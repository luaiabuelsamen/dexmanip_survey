# mujoco_warp_2025 — MuJoCo Warp (MJWarp): GPU-optimized version of the MuJoCo physics simulator (Google DeepMind & NVIDIA, software release, 2025)

source: repository only, no paper — sources: code/md/mujoco_warp_2025.md [87e742d3] (no papers/md file exists for this key: bib `pdf_url`/`arxiv` are null, and `papers/md/mujoco_warp_2025.md` does not exist)

## One-line contribution
A GPU port of MuJoCo built on NVIDIA Warp, maintained by Google DeepMind and NVIDIA as part of the Newton project, positioned as a drop-in accelerated backend for MuJoCo (README).

## Setting
- hand(s) shipped as assets: none directly bundled and visible in the parsed README/examples list — the showcased benchmark scenes are `unitree_g1` (flat and heightfield), `myoarm` (a musculoskeletal arm model), and `aloha` (clutter/pot/SDF/cloth variants, a bimanual *gripper* rig, not a dexterous hand), plus `three_humanoids` and `cloth`. No Allegro/Shadow/LEAP/XHand-style multi-fingered hand example is named in the parsed README.
- simulator / physics: requires an NVIDIA GPU for fast simulation but "supports CPU for development and debugging" (README, "Getting started"). Available via `pip install mujoco-warp`; integrates with MJX (JAX ecosystem) and with PyTorch via Isaac Lab or `mjlab` (README, "Integrating MuJoCo Warp").

## Physics block
- solver: MuJoCo's own constraint/contact solver ported to Warp — `mujoco_warp/_src/constraint.py` (code/md, signatures) implements `_efc_row`, `_efc_D`, `_contact_kbimp`, per-contact Jacobian construction (`_efc_contact_jac_sparse`/`_dense`, with flex variants), and equality/limit/friction constraint rows (`_equality_connect/joint/tendon/flex/weld`, `_friction_dof/tendon`, `_limit_slide_hinge/ball/tendon`) — i.e. the same `solref`/`solimp`-parameterized soft-constraint formulation as native MuJoCo (position/velocity/impedance-based constraint rows, `pos_aref`, `pos_imp`, `D` = constraint stiffness), not a re-derived contact model. A `newton` boolean flag threads through the equality/limit/friction kernels, indicating support for MuJoCo's alternate "Newton" constraint solver in addition to its default (implicit CCP-style) solver.
- integrator: matches native MuJoCo's integrators with one stated exception — "Integrator: `IMPLICITFAST` midpoint integrator feature is not supported" (README, "MuJoCo API Compatibility"). "Solver: `PGS` and `noslip` not yet supported" (same section) — i.e. MJWarp supports MuJoCo's default/Newton solver but not the legacy PGS solver or the no-slip post-processing pass.
- supported materials / features: rigid bodies with contacts, plus "soft bodies, cloth, signed distance fields, and more" (README, "Examples"); an experimental Flex system is present but "not all features are implemented or optimized yet" (README, "MuJoCo API Compatibility"). Actuator/sensor `PLUGIN` types are not yet supported.
- differentiability: not yet available — "[Differentiability via Warp] is not yet available. See [#500] for progress" (README, "MuJoCo API Compatibility"). This directly contradicts treating MJWarp as differentiable in downstream survey claims; as of the parsed commit it is forward-simulation only.
- claimed throughput from the README: none given as a number. The README points to a "Nightly Benchmarks" dashboard (external link, not fetched/parsed) rather than quoting FPS or steps/sec figures in the text itself; nightly-benchmarked scenes are named (`unitree_g1_flat`, `unitree_g1_hfield`, `myoarm`, `aloha_clutter/pot/sdf/cloth`, `three_humanoids`, `cloth`) but no numbers accompany them in the parsed README.
- GPU or CPU: GPU-primary (NVIDIA hardware), with CPU support "for development and debugging" only (README, "Getting started").
- rendering: ships a separate high-throughput GPU batch renderer (ray-tracing based) for simultaneous multi-camera, multi-world rendering — mesh, texture, heightfield, flex-deformable, and Gaussian-splat rendering, heterogeneous per-camera resolution/FOV/intrinsics, lighting and shadows (README, "Batch Rendering"). This is reported as rendering millions of frames/sec on NVIDIA GPUs, but no specific number/hardware pairing is given in the parsed text.
- which hands ship as assets: none identified in the parsed README/example list (see Setting above); this should be flagged as "not stated" rather than assumed absent, since example assets beyond the README table were not captured in the code manifest.

## Notes for the survey
- MJWarp is the GPU contact/constraint backend that both `newton_2025` (which adopts it as its "primary backend") and `comfree_sim_2026` (which benchmarks directly against it) build on or compete with — treat this note as the shared physics-backend reference for both.
- The stated non-differentiability (as of the parsed commit) is an important correction to any assumption that "GPU MuJoCo" implies gradient-based training support; `newton_2025`'s separate solvers (e.g. its Kamino backend, which has a `test_differentiable_contacts.py`) may be the differentiable path instead, not MJWarp itself.
- No hand assets and no numeric throughput claim could be confirmed from the parsed README; both should be re-checked against the live repository or its nightly-benchmark page if a hand-specific or quantitative throughput claim is needed for the survey.
- Code md provenance: `code/md/mujoco_warp_2025.md` (14,550 chars) is README + pruned file tree + one Python source file's signatures (`constraint.py`, `constraint_test.py`); no kernel-level (Warp `@wp.kernel`) bodies were captured, so the solver description above is inferred from function/parameter names, not from reading the kernel implementations.
