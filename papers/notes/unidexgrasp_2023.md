# unidexgrasp_2023 — UniDexGrasp: Universal Robotic Dexterous Grasping via Learning Diverse Proposal Generation and Goal-Conditioned Policy (Xu et al., CVPR 2023)

sources: papers/md/unidexgrasp_2023.md [29cf96b2] ; code/md/unidexgrasp_2023.md [36c9bfcf]

## One-line contribution
Two-stage pipeline — a generative grasp-proposal model (GraspIPDF + GraspGlow + ContactNet) trained on a synthesized 1.12M-grasp / 5519-object dataset, feeding a goal-conditioned PPO teacher policy that is distilled (DAgger) to a point-cloud student — is "the first to achieve universal generalization for dexterous grasping," >60% average success across thousands of objects (Abstract).

## Setting
- hand(s): ShadowHand, "26 degrees of freedom (DoF)" (Sec. 1); no arm, table-top setting, single hand. Asset: `mjcf/open_ai_assets/hand/shadow_hand.xml` (code `dexgrasp_policy/dexgrasp/cfg/shadow_hand_grasp.yaml`).
- simulator / physics: Isaac Gym [32] (Sec. 3, 3.1) for both grasp-dataset validation and RL. Code `cfg/shadow_hand_random_load_vision.yaml` `sim:` block: `substeps: 2`, PhysX `solver_type: 1` (TGS), `num_position_iterations: 8`, `num_velocity_iterations: 0`, `contact_offset: 0.002`, `rest_offset: 0.0`, `bounce_threshold_velocity: 0.2`. `controlFrequencyInv: 1` (comment "# 60 Hz"); no explicit sim dt is stated in the paper. Num. parallel envs (Table 7): 1024, `envSpacing: 1.5`. GPU: proposal-generation networks trained on "an NVIDIA RTX A5000" (Sec. C.2); GPU and wall-clock for the RL policy are not stated. Proposal-model training times: GraspIPDF converges in 24h, GraspGlow+ContactNet "one day," ContactNet alone "8 hours" (Sec. C.2).
- observation: teacher state S^E=(s_r_t, s_o_t, X_O, g); student S^S=(s_r_t, X_t, g) (Sec. 3.3). Robot proprioception s_r (Table 5): joint positions q∈R18, joint velocities q̇∈R18, dof force τ_dof∈R24, fingertip position/orientation/lin.vel/ang.vel/force/torque each ∈R^{3x5} or R^{4x5}, hand root translation t∈R3 and orientation R∈R^{3x3}, action a∈R24. Object oracle state s_o = object pose, linear velocity, angular velocity (Sec. C.1) — this plus the full pre-sampled object point cloud X_O (2048 points from the mesh) is the privileged information available only to the teacher. Student's scene point cloud X_t: 1024 points sampled from object+hand (Sec. C.1); code config `observationType: "full_state"`, vision block down-samples 65536→1024 presampled points, 5 cameras.
- action space: "motor command of 24 actuators on the robotic hand. The first 6 motors control the global position and orientation ... the rest 18 motors control the fingers," normalized to (-1,1) (Sec. C.1) — position targets via PD (config `useRelativeControl: False`, `dofSpeedScale: 20.0`).
- objects / data: 5519 object instances, 133 categories, from ShapeNet + [28] (DDG) + [55], canonicalized to a unit sphere and rescaled by factors {0.06,0.08,0.1,0.12,0.15} (Sec. A). Grasp dataset: 1.12 million valid grasps, "1000 generations for each object instance" (Sec. A, Sec. 4.1). Proposal-generation split (Sec. 4.1): training instances 3251, seen-category unseen instances 754, unseen-category instances 1514 (sums to 5519). Grasp-execution split (Sec. C.2, after filtering out oversized meshes): train set of 3200 object instances, test set of 241 object instances.

## Method
- paradigm: hybrid. Stage 1 (grasp proposal) is generative/self-supervised — conditional normalizing-flow / IPDF density estimation with an NLL loss plus a supervised contact-map regressor, no RL. Stage 2 (grasp execution) is RL (PPO teacher) + imitation distillation (DAgger student).
- **How the grasp pose is generated**: Stage 1 factorizes p(g|X0) = p(R|X0)·p(t,q|X0,R) (Sec. 3.2). GraspIPDF (an IPDF [36] model over PointNet++ features, MLP (256,256,256)) predicts the rotation distribution and is trained with NLL loss L=−log p(R0|X0) (Sec. 3.2.1, B.1.1). Given a sampled R, the point cloud is canonicalized X̃0=R⁻¹X0 and GraspGlow (a 21-block conditional Glow normalizing flow over R^{3+K}, PointNet-conditioned, trained with L_NLL=−log p(t̃_gt,q_gt|X̃0)) samples translation+joint angles (Sec. 3.2.2, B.1.1). ContactNet (two PointNets, MLP (1024,512,512,256,256,128,128,10), 10-bin discretized contact map) is then trained end-to-end with GraspGlow using four extra loss terms (L_cmap, L_pen, L_tpen, L_spen; RotationNet/GraspIPDF frozen) and, at test time, drives a 300-step contact-based optimization (E_TTA = same four terms) to refine the sampled pose (Sec. 3.2.3–3.2.4). Stage 2's PPO teacher then takes one such refined proposal as the fixed goal pose g for the episode; the student is trained purely to imitate the teacher (no further grasp generation).
- algorithm: PPO [52] for the teacher (Sec. 3.3.1), DAgger [49] for teacher→student distillation, objective π^S = argmin ||π^E(S_t^E) − π^S(S_t^S)||₂ (Sec. 3.3.2). Adam optimizer for all proposal-generation networks, lr 1e-3 (GraspIPDF, GraspGlow, ContactNet); GraspIPDF batch size 16, GraspGlow batch 64 (stage 1)/32 (stage 2, 8 samples/object), ContactNet batch 128, β=60 (Sec. C.2).
- teacher-student / privileged info: privileged = object pose, linear/angular velocity, and the full 2048-point object point cloud X_O, all available in sim but not to a real camera; student sees only proprioception s_r_t, a raw fused scene point cloud X_t, and the goal g (Sec. 3.3, C.1).
- key trick(s): rotation/translation factorization (IPDF+Glow) beats a joint CVAE or a single SO(3)×R^n flow (Table 1, "Ablation 1/2"); state canonicalization to a frame fixed by the initial hand pose, giving SO(2) equivariance about the gravity axis (Sec. 3.3.1); 3-stage object curriculum learning — one object → one category → 3 representative categories → all categories (Sec. 3.3.1, ablated in Table 3); joint PointNet training with an object-classification auxiliary loss (built on ILAD [59]'s BC-joint-training trick).
- domain randomisation (code `cfg/shadow_hand_random_load_vision.yaml`, `task.randomize`, default **False** in this file, so off unless enabled): observation noise range [0,.002] additive gaussian (+correlated [0,.001]); action noise [0,.05] (+correlated [0,.015]); gravity +[0,0.4] additive gaussian; hand tendon/dof damping scaling [0.3,3.0] loguniform, stiffness scaling [0.75,1.5] loguniform, dof-limit jitter +[0,0.01]; rigid-body mass scaling [0.5,1.5] uniform (hand and object); rigid-shape friction scaling [0.7,1.3] uniform, 250 buckets (hand and object); object scale [0.95,1.05] uniform. All schedules linear over 30000–40000 steps. The paper text does not mention domain randomisation at all; this list is code-only.

## Reward / objective block
Paper (Sec. 3.3.1, prose only — the reward equations themselves are figure/typeset elements dropped by the PDF-to-text conversion): "r = r_goal + r_reach + r_lift + r_move." r_goal "punished distance between the current hand configuration and the goal hand configuration"; r_reach "encourages the robot fingers to reach the object"; r_lift "encourages the robot hand to lift the object," "non-zero if and only if the goal grasp label is reached within a threshold"; r_move "encourages the object to reach the target." Table 7 lists named weight hyperparameters (values, no formula): ω_g,q=0.1, ω_g,t=0.6, ω_g,R=0.1, ω_r=0.5, ω_l=0.1, ω_m=2, ω_b=10.
Code (`dexgrasp_policy/dexgrasp/tasks/shadow_hand_grasp.py:compute_hand_reward`, goal-conditioned branch, `goal_cond=True`) computes a **different, hardcoded** formula, not the named ω-weights of Table 7:
```
right_hand_dist   = ||object_handle_pos - right_hand_pos||  (clamped to 0.5)
right_hand_finger_dist = sum of ||object_handle_pos - {ff,mf,rf,lf,th}_pos||  (clamped to 3.0)
delta_value = 0.6*delta_hand_pos_value + 0.04*delta_hand_rot_value + 0.1*delta_qpos_value
flag  = (right_hand_finger_dist<=0.6) + (right_hand_dist<=0.12) + target_flag   # target_flag: 3 threshold indicators
goal_hand_rew = 0.9 - 2*goal_dist   if flag==5 else 0
hand_up       = 0.1 + 0.1*actions[:,2]           if lowest>=lift_z and flag2==2
              = 0.2 - goal_hand_dist*0           if lowest>=0.80  and flag2==2
bonus         = 1/(1+10*goal_dist)  if goal_dist<=0.05 else 0
reward = -0.5*right_hand_finger_dist - 1.0*right_hand_dist + goal_hand_rew + hand_up + bonus - 0.5*delta_value
```
(config `dist_reward_scale: 20`, `rot_reward_scale: 1.0`, `action_penalty_scale: -0.0002`, `reach_goal_bonus: 250`, `fall_penalty: 0.0` — these config scales are passed into `compute_hand_reward` but are not visibly used inside the goal-conditioned branch quoted above in the extracted code). **Mismatch, explicit**: the paper names four additive terms (r_goal, r_reach, r_lift, r_move) weighted by seven ω-hyperparameters in Table 7; the released `compute_hand_reward` implements the reward as nested `torch.where` gates on distance/flag thresholds with different literal coefficients (-0.5, -1.0, 0.9, 2, 0.1, 0.2, 0.05, 10, 0.6/0.04/0.1) that do not correspond one-to-one to ω_g,q/ω_g,t/ω_g,R/ω_r/ω_l/ω_m/ω_b. The proposal-generation reward terms (L_cmap, L_pen, L_tpen, L_spen with λ values in Table 6: λ_cmap=0.02, λ_pen=500, λ_tpen=50, λ_spen=10, and TTA variants λ^TTA_cmap=0.07, λ^TTA_pen=10000, λ^TTA_tpen=1000, λ^TTA_spen=10) were not separately checked against code in this pass (no `contact_net`/loss-function source file was in the extracted signature list).

## Contact / penetration handling
Not part of the RL reward. Penetration is handled only in the proposal-generation/dataset pipeline: the energy function used to synthesize grasps includes E_pen ("repulsion energy to eliminate penetration"), E_tpen ("L1 energy that keeps the gripper above the table"), E_spen (self-penetration, Sec. A); grasps are discarded from the dataset if they "penetrate the object for more than 1mm" (Sec. A) or, for the Q1 metric, if "penetrates the table for more than 1cm, or has an object penetration depth larger than 5mm" (Sec. C.3.1). ContactNet's L_pen/L_tpen/L_spen (Sec. 3.2.3) serve the same role during end-to-end training and test-time optimization. Object penetration depth (max penetration from object point cloud to hand mesh) is reported as an evaluation metric (Table 1, Table 2) but is not a reward term for the execution policy. Contact solver: PhysX `contact_offset: 0.002`, `rest_offset: 0.0` (code `sim:` block above).

## Evaluation
- metrics: Simulation success rate — "the target position of the object is 0.3m above its initial position. The task is considered successful if the position difference between the object and the target is smaller than 0.05m at the final step of one sequence" (Sec. C.3.2). MPE (cm) — mean joint-position error between the achieved and goal hand configuration, "only ... for the success grasp" (Sec. C.3.2). Proposal quality: Q1 [19] (minimal wrench to make a grasp unstable, contact relaxed to 1cm, invalidated to 0 if table-penetration>1cm or object-penetration>5mm), object penetration depth (cm), rotation/translation/joint-angle/keypoint standard deviations for diversity, NLL for fit (Sec. C.3.1).
- headline numbers: Table 3 (state-based, 3 random seeds): teacher success = train 0.74±0.07, unseen-obj/seen-cat 0.71±0.05, unseen-cat 0.66±0.06, vs. best baseline ILAD 0.25/0.22/0.20 ("about 49% and 47% improvement," text of Sec. 4.3 — note Table 8's goal-conditioned teacher numbers, 0.74/0.71/0.67, differ slightly from Table 3's 0.74/0.71/0.66 for unseen-cat). Table 4 (vision-based student, GT goals): 0.68/0.65/0.63; with predicted (pipeline) goals: 0.66/0.59/0.58. Table 1 (proposal generation): ours Q1=0.0423 (seen), 0.0322 (unseen) vs. best baseline (R+C+T) 0.0362/0.0336. Abstract: "average success rate of more than 60% on thousands of object instances."
- baselines beaten: proposal generation — GraspTTA [24], DDG [28], ReLie [16]+T, ProHMR [26]+T, and ablations (R+C+T, decoup.T, w/o TTA). Execution — MP (motion planning), PPO [52], DAPG [45], ILAD [59], IBS-Grasp [53] (Table 8, non-goal-conditioned only; IBS-Grasp "cannot train under the goal-conditioned setting"). All were re-run by the authors under the same task/goal setting (Sec. B.2.1), not quoted from their original papers.
- real robot? None. All numbers are Isaac Gym simulation (Sec. 3.1, C.1).

## Limitations stated by the authors
Sec. 5: "The limitation is that we only tackle the grasping of rigid objects, in contrast to articulated objects like scissors. Furthermore, functional dexterous grasping still remains a challenging but promising field to explore." Elsewhere (Sec. 4.3): the vision-based student "success rate decreases by 6% and 7% on the train and test set" vs. the teacher, "limited by the teacher's performance."

## Notes for the survey (which sections this feeds; contradictions with other notes)
- Feeds: the "generative proposal + goal-conditioned RL" two-stage template that later cross-category grasping papers (e.g. UniDexGrasp++) benchmark against; the object-curriculum-learning result (Table 3) as the canonical ablation showing cross-category RL collapses without a curriculum (0.31→0.74 train success, w/o OCL vs. full).
- Reward-block caution for the survey's method-comparison table: paper prose (ω-weighted 4-term sum) and the shipped `compute_hand_reward` (threshold-gated `torch.where` cascade) are not the same function; cite the code version if reproducing, the paper version if only comparing stated design.
- Grasp quality is checked both geometrically (Q1 wrench metric, penetration-depth metric, Sec. C.3.1) and physically (dataset filtering requires the grasp to "resist gravity in all 6 axis-aligned directions in the IsaacGym simulator," Sec. A; execution success is a physically-simulated lift-and-hold in Isaac Gym, Sec. C.3.2) — no real-world check.
- Object split numbers differ by stage and must not be conflated: 5519/133-cat total dataset with a 3251/754/1514 split for proposal generation (Sec. 4.1) vs. a filtered 3200-train/241-test split for policy execution (Sec. C.2).
