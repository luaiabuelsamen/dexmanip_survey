# omnigrasp_2024 — Omnigrasp: Grasping Diverse Objects with Simulated Humanoids (Luo, Xu, Zhu, Karunratanakul, Winkler, Kanazawa, Black, Guibas; NeurIPS 2024)

sources: papers/md/omnigrasp_2024.md [6c22ac6e] ; code/md/omnigrasp_2024.md [f7740cdc]

## One-line contribution
A pretrained universal dexterous humanoid motion representation (PULSE-X, a latent action space distilled from a finger-augmented motion imitator PHC-X) lets a hierarchical RL policy grasp >1200 objects and follow arbitrary 3D object trajectories using a simple, un-paired state and reward design guided only by a single pre-grasp hand pose, without ever needing paired full-body-plus-object human motion (abstract; Sec. 4).

## Setting
- hand(s): SMPL-X whole-body humanoid, 52 joints / 51 actuated, 21 body joints (3 DoF each) + 30 finger joints (3 DoF each) across two hands, action space a_t ∈ R^{51×3} (Sec. 3). Not a robot hand — same simulated-human embodiment as PhysHOI's humanoid. No arm as a separate entity; single continuous kinematic tree; bimanual (both hands available, policy learns to use one or both depending on object size, Sec. 5.1 "OakInk only has pre-grasps using one hand").
- simulator / physics: Isaac Gym (Sec. 5.1 "Implementation Details"). Policy at 30 Hz, simulation at 60 Hz. Object density 1000 kg/m³; static and dynamic friction coefficients of object and humanoid fingers both set to 1. Objects decomposed into convex geometries via v-hacd (required by the simulator) (App. C.1); meshes over 50,000 vertices are quadratically decimated. No explicit #parallel-envs number stated in the parsed text (batch size 3072 is a PPO minibatch size, Table 7, not an env count). Compute: Omnigrasp trained "for three days collecting around 10^9 samples on a Nvidia A100 GPU"; PHC-X trained ~1.5 weeks, PULSE-X ~3 days, both "trained once and frozen" (Sec. 5.1, App. B.1). A PPO-10B baseline (no PULSE-X) trains "for a month (∼10 billion samples)" (Sec. 5.1).
- observation: goal state s_t^g = reference object pose + difference between the reference object trajectory over the next φ=20 future frames (sampled at 15 Hz) and current object state, plus a 512-d object shape latent σ^obj (Basis Point Set encoding of canonical object pose, Sec. 4.2) and p_t^obj − p_t^hand (object-to-each-hand-joint position difference); explicitly excludes body pose, grasp, or phase variables so it generalises to unseen objects/trajectories at test time (Sec. 4.2). Proprioception s_t^p = (q_t, q̇_t, c_t): 3D body pose, velocity, and hand contact forces (Sec. 3). All values heading-normalised.
- action space: not raw joint targets — a latent code z_t^omnigrasp ∈ R^48 from the policy, added as a residual to the PULSE-X prior's mean μ_t^p, then decoded by the frozen PULSE-X decoder D_PULSE-X into the PD target a_t ∈ R^{51×3} (Sec. 4.2, Algo. 1). This "residual action space" leverages the pretrained motion prior for human-like motion.
- objects / data / retargeting: GRAB [70] (1.3k paired full-body-motion + object trajectories, 50 objects, doorknob removed as immovable; cross-object split 45/5, cross-subject split 9 subjects train/1 test, following Braun et al. [6]); OakInk [85] (1700 objects, 32 categories, split 1330/185/185, no paired MoCap — pre-grasps instead come from "an off-the-shelf grasp generator [85]"); OMOMO [34] (15 large objects, 7 used, cleaner meshes) (Sec. 5). Human-hand-to-robot-hand retargeting is not applicable — same SMPL-X embodiment throughout, no cross-embodiment correspondence step. The only "correspondence" concept is the single-frame pre-grasp q̂^pre-grasp (hand translation + rotation) taken directly from MoCap or a generative grasp model, used purely as a reward target, not as an initial pose (Sec. 4.2: "As we do not initialize the humanoid with the pre-grasp pose as in PGDM...").

## Method
- paradigm: hierarchical RL. Stage 1: PHC-X, a motion imitator with articulated fingers (extends PHC [42]), trained with RL to imitate reference full-body+finger poses; fingers "treated similarly as the rest of the body (e.g. toe or wrist)" (Sec. 4.1). Stage 2: PULSE-X, a VAE-like online-distilled (DAgger-style) latent motion representation with encoder/decoder/prior, learned by rolling out in simulation and querying PHC-X for action labels (Sec. 4.1). Stage 3: Omnigrasp policy π_Omnigrasp, RL (PPO) over the frozen PULSE-X latent action space, trained with a simple, unpaired state/reward design (Sec. 4.2). Algorithm: PPO throughout (Sec. 3).
- data augmentation for dexterity: since "91% of the AMASS sequences do not have finger motion," a "dexterous AMASS" dataset is built by randomly pairing full-body motion (AMASS) with hand motion sampled from GRAB and Re:InterHand, BEDLAM-style (Sec. 4.1) — this pairing is ablated (Table 4, R3 vs R6: without it, grasp success stays high but trajectory-following success drops from 94.1% to 77.3%, attributed to the prior lacking "holding the object while moving" motions).
- 3D object trajectory generator T_3D: extends PACER's 2D generator to 3D so that Omnigrasp trains without any ground-truth object trajectories — random velocity/delta-angle sampled per step (velocity bounded [0,2] m/s, angle bounded [0,1] rad, 0.2 probability of a sharp turn up to [0,2π], z-translation bounded [0.1,2.0] m; App. C.2). Training on generated vs. MoCap trajectories is directly compared in Table 1 (Gen beats MoCap on success rate/position error but is worse on rotation error, attributed to a gap between generated and MoCap object rotations, Sec. 5.1).
- hard-negative mining: object j sampled with probability P(j) = s_j / Σ_i s_i, where s_j is the count of failed lifts for object j over all previous runs — chosen over an object curriculum (Sec. 4.2 "Training"); ablated in Table 4 (R5 vs R6: removing it drops Succ_traj from 94.1% to 71.6%).

## Reward / objective block (block C — quoted from both paper and code)
- Paper (Sec. 4.2), pre-grasp/approach stage before time λ=1.5s (the "frame in which grasping should occur"): when hands are far from the pre-grasp (‖p̂^pre-grasp − p_t^hand‖₂ > 0.2 m), an approach reward r_t^approach = ‖p̂^pre-grasp − p_t^hand‖₂ − ‖p̂^pre-grasp − p_{t−1}^hand‖₂ (progress toward the pre-grasp). Once hands are within 0.2 m, a precise hand-imitation reward r_t^pre-grasp = w_hp·e^(−100‖p̂^pre-grasp − p_t^hand‖₂) × 1{‖p̂^pre-grasp − p̂^obj‖₂ ≤ 0.2} + w_hr·e^(−100‖θ̂^pre-grasp − θ_t^hand‖₂). After time λ, only the object-trajectory-following reward r_t^obj is used, "filtered by an indicator variable 1{C} that is set to true if the object is in contact with the humanoid hands," plus a contact-encouragement term 1{C}·w_c (Sec. 4.2). Exact numeric values of w_hp, w_hr are not printed in the parsed paper text (only referenced as "Hyperparameters can be found in Appendix C") and are not resolvable from Appendix Table 7 either — Table 7 lists only w_op, w_or, w_ov, w_oav, w_c (0.5, 0.3, 0.05, 0.05, 0.1) for the object-tracking/contact stage, with no separate pre-grasp-reward weight row. **Flagged: pre-grasp reward weights w_hp/w_hr are not resolvable from this source (paper or code/md).**
- Code (phc/env/tasks/humanoid_omnigrasp.py, `compute_grab_reward`): object position reward `r_obj_pos = exp(-k_pos * mean((ref_obj_pos - obj_pos)**2))`; object rotation reward via quaternion angle-axis difference, `r_obj_rot = exp(-k_rot * mean(diff_global_body_angle**2))`; linear/angular velocity rewards analogously with k_vel/k_ang_vel; contact term `r_contact_lifted = contact_filter.float()`; combined as `reward = (w_pos*r_obj_pos + w_rot*r_obj_rot + w_vel*r_lin_vel + w_ang_vel*r_ang_vel) * contact_filter + r_contact_lifted * w_conctact` — i.e. the tracking terms are gated multiplicatively by `contact_filter` (only paid while the hand is judged in contact), on top of the additive contact bonus. This confirms position AND orientation are both tracked in the object reward (unlike physhoi_2023, where the analogous rotation term was hard-zeroed).
- Code (phc/env/tasks/humanoid_omnigrasp.py, `compute_pregrasp_reward_time`): the pre-grasp reward hard-codes its own weights inside the function body — `w_pos, w_rot = 0.9, 0.1` — **overriding** the `w_pos`/`w_rot` values passed in via `rwd_specs`, a mismatch between the function signature (which accepts weights as arguments) and its actual behaviour (which discards them). `reward = w_pos * r_body_pos + w_rot * r_body_rot` where each term is `exp(-k_pos/k_rot * squared distance)` gated by a `close_hand_flag` (only counted when the reference hand is within `close_distance` of the reference object) and replaced by a capped "getting closer" reward `closer_to_hand_r` (clamped to max 1/10 progress per step) when the hand isn't yet close enough to the reference hand pose (`distance_filter`).
- Both sources agree the total reward is NOT a strict "quote the formula" from a single top-level equation in the paper (Sec. 4.2's equations render blank in the parse); the code is the primary source for the exact functional form here.

## Contact / penetration handling (block D)
Hand-object interpenetration is explicitly and deliberately **not measured or penalised**: "Since all methods are simulation-based, we omit penetration/foot sliding metrics and report the precise trajectory tracking errors instead" (Sec. 5.1, GRAB Dataset paragraph) — a direct statement that penetration is considered a metric the authors chose to skip, not something addressed by the method. Contact itself (not penetration) is used only as a binary gating signal for reward and success, via a force+distance heuristic: "if the object is within 0.2m from the hands, has non-zero contact forces, and has a non-zero velocity, we deem it to have contact with the hands" (App. C.2, "Contact Detection") — because "IsaacGym does not provide easy access to contact labels and only provides contact forces, there is no way of differentiating between contact with the table, humanoid body, or objects." No contact-solver softness/stiffness parameters are given for this key.

## Evaluation
- exact success criteria (Sec. 5.1 "Metrics", all thresholds in metres/seconds): **Succ_grasp** — grasp succeeds if the object is held ≥0.5 s in simulation without dropping. **TTR** (Trajectory Targets Reached) — fraction of timesteps where the object is <12 cm from the target position, measured only on successful trajectories. **Succ_traj** — full-trajectory success fails if at ANY point the object is >25 cm from the reference. Early-termination during training uses the same 12 cm bound: "we terminate the episode whenever the object is more than 12cm away from its desired reference trajectory ... ‖p̂_t^obj − p_t^obj‖₂ > 0.12" (App. C.2). For OakInk/OMOMO (no paired trajectory) the task is standardised to "vertical lifting (30cm) and holding (3s)" (Sec. 5.1).
- other metrics: E_pos (mm) object position error; E_rot (radian) object rotation error; E_acc (mm/frame²) acceleration error; E_vel (mm/frame) velocity error (Sec. 5.1 "Metrics"). Body-imitation-only metrics for PHC-X/PULSE-X (App. B.2, Table 6): E_g-mpjpe / E_mpjpe (global/root-relative mean per-joint position error, mm), Succ (99.9%/99.5% on Dexterous-AMASS training data for PHC-X/PULSE-X respectively).
- object tracked position AND orientation: yes — both E_pos and E_rot are reported, and the code confirms both `r_obj_pos` and `r_obj_rot` (quaternion-angle-axis based) are live reward terms (unlike physhoi_2023's zeroed rotation term). The paper flags rotation as the harder axis: "though the 6DoF input is provided in the input and reward, the rotation error remains to be further improved" (Sec. 6, Limitations).
- headline numbers (Table 1, GRAB, MoCap trajectories): Omnigrasp Succ_grasp 94.6% / Succ_traj 84.8% / TTR 98.7% / E_pos 28.0mm / E_rot 0.5 rad / E_acc 4.2 / E_vel 4.3, vs. PHC [42] (feeding ground-truth kinematic pose to a pretrained imitator) Succ_grasp 3.6% / Succ_traj 11.4%; vs. AMP [56] Succ_grasp 90.4% / Succ_traj 46.6%; vs. Braun et al. [6] Succ_grasp 79% (Succ_traj not reported by them, "-"); vs. PPO-10B (no PULSE-X, ~10^10 samples) Succ_grasp 98.4% but Succ_traj only 55.9%. On generated trajectories, Omnigrasp reaches Succ_grasp 100% / Succ_traj 94.1% / TTR 99.6% (Table 1; also the row used in every ablation in Table 4). OakInk cross-dataset (Table 3): GRAB-trained policy tested on OakInk-Test reaches Succ_grasp 81.9%/Succ_traj 72.1% despite never training on OakInk objects.
- ablations (Table 4, cross-object GRAB test): removing PULSE-X (R1) drops Succ_traj from 94.1% to 33.6%; removing pre-grasp guidance (R2) drops Succ_traj to 57.9% with Succ_grasp also dropping (77.1%); removing dexterous-AMASS training (R3) keeps Succ_grasp high (94.4%) but Succ_traj drops to 77.3%; removing initial-pose randomisation (R4) drops Succ_traj to 79.9%; removing hard-negative mining (R5) drops Succ_traj to 71.6%.
- robustness (Table 5): adding uniform noise [-0.01, 0.01] to observations drops GRAB-Goal Succ_traj from 94.1% to 91.4% and Succ_grasp stays at 100%, with acceleration/velocity error metrics degrading most (5.4→15.6, 4.7→11.5) — presented as sim-to-real potential, explicitly not claimed as real-robot-ready ("we do not claim that Omnigrasp is currently ready for real-world deployment", Sec. 5.2).
- baselines beaten: Braun et al. [6] (quoted, not re-run — the paper reproduces only the numbers Braun et al. reported, "-" for unreported metrics), self-reimplemented AMP [56] and PHC [42], and an internal PPO-10B ablation.
- real robot? none. All in Isaac Gym simulation.

## Limitations stated by the authors (Sec. 6)
- "though the 6DoF input is provided in the input and reward, the rotation error remains to be further improved."
- "Omnigrasp has yet to support precise in-hand manipulations."
- Trajectory-following success rate can still be improved — objects "can be dropped or not picked up."
- No control over specific grasp type; would need additional input such as desired contact points.
- "Human-level dexterity, even in simulation, remains challenging."

## Quotable claims (verbatim, with section)
- "Since all methods are simulation-based, we omit penetration/foot sliding metrics and report the precise trajectory tracking errors instead." (Sec. 5.1)
- "As IsaacGym does not provide easy access to contact labels and only provides contact forces, there is no way of differentiating between contact with the table, humanoid body, or objects." (App. C.2)
- "we can use simple state and reward design and do not require any paired object and human motion to learn grasping policies." (Sec. 4.2)
- "we do not claim that Omnigrasp is currently ready for real-world deployment, but we believe that a similar system design plus sim-to-real modifications ... has the potential." (Sec. 5.2)
- "The gap between trajectory Succ_traj and grasp success Succ_grasp shows that following the full trajectory is a much harder task than just grasping." (Sec. 5.1)

## Notes for the survey
- Feeds: the strongest "learned motion prior as action space" example in this batch (PULSE-X latent action space vs. raw joint targets), and the clearest documented case of a paper choosing NOT to measure interpenetration at all, with an explicit rationale ("we omit penetration/foot sliding metrics") rather than silence — useful as a contrast to PhysHOI's incidental "some minor penetrations may appear" admission and to the RL trackers (e.g. DexTrack) that this survey specifically audits for interpenetration.
- Reward-block gap to flag in any cross-paper table: the pre-grasp reward's weights (w_hp, w_hr) are unresolved from both paper and code in this parse; do not present a complete pre-grasp reward weight row for Omnigrasp without further digging into the actual repo config files (not captured in code/md's extracted signatures).
- Code-level mismatch worth carrying forward: `compute_pregrasp_reward_time`'s hard-coded `w_pos, w_rot = 0.9, 0.1` silently overrides the `rwd_specs` arguments passed to it — a live discrepancy between the function's declared interface and its behaviour, relevant if the survey ever needs to state "these are configurable weights" for this method.
- Same base embodiment (SMPL-X humanoid) as physhoi_2023, but here the object rotation reward is genuinely live in code (contrast physhoi_2023's hard-zeroed `eor`) — good paired citation for the survey's "position only vs. position+orientation, paper vs. code" comparison table.
