# eureka_2023 — Eureka: Human-Level Reward Design via Coding Large Language Models (Ma, Liang, Wang, Huang, Bastani, Jayaraman, Zhu, Fan, Anandkumar; ICLR 2024)

sources: papers/md/eureka_2023.md [aa3b6350] ; code/md/eureka_2023.md [9eee4280]

## One-line contribution
An LLM (GPT-4) writes free-form, executable reward-function code directly from raw environment source code and a one-line task description (no reward templates, no task-specific prompt engineering), then improves it via evolutionary search — sample K candidates, train and score each with RL, feed the best one's per-component training statistics back as a text "reward reflection" — beating human-expert rewards on 83% of 29 tasks (52% avg. normalized improvement) and, combined with curriculum learning, producing the first simulated Shadow Hand pen-spinning policy (Abstract).

## Setting
- hand(s): Shadow Hand (dexterity benchmark: single-hand AllegroHand 88 obs/16 act and ShadowHand 211 obs/20 act tasks; bimanual Dexterity benchmark — 20 tasks, "a pair of Shadow Hands," e.g. HandOver, DoorOpen/Close ×4, Kettle, LiftUnderarm, Catch ×3, ReOrientation, GraspAndPlace, BlockStack, PushBlock, Scissors, Spin, SwingCup, Switch, TwoCatchUnderarm, UpsideDown, Over) — bimanual for Dexterity, single-hand for the 9 core Isaac tasks and pen spinning (App. B). Base is fixed for the Dexterity hands (per HandOver description).
- simulator / physics: NVIDIA IsaacGym (Makoviychuk et al., 2021), unmodified physics; also one MuJoCo Humanoid cross-simulator check (App. E, Table 4). Pen-spinning env "builds on the original Shadow Hand environment in Isaac Gym without any changes to any physics parameter... the cube object... is swapped out with the pen object" (App. D.1).
- observation: task-specific, exposed via each env's own state variables (App. B lists obs/action dims per task, e.g. ShadowHand 211/20, AllegroHand 88/16); code/md `eureka/envs/isaac/shadow_hand_spin.py::compute_full_observations` builds DOF pos/vel (unscaled to limits), object pose, goal pose, quaternion difference to goal, fingertip state, actions — several observation-type variants (`openai`/`full_no_vel`/`full`/`full_state`) plus an asymmetric-obs branch for the critic.
- action space: not itemized generically in the parse; per-task action dims given in App. B tables (e.g. ShadowHand 20-dim, AllegroHand 16-dim, Dexterity tasks 40-52-dim for bimanual).
- objects / data: 29 tasks total — 9 "Isaac" environments (Cartpole, Quadcopter, FrankaCabinet, Anymal, BallBalance, Ant, AllegroHand, Humanoid, ShadowHand) + all 20 "Dexterity" bimanual Shadow Hand tasks from Chen et al. 2022, chosen partly because both suites postdate GPT-4's training cutoff (Sept. 2021), reducing memorization concerns (Sec. 4).

## Method
- paradigm: RL, sim-only, with an outer LLM-driven evolutionary search over reward code ; inner algorithm: PPO ("a well-tuned PPO implementation," Makoviichuk & Makoviychuk 2021), same algorithm and same task-specific hyperparameters (tuned originally for the human rewards) used for every candidate reward, unmodified (Sec. 4.2).
- outer loop (Algorithm 1, quoted structure): given task description l, environment code M, coding LLM, fitness function F, and hyperparameters (search iterations N, batch size K): for N iterations, sample K reward-function candidates R_1..R_K ~ LLM(l, M, prompt); train a policy per candidate and evaluate each with F to get scores s_1..s_K; reward reflection appends `Reflection(R_best^n, s_best^n)` (best = argmax_k s_k) to the prompt for the next iteration; keep the running best (R_Eureka, s_Eureka) whenever s_best^n > s_Eureka. "In all our experiments, EUREKA conducts 5 independent runs per environment, and for each run, searches for 5 iterations with K = 16 samples per iteration" (Sec. 3.2) — i.e. N=5, K=16, 5 random restarts. Note: the released repo's default `eureka/cfg/config.yaml` ships `iteration: 1`, `sample: 3` (a fast-test default, not the paper's reported experiment configuration) — a paper/code default mismatch worth flagging if someone reruns the repo as-is expecting paper-scale search.
- environment-as-context (Sec. 3.1): the raw environment source code (minus any existing reward function) is fed directly as context, with an automatic extraction script pulling only the state/action-exposing snippets so the prompt "does not leak simulation internals" and generalizes across simulators (App. D references this extraction).
- evolutionary search (Sec. 3.2): "the probability that all reward functions from an iteration are buggy exponentially decreases as the number of samples increases... sampling just a modest number of samples (16) contains at least one executable reward code in the first iteration." Each new iteration performs in-context "reward mutation": takes the best-performing reward, its reward reflection, and a fixed mutation prompt (Prompt 2, App. A) as context to produce K new i.i.d. candidates.
- fitness function F (Sec. 2, Definition 2.1, quoted): F: Π → R is "the fitness function that produces a scalar evaluation of any policy, which may only be accessed via policy queries (i.e., evaluate the policy using the ground truth reward function)" — a hand-authored, task-specific, black-box scoring metric, NOT the reward being optimized. Per App. B this is e.g. `duration` (Cartpole), `-cur_dist` (Quadcopter), `1[cabinet_pos > 0.39]` (FrankaCabinet), `-(linvel_error+angvel_error)` (Anymal), `number of consecutive successes where current success is 1[rot_dist < 0.1]` (AllegroHand and ShadowHand). For Dexterity tasks F is uniformly a binary success indicator (e.g. `1[dist < 0.03]` for HandOver). The **Sparse** baseline in the paper's own experiments is literally F used as the training reward, contrasted against Human and EUREKA rewards.
- reward reflection (Sec. 3.3, Prompt 2 quoted verbatim): "We trained a RL policy using the provided reward function code and tracked the values of the individual components in the reward function as well as global policy metrics such as success rates and episode lengths after every {epoch_freq} epochs and the maximum, mean, minimum values encountered: <REWARD REFLECTION HERE> Please carefully analyze the policy feedback and provide a new, improved reward function... (1) If the success rates are always near zero, then you must rewrite the entire reward function (2) If the values for a certain reward component are near identical throughout, then this means RL is not able to optimize this component as it is written... (3) If some reward components' magnitude is significantly larger, then you must re-scale its value to a proper range." Because EUREKA rewards must expose named sub-components (Prompt 3: "the output of the reward function should consist of two items: (1) the total reward, (2) a dictionary of each individual reward component"), the per-component statistics — not just the scalar fitness score — are what get reflected back, giving credit-assignment information the fitness score alone lacks (Sec. 3.3, quoted rationale).
- reward code format constraints (Prompt 1 & 3, App. A, quoted): system prompt requires a `@torch.jit.script`-decorated `compute_reward(...) -> Tuple[torch.Tensor, Dict[str, torch.Tensor]]` signature; formatting tips require any transformed component to introduce its own named temperature variable, correct typing (float vs. torch.Tensor), and forbid introducing new input variables beyond `self.`-prefixed environment attributes.
- actual LLM-generated reward code, quoted verbatim (App. G.1, "Reward Reflection Example 1, ShadowHand," iteration 1 score 9.29 → iteration 2 score 10.43):
```
# Iteration 1
@torch.jit.script
def compute_reward(object_rot, goal_rot) -> Tuple[Tensor, Dict[str, Tensor]]:
    rot_diff = torch.abs(torch.sum(object_rot * goal_rot, dim=1) - 1) / 2
    rotation_reward = torch.exp(-20 * rot_diff)
    rotation_temp = 20.0
    total_reward = rotation_reward
    return total_reward, {"rotation_reward": rotation_reward}

# Iteration 2 (after reflection: "rotation_reward... seems mostly adequate... recommend
# introducing another component, such as a penalty for large angular velocities")
@torch.jit.script
def compute_reward(object_rot, goal_rot, object_angvel) -> Tuple[Tensor, Dict[str, Tensor]]:
    rot_diff = torch.abs(torch.sum(object_rot * goal_rot, dim=1) - 1) / 2
    rotation_reward = torch.exp(-20 * rot_diff)
    angvel_norm = torch.norm(object_angvel, dim=1)
    angvel_threshold = 5.0
    angvel_penalty_temp = 10.0
    angular_velocity_penalty = torch.where(angvel_norm > angvel_threshold,
        torch.exp(angvel_penalty_temp * (angvel_norm - angvel_threshold)), torch.zeros_like(angvel_norm))
    total_reward = rotation_reward - angular_velocity_penalty
    return total_reward, {"rotation_reward": rotation_reward, "angular_velocity_penalty": angular_velocity_penalty}
```
A second verbatim example (App. G.2, "negatively correlated but superior," ShadowHand, Human-Normalized Score 1.45, correlation −0.26 with the human reward) combines a rotation term with a fingertip-proximity term gated by a distance threshold: `total_reward = rot_reward * distance_reward - distance_penalty`, where `distance_penalty = 0.5 * (1 - torch.prod(close_enough, dim=-1))` — this example is offered by the authors specifically to show EUREKA discovering reward structures that run counter to human intuition yet outperform it.
- code repo caveat: the released repo (`code/md/eureka_2023.md`) contains only the base/human `compute_reward` implementations for each `eureka/envs/isaac/*.py` task (e.g. `shadow_hand_spin.py::compute_reward` calls `compute_bonus`/`compute_success`, the original human-authored functions) — LLM-generated reward samples are written at runtime to a gitignored `outputs/` directory and are not checked into the repo; the verbatim reward code above therefore comes from the paper's appendix, not the code parse.
- pen-spinning curriculum (Sec. 4.3, App. D.1): stage 1 "Pre-Trained" — EUREKA reward for reorienting the pen to a uniformly-random SO(3) target (identical mechanism to the standard cube-reorientation task); stage 2 "Fine-Tuned" — same EUREKA reward, but targets switch through "a predetermined sequence of waypoints that specify the pen spinning patterns," advancing to the next waypoint once the current one's pose difference is below a threshold, cycling continuously. A "Scratch" ablation (fine-tuning target directly, no stage-1 pretraining) and "Pre-Trained" alone (no stage-2 fine-tuning) both fail to complete even one spin cycle; only Pre-Trained→Fine-Tuned succeeds (Sec. 4.3, Fig. 7).
- interpenetration / contact: not addressed as a measured or rewarded quantity anywhere in the parse; no penetration metric, and contact only appears implicitly via the fingertip-distance-style reward terms authors show as illustrative examples.

## Evaluation
- metrics: Isaac tasks — human-normalized score = (Method − Sparse) / |Human − Sparse| (quoted formula, Sec. 4.2), a holistic measure relative to the Sparse (fitness-as-reward) and Human baselines. Dexterity tasks — raw binary success rate (all F are success indicators there). Protocol: "For each final reward function obtained from each method, we run 5 independent PPO training runs and report the average of the maximum task metric values achieved from 10 policy checkpoints sampled at fixed intervals" (Sec. 4.2).
- headline numbers: EUREKA "exceeds or performs on par to human level on all Isaac tasks and 15 out of 20 tasks on Dexterity" (Sec. 4.3, Fig. 4 — per-task breakdown is a figure, not a table, in the parse); L2R baseline "comparable on low-dimensional tasks... but lags significantly behind on high-dimensional tasks"; removing evolution (**EUREKA w.o. Evolution (32 Samples)**, same total reward-function budget as 2 iterations) underperforms EUREKA after 2 iterations on both benchmarks (Fig. 5); removing reward reflection (**EUREKA No Reward Reflection**, feedback reduced to only the scalar F) "reduces the average normalized score by 28.6%" averaged over Isaac tasks (Sec. 4.3, quoted). GPT-3.5 ablation: "degrades in performance but still matches or exceeds human-level on most Isaac tasks" (Sec. 4.3). Pen spinning has no numeric success-rate/cycle-count table in the parse — described only qualitatively ("Eureka fine-tuning quickly adapts the policy to successfully spin the pen for many cycles in a row... neither pre-trained or learning-from-scratch policies can complete even a single cycle," Sec. 4.3) plus a training-curve figure (Fig. 7); the MuJoCo cross-sim check does give a number: Table 4, Mujoco Humanoid forward-velocity fitness EUREKA 7.68 vs. Human 5.92.
- baselines beaten: **Human** (original benchmark task rewards, written by the tasks' own RL researchers); **L2R** (Yu et al. 2023 — two-stage LLM pipeline that fills a natural-language motion template then maps it to a fixed set of human-defined reward-API primitives, Table 3; L2R is explicitly given "an advantage as it has access to the original reward functions" for its primitives, Sec. 4.1); **Sparse** (the fitness function F itself used as training reward). Also an ablation series: No Evolution, No Reward Reflection, GPT-3.5 backbone.
- real robot? Only a "preliminary real-robot experiment in App. F, which demonstrates real-world hopping behavior learned via EUREKA reward in a Sim2Real pipeline" (Sec. H, Limitations) — not the hand tasks. No trial counts given for this hopping experiment in the sections read; described as preliminary, not a systematic real-world dexterity evaluation. Pen spinning and all Dexterity/Isaac results are simulation-only.

## Limitations stated by the authors (App. H)
- "EUREKA currently is evaluated on simulation-based tasks with the exception of the preliminary real-robot experiment in App. F" (locomotion hopping, not a hand task).
- "EUREKA requires a task fitness function F to exist and [be] easily definable by humans" — behaviors hard to specify mathematically (e.g. "running in a stable gait") motivate the separate EUREKA-from-Human-Feedback mode (Sec. 4.4) instead.
- "our experiments currently take place on a single simulator and a fixed RL algorithm, with the exception of the MuJoCo Humanoid experiment" — generality to other simulators/optimizers (e.g. MPC) is asserted but not demonstrated broadly.

## Quotable claims (verbatim, with section)
- "EUREKA generates reward functions that outperform expert human-engineered rewards... EUREKA outperforms human experts on 83% of the tasks, leading to an average normalized improvement of 52%." (Abstract)
- "sampling just a modest number of samples (16) contains at least one executable reward code in the first iteration." (Sec. 3.2)
- "EUREKA without reward reflection reduces the average normalized score by 28.6%." (Sec. 4.3)
- "the harder the task is, the less correlated the EUREKA rewards [are with human rewards]... EUREKA can discover novel reward design principles that may run counter to human intuition." (Sec. 4.3)
- "human designers are generally knowledgeable about relevant state variables but are less proficient at designing rewards using them." (Sec. 4.4)
- pen-spinning curriculum: "neither pre-trained or learning-from-scratch policies can complete even a single cycle of pen spinning." (Sec. 4.3)

## Notes for the survey
- This is the mechanism DrEureka (2024, this survey's companion note) builds directly on: same outer loop (Algorithm 1 here = "Background: Eureka Reward Design" in DrEureka Sec. IV-A), same N=5-iteration/K=16-sample defaults reused verbatim ("we use the original Eureka hyperparameters," DrEureka Sec. V). DrEureka's additions — safety-instruction prompting and the reward-aware physics prior for domain randomization — are entirely downstream of this reward-search loop and do not modify it.
- The fitness function F is the load-bearing design choice for the survey's "how was the candidate reward evaluated/selected" comparison: F is always hand-authored and task-specific (never learned, never the LLM's own reward), and is explicitly kept separate from the optimized reward to avoid the reward simply encoding the eval metric — worth contrasting against any paper in this corpus that reports a sparse probe metric that was also used as training signal (c.f. the project's own optimised-measure-must-match-audit rule).
- Pen spinning is EUREKA's flagship dexterity result but has no quantitative success-rate/cycle table in this parse — only qualitative claims and a training-curve figure. Any survey claim about numeric pen-spinning performance from this paper should be flagged as SOURCE THIN (figure-only) rather than quoted as a number.
- Code repo does not contain any LLM-generated reward artifacts (they are produced at runtime, gitignored); all verbatim reward-code quotes in this note come from the paper's Appendix G, not from code/md.
