# hora_2022 — In-Hand Object Rotation via Rapid Motor Adaptation (Qi et al., CoRL 2022)

sources: papers/md/hora_2022.md [sha256 d18d851f] ; code/md/hora_2022.md [commit 410d9582]

## One-line contribution
Object-agnostic z-axis in-hand rotation with an Allegro Hand, using only fingertips and proprioception, via Rapid Motor Adaptation (RMA): a privileged-extrinsics base policy plus an online adaptation module trained by supervised regression on proprioception history (Sec 3, Fig 2).

## Setting
- hand(s): Allegro Hand (Wonik Robotics), 4 fingers x 4 DoF = 16 joints (Sec 4, "Hardware Setup"); code uses two URDF variants, `assets/allegro/allegro_internal.urdf` (internal hand, `AllegroHandHora.yaml` line 365) and `assets/allegro/allegro.urdf` (public hand, `PublicAllegroHandHora.yaml` line 414). Arm/mount: not stated in either source; action space has no arm DoF (numActions=16 = hand only). Palm-up vs palm-down: not stated.
- simulator / physics: IsaacGym (paper Sec 4, ref [35]; code disclaimer says "developed and debugged using IsaacGym Preview 4.0"); PhysX (`configs/task/AllegroHandHora.yaml` `sim.physx` block). Training uses 16384 parallel envs (paper Sec 4: "we use 16384 parallel environments"; code `env.numEnvs: ${resolve_default:16384,...}`).
- observation: proprioception only, no vision/tactile — confirmed by paper Sec 3.1 and abstract ("even without the usage of vision and tactile sensing"). Paper: o_t = (q_{t-2:t}, a_{t-3:t-1}) ∈ R^96 (3 past joint positions + 3 past commanded actions). Code: `env.numObservations: 96`; `compute_observations()` (code/md/hora_2022.md ~L580) builds `obs_buf_lag_history` from noised joint positions (`unscale(joint_noise_matrix + allegro_hand_dof_pos, ...)`) concatenated with `cur_targets` per step, and flattens the last 3 steps into `obs_buf`.
- action space: 16-dim, position targets converted to torque by a PD controller. Paper: "controlled using position control at 20 Hz. Target position commands are converted to torque using a PD Controller (Kp=3.0, Kd=0.1) at 300 Hz" (real hardware, Sec 4). Code sim side: `controller.torque_control: True`, `controlFrequencyInv: 6` (120 Hz sim / 6 = 20 Hz control), `pgain: 3`, `dgain: 0.1` (`AllegroHandHora.yaml`).
- objects / data: training objects are cylinders only, radius 8 cm, height in discretized list [0.8,0.85,...,1.2] cm, scaled by a randomized scale factor (paper Appendix C). Grasp poses: 50,000 pre-sampled stable grasps per discretized scale (paper App. C; code README "cache/*.npy", "50k means there are 50k randomly sampled grasping pose for each scale"). Real-world eval: 30+ objects, diameter 4.5-7.5 cm, mass 5-200 g (paper Sec 5.3). Note: current repo's `configs/task/AllegroHandHora.yaml` `object.type: 'block'` (default) — differs from the paper's cylinder-only training; see Notes below.

## Method
- paradigm: RL (base policy) + supervised regression (adaptation module) — RMA (Rapid Motor Adaptation), following Kumar et al. locomotion work [6] (paper Sec 1, 3).
- algorithm: PPO [33] (Schulman et al.) jointly optimizing policy π and object-property encoder µ (paper Sec 3.1). Code: `algo: PPO` (`configs/train/AllegroHandHora.yaml`), implementation in `hora/algo/ppo/` (own repo; the "RLGames Arguments" comment in `configs/config.yaml` is only a section label, not confirmation the algorithm is from the rl-games library — not stated).
- **A. Embodiment block**
  - hand: Allegro Hand, 16 DoF, Wonik Robotics; two URDF variants (internal vs public), see Setting above.
  - arm/floating base: not stated. Bimanual: no (single hand).
  - simulator + version: IsaacGym Preview 4.0 (code disclaimer); physics engine PhysX (`physics_engine: 'physx'`, `configs/config.yaml`).
  - sim timestep: `sim.dt: 0.0083333` (120 Hz, `AllegroHandHora.yaml`); control rate: 20 Hz (`controlFrequencyInv: 6`); real hardware PD loop: 300 Hz (paper Sec 4).
  - parallel envs: 16384 (train); PPO batch collection horizon_length: 8 (`configs/train/AllegroHandHora.yaml`).
  - GPU used: not stated. Wall-clock training time: not stated as wall-clock; paper reports "It takes about 500 million agent steps which corresponds to roughly 7,000 hours real-world time" (Sec C, "Optimization Details") — this is simulated experience time, not measured wall-clock.
- **B. Learning block**
  - paradigm: RL (PPO) for the base policy; supervised L2 regression (Adam [34]) for the adaptation module φ (paper Sec 3.2).
  - teacher-student / privileged->proprioceptive distillation: yes. Privileged info **e**_t ∈ R^9: "object's properties such as position, size, mass, coefficient of friction, center of mass of the object" (paper Sec 3.1, "Privileged Information"). Code: `hora.privInfoDim: 9`; `privInfo` flags `enableObjPos, enableObjScale, enableObjMass, enableObjCOM, enableObjFriction: True` (`AllegroHandHora.yaml`). This is embedded to an 8-dim extrinsics vector **z**_t = µ(**e**_t) via a 3-layer MLP, hidden dims [256,128,8], ReLU (paper App. C, "Network Architecture"; code `network.priv_mlp.units: [256, 128, 8]`).
  - adaptation module φ: estimates ẑ_t from proprioception+action history of length T=30 (1.5 s) (paper App. C; code `hora.propHistoryLen: 30`). Architecture per paper App. C: per-timestep 2-layer MLP [32,32] encoding (joint pos, action) pairs, then three 1-D conv layers [32,32,9,2],[32,32,5,1],[32,32,5,1] over time, flattened and linearly projected to 8-dim ẑ_t. This module's body is in `hora/algo/padapt/` (directory present in file tree) but its implementation was not captured in code/md/hora_2022.md — architecture recorded from the paper only.
  - observation vector, item by item (code, `compute_observations()`): noised joint position `unscale(joint_noise_matrix + allegro_hand_dof_pos, lower, upper)` concatenated with `cur_targets` (commanded action) per step; last 3 timesteps flattened into `obs_buf` (96-dim, matches paper's o_t).
  - action space: PD position targets (`torque_control: True` with `pgain`/`dgain` — target position converted to torque internally), 16-dim, `clipActions: 1.0`.
  - domain randomisation (paper Table 5 "Train Range" vs code `AllegroHandHora.yaml` `randomization` block — both quoted):
    - Object Scale: paper [0.70, 0.86]; code `randomizeScaleList: [0.7, 0.72, ..., 0.86]` (scaleListInit: True, discretized list matches paper's stated range).
    - Mass: paper [0.01, 0.25] kg; code `randomizeMassLower: 0.01`, `randomizeMassUpper: 0.25` — match.
    - Center of Mass: paper [-1.00, 1.00] cm; code `randomizeCOMLower: -0.01`, `randomizeCOMUpper: 0.01` (metres, i.e. ±1 cm) — match (units differ, cm vs m, values consistent).
    - Coefficient of Friction: paper [0.3, 3.0]; code `randomizeFrictionLower: 0.3`, `randomizeFrictionUpper: 3.0` — match.
    - PD Stiffness: paper [2.9, 3.1]; code `randomizePGainLower: 2.9`, `randomizePGainUpper: 3.1` — match.
    - PD Damping: paper [0.09, 0.11]; code `randomizeDGainLower: 0.09`, `randomizeDGainUpper: 0.11` — match.
    - External Disturbance: paper "(2, 0.25)" i.e. force scale 2·mass, resample probability 0.25, decay 0.9 per 80 ms; code `forceScale`/`randomForceProbScalar` default to 0.0 in `AllegroHandHora.yaml` (disturbance appears disabled by default in this config; paper's non-zero values not found as defaults in the parsed config — flagged as a mismatch).
    - Joint noise: paper "noise ... sampled from a uniform distribution U(0, 0.005)" (App. C); code `jointNoiseScale: 0.02` used as `(rand()*2-1)*0.02`, i.e. U(-0.02, 0.02) — **mismatch**: different range and code samples a signed (not one-sided) noise.
    - Out-of-distribution test ranges (paper Table 5 only, not found replicated in parsed code): Object Scale [0.66,0.90], Mass [0.01,0.30] kg, COM [-1.25,1.25] cm, Friction [0.2,3.5], External Disturbance (4,0.25), PD Stiffness [2.6,3.4], PD Damping [0.08,0.12].

## Evaluation
- **C. Reward / objective block** (quoted verbatim from both sources):
  - Paper (Sec 3.1 and App. C, "Reward Definition"): "r = r_rot + λ_pose·r_pose + λ_linvel·r_linvel + λ_work·r_work + λ_torque·r_torque" where
    - r_rot = max(min(ω·k̂, r_max), r_min), r_max=0.5, r_min=-0.5, k̂=[0,0,1]ᵀ ("rotation reward")
    - r_pose = -‖q - q_init‖²₂, λ_pose = -0.3 ("hand pose deviation penalty")
    - r_torque = -‖τ‖²₂, λ_torque = -0.1 ("torque penalty")
    - r_work = -τᵀq̇, λ_work = -2.0 ("energy consumption penalty")
    - r_linvel = -‖v‖²₂, λ_linvel = -0.3 ("object linear velocity penalty")
  - Code (`configs/task/AllegroHandHora.yaml`, `reward:` block): `angvelClipMin: -0.5`, `angvelClipMax: 0.5`, `rotateRewardScale: 1.0`, `objLinvelPenaltyScale: -0.3`, `poseDiffPenaltyScale: -0.3`, `torquePenaltyScale: -0.1`, `workPenaltyScale: -2.0`. `PublicAllegroHandHora.yaml` overrides `rotateRewardScale: 1.25`.
  - Code function `compute_hand_reward` (code/md/hora_2022.md ~L562): `reward = rotate_reward_scale * rotate_reward; reward += object_linvel_penalty * object_linvel_penalty_scale; reward += pose_diff_penalty * pose_diff_penalty_scale; reward += torque_penalty * torque_pscale; reward += work_penalty * work_pscale`.
  - Match: all four penalty weights (λ_pose, λ_torque, λ_work, λ_linvel) are identical between paper and internal-hand code config. Mismatch: the paper's reward equation has no explicit weight on r_rot (implicitly 1.0); the code's default config also uses `rotateRewardScale: 1.0` but the public-hand config variant uses 1.25 — the paper does not state which hand/scale its headline numbers used.
  - adaptation module loss (paper Sec 3.2): minimize the l2 distance between z_t and ẑ_t using Adam; no weight given (single term).
- **D. Contact / penetration handling**: not addressed as a reward term. `allegro_hand_grasp.py::compute_reward` (the grasp-generation stage, not the rotation task) checks contact counts via `self.gym.get_env_rigid_contacts` to validate a stable grasp (>=2 fingers in contact) but this is a filter for initial pose generation, not a penetration penalty. No interpenetration penalty or measurement term appears in the rotation-task reward. Contact solver settings (`AllegroHandHora.yaml` `sim.physx`): `contact_offset: 0.002`, `rest_offset: 0.0`, `max_depenetration_velocity: 1000.0`, `contact_collection: 2` (all substeps).
- **E. Evaluation block**: Sim metrics (paper Sec 4 "Metrics"): Time-to-Fall (TTF, episode length before object falls, normalized by max episode length: 20 s sim / 30 s real); Rotation Reward (RotR, mean ω·k̂, "we do not train with this reward... a clipped version... during training" — used for eval only); Rotations (net radians rotated about world z, real-world only); Object Linear Velocity (ObjVel, ×100, sim only); Torque Penalty (mean l1 norm of commanded torque). Sim eval: averaged over 500K episodes, 5 seeds (paper Sec 5.1). Real-world eval: 20 initial grasp positions x 6 objects per object set (Fig 3, Fig 4), max episode 30 s. Termination: episode reset at fall (~14.5 cm above palm during training per `reset_height_threshold`; ~10 cm during evaluation per paper App. C — code `reset_height_threshold: 0.645` internal / `0.625` public, absolute frame height not directly comparable to the paper's palm-relative cm figures). Headline numbers: Table 1 (Ours: RotR 222.27±21.20 / TTF 0.82±0.02 / ObjVel 0.29±0.05 / Torque 1.20±0.19 within-distribution; 160.60±10.22 / 0.68±0.07 / 0.47±0.07 / 1.20±0.17 OOD). Real, heavy objects (Fig 3): Ours Rotations 23.96±3.16, TTF 0.98±0.08, Torque 1.84±0.24. Real, irregular objects (Fig 4): Ours Rotations 19.22±4.08, TTF 0.78±0.27, Torque 1.48±0.30.
- baselines beaten: Expert (privileged, upper bound), Periodic (action replay), NoAdapt (frozen ẑ at t=0), DR (domain-randomized robust policy, no privileged info), SysID (predicts e_t directly instead of z_t) — all defined and re-run by the authors (paper Sec 4 "Baselines"), not quoted from elsewhere.
- real robot? Allegro Hand, 20 trials/object x 6 objects per set (heavy-object set and irregular-object set), no success-rate threshold stated as a binary metric — reported as continuous Rotations/TTF/Torque, not a pass/fail rate.

## Limitations stated by the authors
"most of our failure cases in the real-world experiments are due to incorrect contact points which leads to unstable force closure"; fails on tiny objects (diameter < 4.0 cm) because fingers collide with each other; "more extreme and sophisticated shapes are also harder to manipulate... might be necessary to incorporate tactile or visual feedback"; task is single-axis (z) rotation, a simplification of full SO(3) reorientation; no real-world data used to improve the policy (Sec 6).

## Quotable claims (verbatim, with section)
- "we do not enforce any heuristic finger gaiting behaviour. Instead, a stable finger gaiting behaviour emerges from the energy constraints and the penalty on deviation from the initial pose." (Sec 3.1)
- "Our approach shows the surprising effectiveness of using only proprioception sensory signals for adaptation to different objects, even without the usage of vision and tactile sensing." (Abstract)
- "We cannot directly deploy the learned policy π to the real world because we do not directly observe the vector e_t and hence we cannot compute the extrinsics z_t." (Sec 3.2)
- "The reward number in this repository are higher than what is reported in the paper. This is because we change the `reset` function order following LeggedGym instead of the one in IsaacGymEnvs." (code README, "Disclaimer")
