# sapien_2020 — SAPIEN: A SimulAted Part-based Interactive ENvironment (Xiang et al., CVPR 2020; arXiv 2003.08515)

sources: papers/md/sapien_2020.md [sha256 03aa9317] ; code/md/sapien_2020.md [commit 8c5643df]

## One-line contribution
A PhysX-based simulator built around the large-scale PartNet-Mobility dataset (2,346 articulated object models, 14,068 movable parts, 46 categories), pairing a robotics-oriented rigid-body engine and ROS-style controller interfaces with a customizable renderer, and demonstrating perception (part segmentation, motion recognition) and interaction (door-opening, drawer-pulling) benchmarks (Abstract, Secs. 3-4).

## Setting
- hand(s): **none.** SAPIEN's only manipulator asset in this paper is a **flying Kinova Gripper 3** [Campeau-Lecours et al.] — a 2-finger parallel gripper that "can move freely in the workspace" (Sec. 4.2, "Door-opening and Drawer-pulling") — used for both benchmark manipulation tasks. No dexterous or multi-fingered hand appears anywhere in the paper text. The code parse (current `haosulab/SAPIEN` repo, depth-3, assets pruned) shows no hand-asset directory names; the only "shadow" string hits are shadow-mapping shader files (`shadow.glsl`, `shadow.vert`, `shadow.rmiss`), not a Shadow Hand asset.
- arm: none named beyond the flying gripper itself (no arm — gripper has a free 6-DoF floating base, "a typical use case is to move the robot arm to a desired 6-DoF pose," Sec. 3.1, is a generic controller-API example, not the door/drawer task's own embodiment). single/bimanual: single end-effector.
- simulator / physics: **NVIDIA PhysX 4.1**, CPU-based (no GPU-parallel rigid-body simulation claimed in this paper — that PhysX capability is a later addition used by SAPIEN's successors ManiSkill2/ManiSkill3, not described here): "We choose PhysX 4.1 to provide rigid body kinematics and dynamics simulation, since it is open-source, simplistic, and provides functionalities designed for robotics" (Sec. 3.1). Three body-joint systems offered: **kinematic joint system** (objects with parent-child relations, unaffected by small forces, for "very heavy objects"), **dynamic joint system** (PhysX joints driving rigid bodies toward constraints, for "complicated objects that do not require accurate control"), and **PhysX articulation** ("a system specifically designed for robot simulation. It natively supports accurate force control, P-D control and inverse dynamics with the cost of relatively low speed," Sec. 3.1). Both synchronous (client-stepped, for RL) and asynchronous (independently-running, TCP/IP client-server, for sim-to-real code parity) simulation modes are supported (Sec. 3.1).
- observation: task-dependent; door/drawer tasks provide point clouds, normal maps, and segmentation masks from three fixed cameras (left/right/front), plus self-state (6-DoF pose) (Sec. 4.2); three state-representation variants compared: raw-exp (positions/velocities of all parts), mobility-exp (motion-axis pose + normal + target joint angle/velocity), visual-exp (RGB-D + segmentation mask).
- action space: "In the lowest level control, forces and torques are directly applied on joints, similar to OpenAI Gym" (Sec. 3.1); higher levels add joint-space and Cartesian-space control APIs, and MoveIt-based motion planning. The door/drawer RL task uses a velocity controller on the flying gripper.
- objects / data: **PartNet-Mobility dataset** — "over 14K articulated parts over 2,346 object models from 46 common indoor object categories" (Sec. 3.2, Table 3 gives per-category #models/#movable-parts, e.g. Cabinet 345 models / 1,174 parts, Chair 80/1,235, Table 101/420). Motion types annotated: hinge (rotation), slider (translation), screw (combined, with optional axis coupling), each with annotated motion limits (Sec. 3.2). Assets loaded via URDF; "for accurate simulation of contact, we decompose meshes into convex parts" (Sec. 3.2).

## Physics
- **Contact model**: rigid, convex. Collision meshes are explicitly convex-decomposed for accuracy: "For accurate simulation of contact, we decompose meshes into convex parts" (Sec. 3.2, SAPIEN Asset Loader). No numeric contact-point-per-pair count is given.
- **Solver**: PhysX 4.1's internal rigid-body solver is used as-is; the paper gives no LCP/PGS/TGS name or iteration count for it. The only solver-adjacent distinction made is functional, not numerical: PhysX articulation trades speed for accuracy ("natively supports accurate force control, P-D control and inverse dynamics with the cost of relatively low speed," Sec. 3.1) versus the faster but less physically faithful kinematic/dynamic joint systems.
- **Differentiable contacts**: not discussed or claimed anywhere in the paper.
- **Default timestep / substeps**: not stated numerically anywhere in the text.
- **Friction model**: not specified quantitatively; physical properties including friction are "randomize[d] or manually set ... to appropriate ranges" per object (Sec. 3.2), with no coefficient values or friction-cone/pyramid detail given. The door/drawer task states "all dynamics properties except gravity, e.g., contact, friction, and damping, are simulated in our environment" (Sec. 4.2) but gives no numbers.
- **Penetration handling / exposure**: not discussed as a named metric, resolution mechanism, or exposed quantity anywhere in the paper.
- **GPU or CPU**: CPU physics (PhysX 4.1, no GPU rigid-body claim in this paper); GPU used only for rendering (OpenGL 4.5/GLSL rasterization by default, or an optional NVIDIA OptiX ray-traced path for higher-fidelity images at higher cost, Sec. 3.3).
- **Throughput** (Sec. 3.4, "Profiling Analysis," exact): "Our SAPIEN engine can run at about **5000Hz** on the manipulation task we will describe in Sec. 4.2 and can render at about **700Hz** with OpenGL mode." Hardware: "a laptop with Ubuntu 18.04, on **2.2 GHz Intel i7-8750 CPU** and an **Nvidia GeForce RTX 2070 GPU**." No parallel-environment count is given — this is a single-instance CPU-physics throughput number, not a batched/vectorized figure (SAPIEN 2020 predates the GPU-parallel-env paradigm used by its own later ManiSkill2/3 descendants).
- **Robot hands shipped as assets**: none. Only the flying Kinova Gripper 3 (2-finger parallel gripper) appears as a manipulator asset in this paper; the code parse (assets pruned) shows no hand-asset names.

## Evaluation
- metrics: door-opening — final joint angle achieved (degrees), success defined implicitly by "mov[ing] a given joint ... through 90% of its motion range" for the general success criterion (Sec. 4.2, first mention), though the RL results table (Table 6) reports raw "Final Angle Degree" for doors rather than a binary rate; drawer-pulling — success rate of "opening 80% of joint limits" (Sec. 4.2, RL results paragraph; note the two success thresholds quoted in the paper, 90% in the general task description and 80% in the RL-evaluation paragraph, are not reconciled in the text — flagged as an internal inconsistency). Vision benchmarks (Sec. 4.1, Table 1) use per-part mAP for movable-part instance segmentation across four algorithm/input-modality combinations (Mask-RCNN RGB, Mask-RCNN RGB-D, PartNet InsSeg XYZ, PartNet InsSeg XYZRGB).
- headline numbers: heuristic door-opening (PBVS-based edge tracking) = **81.8%** success rate; heuristic drawer-pulling (ground-truth-segmentation grasp + velocity control to joint limit) = **95.3%** success rate (Sec. 4.2, "Heuristic Based Manipulation"). RL (SAC) results (Table 6, train on {2,4,8,16} doors/drawers, test on held-out): door final-angle-degree test scores range from ~14.7 deg (raw-exp, 2 training doors) up to 32.8 deg (mobility-exp, 16 training doors); drawer success-rate test scores range 0.59-0.69 depending on representation and training-set size; "mobility-exp gives the best performance" overall (Sec. 4.2). Vision: overall segmentation mAP across all categories (Table 1, "All" column) = Mask-RCNN RGB 53.0%, Mask-RCNN RGB-D 52.8%, PartNet InsSeg XYZ 36.1%, PartNet InsSeg XYZRGB 37.1%.
- baselines beaten: RL agents are compared against each other's input representations (raw/mobility/visual), not against an external baseline; the heuristic pipeline is presented alongside RL rather than as a baseline to beat.
- real robot? no.

## Limitations stated by the authors
- The RL agent's generalization is described as failing to scale cleanly: "For door-opening, the RL agent tends to overfit the training objects, as when the number of training objects grows, the performance drops [on train]. However, training on more scenarios will improve the generalization capability with increased test performance" (Sec. 4.2) — a nuanced train/test tradeoff, not a clean win.
- Vision representation limitation: for drawer-opening, "the camera is fixed during interaction ... the visual features remain almost the same every time step from the front view, so it provides little information about state changing," causing visual-exp to underperform raw-exp for drawers (Sec. 4.2).
- "RL-based approaches fail to perform well on all the objects [despite the tasks not being hard for heuristic algorithms]. Future works may study how to enhance the transferability and efficiency of RL on the tasks" (Sec. 4.2, closing paragraph).
- Implicit success-threshold inconsistency between the general task description (90% of motion range) and the RL evaluation protocol (80% of joint limits for drawers) — not reconciled or flagged by the authors themselves, but worth noting for the survey.
- The kinematic and dynamic joint systems are explicitly framed as accuracy-vs-speed compromises rather than general-purpose solutions: kinematic bodies "do not respond to external forces," dynamic joints are only "suitable for simulating complicated objects that do not require accurate control" (Sec. 3.1, Appendix C).

## Notes for the survey (which sections this feeds; contradictions with other notes)
- Simulator lineage section: SAPIEN 2020 is the CPU-PhysX-4.1 ancestor of the ManiSkill line (see maniskill2_2023 note); it ships **no dexterous hand and no GPU-parallel physics** in this paper — both capabilities (multi-fingered hand assets and GPU-batched environments) are additions made in later SAPIEN/ManiSkill releases, not present here. Do not attribute Allegro/Ability/Inspire hand support or GPU throughput numbers to this 2020 paper; route those to maniskill2_2023 or maniskill3_2024 instead.
- Throughput number (5000 Hz engine, 700 Hz OpenGL render, single CPU-GPU laptop, no parallel envs) is a single-instance figure from a different era/paradigm than the GPU-batched FPS numbers in isaacgym_2021, brax_2021, mujoco_playground_2025, maniskill3_2024 — do not average or directly compare without noting the protocol gap (single-instance real-time-factor vs. batched-env-steps/sec).
- Convex mesh decomposition for contact accuracy (Sec. 3.2) is consistent with the broader convex-contact theme running through this note batch (mujoco_2012, mujoco_convex_contact_2014) but is a distinct engine (PhysX vs. MuJoCo) with its own solver internals not detailed in this paper.
- Success-threshold inconsistency (90% vs. 80% of joint-limit motion) flagged above should be double-checked against the original PDF table/figure before being quoted precisely in the survey.
- PartNet-Mobility's scale (2,346 models / 14,068 parts / 46 categories, Table 3) is this paper's most durable, reusable contribution for the survey's "object/asset datasets" section, independent of the physics/hand questions this note batch otherwise focuses on.
