# visual_dexterity_2022 — Visual Dexterity: In-Hand Reorientation of Novel and Complex Object Shapes (Chen et al., Science Robotics 2023)

sources: papers/md/visual_dexterity_2022.md [sha256 b35ada5d] ; code/md/visual_dexterity_2022.md [commit ad9634e9]

## One-line contribution
Teacher-student distillation to a real-time (12 Hz), depth-point-cloud-only policy on an open-source, sub-$5,000 D'Claw hand that reorients hundreds of objects to arbitrary SO(3) targets with the hand facing **downward** against gravity, both resting on a table and (with 4 fingers) fully in the air, without any object-specific pose estimator (Summary; Introduction; Results).

## Setting
- hand(s): D'Claw, open-source and low-cost. Three-fingered (9 DoF) and a modified four-fingered (12 DoF) version, "nine and twelve degrees of freedom (DoFs), respectively" (Results). Hands are "fixed on an 80/20 aluminum frame" (Supplementary Methods/Real-world setup) — no arm, single hand, not bimanual. Code default asset: `robot: 'dclaw_4f'` (code/md `dexenv/conf/task/dclaw.yaml`).
  - Hand orientation, quoted: "performing reorientation under the assumption that the hand is below the object (upwards facing hand configuration) ... instead of the hand holding the object from the top (downwards facing hand configuration) is much easier ... With a downward-facing hand, the hand must manipulate the object while simultaneously counteracting gravity" (Introduction). All experiments use the downward-facing configuration; both the on-table and in-air conditions are downward-facing — the paper never tests upward-facing.
  - "We use Isaac Gym (41) as the rigid body physics simulator. We train all the policies on a table-top setup: hands face downward with a supporting table" (Materials and Method/Simulation setup).
- simulator / physics: Isaac Gym, PhysX (`dexenv/conf/task/isaacgym_config.yaml`: `physics_engine: physx`). Sim `dt: 0.01667` (60 Hz), `substeps: 2`; control at `controlFrequencyInv: 5` → 12 Hz, matching "runs in real-time at a control frequency of 12 Hz" (Results). PhysX: `solver_type 1, num_position_iterations 8, num_velocity_iterations 0, contact_offset 0.002, rest_offset 0.0, max_depenetration_velocity 1000.0, default_buffer_size_multiplier 5.0`.
  - Teacher # of envs: Table S1 states "32000"; the shipped default teacher config `dexenv/conf/dclaw.yaml` sets `alg.num_envs: 8000` (its parent `hand_default.yaml` sets 16384) — MISMATCH between paper's stated env count and the released training config. `train_rollout_steps: 8` (hand_default.yaml) × 8000 envs = 64000, which does match Table S1's stated batch size of 64000, so the batch-size number is reproducible even though the env count is not.
  - GPU: RTX 3090 for teacher, Tesla V100 for student (Supplementary Methods/Training setup); total compute <400 GPU-hours, "<$15.6" of V100 electricity (Supplementary Methods/Compute cost).
- observation:
  - **Teacher (privileged)**: o^E_t ∈ R^(19G+21), "joint positions (R^3G) and velocities (R^3G), fingertip pose (R^7G) and velocities (R^6G), object pose (R^7) and velocity (R^6), target orientation ... (R^4), and the rotation difference between current and target object orientation ... (R^4)" where G = number of fingers (Supplementary Methods/Training setup). Code `dexenv/envs/dclaw_base.py::compute_full_observations` concatenates `scaled_dof_pos, dof_vel, object_pose, object_linvel, object_angvel, goal_rot, quat_dist, fingertip_state (pos+quat+vel per finger), actions` — matches the paper term for term.
  - **Student (depth-only)**: point cloud P_t = P^s_t ∪ P^g: scene point cloud (camera depth + FK-generated hand-link point cloud) unioned with the goal object's point cloud in the target orientation. "Since the sim-to-real gap for depth data is less pronounced than RGB data, we only use the depth images provided by the camera along with readings from joint encoders" (Student policy — imitation learning from depth observations). Real-world observation: "the joint positions of each motor in the manipulator and the depth image from a RealSense camera" (Real-world deployment). No object pose, no object/fingertip velocities, no privileged state of any kind reaches the student.
  - Two-stage student point-cloud construction in code: Stage 1 synthetic/complete PC sampled directly from CAD meshes, `dexenv/envs/dclaw_fptd.py::compute_ptd_observations` (`hand_cad_ptd`, `obj_cad_ptd`, no rendering, no occlusion). Stage 2 rendered/occluded PC, `dexenv/envs/dclaw_rptd.py::compute_ptd_observations` (`self.ptd_cam.get_point_cloud`, occluded by fingers, plus FK robot cloud).
  - Teacher gets no object-shape information at all: "inputs to the teacher policy have no information about object shape, yet it could reorient diverse and new objects" (Discussion).
- action space: relative joint-position targets a_t ∈ R^(3G) at 12 Hz through position controllers, EMA-smoothed with α=0.8: q_{t+1}^tgt = q_t + ā_t (Materials and Method/Action space). Code: `useRelativeControl: True`, `action_ema: 0.8`, `controlFrequencyInv: 5`, `dofSpeedScale: 24` (`dclaw.yaml`).
- objects / data: Big dataset B = 150 training objects "from internet sources such as Google Scanned Objects" (Supplementary Methods/Object datasets); Small dataset S = 12 ContactDB objects, no shape overlap with B, used for OOD generalization (5 of the 12 also used for real-world OOD trials). Longest bounding-box side scaled to [0.095, 0.165] m; per-object mass sampled [0.03, 0.18] kg before domain randomization (Supplementary Methods/Object dataset preprocessing); V-HACD convex decomposition at resolution 100,000.

## Method
- paradigm: two-stage teacher-student distillation (RL → IL). Teacher: PPO with privileged low-dimensional state. Student: DAgger imitation from point clouds, itself split into Stage 1 (synthetic PC) and a Stage 2 fine-tune (rendered PC) — "Teacher-student²" (Materials and Method; Fig 6).
- reward or loss:
  - **Paper.** The actual typeset equations (Eq. 1-8) are embedded images in the PDF and were **not recoverable as text** — the source markdown literally reads "The reward terms are mathematically expressed as:" followed by blank lines. What is recoverable is the verbal description plus Table S1's numeric constants:
    - Eq 1, sparse success term, coefficient **c1 = 800** ("the success criteria for the task ... only provides sparse reward supervision").
    - Eq 2, dense orientation term, **c2 = 1**: "a dense reward term that encourages minimization of the distance (Δθt) between the agent's current and target orientation."
    - Eq 3, fingertip-distance penalty, **c3 = -1**: "penalize the agent for moving fingertips far away from the object. Without this term, fingers barely made any contact with the object during training."
    - Eq 4, energy penalty, **c4 = -20**: "penalize the agent for expending energy."
    - Eq 5, too-far-from-hand penalty + termination, **c5 = -100**: "penalize the agent ... for pushing the object too far from the robot's hand ... the episode is also terminated."
    - Eq 7 (in-air variant), table-contact penalty, **c6 = -1**: "a penalty for the contact between the object and table" to discourage relying on the table.
    - Eq 8 (in-air variant), **c7 = -2**: "a penalty for using the penultimate joint instead of the fingertip for reorientation ... not critical, it results in more natural-looking behaviors."
    - Table S1 thresholds/constants: ϵθ = 0.4 rad, p̄ = 0.15, p̄z = 0.16, ¯̇q = 0.25, v̄ = 0.04, ω̄ = 0.5, c_d = 15.
  - **Code** (`dexenv/envs/rewards.py::compute_reward`/`compute_dclaw_reward`, invoked from `dexenv/envs/dclaw_base.py::compute_reward`, weights from `dexenv/conf/task/dclaw.yaml` → `env.rew`):
    ```
    ftip_reward = ftip_dist_mean * ftip_reward_scale        # ftipRewardScale: -1.
    rot_rew = 1.0/(abs_rot_dist + rot_eps) * rot_reward_scale # rotRewardScale: 1.0, rotEps: 0.1
    reward_terms['energy_reward'] = -energy_cost * energy_scale  # energy_scale: 20, clip_energy_reward True, energy_upper_bound: 10
    if penalize_tb_contact:
        reward_terms['tb_contact_reward'] = -in_contact.float() * tb_cf_scale  # pen_tb_contact: False (default), tb_cf_scale: 1
    reward = sum(reward_terms.values())
    reward = where(goal_reach, reward + reach_goal_bonus, reward)   # reachGoalBonus: 800
    reward = where(fall_envs,  reward + fall_penalty,  reward)      # fallPenalty: -100, fallDistance: 0.24 (dclaw.yaml) / 0.15 (hand_default.yaml)
    ```
    `goal_reach` requires `abs_rot_dist <= success_tolerance(=0.4)` AND joint-velocity/action-norm/object-linvel/object-angvel all under threshold — this is the paper's three-part success criterion (orientation + finger motion + object motion), not a single term.
  - **Matches**: reachGoalBonus 800 = c1; rotRewardScale 1.0 = c2; ftipRewardScale -1. = c3; energy_scale 20 (applied with a minus sign) = c4; fallPenalty -100 = c5; tb_cf_scale 1 applied with an explicit minus sign = c6 (-1) effectively.
  - **Mismatches found**: (1) no penultimate-joint penalty (paper Eq 8, c7 = -2) exists anywhere in `rewards.py` or the parsed `env.rew` config keys. (2) `fallDistance` differs across the two shipped config files that both apply to the teacher: `dclaw.yaml` = 0.24 vs `hand_default.yaml` override = 0.15 — only the latter matches Table S1's p̄ = 0.15. (3) config carries `distRewardScale: -10.0`, which never appears inside `compute_reward`'s body — a dead/legacy key. (4) `pen_tb_contact` defaults to `False` in the released `dclaw.yaml`; no separate shipped config with it set `True` (the in-air/Eq-7 variant) appears in the parsed files.
- domain randomization: Table S3 (paper) — state obs +N(-0.002,0.002); action +N(0,0.05); joint stiffness/damping ×U(0.8,1.2); link mass ×U(0.8,1.2); robot/object friction U(0.24,1.6); table friction U(0.05,1.0); restitution U(0.0,1.0); object size scale U(0.95,1.05); object mass U(0.009,0.324) kg; disturbance force F_d^o = c_d·m_o (c_d=15), applied w.p. 0.2, direction uniform in SO(3) (Table S1; Robust policy learning). Code `dexenv/conf/task/task/obj_rand.yaml` scales the *base* per-material values in `dclaw.yaml`: hand/object friction base 0.8 × scale [0.3,2.0] → [0.24,1.6] (matches); object mass base [0.03,0.18] kg × scale [0.3,1.8] → [0.009,0.324] kg (matches exactly); restitution base 0.5 × scale [0,2] → [0,1.0] (matches); object scale [0.95,1.05] (direct match); stiffness/damping/link-mass [0.8,1.2] (direct match). **Mismatch**: table friction base `tableInitialFriction: 0.5` × code scale [0.01,2] → [0.005,1.0] vs paper's stated [0.05,1.0] — factor-of-10 discrepancy at the lower bound. Code also randomizes `sim_params.gravity` ±[0,0.4] additive (`obj_rand.yaml`), a term absent from the paper's Table S3.
- key trick(s): two-stage student training, synthetic-complete-PC pretrain then rendered-occluded-PC fine-tune, "makes training 5× times faster" overall / "7× speedup" for Stage 1 alone (Introduction; Need for two-stage student learning); sparse 3D CNN via the Minkowski Engine for 12 Hz point-cloud inference, plus a GRU since the student has no direct object-velocity signal; CMA-ES black-box system ID of joint stiffness/damping/velocity-limit against real step/sine-wave responses (Identification of robot dynamics); soft elastomer fingertips over a rigid 3D-printed skeleton to raise friction/compliance (Reorientation using a three-fingered manipulator).
- contact / penetration handling: not addressed as an interpenetration term in either source. The only contact-related reward term penalizes **object-table contact** in the in-air variant (Eq 7 / `pen_tb_contact`+`tb_cf_scale`), which is a task-shaping term (discourage using the table), not a penetration penalty. The only "penetration" handling anywhere is the PhysX solver defaults (`contact_offset: 0.002`, `rest_offset: 0.0`, `max_depenetration_velocity: 1000.0`) — solver settings, not a measured or learned quantity.

## Evaluation
- metrics: success rate at orientation-error thresholds of 0.4 rad (22.9°) and 0.8 rad (45.8°) (Table 1), following "the success threshold used in previous work (8)". Orientation error: "the distance between the goal and the object's orientation when the controller predicts it has reached the goal and stops," tracked with an OptiTrack motion-capture system, used only for evaluation (Results). 95% CIs are "bias-corrected and accelerated (BCa) bootstrap" (Table 1). Also: median manipulation time (Fig 4D) and per-object dropping rate (in-air only).
- headline numbers:
  - Table 1 (on table, hand downward-facing), ≤0.4 rad: rigid fingertips train 81% [73,90]%, test(OOD) 45% [32,58]%; soft fingertips train 79% [71,86]%, test 55% [44,62]%; simulation train 96% [94,97]%, test 85% [82,88]%. ≤0.8 rad: rigid 95%/75%, soft 98%/86%, sim 98%/87%.
  - In-air: only the 4-fingered hand succeeds at in-air reorientation, the 3-fingered hand does not (Fig 4B). Contact-penalty ablation: "policies trained with the [table-contact] penalty achieved 87% in-air success, as those without achieved only 4.1%" (Supplementary Discussion/Ablation on the reward terms). Median reorientation time <7 s across full SO(3) in the air (Results). Dropping rate: truck (in-distribution) 23% real / ~20% sim; duck (OOD) 56% real (Results).
  - Comparison to prior work (duck object, Comparison to prior works): prior work (ref 23) reports 60% (3/5) success within 0.1 rad, quasi-static, >70 s, only 2 of 3 SO(3) axes, using a dedicated pose tracker (<2° error). This paper, "if we assume perfect stopping criteria," reports 71% success in sim in the full SO(3) space, ~7 s.
  - Stricter-threshold analysis (Discussion on precise manipulation, 1200 sim tests / 12 objects): 72.3% success @0.4 rad, 25.9% @0.1 rad using the learned stop predictor; with ground-truth stopping, 80.9%/67.4% at 0.4/0.1 rad.
- baselines beaten: none re-run; only an approximate, explicitly-caveated comparison to ref (23) (duck) and to OpenAI's cube work (8) (upward-facing hand, single object, 3 RGB cameras + mocap, no shape generalization, no learned stopping) — "a strictly fair comparison with prior work is not possible" (Comparison to prior works).
- real robot? Yes. D'Claw 3-finger (9 DoF) and 4-finger (12 DoF); 12 evaluation objects (7 train / 5 OOD), each tested 20 times per real-world condition (Table 1 caption, Results); in-air real-world error distribution built from 20 non-dropping trials per object (Fig 4C caption); dropping-rate trial totals not stated.

## Limitations stated by the authors
- 12 Hz control may be too slow to react before an object slips: "it might be challenging to determine when the object is slipping from the fingers in real-time using visual feedback at 12Hz" (Limitations and Possible Extensions).
- No explicit contact/force/slip sensing: "the robot relies purely on occluded vision observations to infer contacts."
- Stopping/rotational-distance prediction, not action quality, is the dominant source of imprecision below 0.4 rad (Limitations; Discussion on precise manipulation).
- D'Claw hardware called "suboptimal": hemispherical fingertip shape, 3-DoF fingers; soft-fingertip iteration was manual and "time-consuming."
- Remaining sim-to-real gap acknowledged generally; real-world reorientation times longer than simulation (Fig 4D), attributed to real contact dynamics differing from the simulator.

## Notes for the survey
- Feeds the "downward-facing hand" subsection directly and unambiguously: every reported condition (on-table and in-air) is downward-facing; the hand is fixed to a frame, not arm-mounted; object is placed on a table or "handed over by a human to the robot" (Results).
- Canonical teacher-student example where the teacher literally gets no shape information — useful contrast point for papers that give the teacher object geometry or a shape latent.
- The reward equations themselves are unrecoverable from this PDF conversion (rendered as images); any quoted "Eq 1-8" content here is reconstructed from surrounding prose + Table S1 constants, not read off the formulas — flag this if another pass tries to re-derive the functional form.
- Success/stopping is trained as a three-part criterion (orientation + finger-motion + object-motion thresholds) baked directly into the reward and re-used at test time via a learned Δθ predictor head — contrast with papers (e.g., OpenAI's cube work, cited here as ref 8) that never train a stop signal at all.
- Multiple paper-vs-code mismatches recorded above (teacher env count 32000 vs 8000/16384; fallDistance 0.24 vs 0.15 across two shipped configs; missing penultimate-joint penalty; dead `distRewardScale` key; table-friction lower bound 0.05 vs 0.005) — worth a footnote if this paper's numbers are used as a hard reproducibility reference elsewhere in the survey.
- Reproducibility: code, Docker image, pretrained teacher and student (Stage 2) checkpoints, and robot/object assets are all released (GitHub `Improbable-AI/dexenv`, commit ad9634e9; HuggingFace dataset `taochenshh/dexenv` for assets and pretrained weights). Student Stage 1 checkpoint is not separately advertised in the README's pretrained-model section.
