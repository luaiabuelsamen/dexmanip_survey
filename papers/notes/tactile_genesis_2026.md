# tactile_genesis_2026 — Tactile Genesis: Exploring Tactile Sensors at Scale for Learning Dexterous Tasks (Chung, Yamazaki, Patel, Duburcq, Qiao, Fragkiadaki, Nayebi; CMU / Genesis AI, arXiv 2026)

sources: papers/md/tactile_genesis_2026.md [e2d96852] ; code/md/tactile_genesis_2026.md [3023bcd2]

## One-line contribution
A GPU-parallel tactile-sensor platform inside the Genesis World physics engine exposing seven sensor abstractions (binary contact, contact depth, per-taxel kinematic force/torque, elastomer marker displacement, proximity, temperature, contact audio) under one interface, scaling past 20,000 parallel environments and 1,000+ taxels/hand, used to ablate which tactile abstraction a dexterous policy actually needs (Abstract).

## Setting
- hand(s): real and simulated XHand1 is the primary hand for the 3 dexterous tasks and sim-to-real check (Fig. 1b, Sec. 3.2, App. C); sensors are also demonstrated on Allegro, Inspire, Franka (gripper), Wuji, SharpaWave, and Shadow hands as "supports any robot" examples (Fig. 1d).
- simulator / physics: built into Genesis World (the open-source physics simulator that is `genesis_2024` in this corpus), which the paper treats as the host rigid-body engine; Tactile Genesis is the tactile-sensor layer added on top (Sec. 3.1).
- observation: 7 sensor types (Table 1) — Surface Distance Probe (shortest distance to tracked-object surface, pre-contact), Contact Depth Probe (raw depth from SDF or raycasting/sphere-triangle), Contact Probe (binarized depth with hysteresis), Kinematic Taxel (per-taxel 6-axis force/torque from SDF depth + contact normal + relative velocity, no substrate model), Proximity Taxel (point-cloud-based sensed mass within a radius, force/torque from object velocities), Elastomer Taxel (marker displacement modeling the sensing surface as an elastomer), Temperature Grid (°C over a voxelized link — "the first of its kind in robot learning physics simulation platforms"), Contact Audio (K synthesized vibration samples/step).
- action space / tasks: teacher-student distillation on three dexterous XHand1 tasks — `in_palm_rotate`, `in_hand_repose`, `screwdriver` (Sec. 3.2, Fig. 7).

## Physics block
- contact model: the tactile sensors are read-only queries on top of Genesis's own rigid-body contact/collision pipeline (Genesis's contact model itself is documented in the `genesis_2024` note — softened/regularized rigid contact akin to MuJoCo's, per that repo's own README "MuJoCo: Reference for rigid body dynamics"). Two independent penetration-depth backends are implemented directly on the collision geometry (App. A.1): **`sdf`** — queries the rigid solver's analytic per-geometry signed-distance field, d^sdf_j = ... (depth positive when penetrating), contact normal = SDF gradient at the winning geometry; default backend, "fast and exact on primitives." **`raycast`** — walks a per-frame BVH over the rigid-body collision meshes (shared with Genesis's raycaster sensor), running a sphere-triangle closest-point test (penetration = R_j − dist) and a ray-triangle test along −a_j (penetration = R_j − hit_distance), taking the deeper of the two; "handles arbitrary triangle meshes uniformly and is preferable when the scene mixes many small or thin objects." The two backends "produce equivalent depths to leading order for smooth meshes and differ at sharp features" (App. A.1).
- solver and iterations: no new contact solver — Genesis's existing rigid-body solver runs unmodified; the tactile layer's own "solve" is a set of vectorized read-out kernels (contact/depth/force probe queries, elastomer dilation kernel, temperature diffusion) rather than an iterative complementarity solve.
- differentiability: not discussed/not claimed in this paper (Genesis itself supports autodiff per its own repo, but this paper does not exercise or discuss gradients through the tactile sensors).
- timestep: not stated numerically; sensors are queried per simulation step of the host Genesis engine, whose own default step is not given here.
- friction model: not modeled explicitly by the tactile layer; the Kinematic Taxel force/torque estimate is derived from SDF depth, contact normal, and relative linear/angular velocity of the object (Table 1; App. A.5), not from an explicit Coulomb friction law — friction physics remains Genesis's own rigid-contact responsibility, and the taxel is a *read-out* of the resulting kinematics/force, not an independent friction model.
- how penetration is resolved / is depth exposed: **exposed directly and used as the core tactile signal**, not merely an artifact to be minimized. `ContactDepthProbe` "reports the raw measured penetration depth d^m_bj at each probe" (App. A.4). `ContactProbe` binarizes it with Schmitt hysteresis: contact-on threshold η_on = 5×10⁻⁴ m, release threshold η_off = 2×10⁻⁴ m in the noisy condition (App. A.3, Table 12). This is a rare case in the corpus where "penetration depth" is treated as the useful sensor output rather than a simulation-fidelity error to be driven to zero.
- GPU or CPU: GPU. All Tactile Genesis benchmarks in Fig. 3/4 were run on a single NVIDIA RTX A6000.
- throughput with the table and hardware: **Fig. 3** — sensor-type performance on a pyramid-of-10-cubes scene, 10×10 (100 taxel) resolution, 500 tracked point-cloud samples for Elastomer/Proximity: scales past 16,384 parallel environments with total throughput of 150,000 environment-steps/sec; adding more sensors or noise costs "small overhead (-10% FPS) for most sensors," while the Elastomer sensor slows more (-22% FPS) since it computes per-sensor local displacement effects. **Fig. 4a/b** — with environments fixed at 1024, sensors "retain low GPU memory and high throughput up to over 10,000 taxels per hand"; the Elastomer sensor scales worse with point-cloud size (tracks every contacted point) but point clouds >~6000 are "not typically needed for dexterous tasks." **Fig. 4c** — temperature sensor achieves "80% of the no-sensor-baseline throughput FPS with 5 active sensors with 8 voxels each." **Comparisons to prior tactile simulators (Fig. 4d-f, all vs. RTX A6000; neither Tacmap nor HydroShear reports its own GPU or numbers beyond 1024 envs)**: vs. **Tacmap** (built on SharpaWave, >1,000 tactile pixels/fingertip) — "our FPS for 10,000 taxels across 5 ContactDepthProbe sensors is 20× Tacmap's and uses 7× less GPU memory per environment." vs. **HydroShear** (per-step time for one 7×9 = 35-taxel elastomer sensor on a robot arm) — Tactile Genesis rolls out a trained hand policy with five 5×4 = 100-taxel elastomer sensors and achieves "1.6× HydroShear's [FPS] at 1024 envs." vs. **TacSL** (Isaac-Lab-integrated, penalty-based tactile force field, compared at 10×10 and 100×100 taxels) — "we consistently achieve around 3× higher throughput" and "can run at 16k envs without running out of memory" where TacSL cannot. Overall: "Tactile Genesis improves throughput by up to 20× at matched sensor configurations and reduces GPU memory per environment by roughly 5×... with the gap widening as the number of parallel environments grows" (Sec. 3.1), attributed to (1) probe/environment-vectorized kernels launched once per batch, (2) BVH-accelerated mesh/point-cloud queries, (3) 2D FFT with separable kernels replacing dense convolution for the elastomer dilation and crosstalk model (Sec. 3.1).

## Tactile-specific fields
- signal simulated: seven distinct signal types (Table 1) spanning geometry-only (surface distance, contact depth, binary contact), force/torque (kinematic taxel, proximity taxel), a deformable-substrate proxy (elastomer marker displacement), and two non-mechanical modalities novel to this platform — voxelized temperature and synthesized contact/actuation audio.
- real sensor calibrated against: the real XHand1's fingertip sensor (aggregate contact-pressure SDK output) for the sim-to-real deployment (App. C); the ElastomerTaxel is validated against a real GelSight under dilation and shear (Fig. 2), building on HydroShear and Yin et al.'s ReSkin-calibrated Proximity approach, both stated as "validated to transfer to a real GelSight Mini on a robot gripper and ReSkin on the Allegro hand" in the cited prior work (Sec. 3.1).
- reported sim-to-real error, with its table:
  - **ElastomerTaxel marker-displacement, relative RMSE (Fig. 2)**: dilation — FOTS 0.514, HydroShear 0.403, **Ours 0.329** (best); shear — FOTS 0.210, HydroShear 0.217, **Ours 0.174** (best). Each simulator's parameters were optimized to match the real GelSight image before comparison.
  - **Sim-to-real policy deployment (App. C)**: the real XHand1 SDK exposes only an aggregate per-fingertip contact-pressure signal (not individual raw taxel values, since their exact position/response is undocumented); the sim `agg_force`/`agg_bool` observation was built to match this. Deploying the `in_palm_rotate` policy on the real XHand1 achieves 1-2 consecutive successful rotations before dropping the object, "which matches the success rate of the fingertip agg_bool student in simulation, the observation type that most closely mirrors the real fingertip readout" (App. C, Sec. 4.1 "Sim-to-real validation") — i.e. the reported "error" is a matched success-count rather than a continuous metric, because only the aggregated signal is comparable across sim and real.

## Evaluation
- metrics: task success/consecutive-successes count for the three dexterous tasks (Fig. 7); relative RMSE for marker-displacement fidelity (Fig. 2); throughput in environment-steps/sec and GPU memory (Fig. 3-4).
- headline numbers: "Proprioception alone is insufficient on every task" — the `none` baseline trails every tactile student, including the cheapest binary-contact variant (Sec. 4.1). Placement dominates sensor type: fingertip-only coverage "trails whole-hand coverage by a large margin" on `in_palm_rotate`; adding palm + proximal-phalange taxels closes most of the remaining gap to the privileged teacher (Sec. 4.1). Per-taxel force/torque is the best default: on `in_hand_repose` (near-continuous contact, incipient-slip failure mode) the `force_torque` student "is best and clearly separates from the binary and depth variants"; aggregated across tasks, "per-taxel force_torque matches or outperforms every other type" (Sec. 4.1). Elastomer displacement underperforms force/torque on both `in_palm_rotate` and `in_hand_repose`, attributed to marker displacement conflating adjacent dilation and local shear (Sec. 4.1). On `screwdriver`, all tactile signals perform similarly and none saturates the teacher.
- baselines beaten: a privileged-teacher / distilled-student comparison, not an external-method baseline; the "none" (proprioception-only) ablation is the weakest condition on every task.
- real robot? Yes — real XHand1, `in_palm_rotate` policy, matching the fingertip-only `agg_bool` simulated student's 1-2 consecutive-success rate (App. C).

## Limitations stated by the authors
- "Because our students distill from a privileged teacher, they inherit its strategy and are therefore bounded by it" (Sec. 5).
- "The real XHand1 SDK reports both a per-taxel raw pressure field and an aggregate contact pressure... but the exact position and response characteristics of each taxel are not documented, so we cannot register the raw field to our simulated probe layout" (App. C) — limits the sim-to-real check to the aggregate signal only.
- "Our teacher policy was deliberately not extensively tuned for robustness" (App. C), so the 1-2 consecutive-success real-world number should not be read as a ceiling on hardware performance.
- Scope is deliberately narrowed to "sensor implementation and observation-type comparison"; the authors flag a larger hands/tasks sweep with continued RL as future work (Sec. 5).

## Quotable claims (verbatim, with section)
- "Proprioception alone is insufficient on every task." (Sec. 4.1)
- "Sensor placement dominates sensor type: fingertip-only coverage trails whole-hand coverage by a wide margin." (Abstract)
- "We find that force/torque per taxel is consistently the most useful sensor type." (Abstract)
- "Tactile Genesis improves throughput by up to 20 times over previous tactile simulators." (Abstract)
- "This is encouraging for rigid-body tactile simulation, since substrate physics is exactly what is most expensive to model faithfully." (Sec. 5)

## Notes for the survey
- This is the most complete "physics block" source in the tactile trio: it is the only one of the three (`tacto_2020`, `taxim_2021`, `tactile_genesis_2026`) that exposes a formal penetration-depth query with two named backends (sdf/raycast) and a documented threshold value (5×10⁻⁴ m on-contact, 2×10⁻⁴ m release) — cite App. A.1-A.4 directly for that comparison cell.
- Table 1 (7 sensor types) is a useful taxonomy for the survey's "what does a tactile simulator expose" table, spanning geometry-only through force/torque to non-mechanical (temperature, audio) modalities in one interface — no other engine in this corpus offers that breadth.
- The Fig. 4 throughput comparisons (vs. Tacmap, HydroShear, TacSL) are self-reported and run only on the authors' own RTX A6000, since neither Tacmap nor HydroShear publishes hardware/scale details beyond 1024 environments (explicitly noted in the Fig. 4 caption) — flag this asymmetry if citing the "20×"/"3×" numbers as a controlled comparison.
- Genesis itself (the host engine) is `genesis_2024` in this corpus; when citing Tactile Genesis's throughput, note that the underlying rigid-body solver characteristics (contact model, differentiability, timestep) come from Genesis, not from this paper.
- Code md provenance: `code/md/tactile_genesis_2026.md` (157,969 chars) is the largest code manifest in this batch; not independently re-verified here since the paper's own Appendix A already gives closed-form definitions for every probe type that would otherwise require reading source.
