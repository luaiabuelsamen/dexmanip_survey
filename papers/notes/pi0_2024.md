# pi0_2024 — π0: A Vision-Language-Action Flow Model for General Robot Control (Black et al., arXiv 2024)

sources: papers/md/pi0_2024.md [sha256 fbdfba56] ; code/md/pi0_2024.md [commit 215abfb2]

## One-line contribution
A flow-matching action-expert bolted onto a 3B-parameter PaliGemma VLM, trained cross-embodiment on ~10,000 hours of robot data from 7 robot configurations (all arms with parallel-jaw grippers) plus OXE/Bridge/DROID, producing 50-step action chunks at up to 50 Hz for long, multi-stage manipulation tasks (laundry folding, box building, table bussing).

## Setting
- hand(s): none — every embodiment is an arm ending in a **parallel jaw gripper** (see embodiment block); no multi-fingered hand anywhere in pretraining or evaluation. arm: single (UR5e, Franka) and dual-arm (Bimanual UR5e, Bimanual Trossen/ALOHA-style, Bimanual ARX/AgileX) plus mobile-base bimanual (Mobile Trossen/ARX, Mobile Fibocom); bimanual: yes for most platforms (§V-C).
- simulator / physics: real robots only; no simulator or physics engine described in the paper. Aloha simulator exists in the code repo (`examples/aloha_sim/`) but is not the evaluation platform used for the paper's numbers.
- observation: **o**_t = [I¹_t,...,Iⁿ_t, ℓ_t, q_t] — 2 or 3 RGB images per robot, a language command token sequence, and a proprioceptive joint-angle vector q_t (§IV). Code confirms for ALOHA: `AlohaInputs`/`AlohaOutputs` docstring "images: dict[name, img] ... ; state: [14]; actions: [action_horizon, 14]" (code/md, `src/openpi/policies/aloha_policy.py`).
- action space: joint/gripper targets, chunked. Config vector q_t and action vectors a_t are zero-padded to the largest robot's dimensionality, "18 in our case, to accommodate two 6-DoF arms, 2 grippers, a mobile base, and a vertically actuated torso" (§V-A). Control rate: "control robots at frequencies of up to 50 Hz" (§I); 20 Hz for UR5e/Franka.
- objects / data: no fixed benchmark dataset of objects/trajectories — real-world household/kitchen objects (clothing, dishes, groceries, eggs, cardboard boxes); pretraining/fine-tuning data sizes are given in hours (see Learning block below), not object/trajectory counts.

## Method
- paradigm: VLA (vision-language-action), flow-matching action head on a pretrained VLM backbone; pretrain/post-train (fine-tune) recipe modeled on LLM pretraining/alignment (§V).
- reward or loss: no RL reward — imitation via conditional flow-matching regression loss (quoted below, Method block C).
- key trick(s): a second, smaller set of transformer weights ("action expert") for robot-specific tokens, interacting with the VLM only through self-attention (mixture-of-experts-style, §IV); blockwise causal attention mask with 3 blocks — [images+language], [state q_t], [noisy actions] — so the VLM-pretrained prefix cannot attend to new robot inputs (Appendix B); KV-caching of the observation prefix across the 10 flow-matching integration steps; timestep sampling from a shifted Beta distribution favoring noisier steps rather than uniform (Appendix B, Fig. 14).

## A. Embodiment block
- hand model + DoF + vendor: none of the 7 robot configurations use a multi-fingered hand. **UR5e**: "An arm with a parallel jaw gripper" (7-dim config/action, 2 cameras). **Bimanual UR5e**: two UR5e, 14-dim. **Franka**: 8-dim, 2 cameras (gripper type not further specified but Franka's standard 1-DoF parallel gripper is implied by the 8th dim). **Bimanual Trossen**: "two 6-DoF Trossen ViperX arms" ALOHA-style, 14-dim. **Bimanual ARX & bimanual AgileX**: two 6-DoF arms, 14-dim. **Mobile Trossen & mobile ARX**: Mobile ALOHA base, 14-dim config / 16-dim action (nonholonomic base +2). **Mobile Fibocom**: two 6-DoF ARX arms on a holonomic base, 14-dim config / 17-dim action (§V-C, Fig. 5).
- arm/floating base: single- and dual-arm fixed bases (UR5e, Bimanual UR5e, Franka, Bimanual Trossen, Bimanual ARX/AgileX) plus two mobile (floating) bases (Mobile Trossen/ARX nonholonomic, Mobile Fibocom holonomic) (§V-C).
- bimanual? yes for 5 of the 7 configurations (all but plain UR5e and Franka).
- simulator + version: not used for the paper's results (real robots only); "not stated" for a training simulator.
- physics engine: not stated (real-world only).
- sim timestep and control rate: no sim timestep; control rate up to 50 Hz, with UR5e/Franka run at 20 Hz (Appendix D).
- number of parallel envs: not applicable (real robots).
- GPU used and wall-clock training time: inference timed "on an NVIDIA GeForce RTX 4090 consumer-grade GPU" (Appendix D, Table I: image encoders 14 ms, observation forward pass 32 ms, 10× action forward pass 27 ms, total on-board 73 ms / off-board 86 ms). Training GPU/wall-clock not stated in the paper text (only step counts: 700k steps main model, 160k "parity" model, §VI-A).

## B. Learning block
- paradigm: imitation learning / behavior cloning via flow matching (a conditional generative model of actions), not RL; not diffusion-in-name but paper states flow matching "a variant of diffusion" (§IV, §II).
- algorithm and implementation: conditional flow matching with linear-Gaussian (optimal-transport) probability path, forward-Euler integration at inference, 10 integration steps (δ=0.1) (§IV). Backbone initialized from open-source PaliGemma [5]; action expert initialized from scratch (§IV). Non-VLM ablation "π0-small" (470M params) uses DistilBERT for language and a smaller pretrained ViT, and cross-attention (encoder-decoder style) rather than the MoE-style shared-attention design (Appendix C).
- teacher-student / distillation: none — direct imitation on collected robot demonstrations, no privileged-information distillation described.
- observation vector, item by item: images I¹_t..Iⁿ_t (2 or 3 per robot), language tokens ℓ_t, proprioceptive state q_t (joint angles), each image/state linearly projected into the transformer embedding space (§IV); code-side, `AlohaInputs`/`AlohaOutputs` (code/md `aloha_policy.py`) build `state: [14]` from qpos and route camera dict images by name.
- action space and whether position/torque/residual: joint-angle/gripper position targets ("absolute joint position" per real-robot code) chunked over H=50 future steps; code docstring for ALOHA, `examples/aloha_real/real_env.py`: "Action space: [left_arm_qpos (6), left_gripper_positions (1), normalized gripper position (0: close, 1: open), right_arm_qpos (6), right_gripper positions (1)...]" — confirms absolute joint targets plus a single scalar normalized gripper open/close value, i.e. a 2-jaw gripper, not multi-DoF fingers.
- domain randomisation: not stated in the paper (real-world data collection, not a randomized simulator); no randomization ranges given anywhere in the source.

## C. Reward / objective block
- Flow matching loss (§IV): "we want to model the data distribution p(A_t|o_t), where A_t = [a_t, a_t+1, ..., a_t+H−1]" is an action chunk (H=50). Noisy actions are formed as A_t^τ = τA_t + (1−τ)ϵ with ϵ ~ N(0,I), τ ∈ [0,1], and probability path q(A_t^τ|A_t) = N(τA_t, (1−τ)I). "The network outputs v_θ(A_t^τ, o_t) to match the denoising vector field u(A_t^τ|A_t) = A_t − ϵ." This is the conditional flow-matching regression loss (implicitly ‖v_θ(A_t^τ,o_t) − (A_t−ϵ)‖² by construction of the described objective; the paper's rendered loss equation itself was not extractable as text from the PDF conversion — the sentence above is the paper's own verbal statement of it).
- timestep sampling: p(τ) = Beta((s−τ)/s; 1.5, 1), s = 0.999 (Appendix B, Fig. 14) — "designed a timestep sampling distribution that emphasizes low timesteps (high noise levels)"; "timesteps above a given threshold s are not sampled at all."
- inference integration: forward Euler, A_t^{τ+δ} = A_t^τ + δ·v_θ(A_t^τ, o_t) [the display equation, lost in conversion, is recovered as `Aτ+δ t = Aτ t + δvθ(Aτ t , ot),` — "where δ is the integration step size" (recovered by OCR from papers/md/pi0_2024.ocr.md; OCR text is noisier than the layout parse, symbols may be imperfect — here the subscript `t` of the left-hand side falls on its own line)], δ = 0.1 (10 steps) (§IV).
- no weighted multi-term reward exists in this paper (pure IL regression loss on the action chunk); code (`code/md`) contains no reward function or numeric loss-weight config for pi0 itself — only data-transform class signatures (`AlohaInputs`, `DroidInputs`, `LiberoInputs`) with no visible loss body in the converted markdown. **Mismatch note**: the code repo (openpi, commit 215abfb2) has evolved past this paper — it also documents π0-FAST (autoregressive) and π0.5 checkpoints/configs not described in this paper; the paper describes only the flow-matching π0 and the non-VLM π0-small ablation.
- action chunking / horizon (for IL): H = 50 timesteps predicted per forward pass (§IV); executed open-loop without temporal ensembling — "We tried temporal ensembling [57] early on and found that it hurt policy performance, so we opted not to aggregate actions" (Appendix D). Re-inference cadence: every 0.8 s (16 of 50 actions) for 20 Hz robots, every 0.5 s (25 of 50 actions) for 50 Hz robots (Appendix D).

## D. Contact / penetration handling
Not addressed. This is a real-robot IL paper with no simulator, no contact solver, and no interpenetration metric or penalty anywhere in the source text.

## E. Evaluation block
- exact success criterion: no single numeric threshold (e.g. metres/radians/seconds); each task has a hand-designed scoring rubric (Appendix E) — e.g. shirt folding is binary success/failure ("folded in the sleeves and performed one half-fold"), bussing/grocery bagging/toast are scored as fraction of objects correctly placed (out of 7, 12, 7, or 4 depending on task).
- number of eval episodes/trials: out-of-box base-model tasks and fine-tuning tasks: "averaged over 10 episodes per task and method" (§VI-A) / "averaging over 10 trials per task" (§VI-B, §VI-C); complex multi-stage tasks (laundry, bussing, box building, egg packing, to-go box): "average scores per task over 10 trials" (§VI-D, Fig. 13).
- sim or real: all evaluation is real-robot; no sim numbers reported for π0 itself in this paper.
- baselines: OpenVLA (7B, autoregressive discrete-token VLA, re-trained on the pi0 mixture, plus a UR5e-only fine-tuned variant), Octo (93M, diffusion-action, re-trained on the same mixture), ACT and Diffusion Policy (trained only on the fine-tuning datasets, "of similar size to the individual datasets used in the ACT and Diffusion Policy experiments"), and an internal non-VLM ablation π0-small. All baselines were re-run by the authors on their own tasks/mixture (not merely quoted from their original papers), per §VI-A/§VI-C.
- headline numbers: Fig. 7 — π0 (700k steps) "attains by far the best results across the board" on shirt folding/bussing-easy/bussing-hard/grocery-bagging/toast, beating OpenVLA, Octo, and even the "parity" (160k-step) π0 beats all baselines; π0-small also beats OpenVLA/Octo (exact per-task scores are only given as a bar chart, not a numeric table, so precise values are not extractable as text — figure-only). Fig. 13 — "The full pre-trained π0 model attains more than 50% of the maximum score across all of the tasks" on the complex multi-stage tasks (laundry folding, mobile laundry, dryer unloading, table bussing, box building, to-go box, egg packing), outperforming both "out-of-box" (no fine-tune) and "scratch" (no pretrain) ablations, again as a bar chart with no tabulated numeric values in the extracted text.
- real robot? all of the above are real-robot trials (10 per task/condition as stated); no simulated evaluation of π0 in this paper.
- **dexterous-hand-evaluated: no**. Every named end-effector across pretraining and evaluation is a parallel-jaw gripper on an arm: "UR5e. An arm with a parallel jaw gripper" (§V-C), and code confirms the ALOHA action space as "left_gripper_positions (1), # normalized gripper position (0: close, 1: open)" (code/md, `examples/aloha_real/real_env.py`) — i.e., a single scalar per gripper, not a multi-fingered hand. No sentence in either source names a multi-fingered or anthropomorphic hand as an end-effector.

## F. Reproducibility
- code released: yes, `github.com/Physical-Intelligence/openpi` (commit 215abfb2 as parsed).
- checkpoints: yes — base models `pi0_base`, `pi0_fast_base`, `pi05_base`, plus fine-tuned "expert" checkpoints (`pi0_fast_droid`, `pi0_droid`, `pi0_aloha_towel`, `pi0_aloha_tupperware`, `pi0_aloha_pen_uncap`, `pi05_libero`, `pi05_droid`) hosted at `gs://openpi-assets/checkpoints/...` (code/md, "Model Checkpoints").
- assets: normalization stats and example configs for ALOHA, DROID, LIBERO, UR5e are included (`examples/aloha_real`, `examples/droid`, `examples/libero`, `examples/ur5`).
- reproducible tables: none of the paper's own headline task-success figures (Figs. 7, 9, 11, 13) can be reproduced from the repo as parsed — those used internal, unreleased dexterous-manipulation datasets (68 tasks, 7 robot configs) and real robots not distributed with the code. What *can* be reproduced from the repo as-is are inference on the public checkpoints (`pi0_fast_droid`, `pi0_aloha_towel`, etc.) and fine-tuning on the public LIBERO/DROID benchmarks — neither of which is a table in this paper.

## Limitations stated by the authors
"our experiments do not yet provide a comprehensive understanding of how the pre-training datasets should be composed... understanding what type of data is more helpful to add and how it should be weighted remains an open problem." "Not all tasks in our evaluation work reliably, and it remains unclear how to predict how much and what kind of data is needed to attain near-perfect performance." "It remains to be seen how much positive transfer there is in combining highly diverse data, particularly from different tasks and different robots... it is left for future work to understand whether this universality extends to much more distinct domains, such as autonomous driving, navigation, and legged locomotion." (§VII)

## Notes for the survey (which sections this feeds; contradictions with other notes)
Feeds the VLA/generalist-policy comparison section: backbone size (3B PaliGemma + 300M action expert = 3.3B), flow-matching action head (H=50 chunk, 50 Hz), and pretraining-mixture scale (903M own timesteps + OXE/Bridge/DROID). Important for the survey's dexterous-hand argument: despite the paper's own language of "dexterous tasks" and "dexterous manipulation," "dexterous" here means task/behavioral complexity (laundry folding, box assembly, egg packing) executed with ordinary 1-DoF parallel-jaw grippers, not multi-fingered end-effectors — this is a recurring terminology gap to flag against notes on papers that use "dexterous" to mean a multi-fingered hand (e.g. Allegro/Shadow-hand papers). No contact/penetration measurement exists here to compare against sim-based dexterous-hand papers.
