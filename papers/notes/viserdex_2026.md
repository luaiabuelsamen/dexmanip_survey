# viserdex_2026 — ViserDex: Visual Sim-to-Real for Robust Dexterous In-hand Reorientation (Bhardwaj, Wilder-Smith, Mittal, Patil, Hutter; arXiv 2026)

sources: papers/md/viserdex_2026.md [cb31fd20] ; no code

## One-line contribution
A monocular-RGB in-hand reorientation pipeline that integrates 3D Gaussian Splatting (3DGS) into the simulation loop and randomizes the Gaussians themselves before rasterization ("pre-rasterization augmentation"), paired with a lightweight performance-based curriculum and teacher-student distillation, so both perception and control train on a single consumer GPU (Abstract; Sec. I).

## Setting
- hand(s): 16-DoF Allegro Hand (Sec. III-E, Appendix). No arm (fixed base implied by wrist-mounted camera setup). Single hand.
- simulator / physics: NVIDIA Isaac Lab (Sec. III-E). 24,576 parallel envs for teacher RL; 4,096 envs for student distillation (Sec. IV-C1). Timestep not stated; joint PD controller runs at 300 Hz, policy at 30 Hz (Sec. III-E).
- observation: three groups (Sec. III-A2, Table X, total dim 199). Proprioceptive O_prop (88): joint positions (16), action history over last 4 steps (64), goal orientation quaternion (4), palm link position (3, constant), remaining time (1). Exteroceptive O_exte (11): object pose (7, ground truth in sim / estimator output at deployment), quaternion diff to goal (4). Privileged O_priv (100, teacher/critic only): joint velocities (16), joint torques (16), fingertip contact forces (12), object linear+angular velocity (6), randomized object/robot scale + mass (7), gravity vector (3), randomized joint stiffness/damping (32), randomized EMA α and delay (2), random external forces/torques (6). At deployment, exteroceptive object pose comes from an RGB pose estimator (Sec. III-D), not ground truth.
- action space: target joint positions a_t ∈ R^16 for the Allegro's 16 joints, scaled to joint limits then smoothed by an EMA filter with α randomized in (0.08, 0.2) per episode (Appendix, "Action Space").
- objects / data: 5 real objects — Cube, 3D Printed Toy, Rubber Duck, Tablet Bottle, Globe — meshes captured with Polycam, rendered in Isaac Lab for pose-annotated training images and for 3DGS scene optimization (Sec. III-E).

## Method
- paradigm: RL (teacher) + student distillation (BC + reconstruction loss) + supervised keypoint regression (pose estimator). Algorithm: PPO (RSL-RL library) for the teacher (Appendix, "Policy Architecture and Optimization").
- teacher-student pipeline (Fig. 2, Sec. III): (1) privileged teacher trained by PPO with full state; (2) teacher distilled into a recurrent student that sees only noisy proprioceptive/exteroceptive observations, via a belief encoder-decoder (architecture from perceptive locomotion [15]) trained with L = L_BC + λ L_recon, online DAgger variant; (3) a monocular RGB pose estimator (ResNet-34, ImageNet-pretrained, regresses 9 keypoints as normalized 2.5D (u,v,d), resolved to 6D pose via Rigid Procrustes) trained on images rendered from a 3DGS scene rolled out by the teacher; (4) deployment feeds RGB → pose estimator → student policy → PD controller.
- asymmetric actor-critic variant: unlike standard practice, BOTH actor and critic receive O_priv; asymmetry is instead introduced by giving the actor a noised/latency-corrupted O_prop while the critic presumably does not need it stated (Appendix, "Policy Architecture and Optimization"). Perception noise generator (student phase, inspired by DeXtreme [7]): temporal downsampling, stochastic jitter, systematic bias, and occasional random-pose injection applied to simulated object-pose observations (Sec. III-B1).
- policy architecture: exteroceptive and privileged groups each go through dedicated MLP encoders to z_exte ∈ R^24 (hidden [64,64]) and z_priv ∈ R^128 (hidden [256,256]); concatenated with normalized proprioception into a backbone MLP [1024,1024,1024,512], ELU (Appendix).
- reward (paper, Appendix Table IX, "Reward Terms" — quoted verbatim):
  - Task: Orientation Tracking, weight 1.0, `(d(θ)+ε)^-1`, ε=0.1; Success Bonus, weight 250.0, `I(d(θ)≤ε_success)`, ε_success = 0.1 rad.
  - Termination penalty: Object Dropped, weight −10.0, `I(drop)`.
  - Curriculum penalties (weights gradually increased during training): Object Distance −20.0 `−‖p_robot−p_obj‖₂`; Object Velocity −1e-3 `−‖v_obj‖₂`; Joint Velocity −8e-2 `−‖q̇‖₂`; Action Magnitude −0.80 `−‖a_t‖₂`; Action Rate −0.12 `−‖a_t−a_{t-1}‖₂`; Joint Work −0.12 `−Σ|τ·q̇|`; Joint Torques −50.0 `−‖τ‖₂`.
  - Text description (Sec. III-A1 / Appendix "Reward Modeling"): "r_t = r_task + r_reg. The task term r_task incentivizes minimizing orientation error, augmented by a sparse success bonus... the regularization term r_reg penalizes aggressive control inputs, high joint velocities, energy consumption and object instability." No separate code source exists for this key (no code/md); Table IX is the only reward specification.
  - "All teacher RL training and student distillation experiments use the same reward weights and hyperparameters across objects" (Sec. IV-C2) — no per-object reward tuning.
- performance-based curriculum (Sec. III-A3, in place of prior work's ADR [1, 7]): three components scaled by the moving average of consecutive successes across envs — (a) regularization penalties increase gradually so the policy prioritizes task completion first; (b) random action latency increases to prepare for real-hardware asynchrony; (c) the allowed time window between consecutive successes narrows. Ablation (Fig. 5): removing the Regularization Penalty curriculum "causes complete failure"; no curriculum also yields "near-zero success"; removing Action Latency or Time Window components "significantly slows learning" especially for complex geometries.
- Gaussian-splat domain randomization ("pre-rasterization augmentation", Sec. III-C3, Table I): object represented as 3DGS with SH color coefficients up to degree L=3. Camera is inverse-transformed relative to the (fixed) object to keep the 3DGS scene static per vanilla-3DGS assumptions; a low-fidelity physics raycaster depth map D_phys masks out pixels where the hand occludes the object (D_phys < D_splat) to restore finger-occlusion consistency. Four augmentation groups perturbing SH0/SHN coefficients before rasterization: Random Noise (per-Gaussian, independent), Spatial Cluster (64 k-means clusters by position), Color Cluster (32 k-means clusters by SH0), Global Shift (whole-scene additive/scaling shift, "Uniform" variant applies one scalar to the whole vector). Table I gives probability/fraction/range per augmentation (e.g. Global Shift Uniform Additive: prob 0.8, fraction 1.0, range [−0.2, 0.2]). Augmentation compute cost: "<2ms per batch... ≈4% of total frame rendering time" (Sec. IV-A).
- domain randomization for control (Appendix "Domain Randomization"): link/object mass, friction, restitution; object geometric scale; actuator stiffness/damping identified via system ID [4] then randomized per-episode around identified ranges; random external forces and gravity-vector perturbations at fixed intervals; ranges listed in Table XI (not captured in this parse — table not reached in the read ranges used).
- key trick(s): replacing ADR with the performance-based curriculum; simulation-integrated 3DGS rendering with occlusion masking from a physics depth raycaster; clustering Gaussians before perturbing them to preserve photometric plausibility (naive per-Gaussian randomization "breaks photometric consistency, producing high-frequency noise").
- contact / penetration handling: not addressed as a measured or penalized quantity. The only contact-related signal is "Fingertip Forces" (12-dim, net contact force at the four fingertips) in the privileged observation group O_priv (Table X) — used for state inference, not reward. No penetration term appears in Table IX and no penetration metric is reported anywhere in the parse; contact dynamics randomization (friction, restitution) is listed only as a DR target (Appendix, "Domain Randomization").
- reproducibility: bib record shows `github: null`; no code/md exists for this key. The paper points only to a project website (https://rffr.leggedrobotics.com/works/viserdex/) for videos, not code or checkpoints. None of the paper's tables can be independently checked against a repository from this corpus.

## Evaluation
- pose-estimator metrics: ADD (Average Distance of Model Points, mm) and accuracy = fraction with error < 10 mm and < 10°, averaged over 5 training seeds (Sec. IV-A, Table II). Real-world test-set labels from FoundationPose given privileged inputs (masks, CAD meshes, RGB-D, multiple refinement iterations), with visually misaligned frames discarded (Sec. IV-A).
- policy/deployment success criterion: "successful in-hand reorientation when the object orientation error is within 0.4 radians" (consistent with prior work [2,7]); metric is Consecutive Successes (CS) — goals reached before a drop — averaged over 5 runs per object per lighting condition (Sec. IV-D, Table IV).
- headline numbers: pose estimation mean accuracy nominal 65.4% (ADD 10.2 mm) vs. Standard Tiled 53.3%, DR Tiled 55.6%, Naive GS 38.4% (Table II); adversarial mean accuracy 56.3% vs. best baseline (DR Tiled) 47.2%, Naive GS collapses to 36.5% (Table II). Ablation (Table III): removing Global Shift is catastrophic — nominal accuracy drops to 51.2% (ADD nearly doubles to 16.9 mm), adversarial accuracy collapses to 23.6%. Deployment (Table IV): mean CS nominal 37.6±21.8, adversarial 25.4±30.1; Cube nominal 35.4±13.8 vs. DeXtreme's reported 27.8±19.0 on the same object; Globe reaches "over 200 CS in one of the trials"; substituting FoundationPose as the pose estimator at deployment collapses to 0.4 CS average, attributed to its ~4 Hz rate (vs. "∼18 Hz throughput" of their estimator) and tracking loss under occlusion.
- compute: teacher training on Cube converges in 26 h on one consumer RTX 4090 (24 GB); more complex objects need dual-GPU (30 GB) and ~90 h; student distillation, 16 h on one RTX 4090 for 4,096 envs. Compared to DeXtreme's "eight A40 GPUs over 60 hours" (Sec. IV-C1) — direct quantitative claim of the "consumer hardware" contribution. 3DGS rendering: 1.6× faster throughput than Isaac Lab's tiled RTX renderer and 12 GB VRAM for 1,024 envs vs. 34 GB for the tiled renderer (Sec. IV-A).
- baselines beaten: Standard Tiled Rendering, DR Tiled Rendering (randomization params for material/background from DexPBT-style prior work [27]), Naive Gaussian Splatting (their own 3DGS pipeline without pre-rasterization augmentation) — all for pose estimation; DeXtreme [7] on hardware Cube CS, and FoundationPose as an alternative deployment-time estimator.
- real robot? yes, quantified. 16-DoF Allegro Hand, wrist-mounted Intel RealSense D435i, i9 CPU + RTX 6000 Ada workstation (Sec. III-E). Table IV reports 5 runs per object per lighting condition (2 conditions × 5 objects = 10 cells, 5 runs each); this is trial-count evaluation, not video-only, though the paper also points to a project website for videos.

## Limitations stated by the authors
- "vision is fundamentally constrained by finger occlusions and its inability to directly sense contact forces" (Sec. V).
- Tablet Bottle shows "a notable sim-to-real gap," attributed to "unmodeled friction effects, particularly the extremely low surface friction introduced by its label" (Sec. IV-D2).
- Object material damping (Globe, Duck) aids real-world stability "despite not being explicitly modeled in simulation" — an unquantified sim-to-real mismatch working in the method's favor rather than against it (Sec. IV-D2).
- "while our method excels at instance-specific manipulation, extending this pipeline to support broader generalization is a key step toward truly general-purpose dexterous manipulation" (Sec. V) — each object gets its own trained pose estimator and, implicitly, policy (Sec. III-E: "For each object, we train a pose estimator and control policy").
- Future work flagged: combining dense vision with high-frequency tactile sensing for unmodeled surface properties (Sec. V).

## Quotable claims (verbatim, with section)
- "Our key insight is performing domain randomization in the Gaussian representation space: by applying physically consistent, pre-rendering augmentations to 3D Gaussians, we generate photorealistic, randomized visual data for object pose estimation." (Abstract)
- "we simplify the RL process by replacing the extensive DR schemes used in previous works [1, 7] with a performance-based curriculum and a student-teacher distillation framework" (Sec. I)
- "Compared to prior work [7], which requires eight A40 GPUs over 60 hours, our pipeline achieves an order-of-magnitude improvement in VRAM efficiency and substantially reduced training time" (Sec. IV-C1)
- "this is the first demonstration of sustained dexterous in-hand manipulation under such extreme visual perturbations" (Sec. IV-D3, re: adversarial lighting)
- "The reduction in overall task success disproportionately exceeds the degradation in pose estimation accuracy... even small perceptual errors can compound into significant control failures." (Sec. IV-D3)
- "Na¨ıvely randomizing individual Gaussians... breaks photometric consistency, producing high-frequency noise rather than realistic lighting variations." (Sec. III-C3)

## Notes for the survey
- Feeds: visual (RGB-only) sim-to-real section — contrasts with DeXtreme's [7] multi-camera + ADR approach and with tactile/depth-based state estimators (Pitz et al. [18], depth [5]) cited in Related Works. Also feeds the "what genuinely changed 2022→2026" comparison: the reward structure (orientation-tracking reciprocal + success bonus + regularization) is essentially the same shape as pre-2023 in-hand reorientation rewards (e.g. Eureka's / OpenAI-style Shadow Hand rewards); the actual novelty is entirely in the perception pipeline (3DGS-in-the-loop + clustered SH perturbation) and the curriculum replacing ADR, not in the RL objective itself.
- Real-robot evaluation has explicit trial counts (5 runs/object/condition) and a genuine baseline number reused from DeXtreme's paper for the shared Cube object — one of the more concrete cross-paper comparisons in this batch.
- Reward block was fully fillable — Appendix Table IX gives every term, weight and equation; no code repository exists for this key to cross-check against, which the note above flags at each reward/DR claim that would otherwise need a code citation.
