# pi05_2025 — pi0.5: a Vision-Language-Action Model with Open-World Generalization (Physical Intelligence, arXiv 2025)

sources: papers/md/pi05_2025.md [sha256 6a1029fd] ; code/md/pi05_2025.md [commit 215abfb2]

## One-line contribution
Co-trains a single VLA (built on pi0) on heterogeneous web, cross-embodiment, subtask-label and verbal-instruction data so a mobile manipulator can perform long-horizon (10-15 min) kitchen/bedroom cleaning in real homes never seen in training (Abstract; Sec. I).

## Setting
- hand(s): **none** — "two 6 DoF arms with parallel jaw grippers" per platform (Sec. IV-E, Fig. 5). No multi-fingered hand anywhere in the paper.
- arm: 2x 6 DoF arms + 1 DoF gripper each, mounted on a torso-lift + 3 DoF holonomic mobile base ("2x 6 DoF arm + 1 DoF gripper", Fig. 5); bimanual (two arms on one mobile robot), single mobile base.
- simulator / physics: **none stated** — all experiments are on real robots in mock and real homes (Sec. V); no sim engine, timestep or #envs given anywhere in the paper.
- observation: "images from all of the cameras and the robot's configuration (joint angles, gripper pose, torso lift pose, and base velocity)" — 4 cameras (front, rear, 2 wrist) total, "all four cameras for high-level inference, and the wrist and forward cameras for the low-level inference process" (Sec. IV-A, Sec. IV-E).
- action space: target joint/end-effector poses for arms+gripper, base velocity, torso lift; "total dimensionality of the state and action spaces is 18 or 19, depending on the platform" (Sec. IV-E). Text prompt is tagged `<control mode> joint/end effector <control mode>` to disambiguate representation (Sec. IV-C).
- objects / data: no fixed object/trajectory count; see data-mixture block below.

## Method
- paradigm: VLA, imitation learning by next-token/flow-matching prediction, with an explicit **hierarchical high-level (discrete subtask) + low-level (continuous action) inference** split (Sec. IV, Sec. III).
- backbone VLM: **PaliGemma**, "adopts the PaliGemma VLM [5] as the backbone" (Appendix E). Two transformers, both "the same dimensions ... as pi0": VLM = `{width=2048, depth=18, mlp_dim=16384, num_heads=18, num_kv_heads=1, head_dim=256}`, described as "the 2B VLM initialized from PaliGemma weights" (Appendix E). Action expert uses the same shape except `{width=1024, mlp_dim=4096}` and has **300M parameters** (Appendix E).
- action head: **flow matching**, added on top of a discrete-token pretraining stage — this is the key change from pi0. Quoting Sec. III / IV-B:
  - Flow-matching target: "Given **a**^{τ,ω}_{t:t+H} = τ**a**_{t:t+H} + (1−τ)ω, ω ∼ N(0, I), where τ ∈ [0,1] is the flow matching time index, the model is trained to predict the flow vector field ω − **a**_t" (Sec. IV-B; note the extracted text gives target "ω − a_t", not "a_t − ω" as in the original pi0 formulation — the markdown extraction is ambiguous here on sign convention, flagged per HOWTO rule 3).
  - Combined loss (Eq. 1, Sec. IV-B): "Our model is therefore trained to predict actions both through autoregressive sampling of tokens (using the FAST tokenizer) and iterative integration of the flow field... Our model is optimized to minimize the combined loss [Eq 1] where H(x_{1:M}, y^ℓ_{1:M}) is the cross entropy loss between the text tokens and predicted logits (including the FAST encoded action tokens), y^a_{1:H} = f^a_θ(a^{τ,ω}_{t:t+H}, o_t, ℓ) is the output from the (smaller) action expert, and α ∈ R is a trade-off parameter."
  - Two-stage schedule: pretrain with α=0 (pure discrete/FAST next-token prediction, no action expert) for **280k gradient steps**, then post-train with **α=10.0 for 80k additional steps**, at which point the flow-matching action expert (randomly initialized) is added (Sec. IV-C, IV-D).
  - Discrete/AR component beyond pi0: the model also autoregressively predicts a **text-token high-level subtask** ℓ̂ (e.g. "pick up the plate") from a high-level command ℓ, before the action expert predicts the low-level chunk conditioned on ℓ̂: "πθ(a_{t:t+H}, ℓ̂ | o_t, ℓ) ... high-level inference captures πθ(ℓ̂|o_t,ℓ), and low-level inference captures πθ(a_{t:t+H}|o_t,ℓ̂), with both distributions represented by the same model" (Sec. IV-A). This hierarchical text-then-action decomposition, and the joint discrete-pretrain/flow-matching-post-train recipe, are the two things pi0.5 changes relative to pi0, which "always uses the action expert" (Sec. V-D).
  - Inference: "we then use standard autoregressive decoding for text tokens ℓ̂ followed by 10 denoising steps, conditioned on text tokens, to produce actions a_{t:t+H}" (Sec. IV-B).
- action chunk length / control rate: action horizon **H=49** ("an action horizon of 50, i.e. H=49", Appendix E); low-level control runs "at 50 Hz (with action chunking)" tracked by "simple PD controllers, without any additional trajectory planning or collision detection" (Sec. IV-E).
- key trick(s): time-step sampling emphasizing low flow-matching timesteps, p(τ)=Beta-like with threshold s=0.999 "accommodates up to 1,000 integration steps" (Appendix E); image augmentation (random crop 0.95, resize, rotate ±5°, color jitter b=0.3/c=0.4/s=0.5) (Appendix E); action expert attention is masked so it cannot attend to FAST action tokens ("to avoid information leakage between the two representations of actions", Appendix E, Fig. 18).

## Pretraining / co-training data mixture (Sec. IV-C, no single stated grand total)
- **MM** (Diverse Mobile Manipulator data): "about 400 hours of data of mobile manipulators performing household tasks in about 100 different home environments."
- **ME** (Diverse Multi-Environment non-mobile robot data): single- or dual-arm, fixed/mounted arms in home environments; no hour/episode count given.
- **CE** (Cross-Embodiment laboratory data): tabletop tasks (bussing a table, folding shirts, "grinding coffee beans"), single- and dual-arm, static and mobile bases, "includes the open-source OXE dataset [15]," described as "an extended version of the dataset used by π0" — no size stated for the extension.
- **HL** (High-Level subtask prediction): manual text annotations of subtasks + bounding boxes over MM/ME/CE data — no separate count; "verbal instruction ... only constitutes about 11% of the high-level mobile manipulation examples" (Sec. V-E).
- **WD** (Multi-modal Web Data): "image captioning (CapsFusion [87], COCO [12]), question answering (Cambrian-7M [77], PixMo [19], VQAv2 [32]), and object localization" (plus extra web indoor/household bounding-box data) — no sizes stated beyond dataset names.
- **VI** (Verbal Instruction, post-training only): collected by expert teleoperators giving step-by-step subtask commands to the trained low-level policy (Sec. IV-D).
- Stated mixture ratio: **"97.6% during the first training phase" of training examples do NOT come from mobile manipulators** (Sec. I) — i.e. only ~2.4% of pretraining examples are MM household data. No overall example/token count for the full mixture is given.

## Embodiments in the mixture / evaluation
Named embodiments: the paper's own two mobile-manipulator platforms (two 6 DoF arms + parallel-jaw grippers + holonomic base + torso lift, Sec. IV-E/Fig. 5); "non-mobile robots" / single- and dual-arm static manipulators (ME, CE); the Open X-Embodiment (OXE) cross-embodiment dataset (CE). **No multi-fingered or dexterous hand is named anywhere in the paper or the code.** Every end-effector mentioned is a gripper: "parallel jaw grippers" (Sec. IV-E) and "gripper pose"/"gripper position" observations (Sec. IV-A; code: `left_gripper_positions`, `_gripper_to_angular`, in `examples/aloha_real/real_env.py` and `src/openpi/policies/aloha_policy.py`). The word "dexterous" appears only describing task complexity ("dexterous manipulation skills," Abstract, Sec. VI), never an end-effector.

## Fine-tuning recipe
Post-training (the paper's own "fine-tuning" of the pretrained model): dataset = MM + ME "filtered down to successful episodes that are below a fixed length threshold," plus WD (to retain semantic/visual capability) and the HL slice for ME, plus newly collected VI data; **80k gradient steps, α=10.0** (Sec. IV-D). Downstream user fine-tuning (code only, `code/md/pi05_2025.md` README "Fine-Tuning Base Models on Your Own Data"): example recipe on LIBERO via `pi05_libero` config, `scripts/compute_norm_stats.py` then `scripts/train.py`, evaluated from a 20,000-step checkpoint — no hyperparameters (LR, batch size) are given in the extracted code text.

## Evaluation
- metrics: task-specific point rubrics, "percent of total points achieved in each evaluation rubric" (Appendix B), e.g. *Dishes in Sink* = +1 per item picked up, +1 per item placed (max 8); *Items in Drawer* = pick up/open drawer/place/close (max 4); *Laundry in Basket* = pick up/place/fully inside (max 3); *Make the Bed* = straighten blanket/place pillow x2/neatness x2 (max 5) (Appendix B, quoted verbatim). Language-following eval uses **language following rate** (correct object selected) and **task success rate** (object placed correctly), with a chance baseline of "∼20% language following accuracy" by design (Appendix C).
- headline numbers: **not extractable as numeric text** — Figs. 7-13 and 16-17 (real-home results, location-scaling, ablations, pi0 comparison, high-level-inference ablation) are bar charts; the markdown conversion of this PDF carries no axis/bar values, only captions and prose describing directions of effects (e.g. "π0.5 significantly outperforms both π0 and π0-FAST+Flow," Sec. V-D/Fig. 12; "improves with more training locations," Sec. V-B/Fig. 8). Per HOWTO rule 3, this ambiguity is flagged rather than guessed.
- protocol: "10 evaluations per task" per policy across "12 different locations" (3 real homes + 3 mock kitchens + 3 mock bedrooms, i.e. "a total of 12"), "leading to a total of 40 evaluations per policy for our standard evaluations," interleaved execution across policies to control for drift, two-sided t-test for significance (Appendix B).
- baselines: pi0 (flow-matching only), an author-built "pi0-FAST+Flow" (hybrid loss but no HL/WD data), GPT-4 as a zero-shot high-level policy, a human "oracle" high-level policy, and a same-architecture model trained directly on test-home data as an upper-bound control (Sec. V-B, V-D, V-E) — all re-run by the authors, none "quoted" from external papers.
- real robot? Yes — all quantitative and qualitative results are on the paper's own two mobile-manipulator platforms in "12 different locations" including 3 real, previously-unseen homes (Sec. V-A, Appendix B); no simulation numbers anywhere.
- dexterous-hand-evaluated: no
  Supporting quote: "Both platforms are equipped with two 6 DoF arms with parallel jaw grippers and wrist-mounted monocular RGB cameras, a wheeled holonomic base, and a torso lift mechanism." (Sec. IV-E)

## Limitations stated by the authors
"it still makes mistakes. Some environments present persistent challenges (e.g., unfamiliar handles on drawers, or cabinets that are physically hard for the robot to open), some behaviors present challenges with partial observability (e.g., the robot arm occluding a spill that should be wiped), and in some cases the high-level subtask inference is easily distracted (e.g., closing and opening a drawer multiple times while putting away items)." Also: "processes relatively simple prompts," and "uses a relatively modest context," limiting long-horizon memory across rooms (Sec. VI).

## Contact / penetration handling
Not addressed. ## Reproducibility
Code released: yes, `github.com/Physical-Intelligence/openpi`, commit `215abfb2` as parsed. Checkpoints released: yes, base and fine-tuned JAX checkpoints listed (e.g. `gs://openpi-assets/checkpoints/pi05_base`, `pi05_libero`, `pi05_droid`) plus PyTorch support (code README lines ~69-99, 200-264). **Mismatch found**: the paper's Sec. IV describes a hybrid pretrain-with-discrete-FAST-tokens-then-add-flow-matching-action-expert recipe (Eq. 1, α: 0→10), but the released repo states plainly: "Note that, in this repository, we currently only support the flow matching head for both π0.5 training and inference" (code README, openpi repo). None of the paper's real-home, mock-home, ablation, or high-level-inference figures/tables (Figs. 7-17) are reproducible from the released code — those are proprietary real-robot rollouts with no released dataset or eval harness in `code/md/pi05_2025.md`; only the LIBERO/DROID fine-tuning pipeline and its own (different) benchmark numbers are runnable from the repo.

## Quotable claims (verbatim, with section)
