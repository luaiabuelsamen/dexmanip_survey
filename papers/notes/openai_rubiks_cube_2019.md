# openai_rubiks_cube_2019 — Solving Rubik's Cube with a Robot Hand (OpenAI et al., arXiv 2019)

sources: papers/md/openai_rubiks_cube_2019.md [sha256 2a6fe430] ; no code

## One-line contribution
Automatic Domain Randomization (ADR) — a curriculum that grows a factorized uniform randomization distribution online, without hand tuning, whenever policy/vision performance clears a threshold — trains a single recurrent PPO policy and a separate CNN state estimator, entirely in MuJoCo/ORRB simulation, to solve a Rubik's cube with a real Shadow Dexterous Hand (best policy: 26.8±4.9 mean successes over 10 real trials on a fixed 43-move fair scramble, Table 6).

## Setting
- hand(s): "Shadow Dexterous E Series Hand (E3M5R)" (Sec. 3.1), Shadow Robot Company. 20 actuated joints (Sec. 6.1, Table 14: "categorical with 11 bins for each one of 20 action coordinates"); 24 hand-joint angles are tracked (Table 1: "Hand joint angles 48D", footnote: angles encoded as sin/cos, doubling dimensionality). Coupled distal joints modeled with a non-actuated spatial tendon and pulleys added to match the physical hand (Sec. 4.1).
- arm / mount: not stated. Section 3.1 ("Physical Setup"/"Robot Platform") describes only the hand, a PhaseSpace motion-capture rig and 3 Basler cameras inside a "cage"; no arm or wrist mount is mentioned.
- palm orientation vs. gravity: not stated.
- bimanual: no — single Shadow hand for both tasks (Sec. 2: "both tasks... use the Shadow Dexterous Hand").
- simulator / physics: MuJoCo [108] for dynamics; ORRB [16] (a Unity3D remote rendering backend) for the synthetic images used to train the vision model (Sec. 4). Rubik's cube modeled as 26 rigid convex cubelets, "6×1 + 20×3 = 66 degrees of freedom" (Sec. 4.2).
- sim timestep / control rate: default average timestep 0.1 s (block) / 0.09 s (Rubik's cube), each ADR-randomized to [0.05, 0.15] s / [0.05, 0.13] s "taken from the end of ADR training" (Table 7). Policy control/observation rate is 12.5 Hz (Sec. 3.2.2: "we used a 12.5 Hz update frequency for the angle readings... we run the control policy at this frequency", footnote 7); consistent with the Δt = 0.08 s per-step interval used in the recurrent-state analysis (Sec. 9.3).
- parallel envs / compute: not given as an explicit env count; given as distributed worker/GPU counts (Table 14): block reorientation — 32 NVIDIA V100 GPUs + 400 worker machines × 32 CPU cores = 12,800 CPU cores; Rubik's cube — 64 NVIDIA V100 GPUs + 920 worker machines × 32 CPU cores = 29,440 CPU cores. Trained "continuously for several months" (Sec. 6.3); cumulative experience "roughly 13 thousand years", compared to OpenAI Five's 40 thousand years (Sec. 6.3). Vision training: 8 V100 GPUs (optimizer) + 16×1 V100 GPU rendering nodes (Table 16).
- observation: state-based, not raw images to the policy. Policy inputs (Table 1, noisy versions only): noisy fingertip positions (15D, from PhaseSpace), noisy cube position (3D) and orientation (4D quaternion), goal orientation (4D), goal face angles (12D) and noisy relative goal face angles (12D). Value network additionally gets non-noisy versions plus full `qpos` (170D) and `qvel` (168D) (privileged/asymmetric actor-critic, Sec. 6.2). Cube pose always comes from the vision CNN; face angles come from either the vision CNN or a custom "Giiker cube" with embedded rotary encoders (Sec. 3.2, 7).
- action space: "discretized action space with 11 bins per actuated joint (of which there are 20). We use a multi-categorical distribution. Actions are relative changes in generalized joint position coordinates." (Sec. 6.1)
- objects / data: standard Rubik's cube (simulated) and a reorientation block (from prior work [77]); no offline demonstration dataset — training data are simulation rollouts and rendered images. Real-world evaluation scrambles use the official World Cube Association "fair scramble" method (Sec. 2.2, 8.4.1).

## Method
- paradigm: RL (PPO) for the control policy; supervised learning (CNN regression/classification) for the vision state estimator, trained separately; behavioral cloning/policy distillation for architecture changes.
- algorithm: "Proximal Policy Optimization [98]" (Sec. 6), on the in-house distributed framework "Rapid" (Sec. 6.3, previously used for OpenAI Five). Vision optimizer: LARS [118], chosen because "we found LARS to be more stable than the Adam optimizer... when using larger batches and higher learning rates (we use at most a batch size of 1024 with a peak learning rate of 6.0)" (Sec. 7.2).
- policy architecture: single feed-forward layer (2048 units, ReLU) + single LSTM layer (1024 units); separate value network, same architecture, L2 regularization coefficient 1e-6; "embed-and-add": each observation type is embedded (512-dim, no weight sharing) then summed and passed through ReLU, replacing simple concatenation (Sec. 6.2). Asymmetric Actor-Critic [81]: value network sees privileged, non-noisy state.
- teacher-student / distillation: "Policy Cloning" (Sec. 6.4) — when changing architecture, a student is trained with actions sampled from itself while "minimizing the difference between the student and the teacher's action distributions (by minimizing KL divergence) and value predictions (by minimizing L2 loss)", in the spirit of DAGGER [88]/policy distillation [23]. "The best ADR policies used in this work were obtained using this approach."
- reward (verbatim, Sec. 6.1): "There are three types of rewards we provide to our agent during training: (a) The difference between the previous and the current distance of the system state from the goal state, (b) an additional reward of 5 whenever a goal is achieved, (c) and a penalty of −20 whenever a cube/block is dropped." No explicit weight is given for term (a) (implicitly 1). No reward code is available (no code source for this key) to cross-check these terms.
- episode termination (Sec. 6.1): 50 consecutive successes, a drop, or a timeout — "400 timesteps for block reorientation and 800 timesteps for the Rubik's Cube" (footnote: 1600 timesteps when training from scratch).
- goal generation (Sec. 6.1, Algorithm 4, App. C.1): block — random goal orientation with one face pointing up; cube — if faces aligned, 50% chance rotate top face CW/CCW by 90°, else perform a "flip" (align faces + random upward orientation). Orientation "aligned" tolerance 0.4 rad; face "aligned" tolerance 0.1 rad (Sec. 2.1, App. C.1).
- key trick — ADR (Sec. 5): each environment is parameterized by λ ∈ R^d sampled from a factorized uniform distribution P_φ with per-dimension bounds (φ_L,i, φ_H,i); "we define ADR entropy as H(P_φ) = −(1/d)∫P_φ(λ) log P_φ(λ) dλ in units of nats/dimension" (Sec. 5.2). Algorithm 1: with probability p_b ("boundary sampling probability") fix one randomly chosen dimension to a boundary value, evaluate model performance there, buffer it; once the buffer reaches length m, average performance p̄ is compared to thresholds — if p̄ ≥ t_H the boundary is pushed out by step Δ, if p̄ ≤ t_L it is pulled in by Δ. ADR hyperparameters (Table 15): max φ = 4.0, boundary sampling probability p_b = 0.5, step size Δ = 0.02, increase threshold t_H = 20, decrease threshold t_L = 10, performance queue length m = 240. "For policy training, [thresholds] are configured as the lower and upper bounds on the number of successes in an episode." Vision ADR increase/decrease thresholds are 70%/30% of samples meeting per-output target error (Sec. 5.1, App. C.3).
- ADR initialization (Sec. 5.3): policy φ0 set so φ0_i,L = φ0_i,H = λ_i^calib (calibrated from the real robot) for all i; vision φ0_i,L = φ0_i,H = 0 (starts unrandomized).
- example randomization ranges "taken from the end of ADR training" (Table 7, physical units):
  | parameter | block avg | block range | cube avg | cube range |
  |---|---|---|---|---|
  | cube size [m] | 0.055 | [0.046, 0.064] | 0.057 | [0.049, 0.066] |
  | time step [s] | 0.1 | [0.05, 0.15] | 0.09 | [0.05, 0.13] |
  | gravity [m/s²] | 9.80 | [6.00, 14.0] | 9.80 | [6.00, 14.0] |
  | cube mass [kg] | 0.0780 | [0.0230, 0.179] | 0.0902 | [0.0360, 0.158] |
  Categories of randomized quantities (Table 9, App. B): simulator physics generic randomizers (actuator force range/gain, body inertia, geom size, tendon length/stiffness, dof armature/damping/friction loss, geom friction/gap/margin/pos, joint stiffness — each with a noise mode from {Additive Gaussian, Unbiased Additive Gaussian, Multiplicative} and scale α, Table 10), custom randomizers (body mass, cube size, tendon range, cube/robot friction), custom physics (action latency, motor backlash, joint margin/range, time step, action noise), a "Random Network Adversary" (RNA, App. B.3), and observation noise (correlated + uncorrelated Gaussian, App. B.4). Vision randomizes ORRB scene appearance (lighting, camera pose, materials, background texture, post-processing) and TensorFlow image distortions (Sec. 5.4, App. B.5, Table 11).
- adversarial randomization (App. B.3): RNA uses a freshly re-initialized random (untrained) 3-hidden-layer (265 units) feed-forward network per episode to generate action perturbations (a_t = (1−α)a_robot + α·a_adv) and force/torque perturbations on object bodies, with α, β controlled by ADR; found to outperform a trained adversary for sim2sim transfer.
- meta-learning claim: "training on a maximally diverse distribution over environments leads to transfer via emergent meta-learning" (Sec. 5); the approach is explicitly framed as RL² [27, 116] combined with ADR's automated curriculum (Sec. 10.4).

## Contact / penetration handling (D)
Not penalized in the reward; treated as a passive property of the contact solver, not measured as a metric anywhere in the paper. "MuJoCo allows for these shapes to penetrate each other by a small margin when a force is applied" (Sec. 4.2, re: the 26-cubelet Rubik's cube model). "We do not implement any custom physics in our modelling, but rely on the cubelet shapes, contact forces and friction to drive the movement of the cube" (Sec. 4.2). Contact-solver parameters — `geom_gap`, `geom_margin`, `geom_solimp`, `geom_solref` (cube and robot, separately) — are themselves domain-randomized (Table 9, App. B.1.2), meaning the amount of tolerated penetration is varied across training environments rather than constrained or reported.

## Evaluation
- metrics (exact definitions, Sec. 2.1, 6.1, 8.4.1): block goal success = orientation within 0.4 rad of target; episode score = number of consecutive successes before drop/50-success cap/timeout. Rubik's cube trial score = total successful rotations+flips; "half" success = ≥22/43 successes on the fixed fair-scramble sequence, "full" success = all 43 (26 rotations + 17 flips), "equivalent to solving the Rubik's cube". Vision errors: orientation = rotational distance over quaternion, position = Euclidean distance in mm, face-angle error in degrees, active-axis error = 1 − accuracy (Table 2, App. D.3).
- eval episodes/seeds: block — sim N=500 trials, real N=10 trials per policy (Table 3). Rubik's cube — real N=10 trials per policy on the fixed WCA scramble "L2 U2 R2 B D2 B2 D2 L2 F' D' R B F L U' F D' L2" (Table 6, Sec. 8.4.1); real trial timeout 1600 timesteps = 128 s per goal. Simplified 2-DoF "face cube" calibration ablation: N=10 real trials (Table 19). Meta-learning perturbation study: 10,000 simulated trials (Fig. 18, 21).
- sim vs. real: reported separately throughout (Tables 3–6); vision Table 2 gives both Sim and Real columns; policy transfer studied as both sim2sim (against a fixed manually-randomized test distribution, Sec. 8.1.1) and sim2real (Sec. 8.1.2, 8.4).
- baselines: "Baseline (data from [77])" and "Baseline (re-run of [77])" (same checkpoint re-deployed on the current cage/sim, which "performs much worse today" — Sec. 8.1.2); "Manual DR" (same fixed randomization scheme as [77], retrained with current architecture/hyperparameters, "fully comparable" wall-clock and compute to "ADR (Large)"). Not re-run: [77]'s own reported numbers are quoted, not rerun, for the first Baseline row.
- headline numbers: block reorientation, real robot (Table 3): Manual DR 2.7±1.1; ADR (Small) 1.4±0.9; ADR (Medium) 3.2±1.2; ADR (Large) 13.3±3.6; ADR (XL) 16.0±4.0; ADR (XXL) 32.0±6.4 mean successes (vs. Baseline re-run 4.0±1.7). Rubik's cube, real robot (Table 6): Manual DR 1.8±0.4; ADR 3.8±1.0; ADR (XL) 17.8±4.2 (half 30%, full 10%); ADR (XXL) with Giiker face angles 26.8±4.9 mean (median 22.0, half 60%, full 20%); ADR (XXL) with vision-only face angles 12.8±3.4 (half 20%, full 0%). "26 quarter face rotations is the worst case for solving a Rubik's cube with only about 3 Rubik's cube configurations requiring that many [87]" (Sec. 8.4.1). Simulation-calibration ablation (Table 19): new coupled-joint + calibrated sim gives 14.30±6.56 mean successes on the 2-DoF face-cube vs. 4.8±2.89 for the old sim. Vision (Table 5, Rubik's cube): ADR (Large) real errors 7.48° orientation / 6.24 mm position / 13.82° top-face-angle vs. Baseline (manual DR) 7.81°/6.47 mm/15.92°.
- baselines beaten: prior manually-randomized domain-randomization policy/vision pipeline from [77] (Andrychowicz et al.), on both block reorientation and Rubik's cube; fixed-entropy DR policies at matched compute (Sec. 8.2, Fig. 16); a trained zero-sum adversary, beaten by random-network adversarial perturbations (App. B.3).
- real robot? Yes — Shadow Dexterous Hand E3M5R in a custom cage with PhaseSpace mocap + 3 Basler cameras; trial counts as above (N=10 per policy for both tasks; N=10 for the sim-calibration ablation).

## Limitations stated by the authors
- Vision-only face-angle tracking on a standard (unmarked) cube is unsolved: they cut a corner off each center sticker to break rotational symmetry, and "we would like to fully solve this problem from vision alone using a standard Rubik's cube... This remains an active area of research for us" (Sec. 7).
- "We experimented with a recurrent vision model but found it very difficult to train to the necessary performance level. Due to the project's time constraints, we could not investigate this approach further." (footnote 12)
- Manual domain randomization "achieves high performance in simulation. However, when deployed on the robot, it fails" (Sec. 8.1.2) — a large sim2real gap the paper attributes to not hand-tuning to the current (changed) hardware/sim.
- Broken-joint adaptation is incomplete: "the 'Broken joint perturbation' performance never quite catches up to the 'Broken joint baseline'... the policy can not fully recover performance." (Sec. 9.2)
- Perturbation robustness (glove, tied fingers, blanket occlusion, pen/giraffe pokes) is only qualitative: "we do not quantify these experiments" (Sec. 8.4.2).
- Even the best policy solves the hardest (26-rotation) scrambles only 20% of the time and the full fixed scramble 20% of the time overall (Table 6).

## Notes for the survey
- Feeds the domain-randomization / sim2real section as the canonical automated-curriculum method (ADR), directly comparable against fixed-range manual DR at matched compute (Sec. 8.1.2, 8.2) and against the same authors' earlier manual-DR pipeline [77] on identical hardware.
- Feeds the reward-design comparison: reward is a minimal 3-term shaped distance + sparse bonus/penalty, no penetration term, no per-joint imitation term — a useful contrast point against denser trajectory-imitation rewards used elsewhere in the corpus (e.g. artigrasp_2023's multi-term pose/contact/task reward).
- Contact/penetration is explicitly *not* a controlled or reported quantity here (soft-contact tolerance itself is domain-randomized); flag this against any note in this corpus that claims a "no interpenetration" guarantee from a physics engine, since here interpenetration is allowed by design and its bounds are part of the randomized distribution rather than reported.
- Embodiment block is single-hand, no arm — a data point for the "hand-only vs. arm+hand" split in the survey's embodiment table; note that arm/mount and palm orientation are simply absent from the text, not zero/negative results.
