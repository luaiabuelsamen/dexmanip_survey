# dexpbt_2023 — DexPBT: Scaling up Dexterous Manipulation for Hand-Arm Systems with Population Based Training (Petrenko et al., RSS 2023)

sources: papers/md/dexpbt_2023.md [sha256 66bc06ad] ; code/md/dexpbt_2023.md [commit aeed2986]

## One-line contribution
A decentralized Population-Based Training outer loop (mutating RL hyperparameters and reward-shaping coefficients) on top of PPO/Isaac Gym, applied to a 7-DoF Kuka arm + 16-DoF Allegro Hand system (single- and dual-arm) on regrasping, grasp-and-throw, and reorientation, letting single-arm reorientation reach non-trivial success where plain PPO fails to hit target tolerance (Fig. 4, Sec. IV).

## Method
- paradigm: RL (on-policy). algorithm: PPO [36], LSTM(768) + 3-layer MLP [768,512,256], ELU (paper Sec. III-C, Table II); implementation is the GPU-resident rl_games PPO [23] (code `train.py`/`rl_games` per README).
- PBT: decentralized Population-Based Training [13], population sizes |P| ∈ {8,16,32}; split 30%/40%/30% into top/mid/bottom (Table III); top continues untouched, mid is mutated, bottom is replaced by a mutated copy of a randomly sampled top-30% agent (Algorithm 1). Mutation: each float hyperparameter has probability β_mut=0.2 of being multiplied or divided by µ~U(1.1,1.5) (Algorithm 2, Table III). PBT delayed N_start=2×10^8 env steps, checked every N_iter=2×10^7 steps, with a burn-in N_adapt=5×10^7 steps after a mutation.
- meta-objective: combines tolerance progress and success count (Sec. III-D): "Until the target tolerance ε* is reached, this objective is dominated by the term 0≤(ε0−ε)/(ε0−ε*)≤1 which is maximized when ε approaches ε*. After the desired tolerance is reached the maximization of N_succ is prioritized." (exact closed form not fully OCR'd from the equation image; the described behavior is quoted verbatim.)
- key trick(s): keypoint-based object/goal representation (Nkp=4) unifying rotation+translation error into one tolerance; adaptive success-tolerance curriculum ε ← max(0.9ε, ε*) triggered once N_succ>3 (Sec. III-C) — code matches exactly: `successTolerance: 0.075` → `targetSuccessTolerance: 0.01`, `toleranceCurriculumIncrement: 0.9` (multiplicative), `toleranceCurriculumInterval: 3000` env-steps-across-agents (`AllegroKuka.yaml`); adaptive-KL learning rate (reduce ×1/1.5 if KL>threshold, else ×1.5, Sec. III-C).

## A. Embodiment block
- hand: Allegro Hand, 4-finger, 16-DoF; arm: Kuka (7-DoF), fully actuated, arm-mounted (not floating base). Bimanual variant: two Kuka+Allegro systems, 46 combined DoF, `armXOfs: 1.1` m offset (code).
- simulator: Isaac Gym; physics engine PhysX (implied by IsaacGymEnvs default; not explicitly restated for this task in the parsed dump). sim timestep `dt: 0.01667` (1/60 s), `substeps: 2`; control rate 60 Hz (`controlFrequencyInv: 1`).
- num parallel envs: 8192 (single-GPU). GPU: "8 CPU cores and a single Nvidia V100 GPU with 16 Gb of VRAM" (Sec. IV). Wall-clock: throughput 5×10^4 samples/s (single-arm) and 3.5×10^4 samples/s (dual-arm); "to train successful policies on 5×10^9 environment transitions, it takes 30 hours for single- and 40 hours for dual-arm tasks" (Sec. IV). Largest PBT run (|P|=32) trains to 10^10 steps per agent, 0.32 trillion env steps total (Sec. IV) — no aggregate GPU-hours given for that run.

## Evaluation
- exact success criterion: all Nkp keypoints (or object center, for position-only tasks) within tolerance ε* of target; final ε*=1 cm for regrasping/reorientation, ε*=7.5 cm for grasp-and-throw (Sec. III-A/B). Episode ends at N_max consecutive successes or first failure/drop; N_max=50 (code `maxConsecutiveSuccesses: 50`; paper Sec. IV: dual-arm reorientation "reaching almost 40 out of N_max=50 successes").
- metric: N_succ = number of consecutive successes per episode (Sec. III-A).
- headline numbers (Figs. 4-6, no exact numeric table given — read off plot descriptions in text): single-arm reorientation without PBT never reaches target tolerance in any of 8 seeds (Sec. IV, "without PBT none of the eight single-GPU training sessions reached the target tolerance"); dual-arm PBT reorientation reaches "almost 40 out of N_max=50"; scaling |P| to 16/32 agents over 10^10 steps reaches "N_succ>42 for the best agent" (Fig. 6, |P|=32).
- baselines beaten: "regular end-to-end learning" / non-PBT PPO with 8 independent seeds, same total compute (Sec. IV, Figs. 4-5).
- real robot? not stated — paper's Conclusion frames sim-to-real (domain randomization, RMPs/Geometric Fabrics) as future work; no real-robot trials reported in this paper.
- eval episodes/seeds: 8 seeds/agents per condition for Figs. 4-5; |P|=16 and |P|=32 for the scaling experiment (Fig. 6). Exact number of held-out evaluation episodes per checkpoint is not stated (paper notes `r_meta` is measured "at the end of the training iteration to approximate a separate evaluation procedure EVAL(θ)," i.e. it is not a distinct held-out eval run).

## C. Reward / objective block
Paper (Sec. III-C, Eq. 1-4), quoted:
- "r(s,a) = r_reach(s) + r_pick(s) + r_targ(s) − r_vel(a)" (Eq. 1)
- r_reach: "rewards the agent for moving the hand closer to the object at the start of the attempt," using current distance d and closest-so-far distance d_closest (end-effector to object; in dual-arm, "we calculate distance d for the end-effector that's closer to the object").
- r_pick: "rewards the agent for picking up the object and lifting it off the table," gated by indicator 1_picked which "becomes 1 once the height of the object relative to the table h_t exceeds a predefined threshold of 15 cm," at which point the agent "receives an additional sparse reward r_picked."
- r_targ = "1_picked ∗ α_targ ∗ max(d̂_closest − d̂, 0) + r_success" (Eq. 4), with d̂ = max over Nkp keypoint distances for reorientation, or center distance otherwise; "A large sparse reward r_success is added when the desired position and/or orientation is reached, d̂ = d̂_closest ≤ ε*."
- r_vel: "a simple joint velocity penalty that can be tuned to promote smoother movement."
- Table II initial reward coefficients: α_reach=50, α_pick=20, r_picked=300, α_targ=200, r_success=1000 (rightmost column shows one PBT-optimized dual-arm-reorientation example: 74.8, 22.1, 414.4, 263.5, 1322.7 respectively).

Code (`isaacgymenvs/tasks/allegro_kuka/allegro_kuka_base.py`, `compute_kuka_reward` and helpers, `code/md/dexpbt_2023.md` ~lines 5940-6070), quoted:
```
reward = (
    fingertip_delta_rew
    + hand_delta_penalty  # + sign here because hand_delta_penalty is negative
    + lifting_rew
    + lift_bonus_rew
    + keypoint_rew
    + kuka_actions_penalty
    + allegro_actions_penalty
    + bonus_rew
)
```
with, before summation: `hand_delta_penalty *= self.distance_delta_rew_scale * 0  # currently disabled`. Config weights (`AllegroKuka.yaml`): `distanceDeltaRewScale: 50.0`, `liftingRewScale: 20.0`, `liftingBonus: 300.0`, `liftingBonusThreshold: 0.15`, `keypointRewScale: 200.0`, `reachGoalBonus: 1000.0`, `kukaActionsPenaltyScale: 0.003`, `allegroActionsPenaltyScale: 0.0003`. `_lifting_reward` docstring: "Reward for lifting the object off the table." `_keypoint_reward`: administers `keypoint_rew` "only when we already lifted an object from the table to prevent the situation where the agent just rolls it around the table." `_action_penalties` (kuka/allegro action penalties) body is not present in code/md — only its signature is listed — so its exact functional form could not be quoted from code.

**Paper-vs-code mismatch (flagged):** the paper's reward is presented as four mutually exclusive stage terms (r_reach, r_pick, r_targ, −r_vel), explicitly stating "we apply virtually the same reward function in all scenarios." The code's actual `compute_kuka_reward` sums eight named components (`fingertip_delta_rew`, `hand_delta_penalty`, `lifting_rew`, `lift_bonus_rew`, `keypoint_rew`, `kuka_actions_penalty`, `allegro_actions_penalty`, `bonus_rew`), and one of those components — `hand_delta_penalty` (the paper's implicit "moving away" penalty inside r_reach) — is multiplied by 0 and thus disabled in this dump's config, i.e. not actually contributing despite existing in code. There is also no single joint-velocity penalty term `r_vel` in the code; instead there are separate `kukaActionsPenaltyScale`/`allegroActionsPenaltyScale` action penalties, whose exact formula is not shown in code/md. The five weight names/values that ARE named in both (α_reach≈distanceDeltaRewScale=50, α_pick≈liftingRewScale=20, r_picked≈liftingBonus=300, α_targ≈keypointRewScale=200, r_success≈reachGoalBonus=1000) match exactly between Table II's "initial value" column and the `AllegroKuka.yaml` defaults.

## Domain randomization (record from both; exact ranges)
Paper: no DR is used in the reported experiments. Domain randomization is mentioned only in the Conclusion as future work: "One of the most important future research directions is closing the sim-to-real gap. One approach ... is the randomization of physical parameters during training... Our approach, similar to DeXtreme [10] ... has the potential to significantly reduce computational requirements" — i.e. explicitly not yet applied here.
Code: `AllegroKuka.yaml` sets `task.randomize: False` by default (so DR is present in config but disabled), with `randomization_params` defining, if enabled: observations noise `range: [0, .002]` (white) / `range_correlated: [0, .001]`, additive Gaussian, `schedule_steps: 40000`; actions noise `range: [0., .05]` / `range_correlated: [0, .015]`, additive Gaussian, `schedule_steps: 40000`; gravity `range: [0, 0.4]`, additive Gaussian, `schedule_steps: 40000`; Allegro `dof_properties`: damping scaling range `[0.3, 3.0]` (loguniform), stiffness scaling `[0.75, 1.5]` (loguniform), lower/upper joint-limit additive Gaussian `[0, 0.01]`, all `schedule_steps: 30000`; Allegro `rigid_body_properties.mass` scaling `[0.5, 1.5]` (uniform); Allegro `rigid_shape_properties.friction` scaling `[0.7, 1.3]` (uniform, 250 buckets); object `scale` `[0.5, 2.0]` (uniform, `schedule_steps: 1`), object `mass` `[0.5, 1.5]` (uniform), object `friction` `[0.7, 1.3]` (uniform, 250 buckets). Random disturbance forces on the object (separate from the DR block): `forceScale: 2.0`, `forceProbRange: [0.001, 0.1]`, `forceDecay: 0.99`, `forceDecayInterval: 0.08` — disabled for the throw subtask (`forceScale: 0.0`, "random forces don't allow us to throw precisely so we turn them off").
**Mismatch note:** this is a mismatch worth flagging on its own — the paper reports zero experiments with DR turned on, yet the shipped task config already carries a fully specified DR schedule (`randomize: False` as the switch), identical in spirit to DeXtreme's ADR/manual-DR machinery in the same repo.

## Limitations stated by the authors
"Our scenarios only cover a small part of the robotic dexterity domain." Policies show "aggressive control on the limits of robot capabilities which can lead to equipment damage in the real world" — proposed mitigation: Riemannian Motion Policies or Geometric Fabrics for safety priors (not implemented here). Sim-to-real gap not closed: no domain randomization was used in these experiments, which the authors flag as future work, noting DR "is particularly challenging and can require substantial computational budget" (citing Dactyl).

## Quotable claims (verbatim, with section)
- "we introduce a decentralized Population-Based Training (PBT) algorithm that allows us to massively amplify the exploration capabilities of deep reinforcement learning" (Abstract).
- "in single-arm reorientation task, without PBT none of the eight single-GPU training sessions reached the target tolerance" (Sec. IV).
- "the dual-arm task requires the agent to constantly pass the object from one hand to another, as a result the policy became more confident at juggling and tossing the object in-hand, while single-handed agents tend to rely on more conservative in-hand rotations" (Sec. IV).
- "only our largest experiment (|P|=32) was able to find solutions with higher γ. The highest-performing agent in this experiment employs an alternative strategy: for certain reorientations it chooses to place the object back on the table, rotate it, and then pick up again and put the object into the target position" (Sec. IV).
