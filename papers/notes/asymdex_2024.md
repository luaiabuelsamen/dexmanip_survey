# asymdex_2024 — AsymDex: Asymmetry and Relative Coordinates for RL-based Bimanual Dexterity (Yang, Han, Hu, Ravichandar, RSS 2025 WCBM workshop / arXiv 2024)

sources: papers/md/asymdex_2024.md [56f529de / arxiv 2411.13020] ; code/md/asymdex_2024.md [40b29f95]

## One-line contribution
AsymDex is a demonstration-free RL framework for bimanual dexterous manipulation that (1) assigns a fixed "dominant hand" (full finger+wrist control) and "facilitating hand" (6-DoF base pose only, no finger control) role split, and (2) represents observations/actions in a frame relative to the object held by the facilitating hand, cutting observation/action dimensionality roughly in half and enabling sample-efficient PPO training on seven bimanual dexterous tasks (four sim, three real) without any demonstrations (Abstract, §3-4).

## Setting
- hand(s): simulation experiments use two Shadow Hands, "each a 30-DoF simulated multi-finger hand system (24-DoF hand + 6-DoF floating wrist base)" built in Isaac Gym (§5.1) — multi-fingered. Real-world experiments use "one 16-dof Allegro hand from Wonik Robotics and one 6-DoF Ability Hand from Psyonic" (§5.2) — i.e. the two real hands are of DIFFERENT models/DoF (Allegro used only because a second physical unit wasn't available), both multi-fingered, not grippers. Arm: real setup mounts the two hands on two 7-DoF Kinova Gen3 arms. Bimanual, fixed torso (tabletop dual-arm rig, no mobile base or humanoid torso).
- simulator / physics: Isaac Gym (§5.1); `max_depenetration_velocity: 1000.0` appears in essentially every task config file in code (a generic PhysX solver setting, not a paper-specific contact model — this is Isaac Gym's default depenetration-velocity cap, not evidence of a custom collision-handling scheme).
- observation: general (symmetric) formulation z(t) = [ξ1(t), ξ2(t), ξ_obj(t)] where each ξ_i(t) contains the hand's full (fingers+wrist) configuration ξ_i^h(t) and its 6-DoF base pose ξ_i^b(t)∈SE(3), and ξ_obj(t) contains the 6-DoF poses of up to two objects/parts (§3). AsymDex's reduced observation z_AsymDex(t) = [ξ_d^h(t), ξ_r^b(t), ξ_r^obj(t)] — the dominant hand's full joint state, plus the dominant hand base pose and the manipulated-object pose, BOTH expressed relative to a coordinate frame P_f attached to the object held by the facilitating hand (§4.2); the facilitating hand's own joint/base state is dropped entirely from the observation since it is provably invariant in that frame. Confirmed dimension counts (Table 4, sim tasks; all four tasks identical): Sym 176-dim obs / 52-dim action; Asym-w/o-rel 108/32; Rel-w/o-Asym 163/46; AsymDex 88/26. Real-world tasks (Table 5): Sym 60/44; Asym-w/o-rel 44/28; Rel-w/o-Asym 53/38; AsymDex 30/22.
- action space: general a(t) = [ξ̂1(t), ξ̂2(t)] (target joint config + target 6-DoF base pose for each hand, §3). AsymDex's reduced action a_AsymDex(t) = (ξ̂_r^b(t), ξ̂_d^h(t)) — target relative base pose of the dominant hand (relative to P_f) plus target joint configuration of the dominant hand only; the facilitating hand's action is not learned directly but computed by a separate "Relative Pose Tracking Controller" (§4.3, Eqn. 1) that converts the policy's relative target into absolute target poses for both hand bases using a rotational transform R_world^f from P_f to the world frame and a hyperparameter α controlling "the relative involvement of each hand."
- objects / data: no demonstrations used anywhere ("does not rely on demonstrations", Abstract) — pure RL from scratch, except for the separately-trained grasping policy (PDGM-based) used in the two-phase/acquisition experiments (§4.4). Simulation tasks are original or BiDexHands-adapted: Block in cup, Stack, Bottle cap (original), Switch (adapted from BiDexHands, made harder by removing the supporting table surface). Real-world tasks: Block in Cup, Pour (dry beans between cups), Twist Lid.

## Method
- paradigm: pure RL (PPO), demonstration-free, with an optional two-stage acquisition+interaction decomposition integrating a separately-learned grasping policy (PDGM-style) for the acquisition phase (§4.4).
- algorithm: PPO for π_sym, π_asym, and π_AsymDex, each with its own value function; policy and value networks are 3-layer MLPs — policy hidden sizes (256, 256, 128), value function hidden sizes (512, 512, 512), ELU activations; PPO hyperparameters shared across all baselines and AsymDex: γ=0.98, λ=0.95, clip range 0.2, minibatch size 8092, adaptive learning rate with KL threshold 0.016; trained on a single NVIDIA RTX 4090 GPU (Appendix A).
- teacher-student / privileged->vision distillation: none — this is state-based RL throughout, no vision, no distillation stage.
- observation vector, item by item (Appendix A, Algorithm 1 "AsymDex: Interaction Phase"): collect ξ_f^b(t), ξ_d^b(t), ξ_d^h(t), o_f(t), o_d(t); compute relative states ξ_r^b(t) = ξ_d^b(t) ⊖ P_f and o_r(t) = o_d(t) ⊖ P_f; policy π_AsymDex(ξ̂_r^b(t), ξ̂_d^h(t) | ξ_r^b(t), ξ_d^h(t), o_r(t)) outputs relative actions; the bimanual controller (Eqn. 1) converts ξ̂_r^b(t) into absolute target poses ξ̂_f^b(t), ξ̂_d^b(t) for both hand bases before physics stepping.
- domain randomization: for sim-to-real transfer specifically (not for the simulation-only comparisons) — "we apply domain randomization during reinforcement learning" (§5.2); for Block in Cup and Pour, only "observation noise" was needed; for the hardest task, Twist Lid, "we added observation noise and action noise, as well as other randomization components" (§5.2, full details deferred to Appendix D, exact ranges not captured in the parsed excerpt beyond this qualitative statement).

## Reward / objective block (quoted per HOWTO_METHOD)
Paper's general BiDexHands task reward (Appendix C, quoted): "Reward = α1 R_hand_distance + α2 R_progress + α3 R_action_penalty + α4 R_success_bonus", where R_action_penalty = -||a(t)||^2 and R_success_bonus is the task success reward; R_hand_distance and R_progress are task-specific:
- Block in cup: R_hand_distance = e^(-||x_palm - x_cupmouth||) (dominant-hand palm to cup mouth); R_progress = -||x_cup - x_block||.
- Stack: R_hand_distance = e^(-||x_palm - x_cupmouth||) (cup held by facilitating hand); R_progress = -||x_cup_d - x_cup_f||.
- Bottle cap: R_hand_distance = (1 - (||x_index - x_cap|| + ||x_thumb - x_cap||))^3; R_progress = ||x_cap - x_bottletop||.
- Switch: R_hand_distance = (1 - (||x_index - x_button|| + ||x_thumb - x_button||))^3; R_progress = 2*θ_button (rotated joint angle).
Grasping-phase reward for the two-stage acquisition policies (Appendix B, quoted): "Reward = R_rel_pos + R_rel_rot", where R_rel_pos = (α - ||x_obj - x_initial||)*β (keeping the object's relative position to the hand constant during a scripted lift) and R_rel_rot = <u_obj, u_hand> (inner product of object and hand direction vectors, initialized equal). Code (`bidexhands/environments/.../AllegroHandDualArmGraspAndPlaceAsymDex.py`, function `compute_hand_reward`) shows a related but not identical reward construction for the GraspAndPlace task family: exponential hand-distance terms `right_hand_dist_rew = exp(-10*right_hand_cup_dist)`, `left_hand_dist_rew = exp(-10*left_hand_block_dist)`, goal-distance terms `exp(-1*...)`, a block-alignment term `up_rew = exp(-10*||block_right_handle_pos - block_left_handle_pos||)*2`, and an action penalty `sum(actions**2)/50` — this is a GraspAndPlace-specific variant not one of the four paper-described BiDexHands tasks (Block in cup/Stack/Bottle cap/Switch), so it should be read as an additional task family present in the codebase but not detailed in the paper body; no explicit hand-hand collision/penetration term appears in this reward function.

## Contact / penetration handling
Not addressed via any explicit interpenetration penalty or measurement in either the paper text or the inspected reward-function code. The only collision-adjacent design element is architectural, not a reward term: the coordination scheme is built so the facilitating hand holds an object with "no relative motion between the facilitating hand and the object that it is holding... i.e., no in-hand reorientation" (§4.1) — this reduces unwanted hand-object slip by construction rather than by penalizing penetration. Code's `max_depenetration_velocity: 1000.0` is a generic Isaac Gym/PhysX solver parameter present in every task config, not an authored contact-penalty term. No two-hand collision-avoidance reward or measurement is reported anywhere.

## Coordination and embodiment (survey fields)
- two-hand coordination: explicit, fixed leader/follower-style role assignment PLUS relative-frame observations — this is the most explicit example of "asymmetric role assignment" in the whole survey batch. A "dominant hand" performs full finger+wrist manipulation; a "facilitating hand" only repositions/reorients the held object via its 6-DoF base pose (no finger control) (§4.1). On top of this asymmetry, AsymDex expresses the dominant hand's pose and the manipulated object's pose in a coordinate frame P_f attached to the object held by the facilitating hand (§4.2) — a genuine relative-frame bimanual representation, not merely a role split. A single policy (π_AsymDex) outputs actions for the dominant hand (and, via the separate bimanual controller, implicitly for the facilitating hand's base target) — so it is "one policy," but that policy's action space itself encodes the asymmetric role split, unlike a symmetric single policy over both full hands (the `Sym` baseline, π_sym(a(t)|z(t))). Authors explicitly distinguish AsymDex's simultaneous-role design from prior asymmetric bimanual work: "some of these approaches restrict the role of the facilitating hand to stabilizing the object while the dominant hand manipulates it... In contrast, AsymDex allows the facilitating hand to reposition and reorient the object simultaneously as the dominant hand executes its role" (§2).
- torso: fixed — tabletop dual-arm setup (sim: two Shadow Hands with floating 6-DoF wrist bases, no described torso; real: two Kinova Gen3 arms mounted presumably on a fixed table/frame), no locomotion or mobile base.
- hand model/DoF each side: simulation — identical Shadow Hands both sides (30 DoF: 24-DoF hand + 6-DoF floating wrist). Real world — asymmetric hardware: 16-DoF Allegro hand on one side, 6-DoF Ability Hand on the other, explicitly because only one physical Allegro hand was available ("We used the Ability Hand for one of the hands since we only had access to one physical Allegro hand," §5.2) — i.e. the real-world hand mismatch is a hardware-availability artifact, not a deliberate asymmetric-hand design choice, though it does mean the dominant/facilitating role assignment in the real experiments is confounded with which physical hand is used.

## Evaluation
- metrics (exact definitions): success rate (task-specific criteria, Appendix C/D) and sample efficiency (learning curves), reported "across five random seeds in all experiments" (§5.1). Success criteria (Appendix C, quoted): Block in cup — "distance of the block center and the cup center is smaller than 0.035 meters"; Stack — "distance between the cup centers is smaller than 0.02 meters"; Bottle cap — "cap is taken off from its original position 0.05 meters away within a time duration"; Switch — "button is pressed and rotated 0.3585 rads within a time duration" (joint range 0 to 0.5585 rad).
- headline numbers: Table 1 (interaction-phase-only, hands pre-positioned near objects, mean±std over 5 seeds): AsymDex vs. Sym / Asym-w/o-rel / Rel-w/o-Asym — Block in cup 0.7701±0.0559 vs. 0.0429±0.0266 / 0.0164±0.0190 / 0.1086±0.1378; Stack 0.8392±0.0596 vs. 0.0771±0.0611 / 0.2185±0.3232 / 0.6560±0.3213; Bottle cap 0.6295±0.1422 vs. 0.3111±0.1813 / 0.4143±0.1410 / 0.4730±0.2011; Switch 0.6700±0.0359 vs. 0.0563±0.0126 / 0.1626±0.0882 / 0.1149±0.0176. Table 2 (acquisition+interaction combined, mean±std over 5 seeds): AsymDex vs. Monolithic / 2-stage-sym — Block in cup 0.7938±0.0897 vs. 0.0321±0.0251 / 0.1505±0.1059; Bottle cap 0.6116±0.1328 vs. 0.0±0.0 / 0.2552±0.1573. Table 3 (real-world zero-shot deployment, AsymDex only): Block in Cup 16/20, Pouring 17/20, Twist Lid 18/20.
- baselines beaten: `Sym` (symmetric monolithic policy, no asymmetry or relative spaces), `Asym-w/o-rel` (asymmetry only, absolute coordinates), `Rel-w/o-Asym` (relative spaces only, symmetric roles), `Monolithic` (single policy for both acquisition and interaction phases, no decomposition), `2-stage-sym` (two-phase decomposition without asymmetry or relative spaces). All ablations directly test AsymDex's two claimed design ingredients (asymmetry, relative spaces) plus the phase-decomposition contribution.
- baselines beaten (real): none deployed except AsymDex — "We deployed only the AsymDex policies on hardware since the baseline policies tended to exhibit either negligible success rates or aggressive behaviors that could damage the hardware" (§5.2) — i.e. real-world baseline comparisons could not be run for safety/performance reasons, only simulated counterparts of the real tasks were compared (Fig. 4b).
- real robot? Yes for Table 3 — two Kinova Gen3 arms with Allegro + Ability hands, 20 trials per task (16/20, 17/20, 18/20 for Block in Cup / Pouring / Twist Lid), zero-shot sim-to-real transfer with task-specific domain randomization (observation noise only for the first two; observation+action noise plus additional randomization for Twist Lid).

## Limitations stated by the authors
"AsymDex in its current form cannot handle certain bimanual tasks that require complex multi-finger manipulation from both hands (e.g., reorienting a heavy object, dynamic handover)." "AsymDex does not consider the kinodynamic constraints that might result from manipulator arms" (i.e. the arm/IK layer is not explicitly modeled in the RL problem). "Behaviors produced by AsymDex are not always natural or human-like due to lack of necessary incentives" (§7).

## Quotable claims (verbatim, with section)
- "we assign complementary roles to each hand: the facilitating hand repositions and reorients one object, while the dominant hand performs complex manipulations to achieve the desired result" (Abstract).
- "AsymDex allows the facilitating hand to reposition and reorient the object simultaneously as the dominant hand executes its role" (§2) — contrasted with prior work that restricts the facilitating hand to pure stabilization.
- "We deployed only the AsymDex policies on hardware since the baseline policies tended to exhibit either negligible success rates or aggressive behaviors that could damage the hardware" (§5.2).
- "AsymDex is able to reposition and reorient both hand bases while two hands interact, enabling more fluent bimanual coordination," unlike prior work "which fixes the hand base motion" (§5.2).

## Notes for the survey (which sections this feeds; contradictions with other notes)
Feeds: the central "how are the two hands coordinated" comparison row for the whole survey — AsymDex is the cleanest, most explicitly-labeled example of (a) an asymmetric leader/follower-style role split and (b) genuine relative-frame bimanual observations/actions, both ablated in isolation (Table 1: `Asym-w/o-rel` vs `Rel-w/o-Asym` vs `Sym` vs `AsymDex`), giving the survey hard numbers on how much each mechanism contributes independently — directly relevant when comparing to humanplus_2024/gr_dexter_2025/humanoid_sim2real_recipe_2025's "one policy over both hands, no explicit relative frame" designs and to dexmimicgen_2024's structural (not RL-observation) relative-pose preservation in coordination subtasks. Also worth flagging for the survey's real-world-hardware table: this is the one paper here that deploys two DIFFERENT hand models simultaneously (16-DoF Allegro + 6-DoF Ability Hand) purely due to hardware availability, not by design — a caveat when comparing "matched vs. mismatched hand hardware" across bimanual setups. No demonstration data of any kind is used (pure RL) — distinct from every other note in this batch except humanoid_sim2real_recipe_2025 (which also trains from scratch via RL, though with a human-play initialization step AsymDex does not use).
