# dexmachina_2025 — DexMachina: Functional Retargeting for Bimanual Dexterous Manipulation (Mandi, Hou, Fox, Narang, Mandlekar, Song; arXiv 2025)

sources: papers/md/dexmachina_2025.md [7b67a6ad] ; code/md/dexmachina_2025.md [adae5bf6]

Parse caveat: the displayed equations for r_imi, r_bc, r_con and the hybrid-action mapping (Sec. 4.2, App. A.3) are images and are blank in the markdown; Fig. 3 and Fig. 5 (the main results) are bar charts with no numbers in the text. ## One-line contribution
"Functional retargeting": RL policies for a pair of dexterous hands that make an articulated object track one ARCTIC human demonstration, trained with a curriculum of decaying virtual object controllers (spring-dampers that first move the object themselves) plus motion and contact auxiliary rewards; released as a benchmark over 6 hands and 5 objects (abstract; Sec. 1 contributions).

## Setting
- hand(s): six open-source hand URDFs, each given a 6-DoF floating wrist: Inspire, Allegro, XHand, Schunk (main results), plus Ability and DexRobot "Dex Hand" (Sec. 5.1, 5.3; App. A.1). No arm. bimanual.
- simulator / physics: Genesis (Sec. 5; App. B.1). 12,000 parallel envs (10,000 for Dex Hand), one L40s or H100 per run (App. B.1). Timestep not stated in the parse (`dt` is an argument of `get_scene_cfg` in code/md dexmachina/envs/base_env.py). Hand assets manually edited: mass/inertia changed, convex decomposition for collision meshes, dummy fingertip links (App. A.1).
- observation: "state-based input ... object states, joint targets, finger-to-object distances, and normalized hand-object contact forces" (App. B.2). Code, dexmachina/envs/robot.py `get_observations`: per hand `dof_target_pos` (target − pos), `dof_pos` (unscaled to limits), `dof_vel`, `kpt_pos`, `wrist_pose` (7); dexmachina/envs/object.py `get_observations`: `parts_pos`, `parts_quat`, `dof_pos`, `state_diff` (8), `root_ang_vel`, `root_lin_vel`; base_env.py `get_observations` appends normalised episode time, optionally keypoint-to-part-surface distances for both hands and both parts (`observe_tip_dist`), and contact-force norms ×0.01 (`observe_contact_force`). Critic gets the same obs (`critic=obs`).
- action space: hybrid — wrist 6-DoF: retargeted joint value as base + policy residual (scaled by s_T, s_R); finger joints: absolute, normalised by joint limits (Sec. 4.2, App. A.3). Code group cfg `env_kwargs.robot_cfgs.left.hybrid_scales: [0.1, 1]` and `action_mode: hybrid` (code/md dexmachina/eval/group_cfgs/dexmachina_main.yaml). PD joint control.
- objects / data: ARCTIC [10]: 5 articulated objects, 7 clips; clip = object + subject tag + (start, end) (Sec. 5; App. A.1). Group cfg lists: ketchup30-130-s01-u01, box30-230-s01-u01, mixer30-200-s01-u01, ketchup40-340-s01-u02, mixer40-340-s01-u01, notebook40-340-s02-u02, waffleiron40-340-s01-u01. The last four (300 frames) are the long-horizon tasks (Sec. 5.1, footnote 2).

## Method
- paradigm: RL, sim only ; algorithm: PPO via rl-games (App. B.1). Code cfg dexmachina/rl/configs/rl_games_ppo_cfg.yaml: MLP [512,512,256,128] ELU, shared actor-critic (`separate: False`), fixed sigma, gamma 0.99, tau 0.95, lr 3e-4 adaptive with kl_threshold 0.008, e_clip 0.2, horizon 32, minibatch 2048, mini_epochs 5, critic_coef 4, entropy 0, reward_shaper scale 0.1, clip_observations 5.0.
- coordination of the two hands: one policy "control[s] both hands at once" with a shared observation vector concatenating left robot, right robot, and object entries (Sec. 5; base_env.py `get_observations` iterates `self.robots` then `self.objects`). Roles come from the demonstration: each hand has its own retargeted wrist base action, keypoint references, and contact targets (App. A.4: "each bi-manual RL task environment has two copies of contact information"). The policy may deviate from the demonstrated role split, e.g. Inspire "learns to use both hands to stabilize the object and close the cover" where the human used one (Sec. 5.1, Fig. 4).
- reward (paper, Sec. 4.1-4.2): r_task = r_pos · r_rot · r_angle = exp(−β_pos d_pos) exp(−β_rot d_rot) exp(−β_ang d_ang); r_imi (keypoint matching), r_bc (joint-angle distance to retargeted joints), r_con (masked L2 between policy and demo contact positions per hand link and object part); total r_t = λ_task r_task + λ_imi r_imi + λ_bc r_bc + λ_con r_con. The text says "See Appendix A.4 for precise weights" but A.4 contains only the contact approximation; no λ values are printed.
- reward (code, dexmachina/envs/rewards.py `get_reward_cfg` defaults): obj_pos_beta 20.0, obj_rot_beta 5.0, obj_arti_beta 20.0, `multiply_task_rew: True`, task_rew_weight 1.0; imi_fingertip_beta 20.0 with `exp_kpt_first` (mean over links of exp(−β d), averaged over left/right), imi_wrist_weight 0.0; bc_beta 500.0; contact_rew_function "exp", contact_beta 30.0, contact computed in both object and wrist frames (`wrist_frame_contact: True`) via `chamfer_distance` per part id (1 = top, 2 = bottom); force_penalty 0.1 ("~60 contact pairs in each env"), action_penalty 0.0. Defaults set imi/bc/contact weights to 0.0; the main-results group cfg (dexmachina/eval/group_cfgs/dexmachina_main.yaml) selects runs with `imi_rew_weight: 0.2` (0.3 for Inspire), `contact_rew_weight: 2`, and `curriculum_cfg.lower_ratios.kp: 0.5` or 0.6, `schedule: uniform`, 5 seeds (42, 24, 66, 15, 113). No bc weight is set in that cfg, so the BC term appears unused in the main results. `compute_task_reward` also defines `well_track = (pos_dist < 0.005) & (rot_dist < 0.1) & (arti_dist < 0.1) & (demo_arti > 0.1)` with an optional bonus scale (default 1.0, i.e. off). The body of `compute_reward` (the weighted sum) is not in the code md; only its signature is.
- mismatch: the paper writes a plain weighted sum with unspecified λ; the code exposes a multiplicative task term with per-component β, a contact-force penalty (0.1) not mentioned in the paper, and curriculum-driven decay of the auxiliary weights (`Curriculum.decay_reward_weights`: ×0.95 per trigger for imi/bc/contact weights and thresholds) which the paper describes only as auxiliary weights being "much smaller" (Sec. 4.3).
- curriculum (Sec. 4.3, Alg. 1): object gets six virtual 1-DoF base joints plus its articulation joint, all PD-actuated toward the demo state; gains (kp, kv) start high with critical damping and decay exponentially when all four running-mean normalised rewards exceed thresholds σ; kp ≤ 0.01 → 0. Code: dexmachina/envs/curriculum.py (`set_auto_exp_decay`, `set_auto_uniform_decay`, `determine_dialback`, `reset_solimp`); dexmachina/envs/object.py `set_joint_gains(kp, kv, force_range, env_idxs)`.
- interpenetration / contact: (a) retargeting post-processing — pure kinematic retargeting "results in frequent penetration with the object"; they replay retargeted joints as soft PD targets with the object fixed at its demo state and record the achieved joints/keypoints, "to eliminate object penetrations" (Sec. 4.2 item 1; App. A.2). (b) demo contacts approximated by object-mesh vertices within γ = 0.01 of the MANO mesh, max N_c = 50, farthest-point subsampled, assigned to nearest hand link (App. A.4). (c) Genesis "uses a more stable simulation contact modeling" (App. B.3). (d) code: `create_scene(..., enable_self_collision)` and `group_collisions` args, contact-force observation scaled ×0.01, `force_penalty` 0.1. No penetration metric is measured or reported.
- key trick(s): hybrid wrist-residual/finger-absolute actions (Fig. 8: tighter wrist bounds beat absolute and full-residual actions, 3 seeds, no curriculum); per-part ADD-AUC as the single success metric (App. B.4).

## Evaluation
- metrics: per-part ADD-AUC — "we compute ADD for each object part separately (to accommodate articulated objects) and average ADD results before computing AUC"; reported as one "success rate" per method (App. B.4). Explicitly chosen over per-step threshold success [35] and raw tracking error [36]. Evaluation: 5 seeds, best checkpoint by cumulative task reward, 20 episodes each (App. B.4).
- headline numbers: Fig. 3 (4 hands × 7 clips, values not in the parse) — "With rare exceptions, DexMachina demonstrates clear improvements over baseline methods, especially on long-horizon tasks" (Fig. 3 caption). Only printed numbers, App. B.3: re-implemented ObjDex on Ketchup-100 ">90% success rate for all hands, whereas the original paper reports 41.2%"; Mixer-170 ">70% ... for three out of four hands, whereas the paper reports 57.6%". Fig. 5: all six hands on the four long-horizon tasks (values not in the parse).
- baselines beaten (Fig. 3): Kinematics Only (cannot lift beyond "slightly"), Task Rew (ObjDex re-impl.), Task + Aux Reward without curriculum, ManipTrans curriculum re-impl. (Sec. 5.1-5.2). The ManipTrans re-implementation "achieves no clear improvements over the no-curriculum setting" and its performance "drops as the curriculum progresses and cannot recover" (Sec. 5.2); its gravity/friction ranges were chosen by the authors (g ∈ [0, −9.81], μ ∈ [4.0, 1.0]) because the original did not disclose them (App. B.3).
- hardware findings (Sec. 5.3): "Larger, fully-actuated hands achieve both higher final performance and better learning efficiency"; Allegro "surprisingly capable due to its long finger length"; Schunk beats similar-sized Inspire and Ability.
- real robot? none — "our learned RL policies have not yet been evaluated in real-world settings" (Sec. 7).

## Limitations stated by the authors (Sec. 7)
- State-based input "relies on privileged information from the physics simulator".
- Requires "high-quality human hand-object demonstration data" (ARCTIC uses mocap with dense manual annotation).
- Hand assets' mass, inertia, collision shapes are estimated; "simulated hands might fail to capture some of the dynamics and capabilities of the real hardware".
- No real-world evaluation.
- Conclusions "limited by the objects and tasks that we test on" (Sec. 5.3).

## Quotable claims (verbatim, with section)
- "a purely kinematic retargeting algorithm [26] on fingertip positions results in frequent penetration with the object, which leads to damaging base-actions during policy learning" (App. A.2)
- "The auxiliary rewards do not always align with the best task strategy, but instead act as soft guidance to serve the curriculum" (Sec. 5.1)
- "merely decaying physics parameters is not sufficient for long-horizon tasks with articulated objects" (Sec. 5.2, on ManipTrans)
- "Similarity in size is less important than degrees of freedom." (Sec. 5.3)
- "success rate reporting is based on how many timesteps ... within given error thresholds, hence the results are highly sensitive to the threshold values" (App. B.4)

## Notes for the survey
- Feeds: bimanual physics-based tracking from human demos; curriculum design (virtual object controllers vs. ManipTrans's physics-parameter decay); benchmark for hand morphology; metric choice for articulated tracking.
- Direct contradiction with maniptrans_2025's framing: here ManipTrans's curriculum (re-implemented, Genesis, ARCTIC) does not beat no-curriculum; their own paper evaluates on rigid objects in Isaac Gym. Both claims are on different setups; quote both.
- Penetration is handled once, offline, in retargeting (object fixed, hands pushed out by the sim); at policy time the only contact-related terms are a matched-contact reward and a 0.1 force penalty. No penetration is measured. Relevant to the survey's interpenetration section as an example of "resolved by replay" — compare the replay-is-placement caveat.
- Headline success values are figure-only; do not quote a DexMachina number beyond the App. B.3 ObjDex re-implementation figures without going back to the PDF.
