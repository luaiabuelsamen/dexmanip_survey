# tacto_2020 — TACTO: A Fast, Flexible, and Open-source Simulator for High-Resolution Vision-based Tactile Sensors (Wang, Sanchez-Gonzalez, Bauza, et al.; Meta AI, IEEE RA-L 2022, arXiv 2020)

sources: papers/md/tacto_2020.md [3d656371] ; code/md/tacto_2020.md [a21d0c46]

## One-line contribution
Renders realistic RGB+depth tactile-sensor imprints (DIGIT, OmniTact) by synchronizing a physics engine's (PyBullet's) contact geometry into an OpenGL/Pyrender scene at up to 200 FPS per sensor, plus a force-to-deformation mapping and optional real-sensor calibration/fine-tuning (Abstract, Sec. III).

## Setting
- hand(s): four DIGIT sensors mounted on an Allegro hand (rendering demo, 50 FPS on GPU, Sec. III-D "Fast"); two DIGIT sensors on a WSG-50 parallel-jaw gripper (grasp-stability experiment, Sec. IV-A); two DIGIT sensors, one fixed/one actuated, for in-hand marble rolling (Sec. IV-B).
- simulator / physics: PyBullet as the default physics backend providing rigid-body contact forces ("currently by default PyBullet with a rigid body contact model," Sec. III-D "Force dependent"); TACTO itself is a rendering/synchronization layer on top, using Pyrender (OpenGL) for the vision-based tactile image.
- observation: what signal is simulated — RGB and depth "tactile imprint" images per sensor (e.g. 160×120 default), i.e. an **optical image**, not a raw force field or marker-flow field directly (TACTO's own marker/flow modeling is not implemented in this paper — that is Taxim's contribution). A force→deformation piecewise-linear mapping perturbs the rendered gel mesh so "light forces will yield fewer deformations, and higher forces to more deformation of the gel," with a lower threshold (below which no deformation is sensed) and an upper saturation threshold (Sec. III-D "Force dependent").
- action space / data: 1,000,000 self-supervised grasps (randomized position/orientation/gripper force) collected in one day with 5 parallel threads on a single box object, labeled by whether the object stayed gripped after lift-off (Sec. IV-A).

## Physics block
- contact model: whatever the underlying physics engine provides — PyBullet's rigid-body contact model by default (Sec. III-D). TACTO does not introduce or modify a contact solver; it reads post-solve object/link poses and (for the "Force dependent" feature) the physics engine's reported normal contact force, then maps that force to a *rendering-level* gel-mesh deformation, not to a physically resolved soft-body contact.
- solver and iterations: not applicable — TACTO defers entirely to the host physics engine's own solver (PyBullet or, via the two documented integration paths, any engine that exposes link poses and contact forces, Sec. III-D "Compatibility to different physics engines").
- differentiability: not discussed / not implemented in this paper.
- timestep: not stated (inherited from whichever physics engine and its own default timestep; TACTO's rendering step is decoupled — "physics simulation can run asynchronously to speed up," Table I caption).
- friction model: not discussed — again inherited from the underlying rigid-body engine (PyBullet), not a TACTO-level model.
- how penetration is resolved / is depth exposed: not addressed as a physics quantity. TACTO instead reports a rendering-level "depth image" per tactile sensor (the local contact-region height map used to synthesize the RGB imprint), not an interpenetration measurement between rigid bodies.
- GPU or CPU: both supported; Table I benchmarks a CPU machine (Intel Core i7-6820HQ) and a GPU machine (NVIDIA RTX 2080 Super + Intel Core i9-9900K), excluding physics-simulation time.
- throughput with the table and hardware (Table I, DIGIT sensor, 12K-face object meshes, times in ms per stage — Step/Sync/Render — and overall FPS excluding physics simulation): **GPU** (RTX 2080 Super + i9-9900K) — 1 object in contact: 160×120 → 220 FPS; 320×240 → 140 FPS; 640×480 → 90 FPS. 100 objects (1 in contact): 160×120 → 200 FPS; 320×240 → 100 FPS; 640×480 → 90 FPS. 100 objects (100 in contact): 160×120 → 80 FPS; 320×240 → 60 FPS; 640×480 → 50 FPS. **CPU** (i7-6820HQ) — 1 object in contact: 160×120 → 60 FPS; 320×240 → 30 FPS; 640×480 → 10 FPS; 100 objects (100 in contact), 640×480 → 10 FPS. Four DIGIT sensors on an Allegro hand render at 50 FPS on GPU at 160×120 (Sec. III-D "Fast"). Shadow rendering adds "only ≈2 extra milliseconds" on GPU (meshes 19K faces, 640×480, Sec. III-D "Calibration").

## Tactile-specific fields
- signal simulated: optical RGB + depth tactile image (a rendered "imprint"), i.e. the vision-based-tactile-sensor image, not a marker-flow field and not a raw normal-force array. (Marker/flow and force-field simulation are cited as future/related work, not implemented here.)
- real sensor calibrated against: DIGIT (Lambeta et al.) and OmniTact (5-camera, 11-light complex sensor); GelSight-style sensors are the broader target class the architecture is designed for.
- reported sim-to-real error (Table II, pose-estimation of a contact pen, position in mm / rotation in degrees, mean ± std over 5 repeats): Random baseline 11.75±1.15 mm / 46.56±5.91°; Sim2Sim 0.41±0.01 mm / 3.48±0.34°; Real2Real (16 datapoints) 4.45±0.86 / 33.85±1.07; Real2Real (32) 3.48±0.56 / 25.45±2.07; Real2Real (64) 2.01±0.14 / 10.96±0.24; Real2Real (128) 0.76±0.07 / 4.96±0.70; **Sim2Real without augmentation** 4.56±0.40 mm / 17.64±2.34°; **Sim2Real with augmentation** (color jitter) 1.66±0.16 mm / 11.60±4.65°; Sim+Real mixed (16/32/64/128 real datapoints) improves monotonically from 1.55±0.12 / 9.08±1.65 down to **0.52±0.03 mm / 4.14±0.57°** at 128 real datapoints mixed in (best overall result in the table). Sim2Real-with-augmentation is roughly comparable to Real2Real(64).
- optical-simulation quality vs. other simulators (Table I in the companion paper `taxim_2021`, quoted there): TACTO scores L1=10.861, MSE=215.861, SSIM=0.808, PSNR=25.495 against real DIGIT images — worse on every metric than Taxim's example-based method (L1=5.565, MSE=58.358, SSIM=0.882, PSNR=30.974) and worse than a Phong's-model baseline on MSE/SSIM; TACTO is also the slowest of the compared methods at 1.9 fps on CPU vs. Taxim's 9.6-18.1 fps (`taxim_2021` Table II) — TACTO is designed for GPU-accelerated OpenGL rendering, so this CPU-only comparison undersells its GPU throughput reported in Table I above.

## Evaluation
- metrics (exact definitions): grasp-stability binary classification accuracy vs. dataset size (Fig. 10), K-fold cross-validation (K=10 up to 1,000 points, K=5 up to 10,000, single 80/20 split above that); in-hand marble manipulation cost = cumulative tactile-space position error Σ_t‖x̄_t‖, averaged over 8 target locations; pose-estimation position/rotation error (Table II, above).
- headline numbers: grasp stability — touch-only models reach high accuracy "with only a little amount of data, while vision requires 3 or 4 orders of magnitude more data to catch up"; a single tactile sensor performs "significantly worse" than two; combining vision+touch is best in the low-data regime (Fig. 10, Sec. IV-A). Marble-rolling: Bayesian optimization over a 2×2 gain matrix K converges within 50 iterations in 8 minutes total (6 min acquisition-function optimization + 2 min simulation: 50 iters × 50 steps × 8 directions = 20,000 rendered 160×120 tactile imprints) (Sec. IV-B).
- baselines beaten: real-world grasp-stability results of Calandra et al. 2017 (matched trend, 2 orders of magnitude more data explorable in sim); real-world marble-rolling of prior work (comparable qualitative behavior).
- real robot? No physical robot trial in this paper; Sim2Real experiments (Table II) compare simulated vs. real DIGIT tactile images for a pose-estimation task, not a robot manipulation trial.

## Limitations stated by the authors
- "One limitation of the method is that it is difficult to model the deformation of the gel on the contact boundary, because the RGB and depth images are calculated at the same time" — mainly affects sharp edges; mitigated by mesh smoothing during preprocessing (Sec. III-B).
- Rendering-from-depth mode (for very deformable objects) is slower due to an I/O bottleneck loading meshes (Sec. III-B, III-D "Rendering from depth").
- Future work: "improving the modeling of the effects of forces through the deformation of the elastomers" and evaluating different deformation models / image-filtering effects (Sec. VI).

## Quotable claims (verbatim, with section)
- "TACTO is able to render a single DIGIT sensor at 200 frames per second on GPU with an output resolution of 160x120 pixels." (Sec. III-D)
- "It can also render multiple sensor outputs, e.g., rendering four DIGIT sensors mounted on an Allegro hand at 50 frames per second on GPU." (Sec. III-D)
- "In TACTO, the contact forces are generated from the physics engine of choice (currently by default PyBullet with a rigid body contact model)." (Sec. III-D)
- "The major goal with TACTO is to provide a platform to study representations and algorithms for robot learning using touch as a sensor modality." (Sec. V)

## Notes for the survey
- TACTO is a rendering layer, not a contact-physics engine: its "physics block" is almost entirely "inherited from the host engine" — this should be stated explicitly in the survey's tactile-simulator comparison so TACTO is not conflated with a contact-solver contribution the way `comfree_sim_2026` or `dojo_2022` are.
- Table II (Sim2Real pose-estimation error) is TACTO's only sim-to-real number in this paper and is on a *pose-estimation from tactile image* task (pen/cylinder contact center + angle), not a manipulation success rate; it should not be conflated with the marker-motion sim-to-real errors reported by `taxim_2021` (mm-scale FEM/real displacement errors) or `tactile_genesis_2026` (elastomer marker RMSE table), which measure a different quantity.
- Cross-reference: `taxim_2021` directly benchmarks against TACTO (its Table I/II) and reports TACTO as both less accurate and slower (on CPU) than Taxim's example-based method — that comparison is the more informative one for ranking tactile-image simulators and is reproduced in the Taxim note.
- Code md provenance: `code/md/tacto_2020.md` (24,174 chars) includes README + file tree; solver-level detail is absent because TACTO itself has no solver — all content above is from the paper text.
