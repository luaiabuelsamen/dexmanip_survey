# openvla_2024 — OpenVLA: An Open-Source Vision-Language-Action Model (Kim et al., CoRL 2024)

sources: papers/md/openvla_2024.md [sha256 353c37df] ; code/md/openvla_2024.md [commit c8f03f48]

## One-line contribution
A 7B-parameter open-source VLA (Prismatic-7B VLM fine-tuned on 970k Open X-Embodiment trajectories) that predicts robot actions as discretized language-model tokens, beating the 55B closed RT-2-X by 16.5% absolute success across 29 tasks, and shown to be LoRA-fine-tunable on a single GPU (§Abstract, §3, §5.1).

## Setting
- hand(s): none — all evaluated embodiments use parallel-jaw end-effectors ("Grip" is a single scalar dimension of the 7D action, Fig. 2); no multi-fingered hand is named anywhere in the paper or code sources read.
- arm: WidowX (BridgeData V2, §5.1), Google-robot mobile manipulator from RT-1/RT-2 (§5.1), Franka Emika Panda — "Franka-Tabletop" and "Franka-DROID" setups (§5.2), plus simulated Franka in LIBERO (Appendix E). All single-arm.
- simulator / physics: real-robot evaluations only for §5.1–5.3; LIBERO benchmark used for simulated fine-tuning experiments (Appendix E), "the original paper" cited [116] but no engine/timestep given in this source.
- observation: single third-person camera image + language instruction ("OpenVLA currently only supports single-image observations", §6 Limitations); LIBERO experiments explicitly drop wrist-camera images "for sake of having fair comparisons, as OpenVLA's visual inputs only consist of third-person camera images" (Appendix E.1).
- action space: 7-dimensional robot control action — "Δx, Δθ, Grip" (Fig. 1/2 caption: "the model predicts 7-dimensional robot control actions"); relative/delta position control except where noted (see Method).
- objects / data: pretraining on Open X-Embodiment; "we curated a much larger training dataset for OpenVLA with 970k trajectories (vs. 350k for RT-2-X)" (§5.1).

## Method
- paradigm: autoregressive VLA — action prediction is "formulated as a 'vision-language' task, where an input observation image and a natural language task instruction are mapped to a string of predicted robot actions" (§3.2).
- **Backbone (Prismatic-7B VLM):** "a 600M-parameter visual encoder, a small 2-layer MLP projector, and a 7B-parameter Llama 2 language model backbone" (§3.1). The visual encoder is "two-part": "Input image patches are passed separately through both [SigLIP and DinoV2] encoders and the resulting feature vectors are concatenated channel-wise" (§3.1). Total model is described throughout as "OpenVLA, a 7B-parameter ... VLA" (Abstract, §3).
- **Action tokenization (quoted verbatim, §3.2):**
  > "Following Brohan et al. [7], we discretize each dimension of the robot actions separately into one of 256 bins. For each action dimension, we set the bin width to uniformly divide the interval between the 1st and 99th quantile of the actions in the training data."
  > "Using this discretization, we obtain N discrete integers ∈ [0...255] for an N-dimensional robot action. Unfortunately, the tokenizer used by OpenVLA's language backbone, the Llama tokenizer [10], only reserves 100 'special tokens' for tokens newly introduced during fine-tuning, which is too few for the 256 tokens of our action discretization. Instead, we again opt for simplicity and follow Brohan et al. [7]'s approach by simply overwriting the 256 least used tokens in the Llama tokenizer's vocabulary (which corresponds to the last 256 tokens) with our action tokens."
  > "Once the actions are processed into a sequence of tokens, OpenVLA is trained with a standard next-token prediction objective, evaluating the cross-entropy loss on the predicted action tokens only."
  De-tokenization is not spelled out algebraically in the paper text beyond "un-normalize" at inference (README example: `vla.predict_action(**inputs, unnorm_key="bridge_orig", ...)`, code/md line ~79); it maps predicted bin-token IDs back to per-dimension bin centers using per-dataset action statistics (`unnorm_key` selects the normalization stats for a given dataset, per code signatures below).
- **Action chunking / control rate:** OpenVLA predicts a single action per forward pass, not a chunk — this is stated as a *limitation* relative to chunked methods: "For narrower but highly dexterous tasks, Diffusion Policy still shows smoother and more precise trajectories; incorporating action chunking and temporal smoothing, as implemented in Diffusion Policy, may help OpenVLA attain the same level of dexterity" (§5.2), and data cleaning explicitly targets "highly expressive single-step policies such as OpenVLA" (Appendix E.1, item 2). Inference rate: "runs at approximately 6Hz on one NVIDIA RTX 4090 GPU (without compilation, speculative decoding, or other inference speed-up tricks)" (§3.5). Robot control frequencies used at eval: WidowX/BridgeData V2 uses a "5Hz non-blocking controller" (§5.4); Franka-Tabletop and Franka-DROID "use 5Hz and 15Hz non-blocking controllers, respectively" (§5.2). Quantized inference: 8-bit runs "at 1.2Hz" and 4-bit "at 3Hz" on an A5000 (§5.4).
- key trick(s): quantile-based (1st–99th percentile) bin edges instead of Brohan et al.'s min-max bounds "to ignore outlier actions" (§3.2); fine-tuning the vision encoder during VLA training (found crucial, contra typical frozen-VLM practice, §3.4); training to 27 epochs / >95% token accuracy rather than 1-2 epochs (§3.4); LoRA + quantization for compute-efficient fine-tuning/inference (§5.3, §5.4).

## Embodiment block (HOWTO_METHOD A)
- hand model: not applicable — no multi-fingered hand in any dataset/eval read; end-effectors are parallel grippers (WidowX gripper, Google-robot gripper, Franka Panda gripper), one scalar "Grip" action dimension (Fig. 2).
- arm/floating base: single fixed arm per platform (WidowX, Franka Panda) or mobile-base mounted arm (Google robot); bimanual explicitly absent — "This will also enable testing VLAs on more dexterous, bi-manual manipulation tasks than what we investigated in this work" (§6, discussing future ALOHA-class 50Hz control).
- simulator + version: LIBERO benchmark only (Appendix E); no version/engine given in this source.
- sim timestep / control rate: not stated for LIBERO; real-robot control rates 5Hz (BridgeData V2, Franka-Tabletop) and 15Hz (Franka-DROID) (§5.2, §5.4).
- number of parallel envs: not applicable (real robots + LIBERO offline BC).
- GPU / wall-clock: pretraining "on a cluster of 64 A100 GPUs for 14 days, or a total of 21,500 A100-hours, using a batch size of 2048" (§3.5). Full fine-tuning: "8 A100 GPUs for 5-15 hours per task" (§5.3). LoRA fine-tuning: "within 10-15 hours on a single A100 GPU" (§5.3).

## Learning block (HOWTO_METHOD B)
- paradigm: supervised imitation learning via next-token prediction on discretized actions (autoregressive VLA), not RL.
- algorithm/implementation: standard cross-entropy next-token-prediction fine-tuning of the Prismatic VLM (§3.2); training infra uses "automatic mixed precision (AMP, PyTorch), FlashAttention, and fully sharded data parallelism (FSDP, Zhao et al.)" (§4). Code: `scripts/pretrain.py` — "Pretraining script for Prismatic VLM pretraining in native PyTorch, using Fully-Sharded Data Parallel (FSDP)" (code/md).
- teacher-student / distillation: not used — none stated.
- observation vector: single RGB image + language instruction string; code interface confirms this — `get_vla_action(vla, processor, base_vla_name, obs, task_label, unnorm_key, center_crop)` (`experiments/robot/openvla_utils.py`, code/md).
- action space: 7-D, discretized into per-dimension 256-bin tokens (see Method above); config surface confirmed in code — `class OpenVLAConfig(PrismaticConfig): def __init__(self, norm_stats, n_action_bins)` (`prismatic/extern/hf/configuration_prismatic.py`, code/md).
- domain randomization: not addressed in the read sections beyond LIBERO's random initial-condition sampling (inherited from the benchmark, not described further); "image_aug" flag appears in the LoRA fine-tuning command (`--image_aug <True or False>`, code/md README) but the augmentation set/ranges are not specified in the sources read.

## Reward / objective block (HOWTO_METHOD C)
- loss (quoted, §3.2): "OpenVLA is trained with a standard next-token prediction objective, evaluating the cross-entropy loss on the predicted action tokens only."
- weight terms: none — single cross-entropy term over action tokens; no auxiliary losses stated.
- action chunking / horizon: OpenVLA itself predicts single-step actions (see Method); by contrast the baseline Diffusion Policy used in comparisons "predict[s] a chunk of T future actions and execut[es] the first X actions in open-loop fashion ... for 15Hz control, we set T=16, X=8 ... for 5Hz control, we reduce the chunk sizes to T=8, X=3" (§5.2, footnote 3) — quoted for contrast, not OpenVLA's own recipe.
- code vs. paper mismatch: none found in the read excerpts; code/md exposes only signatures (`class ActionTokenizer(): def __init__(self, tokenizer, bins, min_action, max_action); def __call__(self, action); def decode_token_ids_to_actions(self, action_token_ids); def vocab_size(self)` in `prismatic/vla/action_tokenizer.py`) which structurally match the paper's description (per-dimension bins, min/max-derived tokenization, explicit decode method) but the method bodies are not present in code/md, so the exact de-tokenization arithmetic could not be verified against the paper's quantile description — flagged as unverified at the code level.

## Evaluation block
- exact success criterion: binary success (1)/failure (0) per rollout, with explicit partial credit (0.5) defined per-task in several tasks (e.g. "Flip Pot Upright" partial-success rubric, Appendix B.3.1); Franka-DROID "Wipe Table" uses a 0/1/2-point rubric ("The policy receives the full 2 points if the robot sweeps all three objects into the dustpan. It receives 1 point for successfully sweeping one or two objects...", Appendix B.3.1).
- episode/trial counts: BridgeData V2 — "170 rollouts (17 tasks with 10 trials each)" (§5.1, Table 4); Google robot — "60 rollouts (12 tasks with 5 trials each)" (§5.1, Table 6); Franka fine-tuning — "129 rollouts per approach (99 for Franka-Tabletop tasks and 30 for Franka-DROID tasks)" (Fig. 5 caption, Table 7); Table 1 (fine-tuning strategies) — "33 rollouts per approach on select Franka-Tabletop tasks"; Table 2 (quantization) — "80 rollouts per approach" across "8 representative BridgeData V2 tasks"; LIBERO — "500 trials for each task suite... average success rate over three random seeds (resulting in 1500 total trials per statistic)" (Appendix E.1).
- headline numbers: BridgeData V2 mean success (Table 4) — RT-1-X 18.5±2.7%, Octo 20.0±2.6%, RT-2-X 50.6±3.5%, **OpenVLA 70.6±3.2%**. Google robot mean success (Table 6) — RT-1-X 33.3±6.1%, Octo 26.7±5.8%, RT-2-X 78.3±5.4%, OpenVLA 85.0±4.6%. LoRA vs. full fine-tuning (Table 1, Franka-Tabletop subset, 33 rollouts): Full FT 69.7±7.2% (7,188.1M train params, 163.3GB VRAM), LoRA rank=32 68.2±7.5% (97.6M params, 59.7GB VRAM) — "training only 1.4% of the model parameters." Quantization (Table 2, 80 rollouts): bfloat16 71.3±4.8% (16.8GB), int8 58.1±5.1% (10.2GB), int4 71.9±4.7% (7.0GB). LIBERO (Table 12) average SR: Diffusion Policy 72.4±0.7%, Octo fine-tuned 75.1±0.6%, OpenVLA fine-tuned 76.5±0.6% (rank 1.5 avg).
- baselines beaten: RT-1-X (35M params, from scratch), Octo (93M params, from scratch, "state-of-the-art model among open-source manipulation policies"), RT-2-X (55B params, closed VLA) (§5.1); Diffusion Policy and Diffusion Policy (matched) for fine-tuning (§5.2); all compared as A/B evaluations "using the same tasks with the same sets of initial robot and object states" (§5.1). Baselines are re-run by the authors (RT-2-X via "alpha access to the RT-2-X API," Acknowledgments), not merely quoted from prior papers.
- real robot? WidowX (BridgeData V2), Google-robot mobile manipulator, and Franka Emika Panda (Franka-Tabletop / Franka-DROID) — all real-robot trials, counts as listed above. No dexterous/multi-fingered hand used.

## Limitations stated by the authors
"First, it currently only supports single-image observations... Secondly, improving the inference throughput of OpenVLA is critical to enable VLA control for high-frequency control setups such as ALOHA [90], which runs at 50Hz. This will also enable testing VLAs on more dexterous, bi-manual manipulation tasks than what we investigated in this work... Additionally, there is room for further performance improvements. While OpenVLA outperforms prior generalist policies, it does not yet offer very high reliability on the tested tasks, typically achieving <90% success rate." (§6)

## Notes for the survey (which sections this feeds; contradictions with other notes)
Feeds the VLA/generalist-policy comparison table: backbone size (7B), action tokenization scheme (256-bin per-dimension discretization overwriting the least-used Llama tokens), and control rate (6Hz single-step inference; 5/15Hz robot control loops) are the load-bearing numbers other VLA notes in this survey should be checked against. Critically for the dexterous-hand survey angle: OpenVLA's entire pretraining mixture (Table 3, 27 OpenX sub-datasets) and all evaluation platforms (WidowX, Google robot, Franka Panda) use single-scalar-gripper end-effectors — this note found **no multi-fingered hand anywhere** in the paper or code sources, making it a pure parallel-jaw baseline for any survey claim about VLA transfer to dexterous hands. The paper itself flags this gap as unaddressed future work, tying dexterity/action-chunking absence to bimanual/ALOHA-class control (§6) rather than to hand morphology directly.
