# dextreme_2022 — DeXtreme: Transfer of Agile In-hand Manipulation from Simulation to Reality (Handa et al., ICRA 2023, arXiv 2210.13702)

sources: papers/md/dextreme_2022.md [sha256 753b6f9b] ; code/md/dextreme_2022.md [commit aeed2986]

## One-line contribution
Cube reorientation on a fixed-wrist Allegro Hand, trained entirely in Isaac Gym with Vectorised Automatic Domain Randomisation (VADR) and transferred to a real Allegro Hand using a purely RGB, marker-free vision pose estimator; best real-world policy averages 27.8±19.0 consecutive successes (Table 7) and beats OpenAI's vision-based policy from [1] by ~2.5x on best rollout (Table 9).

## Setting
- hand(s): Allegro Hand, 16 joints/DoF (4 fingers x4), "comparatively affordable ... with a locked wrist and four fingers, using only position encoders on servo motors" (Sec 1). Code asset: `assetFileName: "urdf/kuka_allegro_description/allegro_touch_sensor.urdf"` (task/AllegroHandDextremeADR.yaml, code/md line ~995).
- arm: not actuated — "Our hardware setup ... consists of an Allegro Hand rigidly mounted at the wrist" (Sec 2.2); action space is only the 16 hand joints (Sec 2.3), no arm DoF in the action vector. Wrist is fixed/locked, not compliant.
- single/bimanual: single hand.
- palm-up or palm-down: not stated. Paper says only "the object to be manipulated is placed on the palm of the hand" (Sec 2.1); no explicit statement of palm orientation relative to gravity in either the paper text or the code excerpts examined.
- simulator / physics: Isaac Gym [6], PhysX ("Isaac Gym ... models contacts differently than MuJoCo's soft-contact model ... used in [1]", Sec 2.5). #envs: "16384 agents per GPU" (Sec 3.1, text); Appendix A.4 (Table 13) gives "Num Envs 8192/16384".
- sim timestep / control rate: "simulation dt of 1/60 s and a control dt of 1/30 s" (Sec 3.1); Appendix A.4 (Table 13): Sim dt 1/60 s, Control dt 1/30 s, Num Substeps 2, Num Pos Iterations 8, Num Vel Iterations 0. Code `controlFrequencyInv: 2 #2 # 30 Hz` in task/AllegroHandDextremeADR.yaml — matches (control dt = sim dt x controlFrequencyInv = 1/30 s).
- GPU / wall-clock: 8x NVIDIA A40. Manual DR: "~32 hours" (Sec 3.1, main text) / Table 9 lists "1.41 days (34 hours)" for manual-DR training time — a minor internal inconsistency (32 h vs 34 h) between prose and table. ADR: "2.5 days" (Sec 3.1) = "2.5 days (60 hours)" (Table 9).
- observation: state (sim) / vision-estimated pose (real). Table 1 gives the full actor/critic observation table: Actor (50D) = object position w/ noise (3D), object orientation w/ noise (4D quat), target position (3D), target orientation (4D quat), relative target orientation (4D quat), last actions (16D), hand joint angles (16D). Critic (265D total) adds: stochastic delays (4D), fingertip positions (12D), fingertip rotations (16D quat), fingertip velocities (24D), fingertip forces/torques (24D), hand joint velocities (16D), hand joint generalised forces (16D), object scale/mass/friction (3D), object linear velocity (3D), object angular velocity (3D), object position (3D), object rotation (4D), random forces on object (3D), domain-randomisation params (78D), gravity vector (3D), rotation distances (2D), hand scale (1D).
  - Code (`train/AllegroHandDextremeADRPPO.yaml`) actor network `inputs`: `dof_pos_randomized, object_pose_cam_randomized, goal_pose, goal_relative_rot_cam_randomized, last_actions` — matches the six actor groups in Table 1 in substance (object pose+noise, target pose, relative target rot, last actions, hand joint angles), naming differs (no line-numbered obs_buf assembly for the DeXtreme-specific `compute_observations` was found in the excerpted code — this file's observation-building body is not shown in code/md/dextreme_2022.md; only the RL-games network `inputs` dict is verifiable). Critic (`central_value_config.network.inputs`): `dof_pos, dof_vel, dof_force, object_pose, object_pose_cam_randomized, object_vels, goal_pose, goal_relative_rot, last_actions, stochastic_delay_params, affine_params, cube_random_params, hand_random_params, ft_force_torques, gravity_vec, ft_states, rot_dist, rb_forces` — matches Table 1's critic-only additions term for term.
- action space: "PD controller target for each of the 16 joints on the robot hand" (Sec 2.3), continuous (16D). Appendix A.3 (Table 12): "Action distribution 16D Continuous actions." Quirks section: "Our best policies were trained with continuous actions unlike OpenAI et al. [1, 8], where discrete actions were used" (Sec 3.3).
- objects / data: single 6.5 cm cuboid ("The object we learn to manipulate is a 6.5 cm cuboid with coloured and lettered stickers on the sides", Sec 2.2). Vision training data: 5M synthetic images (320x240) from NVIDIA Omniverse Isaac Sim/Replicator (Sec 2.7), plus a 50K-image test set (Table 6).

## Method
- paradigm: RL (policy) + supervised vision (pose estimator, teacher-student in the sense that sim state is privileged during RL training and is replaced at test time by the vision estimate — paper does not use the words "teacher/student" or "distillation"; the RL policy itself is trained with full simulator state/observations, not a privileged-to-vision distillation pipeline).
- algorithm: PPO [9], "high-performance PPO implementation from rl-games [11]" (Sec 2.3); code `algo.name: a2c_continuous`, `model.name: continuous_a2c_logstd` (train/AllegroHandDextremeADRPPO.yaml). Actor: LSTM, 1024 hidden units + layer norm, then 2 MLP layers of 512 with ELU (Sec 2.3); code `rnn: units: 1024, layers: 1, before_mlp: True, layer_norm: True`, `mlp.units: [512, 512]`, `activation: elu`. Critic: LSTM 2048 hidden units + layer norm, then MLP 1024/512 with ELU (Sec 2.3); code `central_value_config.network.rnn.units: 2048`, `mlp.units: [1024, 512]`. LSTM BPTT truncation length 16 (Sec 2.3); code `seq_length: 16`.
- teacher-student / distillation: not used in this paper's RL stage (state-privileged critic per Pinto et al. [10]: "the critic does not take in the same observations as the actor, but receives additional observations including states s ∈ S in the POMDP", Sec 2.3). At deployment, the vision pose estimator (a separate, supervised-trained Mask-RCNN-style network, Sec 2.7) supplies the policy's cube-pose observation in place of ground-truth simulator state — this is a state->vision substitution at test time, not an RL distillation step.
- domain randomisation: full Table 3 (paper), quoted verbatim (Type / Distribution / Initial Range / ADR-Discovered Range):
  - Hand: Mass scaling uniform [0.4,1.5]->[0.4,1.5]; Scale scaling uniform [0.95,1.05]->[0.95,1.05]; Friction scaling uniform [0.8,1.2]->[0.54,1.58]; Armature scaling uniform [0.8,1.02]->[0.31,1.24]; Effort scaling uniform [0.9,1.1]->[0.9,2.49]; Joint Stiffness scaling loguniform [0.3,3.0]->[0.3,3.52]; Joint Damping scaling loguniform [0.75,1.5]->[0.43,1.6]; Restitution additive uniform [0.0,0.4]->[0.0,0.4].
  - Object: Mass scaling uniform [0.4,1.6]->[0.4,1.6]; Friction scaling uniform [0.3,0.9]->[0.01,1.60]; Scale scaling uniform [0.95,1.05]->[0.95,1.05]; External Forces additive "Refer to [1]"; Restitution additive uniform [0.0,0.4]->[0.0,0.4].
  - Observation: Obj. Pose Delay Prob. [0.0,0.05]->[0.0,0.47]; Obj. Pose Freq. [1.0,1.0]->[1.0,6.0]; Obs Corr. Noise gaussian [0.0,0.04]->[0.0,0.12]; Obs Uncorr. Noise gaussian [0.0,0.04]->[0.0,0.14]; Random Pose Injection [0.3,0.3]->[0.3,0.3].
  - Action: Action Delay Prob. [0.0,0.05]->[0.0,0.31]; Action Latency [0.0,0.0]->[0.0,1.5]; Action Corr. Noise gaussian [0.0,0.04]->[0.0,0.32]; Action Uncorr. Noise gaussian [0.0,0.04]->[0.0,0.48]; RNA alpha [0.0,0.0]->[0.0,0.16].
  - Environment: Gravity (each coord.) additive normal [0,0.5]->[0,0.5].
  - Code confirms the mechanism and many ranges but with different numeric bounds in places (`task/AllegroHandDextremeADR.yaml`, `randomization_params.actor_params`): hand dof damping loguniform [0.01,20.0], stiffness loguniform [0.01,20.0], effort uniform [0.4,10.0], friction uniform [0.0,10.0], armature uniform [0.0,10.0] — these are the raw Isaac Gym DR-framework ranges (feeding the ADR mechanism), wider than the "ADR-Discovered Range" column reported in the paper's Table 3; object rigid_shape friction uniform [0.01,2.0]; hand/object rigid_body mass scaling [0.4,1.6]/[0.3,1.7]; sim_params gravity additive gaussian range [0,0.6] (ADR yaml) vs [0,0.5] in ManualDR yaml and in the paper's Table 3 — a numeric mismatch between the two yaml task variants and the paper's single quoted range.
  - Environment-level: "Gravity cannot be randomised per-environment in Isaac Gym currently, but a new gravity value is sampled every 720 concurrent simulation steps for all environments" (Sec 2.6.1); code `randomization_params.frequency: 720` in AllegroHandDextremeADR.yaml — matches.
  - ADR algorithm (VADR): boundary-performance queue length N=256, widen threshold t_H=20, tighten threshold t_L=5 (Sec 2.6), 40% of vectorised envs dedicated to boundary evaluation; ADR run independently per GPU (8 GPUs) (Sec 2.6).

## Reward / objective block (verbatim, paper Table 2, and code)
Paper, Table 2 ("Reward terms are computed, multiplied by their weight, and summed to produce the reward at each timestep"):
- Rotation Close to Goal: `1/(d+0.1)`, weight 1.0, "Shaped reward to bring cube close to goal"
- Position Close to Fixed Target: `||p_object - p_goal||`, weight -10.0, "Encourage the cube to stay in the hand"
- Action Penalty: `||a||^2`, weight -0.001, "Prevent actions that are too large"
- Action Delta Penalty: `||targ_curr - targ_prev||^2`, weight -0.25, "Prevent rapid changes in joint target"
- Joint Velocity Penalty: `||v_joints||^2`, weight -0.003, "Stop fingers from moving too quickly"
- Reset Reward — Reach Goal Bonus: condition d<0.1, value 250.0, "Large reward for getting the cube to the target"

Code, `def compute_hand_reward(...)` in `isaacgymenvs/tasks/dextreme/allegro_hand_dextreme.py`:
```
dist_rew = goal_dist * dist_reward_scale
rot_rew = 1.0/(torch.abs(rot_dist) + rot_eps) * rot_reward_scale
action_penalty = action_penalty_scale * torch.sum(actions ** 2, dim=-1)
action_delta_penalty = action_delta_penalty_scale * torch.sum((cur_targets - prev_targets) ** 2, dim=-1)
max_velocity = 5.0  # rad/s
vel_tolerance = 1.0
velocity_penalty_coef = -0.05
velocity_penalty = velocity_penalty_coef * torch.sum((hand_dof_vel/(max_velocity - vel_tolerance)) ** 2, dim=-1)
...
reach_goal_rew = (goal_resets == 1) * reach_goal_bonus
fall_rew = (goal_dist >= fall_dist) * fall_penalty
timeout_rew = timed_out * 0.5 * fall_penalty
reward = dist_rew + rot_rew + action_penalty + action_delta_penalty + velocity_penalty + reach_goal_rew + fall_rew + timeout_rew
```
Weights from `task/AllegroHandDextremeADR.yaml`: `distRewardScale: -10.0`, `rotRewardScale: 1.0`, `rotEps: 0.1`, `actionPenaltyScale: -0.001`, `actionDeltaPenaltyScale: -0.2` (comment shows an earlier `-0.01`), `reachGoalBonus: 250`, `fallDistance: 0.24`, `fallPenalty: 0.0`, `successTolerance: 0.1`. `task/AllegroHandDextremeManualDR.yaml` instead sets `actionPenaltyScale: -0.0001`, `actionDeltaPenaltyScale: -0.01`, `successTolerance: 0.4` (same `distRewardScale`, `rotRewardScale`, `rotEps`, `reachGoalBonus`, `fallDistance`, `fallPenalty`).

Mismatches paper vs. code, and internal (ADR vs ManualDR config) mismatches:
- Action Delta Penalty weight: paper Table 2 states -0.25; ADR yaml uses -0.2, ManualDR yaml uses -0.01. Neither config file matches the paper's quoted -0.25.
- Action Penalty weight: paper Table 2 states -0.001, which matches ADR yaml (`-0.001`) but not ManualDR yaml (`-0.0001`, 10x smaller). The paper's single Table 2 does not distinguish which config it is quoting.
- Joint Velocity Penalty: paper's formula is `||v_joints||^2` with weight -0.003. Code instead computes `velocity_penalty_coef * sum((hand_dof_vel/(max_velocity - vel_tolerance))^2)` with `velocity_penalty_coef = -0.05` and `(max_velocity - vel_tolerance) = 4.0`, i.e. an effective per-term coefficient of `-0.05/16 = -0.003125` — numerically close to the paper's -0.003 but the code normalises velocity by 4.0 rad/s first, a formula not stated in the paper's table.
- Code has a `timeout_rew = timed_out * 0.5 * fall_penalty` term not listed anywhere in paper Table 2 (evaluates to 0 given `fallPenalty: 0.0` in both configs, so numerically inert but structurally present in code and absent from the paper).
- `fall_penalty` (`fallPenalty: 0.0` both configs) means the paper's implicit "fall" case carries no reward penalty beyond the position term and episode reset; paper's Table 2 has no explicit "fall penalty" row, consistent with the code's zero setting.

## Contact / penetration handling
Not addressed as a reward term (no interpenetration penalty in Table 2 or in `compute_hand_reward`). Interpenetration is only discussed as a diagnostic in Limitations: "there is still some sim-to-real gap in pose estimation. This is manifested when we played back the real states in sim (real-to-sim) with physics enabled, which sometimes resulted in interpenetrations. Therefore, we were not able to easily calibrate physics parameters of the cube" (Sec 5). Contact/solver settings given in Appendix A.4 (Table 13): Num Substeps 2, Num Pos Iterations 8, Num Vel Iterations 0 (PhysX). No contact offset / rest offset / friction-solver values are stated in the paper or in the excerpted config.

## Evaluation block
- success criterion (training/eval threshold): text (Sec 2.1) states object orientation within 0.4 rad of target triggers a new target; Sec 3.1 clarifies "we use a goal-reaching orientation threshold of 0.1 rad but test with 0.4 rad as in [1, 6] for all experiments both in simulation and the real world." Code: `successTolerance: 0.1` in AllegroHandDextremeADR.yaml (training), `successTolerance: 0.4` in AllegroHandDextremeManualDR.yaml. A run is reset ("fallen") when `goal_dist >= fall_dist`, `fallDistance: 0.24` (both configs) — 0.24 m fixed-target distance triggers a fall/reset. Episode also times out at `resetTime: 8` seconds (`episodeLength: 320` "not used" per comment) or after `maxConsecutiveSuccesses: 50` in either config, or after "the object ... stuck in the same configuration for more than 80 seconds" (Sec 2.1, no corresponding config parameter identified in the excerpted code).
- eval episodes/trials: real-world Table 7 — 10 trials per policy, repeated across different days; ± is a "90% confidence interval." Frame-hold ablation (Table 8, sim only) at N in {0,5,10,20} hold frames, ADR policies only.
- sim vs real: Table 7/9 numbers are real-robot trials (vision pose estimate in the loop); Table 8 numbers are simulation-only (ground-truth state, no vision). Pose estimator itself benchmarked only in simulation (Table 6, since "we do not use any marker-based system in the real world, we can only precisely evaluate the performance of the pose estimator in simulation," Sec 2.7).
- headline numbers: Table 7, best real-world ADR model: 10 trials sorted `1, 6, 6, 10, 10, 18, 18, 36, 61, 112`, average 27.8±19.0, median 14.0. Non-ADR (manual DR) model: `1, 1, 3, 7, 8, 11, 14, 17, 22, 35`, average 11.9±5.8, median 9.5 (one of several rows shown). Table 9 comparison: Ours (vision, best avg) 27.8±19.0, median 14.0, best rollout 112; Ours (vision) manual-DR 14.8±5.4, median 14.5, best rollout 29; OpenAI et al. [1] vision (Manual DR, PhaseSpace-trained network) 15.2±7.8, median 11.5, best 46; OpenAI et al. [1] state (Manual, PhaseSpace) 18.8±5.4, median 13.0, best 50; OpenAI et al. [1] state, locked wrist 26.4±7.3, median 28.5, best 50; OpenAI et al. [8] state ADR(L) 13.3±3.6, median 11.5; ADR(XL) 16.0±4.0, median 12.5; ADR(XXL) 32±6.4, median 42.0.
- baselines beaten / not beaten: beats OpenAI et al. [1] vision-based policy and OpenAI et al. [8] ADR(XL) state+PhaseSpace policy on average consecutive successes (Sec 3.2); does not reach OpenAI et al. [8] ADR(XXL) state+PhaseSpace average (32±6.4) — attributed by the authors to (a) PhaseSpace marker accuracy, (b) higher observation frame-rate with PhaseSpace, (c) "increased diversity of data with ADR (XXL)" (Sec 3.2). Baselines are quoted from [1] and [8], not re-run.
- real robot: Allegro Hand, 10 trials per policy per day, multiple days per policy (Table 7); compute/training-cost comparison in Table 10 (Appendix A.1): Ours ADR $977.2 on 8x A40 vs OpenAI [8] ADR $215,685.1 on 400 CPU servers + 32 V100s.

## Limitations stated by the authors
- Sim-to-real gap remains: manual-DR policy averages ~35 consecutive successes in simulation (Fig 7a) but only ~15 in the real world (Sec 5).
- ADR policies still fall short of OpenAI et al. [8] ADR(XXL) real-world average; unclear whether due to pose-estimation reliability, insufficient training data diversity, or the malfunctioning Allegro thumb used in most trials (Sec 5).
- Best npd (nats-per-dimension, an ADR-diversity proxy) with ADR policies is "around -0.2"; authors note "it is possible that further improvements can be made" (Sec 5).
- Real-to-sim playback of recorded real states "sometimes resulted in interpenetrations," preventing easy calibration of the cube's physics parameters (Sec 5).
- ADR "does not model the joint distribution and relationships between performance with different parameters," so it can over-optimise one randomisation dimension at another's expense, and results depend on the order ranges are widened (Sec 3.3).
- Deployment variability across seeds with identical DR settings ("null space" of policies that perform similarly in sim but differently on hardware), also noted in a cited prior work [21] (Sec 3.3).
- Hardware fragility: ribbon cables can burn/break during aggressive manoeuvres, requiring regular health checks (Sec 3.2, Fig 10).

## Quotable claims (verbatim, with section)
- "Our best models required only 8 NVIDIA A40 GPUs to train, as opposed to OpenAI's use of a CPU cluster composed of 400 servers with 32 CPU-cores each, as well as 32 NVIDIA V100 GPUs [8]" (Sec 1).
- "The success criterion is the number of consecutive target orientations achieved without dropping the object or having the object stuck in the same configuration for more than 80 seconds" (Sec 2.1).
- "Our ADR policies using the same compute resources — 8 NVIDIA A40s — achieved the best performance in the real world after training for only 2.5 days in contrast to [8] that trained for 2 weeks to months for the task of block reorientation" (Sec 3.1).
- "Our best policies were trained with continuous actions unlike OpenAI et al. [1, 8], where discrete actions were used" (Sec 3.3).
