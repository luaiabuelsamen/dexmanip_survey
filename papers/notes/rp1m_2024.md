# rp1m_2024 — RP1M: A Large-Scale Motion Dataset for Piano Playing with Bi-Manual Dexterous Robot Hands (Zhao et al., CoRL 2024)

sources: papers/md/rp1m_2024.md [sha256 61668f66] ; no code

## One-line contribution
Casts finger-to-key assignment as an optimal-transport problem to remove the
need for human fingering labels, trains ~2k per-song RL specialist agents on
RoboPianist with it, releases RP1M (~1M expert bimanual trajectories), and
benchmarks multi-task imitation learning on the resulting dataset (Sec. 1, 4).

## Setting
- hand(s): "two Shadow robot hands [36]" (Sec. 3); exact DoF count not stated
  — only the collapsed action space is given. Bimanual.
- arm/base: forearms are position-controlled DoFs in the action space (Sec. 3).
- simulator / physics: RoboPianist [4] (MuJoCo), plus a MuJoCo-XLA (MJX)
  re-implementation for parallel GPU sim (App. B.4); control timestep 0.05,
  action repeat 1 (Table 4). Piano: "a full-size keyboard with 88 keys driven
  by linear springs" plus "a pseudo sustain pedal" (Sec. 3). MJX "disable[s]
  most of the contacts but only keep[s] the contacts between fingers and piano
  keys as well as the contact between forearms" (App. B.4).
- observation: 1144-D — proprioceptive state + L=11-step (current + 10-step
  lookahead) MIDI goal. Table 3: piano goal state L·88, sustain goal L·1,
  piano key joints 88, piano sustain state 1, fingertip position 3·10, hand
  state 46. The OT method removes RoboPianist's 10-step human-fingering
  observation channel (Sec. 3, App. B.2).
- action space: 39-D — joint position targets of both hands + forearm
  positions + sustain pedal; DoFs "that do not exist in the human hand or are
  used in most songs" are removed (Sec. 3).
- objects / data: sheet music as MIDI — "Each time step in the MIDI file
  specifies which piano keys to press (active keys)" (Sec. 3) — from the PIG
  dataset [6] and "a subset (1788 pieces) of the GiantMIDI-Piano dataset [7]"
  (Sec. 4.3).

## Method
- paradigm: RL (per-song specialist, data generation) -> multi-task IL
  (downstream, benchmarked on RP1M).
- expert-generation algorithm: DroQ [40] ("uses Dropout and Layer
  normalization in the Q function to improve sample efficiency", App. B.2),
  chosen "as Zakka et al. [4] for fair comparison." Key hyperparams (Table 4):
  8M training steps, episode length 550, discount 0.88, Adam lr 3e-4, MLP
  [256,256,256], GeLU, dropout 0.01. No privileged-state distillation stated;
  fingering is "discovered automatically" rather than labeled (Sec. 2).
- downstream IL algorithms (Sec. 5, App. C.1): BC-MLP (3x512 MLP + LayerNorm +
  ELU, MSE loss on actions, Table 5), BeT [44] (k-means action discretization
  + MinGPT), Diffusion Policy U-Net (DP-U) and Transformer (DP-T) with DDPM
  [47], "same code and hyperparameters as Chi et al. [5]." All trained on
  RP1M subsets (12/25/50/100/150 songs), evaluated zero-shot (Sec. 5).
- domain randomisation: not stated for either stage.
- reward (RL expert policy, App. B.1, Eq. 1-3 — the equations themselves are
  images that did not survive PDF->markdown conversion; only the prose
  description below could be recovered):
  - OT finger-placement cost (Eq. 1, Sec. 4.1): "we define the minimized
    cumulative moving distance between fingers and target keys as d^OT_t...
    K_t represents the set of keys to press at time step t and F represents
    the fingers... c_t(k_i,f_j) represents the cost of moving finger f_j to
    piano key k_i... calculated by their Euclidean distance... w_t(k_i,f_j) is
    a boolean weight [enforcing] each key in K_t will be pressed by only one
    finger in F, and each finger presses at most one key." Solved with "a
    modified Jonker-Volgenant algorithm [37] from SciPy [38]."
  - OT reward (Eq. 2): "r_t^OT... increases exponentially as d^OT_t decreases
    and is set as 1 once d^OT_t is smaller than a pre-defined threshold
    (0.01)" (Sec. 4.1).
  - Overall reward (Eq. 3, App. B.1): "r^Press and r_t^Sustain represent the
    reward for correctly pressing the target keys and the sustain pedal.
    r_t^Collision encourages the agent to avoid collision between forearms
    and r_t^Energy prefers energy-saving behaviors. alpha_1 and alpha_2 are
    coefficient terms, and alpha_1 = 0.5 and alpha_2 = 5e-3 are adopted."
  - Per-term (App. B.1, transcription of a garbled equation, symbol layout
    unreliable but terms are as named): r_t^Press uses tolerance g "from
    Tassa et al. [39]" and a flag 1_fp "indicat[ing] whether the inactive
    keys are pressed"; r_t^Sustain "= g(s_t - s_t^target)"; r_t^Collision
    "= 1 - 1_collision... 1 if collision happens and 0 otherwise";
    r_t^Energy "= |tau_joints|^T |v_joints|" (joint torques dot velocities).
  - IL loss (BC): "minimizing the Mean Squared Error (MSE) between predicted
    and actual expert actions" (App. C.1.1); BeT/DP losses cited to their
    original papers, not requoted (App. C.1.2-C.1.3).
- contact / penetration handling: not framed as interpenetration measurement;
  only contact-related term is r_t^Collision, penalising forearm-forearm
  collision (App. B.1). Finger-key interpenetration is not separately
  measured or penalised beyond the key-press state itself.
- key trick(s): OT fingering "is compatible with different embodiments" —
  tested with the little finger disabled ("four-finger" hand) on French Suite
  No.5 Sarabande, first 550 steps, 0.95 F1 vs 0.96 for the original hand
  (Sec. 4.2, "Cross Embodiments").

## Evaluation
- metrics (exact definition, Sec. 3, Background): "We evaluate the
  performance of the trained agent with an average F1 score calculated by
  F1 = 2*precision*recall / (precision + recall). For piano playing, recall
  and precision measure the agent's performance on pressing the active keys
  and avoiding inactive keys respectively [4]."
- dataset size (Sec. 4.3, Table 1): "Our dataset includes ~1M expert
  trajectories covering ~2k musical pieces. For each musical piece, we train
  an individual DroQ agent... for 8 million environment steps and collect 500
  expert trajectories... We chunk each sheet music every 550 time steps,
  corresponding to 27.5 seconds." Table 1 lists RP1M demonstrations as "1M"
  against DexGraspNet 1.3M, UniDexGrasp 1.1M, Bi-DexHands ~20K. No total-hours
  or file-size figure appears anywhere in the parsed text.
- headline numbers:
  - RL specialist quality (Sec. 4.3, Fig. 4): "most agents (79.00%) achieve F1
    scores larger than 0.75, and 99.89% of the agents' F1 scores are larger
    than 0.5."
  - "Flight of the Bumblebee": "0.79 F1 score after 3M training steps"
    (Sec. 4.2).
  - Multi-task IL, Table 2, F1 by training-set size 12/25/50/100/150:
    - In-distribution: BC-MLP 0.529/0.315/0.319/0.193/0.250; BeT
      0.062/0.080/0.065/0.078/0.088; DP-U 0.539/0.541/0.546/0.505/0.454;
      DP-T 0.357/0.304/0.297/0.301/0.318.
    - OOD: BC-MLP 0.079/0.119/0.100/0.108/0.187; BeT 0.094/0.110/0.111/
      0.120/0.125; DP-U 0.181/0.189/0.198/0.215/0.256; DP-T 0.186/0.210/
      0.230/0.291/0.316.
    - Text (Sec. 5, Discussion): 12->150 songs, in-distribution "DP-U and
      DP-T show performance drops of 15.77% and 10.92%... BC-MLP suffers a
      more significant decline of 52.74%"; OOD "F1 scores for DP-U and DP-T
      rise from 0.181 to 0.256 and from 0.186 to 0.316, respectively."
- baselines beaten: OT method matches (not beats) RoboPianist-RL with human
  fingering, and beats "No Fingering" "by a large margin" (Fig. 2, Sec. 4.2);
  among IL baselines DP-U/DP-T outperform BC-MLP/BeT as data scales (Table 2).
- real robot? Not attempted; sim-only (Sec. 6 lists sim-to-real as unresolved
  future work). Eval episodes/seeds beyond "3 random seeds" for Fig. 2 and the
  500-rollout-per-song dataset collection are not otherwise quantified.
- reproducibility: bib lists `github: null`; project page
  `https://rp1m.github.io/` given in-text (p.1 footnote); `code/md/rp1m_2024.md`
  absent, so no code-vs-paper check is possible here.

## Limitations stated by the authors
(Sec. 6) Fails "to achieve strong performance on challenging songs due to fast
rhythms and mechanical limitations of the robot hands"; "the evaluation
metric, F1 score, may not adequately capture musical performance and the
position-based controller missing the target velocity would hinder the
performance"; dataset "includes only proprioceptive observations, whereas
humans play piano using multi-modal inputs like vision, touch, and hearing";
real-world deployment needs "obtaining the state of the piano and the hands...
optimizing a precise position controller at high speed as well as the
sim-to-real gap"; "there is still a gap between our best multi-task agent and
RL specialists, which requires future investigation."

## Quotable claims (verbatim, with section)
- "RP1M... contain[s] bimanual robot piano playing motion data of more than
  one million trajectories" (Abstract).
- "white keys, taking 65.7%, are more likely to be pressed than black keys"
  and "90.70% musical pieces in our dataset include 1000-4000 active keys"
  (Sec. 4.3, Fig. 4).
- Compute: "Each agent takes 21 hours to train. The overall data collection
  cost is roughly 21 hours * 2089 agents = 43,869 GPU hours" on LUMI (AMD
  MI250X GPUs) (App. B.3).
