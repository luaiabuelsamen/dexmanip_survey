## One-line contribution
From a single human RGB-D video, extract (1) an object 6D-pose trajectory (via FoundationPose+SAM2) to define an embodiment-agnostic, object-centric anchor-point tracking reward, and (2) one pre-manipulation hand pose (via HaMeR+depth-ICP, then two-step cuRobo IK) to seed RL exploration; a PPO policy trained purely in an IsaacGym digital twin then transfers zero-shot to a real KUKA arm + Allegro hand, beating trajectory-replay and behavior-cloning baselines by 55-68% (Abstract).

## Setting
- hand(s): Allegro Hand (16-DoF) mounted on a 7-DoF KUKA LBR iiwa 14 arm (Sec. 4.1). Single arm-hand (not bimanual). Preliminary cross-embodiment tests (App. J) also run on a LEAP Hand and a UMI gripper for one task (`snackbox-push`), simulation only.
- simulator / physics: IsaacGym [51], 4096 parallel envs per single NVIDIA A100 (40GB), ~7k FPS simulation speed (App. E). Control timestep 66.7ms (15Hz action rate), each subdivided into 8 physics substeps of 8.33ms (120Hz) (App. E). PhysX solver settings (code, `CrossEmbodiment.yaml`): `num_position_iterations: 8`, `num_velocity_iterations: 8`, `contact_offset: 0.005`, `rest_offset: 0.0`, `bounce_threshold_velocity: 0.2`, `max_depenetration_velocity: 10000.0` (comment: "Original: 1000.0" — raised 10×), `contact_collection: 1` (CC_LAST_SUBSTEP). Training wall-clock: "approximately 5 to 24 hours" per task, ~0.6 billion frames total (App. E).
- observation: policy obs o_t = [q_t, q̇_t, X_t^fingertips, x_t^palm, X_t^obj, X_{τ+t}^target] — joint angles/velocities, fingertip positions, palm position, object and target anchor-point positions (Sec. 3.2). Asymmetric actor-critic (privileged critic): critic state s_t = [o_t, v_t, ω_t, t, f_t^dof, F_t^fingers] additionally includes object linear/angular velocity, timestep, joint forces, and fingertip contact forces (App. E) — policy itself never sees these at deployment.
- action space: a_t = [x_t^palm-target (R^3), r_t^palm-target (Euler angles, R^3), x_t^pca-target (R^5 PCA components for hand joints)] (Sec. 3.2), fed through a geometric fabric controller [44] (60Hz) producing joint PD targets executed at 200Hz on hardware (App. F.1); code confirms `USE_FABRIC_ACTION_SPACE: True`, `FABRIC_HAND_ACTION_SPACE: "PCA"`.
- objects / data: one RGB-D human demo per task, ZED 1 stereo camera; three physical objects (snackbox, pitcher, plate) across 7 named tasks (App. G): snackbox-push, plate-push, snackbox-pivot, pitcher-pour, snackbox-push-pivot, plate-lift-rack, plate-pivot-lift-rack.

## Method
- paradigm: RL (single-demo-guided) with an asymmetric actor-critic; no imitation learning of actions (baselines only) ; algorithm: PPO [52] via rl-games [57] (App. E): lr 5e-4, γ=0.998, entropy coef 0, ε_clip=0.2, 4 mini-epochs/update, horizon length 16, 4096 parallel agents, MLP [512,512] + LSTM 1024 units (policy), critic MLP [1024,512].
- human dataset used and retargeting: NOT a mocap dataset — a single monocular RGB-D video per task (Sec. 3.1). Object pose trajectory {T_t^target} extracted via FoundationPose [48] (needs a LiDAR-scanned object mesh + SAM2 [49] masks); human hand pose {(θ_t,β_t)} (MANO parameters) extracted via HaMeR [12] from RGB, then depth-aligned by ICP registration of MANO-predicted hand vertices against a SAM2-segmented, KD-tree-filtered depth point cloud (App. A.3) — HaMeR alone has 3D errors "as large as 20-30 cm" without this step. Only ONE pre-manipulation hand pose (at the frame τ=t0−t_offset just before object velocity exceeds v_min=5cm/s, t_offset=30 frames=1s by default) is retargeted to the robot, via a two-step IK: (1) cuRobo [50] arm IK aligns the robot hand's middle-knuckle pose to the human's (100 candidate solutions, 20 seeds each with 15°-std noise, accept within 5cm/3° of target, offsets: 3cm along negative palm normal and 3cm along negative wrist-to-knuckle direction); (2) PyBullet IK aligns the four Allegro fingertips to the human's index/middle/ring/thumb fingertip positions, no adjustment (App. B). This pre-manip pose is only a soft prior for RL initialization — "the pre-manipulation pose retargeting does not need to be extremely precise, as it is just a prior to facilitate exploration" (Sec. 3.1). The full hand trajectory is retargeted only for the Replay/OA-Replay/BC/Residual-Policy baselines and the "Hand Tracking Reward"/"Residual Policy" ablations, not for the main method.
- reward (paper, Sec. 3.2 + Eq. 1 + App. C): r_t = r_t^obj, an object-centric anchor-point pose-tracking reward comparing the target pose T_{τ+t}^target against the current object pose T_t^obj using N_anchor=3 anchor points k1=[L,0,0], k2=[0,L,0], k3=[0,0,L] in the object's local frame with L=0.2m, and a temperature α=10 (exact functional form of Eq. 1 is a blank image in the parse; described as an exponential-family "relative pose distance function d"). "This formulation integrates position and orientation naturally: larger L emphasizes orientation." For rotationally symmetric objects, anchor points orthogonal to the symmetry axis are automatically removed (App. C, Fig. 11), used identically for reward and for the policy's object-pose observation.
- reward (code): the environment YAML `CrossEmbodiment.yaml` sets flags controlling the reward but not its numeric form: `FORCE_REFERENCE_TRAJECTORY_TRACKING: True`, `OBJECT_ORIENTATION_MATTERS: True`, `RANDOMIZE_GOAL_OBJECT_ORIENTATION_DEG: 60`, `SUCCESS_REGION_RADIUS: 0.05`, `action_smoothing_penalty_weight: 0`. The class exposes `_setup_reward_weights(self)` and `compute_reward(self)` as methods, but neither body nor the weight values themselves are present in the parsed code md (only ~140 method signatures for this class are captured) — SOURCE THIN FOR REWARD BLOCK on the code side only: the paper's α=10/L=0.2m values cannot be cross-checked against a weight table in code, and it is not possible to confirm from the parse whether other reward terms (e.g. an action-smoothing penalty, weight 0 by default per config) are active in the main results.
- key trick(s): decoupling "task specification" (dense object-pose reward, embodiment-agnostic) from "task guidance" (one pre-manipulation pose, embodiment-specific via IK) so the policy is not forced to imitate human finger motion; asymmetric actor-critic with privileged velocity/contact-force info for the critic only; random SE(3) object-pose perturbation of the initial state (yaw ±20°, xy ±10cm, App. D) plus matching wrist-pose perturbation, both computed relative to the human demo's pre-manip frame.

## Evaluation
- metrics: real-world — per-task binary or graded success rate over 10 rollouts (Fig. 6); multi-step tasks scored on a 3- or 4-level scale (e.g. plate-pivot-lift-rack: 0 / 0.33 / 0.66 / 1 for pivot/lift/rack sub-successes, App. G). Sim ablations — average episodic reward curves over 3 seeds vs. environment steps (Figs. 7-9), no separate success threshold reported for ablations beyond reward magnitude.
- failure / termination criteria (Sec. 3.2, exact): episode resets if (a) object too far from current target, d(T_{τ+t}^target, T_t^obj) > D_max; (b) robot palm too far from object, ‖x_t^palm − x_t^obj‖ > D_max; or (c) reference trajectory finished (τ+t > T). D_max = 0.25 m for both (a) and (b) (Sec. 3.2, footnote-adjacent text). Max episode length in code (`CrossEmbodiment.yaml`): `maxEpisodeLength = int(8 / (dt·controlFrequencyInv))` ≈ 6 seconds' worth of 15Hz control steps ("# 6 seconds" comment).
- headline numbers: Fig. 6 — "HUMAN2SIM2ROBOT policies outperform Replay by 67%, Object-Aware (OA) Replay by 55%, and Behavior Cloning (BC) by 68% across all tasks" (success rate out of 10 rollouts, 7 real tasks). Domain-randomization/reward ablations (Figs. 7-9, sim, `plate-pivot-lift-rack` task) are qualitative reward-curve comparisons, no single scalar reported outside the figures.
- baselines beaten: Replay (open-loop PD-target replay of the full retargeted trajectory), Object-Aware (OA) Replay (replay warped by the initial-object-pose transform, cf. [28,29]), Behavior Cloning (diffusion policy [53] on 30 demos synthesized from the one real demo via OA-replay + object-pose sampling, matching the demo count of [2]); simulation-only ablations: Fixed Target, Interpolated Target, Downsampled Trajectory (reward-shaping ablations, Sec. 4.3), Default/Overhead/Pre-Manip-Far Initialization (Sec. 4.4), Hand Tracking Reward and Residual Policy (Sec. 4.5, requiring the full hand trajectory instead of one pose).
- real robot? yes — KUKA LBR iiwa 14 + Allegro Hand, 7 real tasks, 10 rollouts each for the main comparison (Fig. 6); qualitative-only preliminary tests on LEAP Hand and UMI gripper in simulation (App. J, no real-world trial count given for those).

## Limitations stated by the authors (Sec. 6)
- Cross-embodiment generality validated only "preliminarily" on LEAP Hand/UMI gripper in sim, "not conducted extensive quantitative evaluations on other embodiments."
- Single-object tasks only; multi-object would "require additional modifications."
- Assumes a high-quality rigid-body object tracker and simulator; does not handle articulated or deformable objects.
- Pose estimator "struggles with pose ambiguity of symmetric objects and sensor noise from reflective objects" (mitigations proposed but not implemented for reflectivity).
- Trains single-object, single-task policies only; no generalist multi-task/multi-object policy.

## Notes for the survey
- Feeds: the retargeting section as the minimal-supervision extreme — only ONE hand pose is ever retargeted (not a trajectory), everything else is RL-discovered; directly comparable/contrastable with objdex_2024's "wrist-only" retargeting philosophy (both papers independently converge on "retarget less, let RL fill the gap," but this paper retargets a single static pose rather than a continuous wrist trajectory). Domain-randomization table for the survey's sim-to-real section: object friction/mass/inertia/robot friction/damping/stiffness/mass all scaled ∈[0.7,1.3] (App. E); object-pose observation noise 0.01 std; gravity noise 0.3 std; random object force at 5% prob/step, magnitude 50× object mass; randomization re-sampled every 720 sim steps.
- Object tracking: BOTH position and orientation via the anchor-point representation ("integrates position and orientation naturally... larger L emphasizes orientation," Sec. 3.2/App. C) — genuinely 6D, and orientation matters is confirmed independently in code (`OBJECT_ORIENTATION_MATTERS: True`, `RANDOMIZE_GOAL_OBJECT_ORIENTATION_DEG: 60`).
- Block D (interpenetration): NOT ADDRESSED as a measured or reward-penalized quantity anywhere in the paper — no mention of "penetration" or "interpenetration" in the text. The only related artifact is a PhysX contact-solver setting in the released config, `max_depenetration_velocity: 10000.0` (raised 10× from IsaacGym's "Original: 1000.0" default), which controls how fast the solver is allowed to push overlapping bodies apart — a numerical-stability knob, not a penetration measurement or penalty, and never reported as a metric.
