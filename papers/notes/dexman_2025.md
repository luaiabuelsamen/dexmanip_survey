# dexman_2025 — DexMan: Learning Bimanual Dexterous Manipulation from Human and Generated Videos (Hsieh, Tu, Hung, Ke, arXiv 2025)

sources: papers/md/dexman_2025.md [2ca475e0 / arxiv 2510.08475] ; no code

## One-line contribution
DexMan converts uncalibrated monocular RGB videos of humans manipulating rigid objects (real or Veo3-generated) into bimanual dexterous skills on a full humanoid robot in simulation, by reconstructing 3D objects, estimating noisy hand/object poses, retargeting them to the robot, and training a residual RL policy with a novel object-centric contact-prior reward that avoids the "trivial contact" pitfalls of prior contact rewards (Abstract, §3, §3.4).

## Setting
- hand(s): Shadow Dexterous Hands, one per arm, on a Unitree G1 humanoid (§4.2) — multi-fingered, not grippers. Arm: Unitree G1's arms (full humanoid, not floating hands — explicitly contrasted with prior work: "Unlike prior work that considers manipulation with floating hands (Li et al., 2025; Mandi et al., 2025), DexMan addresses a more realistic and challenging setting: controlling a humanoid robot," §3.3). Bimanual.
- simulator / physics: NVIDIA Isaac Gym (Makoviychuk et al., 2021), PPO via RL_GAMES; control frequency 30 Hz, dt = 1/30, 4 substeps (Appendix Table 5). ShadowHand friction 4.0 (following MANIPTRANS), object friction 1.0, table friction 0.25. Training: 2,048 parallel environments, 32-step rollouts per PPO update, 500 updates for the OakInk-v2 residual-RL comparison and 1,000 updates for the full video-to-robot pipeline (§4.2, §4.3).
- observation: state-based, not raw vision — "the policy directly observes low-dimensional state features rather than raw visual inputs" (Appendix B.5, Table 6): robot joint positions/velocities, reference human hand joint angles, current 6D wrist poses (both hands), reference 6D wrist pose from the human motion, 6D object pose, 6D target object pose.
- action space: residual RL policy outputs small corrections {Δx_t^h, Δω_t^h, Δθ_t^h} (wrist position, wrist orientation, hand joint angle residuals) per hand, added to the retargeted human motion (x̄_t^h, q̄_t^h, θ̄_t^h); final wrist pose targets are sent to a real-time bimanual IK solver (Genesis), and the resulting joint positions are commanded via a PD controller (§3.4, Appendix B.5) — i.e. this is residual position-target control layered on top of IK-retargeted human motion, not raw joint torques.
- objects / data: TACO dataset (244 bimanual motion-capture sequences with ground-truth hand-object poses, used both for pose-estimation evaluation and for 50-sequence video-to-robot evaluation, §4.1/§4.3); OakInk-v2 benchmark, 77 validation motion sequences (§4.2, following MANIPTRANS's protocol); 50 Veo3-generated synthetic videos of humans performing bimanual manipulation (§4.3).

## Method
- paradigm: hybrid — geometric/vision pipeline (3D reconstruction + pose estimation + IK retargeting) feeding a residual RL policy (PPO). Not pure IL, not pure RL-from-scratch.
- algorithm: PPO (RL_GAMES implementation) with an actor-critic MLP [256, 512, 128, 64], ELU activations, lr 5e-4 with warmup schedule, γ=0.99, GAE τ=0.95, horizon length 32, minibatch size 1024, 5 mini-epochs, entropy coefficient 0.0, critic coefficient 4, gradient norm clip 1.0, clipping ε=0.2, bounds loss coefficient 1e-4 (Appendix Table 5).
- teacher-student / privileged->vision distillation: no distillation stage — this is state-based RL throughout (no vision-based student policy is trained); "we do not address" vision-based deployment is implicit since the paper states the framework is simulation-only (§5 Limitations).
- domain randomization: not described as a standard DR sweep; instead the paper stabilizes reconstructed-object initial poses via a sampling procedure: "it perturbs the original pose with 20 random rotations (up to ±45° around sampled axes), simulates each configuration for 20 steps, and selects the stable pose with minimal rotational deviation from the original" (§3.3) — this raises "stable configurations" from 86% (no sampling) to 98% (with sampling) across 50 TACO + 50 Veo3 videos (Table 4), where stability is defined as settling within 0.75 rad of the estimated initial pose.
- key trick(s): (1) point-trajectory-regularized object pose estimation, integrating FoundationPose-style analysis-by-synthesis with SpatialTracker-style 3D point tracking (§3.1-3.2, Related Work); (2) staged human-to-robot motion retargeting — IK solver (Genesis) for wrist motion with lower body fixed, plus a separately-trained 5-layer MLP neural IK solver mapping 5 fingertip 3D positions to finger joint angles for finger retargeting (§3.3); (3) the "Contact-Prior Attraction Reward" (below) as the central technical contribution.

## Reward / objective block (quoted, per HOWTO_METHOD)
Total reward: R(t) = R_contact(t) + R_obj(t) + R_imit(t) (§3.4).
- **Contact reward**: built from an offline-extracted correspondence set P(t) = {(j,o) | ∀j∈J, ∀o∈O, ||p_j,t^hum - v_j,t^o||_2 ≤ τ_j} pairing each human hand keypoint j (fingertips + MCP palm keypoints of index/middle/ring/little, per Appendix B.5) with its nearest mesh vertex on object o, kept only if within a per-keypoint threshold τ_j. Online, two terms: "(1) an attraction term that pull[s] the robot keypoints toward the human-contacted object vertices, and (2) a directional alignment term that prevents unrealistic back-of-hand contacts," using d̂_j,t^o = (v_j,t^o - p_j,t^rob)/||v_j,t^o - p_j,t^rob|| and the robot keypoint's outward surface normal n_j,t^rob, with an indicator 1_lifted^o for whether the object is lifted (§3.4; the exact closed-form expression rendered ambiguously in the parsed markdown, so is not re-quoted symbol-for-symbol here — flagged as a parsing gap). Weights (Appendix Table 7): γ_c^j = 1 for all j; w_c^j = 0.5 (fingertips), 2.0 (palm keypoints); λ_c = 400; w_c1 = 1.0; w_c2 = 1.0.
- **Object-following reward**: based on positional/rotational differences Δ_pos^o, Δ_rot^o between current and reference object pose. Weights: w_o^pos = 5, w_o^rot = 1, λ_o^pos = 80, λ_o^rot = 3, w_o1 = 0.1, w_o2 = 4 (Table 7).
- **Imitation reward** (quoted): "R_imit(t) = w_i^pos e^(-λ_i^pos Δ_pos^hand) + w_i^rot e^(-λ_i^rot Δ_rot^hand) + w_i^jnt Σ_jnt e^(-λ_i^jnt Δ_jnt^hand)" (§3.4) where Δ_pos^hand, Δ_rot^hand, Δ_jnt^hand are wrist positional, wrist rotational, and per-joint finger positional differences from the reference. Weights: w_i^pos=0.5, w_i^rot=0.5, w_i^jnt=0.5, λ_i^pos=2, λ_i^rot=20, λ_i^jnt=20 (Table 7).
- Explicit critique of prior contact-reward designs (§2, quoted): MANIPTRANS "rewards proximity between hand keypoints and the nearest object surface... does not differentiate task-relevant grasp regions from arbitrary surfaces," so "the policy often exploits trivial contacts"; DexMachina "rewards reaching prerecorded world-space contact coordinates, but it is highly sensitive to object pose variation and encourages simple positional imitation." DexMan's object-centric keypoint-to-vertex correspondence is explicitly positioned to fix both failure modes.

## Contact / penetration handling
Contact is the paper's central mechanism, but strictly as a *reward-shaping attraction/alignment* signal (drawing hand keypoints toward the right object vertices, with a directional term to prevent back-of-hand contact) — not as an interpenetration penalty or measurement. No hand-object or two-hand penetration metric, force limit, or collision-avoidance term is reported anywhere in the paper or appendix; the "directional alignment term that prevents unrealistic back-of-hand contacts" is the closest thing to a contact-quality constraint, but it shapes which surface normal side is contacted, not how deep. Author-stated limitation directly on this point: "our end-effector control parameterization overlooks full arm posture, which is crucial for collision avoidance and effective multi-arm coordination in complex manipulation scenarios" (§5) — i.e. collision avoidance for the arms (not just hands) is explicitly named as unaddressed.

## Coordination and embodiment (survey fields)
- two-hand coordination: one residual RL policy over both hands — at each timestep the policy "observes robot proprioception and the states of all objects, and outputs small residual updates {Δx_t^h, Δω_t^h, Δθ_t^h} for each hand" (Appendix B.5), i.e. a single policy jointly controls both wrists/hands' residual corrections. Retargeting is likewise done per-hand from the corresponding human hand's estimated motion (finger retargeting via the same trained 5-layer MLP applied independently "to either hand," §3.3), so there is no explicit leader/follower split; both hands are driven symmetrically from the human demonstration and jointly refined by one policy. No explicit relative-frame representation between the two hands is described — observations are per-hand wrist pose plus object pose, all in the robot/world frame (Table 6), not a hand-relative-to-hand frame.
- torso: fixed relative to a tabletop workspace — "keeping the lower body fixed since tabletop tasks do not involve lower-body motion" (§3.3); the humanoid's legs/base are not actuated during these tasks. Limitations section flags this as restrictive: "constrained action space... suggests the need for mobile manipulation platforms" (§5).
- hand model/DoF each side: Shadow Dexterous Hand, identical on both arms, multi-fingered (standard Shadow Hand hardware, DoF count not restated numerically in the parsed text beyond citing the hand's origin, Plappert et al. 2018).

## Evaluation
- metrics (exact definitions): pose estimation — ADD-S and VSD reported as AUC scores, plus Failure Rate and Temporal Stability (Appendix B.6 defines these fully; not reproduced verbatim here). Manipulation — success rate defined per MANIPTRANS's protocol: "each sequence is evaluated over 10 independent rollouts, with success requiring rotational error below 0.5 radians and positional error below 3cm at every time step," extended by DexMan "to consider entire episodes rather than just intermediate frames as in MANIPTRANS" (§4.2). E_r and E_t (average object rotation/translation error) are "computed only for successful rollouts" (§4.2, §4.3). For the video-to-robot pipeline, an additional Trajectory-to-Mask IoU metric compares detected object masks to masks rendered from the simulated object trajectory, used "since ground-truth object motion is unavailable" (§4.3).
- headline numbers: Table 1 (TACO pose estimation): DexMan ADD-S 0.57, VSD 0.82, Failure Rate 0.01, Temporal Stability 0.76, vs. FoundationPose (0.49, 0.70, 0.14, 0.70) and SpatialTracker (0.55, 0.56, 0.13, 0.79) — "gains of 0.08, 0.12, 0.13, and 0.06" over FoundationPose. Table 2 (OakInk-v2, ground-truth object assets/poses used by both methods, 77 sequences x 10 rollouts): DexMan success rate 44.3% vs. MANIPTRANS 25.3% (E_r 0.178 vs. 0.180, E_t 0.00688 vs. 0.00646) — "19% higher success rate," attributed to the contact-based reward (a footnote flags a GitHub issue discussion of a possible MANIPTRANS reproduction caveat). Table 3 (full video-to-robot pipeline, no ground-truth annotations, 1000 PPO updates): TACO — DexMan 27.4% success, E_r 0.314, E_t 0.016, IoU 49.0%; ablation "w/o task reward" drops to 18.4% (a 9.0-point drop); "w/o contact reward" collapses to 7.2% (a 20.2-point drop). Synthetic (Veo3) videos — DexMan 39.0% success, E_r 0.248, E_t 0.017, IoU 44.7%; "w/o task reward" 34.6% (4.4-point drop); "w/o contact reward" 7.8% (31.2-point drop). Table 4: stable-configuration rate 98% with sampling vs. 86% without, across 50 TACO + 50 Veo3 videos.
- baselines beaten: FoundationPose and SpatialTracker (pose estimation, Table 1); MANIPTRANS (bimanual dexterous manipulation on OakInk-v2 with ground-truth annotations, Table 2). No baseline exists for the full video-to-robot pipeline: "we do not compare against other baselines as, to the best of our knowledge, DexMan is the first framework capable of transferring monocular RGB human videos into bimanual dexterous robot policies" (§4.3).
- real robot? No — "Our framework has been developed and evaluated exclusively in simulation environments without deployment on physical robots, leaving a substantial sim-to-real gap to be addressed" (§5, explicit limitation). All numbers above are simulation (Isaac Gym).

## Data-generation specifics (survey field: demos synthesized / success rate of generation)
Not a demonstration-generation-from-few-human-demos system like DexMimicGen or HumanoidGen — DexMan converts each individual input video into (at most) one robot skill via RL, rather than multiplying a small demo set into thousands of trajectories. Scale reported instead as skill-recovery success rate over a video set: "27.4% of skills from TACO videos and 37.0% from Veo3-generated synthetic videos" (Abstract) — note Table 3 in the body reports 39.0% for synthetic videos, a discrepancy with the Abstract's 37.0% figure; flagged as an internal inconsistency in the source, use Table 3's 39.0% for the body-derived number and the Abstract's 37.0% only when quoting the abstract itself. 50 real (TACO) and 50 synthetic (Veo3) videos were attempted (§4.3), each independently producing a trained policy whose success is evaluated by the criteria above.

## Limitations stated by the authors
"Our framework has been developed and evaluated exclusively in simulation environments without deployment on physical robots"; restricted to "single-human demonstrations with rigid tabletop objects," excluding deformable/articulated objects; "prioritizes task completion over motion naturalness, resulting in robot trajectories that deviate from human movements"; "constrained action space, which limits motion replication capabilities and suggests the need for mobile manipulation platforms"; "end-effector control parameterization overlooks full arm posture, which is crucial for collision avoidance and effective multi-arm coordination in complex manipulation scenarios"; sequential (decoupled) pose-then-contact pipeline "may compromise the consistency of contact reasoning" since hand and object poses are estimated separately before contact priors are extracted (§5). Failure case: guitar-lifting task fails because the smaller Unitree G1 cannot reproduce the human demonstrator's larger-body arm poses needed to stably hold the guitar — an explicit embodiment-gap failure (§4.3, Fig. 6).

## Quotable claims (verbatim, with section)
- "DexMan directly controls a full humanoid robot from raw videos, making it the first framework to derive feasible multi-arm, multi-fingered robot skills directly from monocular RGB inputs" (§1).
- "Without them, success rates collapse from 27.4% to 7.2% on TACO and from 39.0% to 7.8% on Veo3 videos, highlighting that contact guidance is the dominant factor for recovering physically plausible robot skills directly from monocular videos" (§4.3).
- "our end-effector control parameterization overlooks full arm posture, which is crucial for collision avoidance and effective multi-arm coordination in complex manipulation scenarios" (§5).
