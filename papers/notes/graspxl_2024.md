# graspxl_2024 — GraspXL: Generating Grasping Motions for Diverse Objects at Scale (Zhang et al., ECCV 2024)

sources: papers/md/graspxl_2024.md [sha 52837875] ; code/md/graspxl_2024.md [commit 53ab112d]

## One-line contribution
An RL policy trained on only 58 objects generates objective-driven (heading direction, wrist rotation, midpoint, graspable area) grasping motions that transfer, with no hand-object data and no per-object reference generation, to 500k+ unseen objects and to four different hand morphologies (Abstract; Sec. 1; Sec. 4.3).

## Setting
- hand(s): MANO (45 finger joints), Shadow Hand (22), Allegro Hand (16), Faive Hand (30) — counts as stated in Sec. 4.3 ("Faive Hand has 30, Shadow Hand 22, Allegro Hand 16, and MANO 45 finger joints"); DoF beyond finger-joint counts not stated. Floating/free wrist base ("root_guided: True" in code cfgs); single-hand grasping in every reported experiment. Code API (`RaisimGymVecEnv.step(action_r, action_l)`) exposes left/right hand arguments, but the paper does not report a bimanual result.
- simulator / physics: RaiSim [23] (Sec. 4.1: "we use PPO [36] for RL training with the RaiSim [23] physics simulator"); version not stated.
- observation: feature extractor Φ(s,T): finger joint angles **q**, PD tracking error **d**, hand/object velocities **u_h**, **u_o**, contact vector **c**, force-magnitude vector **f**, differences to target heading/midpoint/rotation (ṽ, m̃, ω̃), and per-link nearest-point distance features **l⁺**, **l⁻** to the graspable/non-graspable point sets (Sec. 3, "Feature Extraction"). The exact per-item vector is not built in any file present in code/md — the wrapper only calls `self.wrapper.rewardInfoLeft()/rewardInfoRight()` and `.observe()` on a compiled RaiSim `impl` (code/md `RaisimGymVecEnv.py`, ~line 3540); the C++ `Environment.hpp` that assembles it is not included in code/md.
- action space: PD-control targets ("the policy **π** ... generates the actions **a**, representing the PD-control targets used to compute the torques **τ**", Sec. 3) — i.e. position targets, not raw torques. `finger_action_std: 0.015`, `rot_action_std: 0.01` (code `cfg_reg.yaml`, e.g. `raisimGymTorch/raisimGymTorch/env/envs/ours_floating/cfgs/cfg_reg.yaml`) are the exploration-noise stds on those targets. Control rate: simulation timestep 2.5e-3 s, 4 sim steps per action (Table 8) → control_dt = 0.01 s, matching code cfg `control_dt: 0.01`.
- objects / data: training set = 32 PartNet objects + 26 ShapeNet objects = 58 objects total (Sec. 4.1, matches Abstract's "policy trained with 58 objects"). Test sets after filtering: PartNet 48 objects, ShapeNet 3,993 objects, Objaverse 503,409 objects (Sec. 4.1; SupMat 8.1 confirms 32+48=80 PartNet objects selected and 26+3993=4019 ShapeNet/ACRONYM objects after filtering). PartNet test objects are unseen instances from seen categories; ShapeNet and Objaverse test objects are entirely novel categories/instances (Sec. 4.1). Table 1 reports GraspXL's "Number of Novel Test Objects" as 503,409 against baselines' 0–1,174.

## Method
- paradigm: end-to-end RL (PPO) — no separate analytic or generative grasp-pose module. The policy is queried directly in simulation ("our method can directly infer in simulation whereas the baselines rely on pre-generated hand pose references through a time-consuming optimization procedure", Sec. 4.2). This is explicitly contrasted with the SynH2R baseline, which first optimizes static reference poses and then tracks them.
- algorithm: PPO [36], "follow the implementation provided in [9]" (SupMat 7.1, Table 8: 1e4 epochs, 3e4 steps/epoch, 2000 batch size, 20 updates/epoch, γ=0.996, GAE λ=0.95, clip 0.2, max grad norm 0.5, value-loss coeff 0.5, entropy coeff 0.0, Adam lr 5e-4, 2-layer 128-unit hidden nets). Code: `num_threads: 32` in `cfg_reg.yaml` (parallel RaiSim environments); paper Table 8 does not itself state a parallel-env count, so 32 is a code-only number.
- teacher-student / distillation: not used here — state-based policy trained and evaluated directly (paper explicitly distinguishes itself from Wan et al. [43]'s state→vision distillation curriculum, Sec. 2.2).
- domain randomisation: target heading direction **v̄** ∈ IR³ and wrist rotation ω̄ ∈ [0, 2π) sampled at random per episode subject to the graspable width being < 12 cm between thumb and fingers; midpoint sampled from the graspable surface (Sec. 4.1, "Training Details"). Object mass varies naturally (volume × a fixed density) but density/friction are constant across objects during training; SupMat 9.2 separately evaluates (does not confirm as a training-time randomization) a friction range of ±0.3 around the default coefficient — ambiguous whether this range was used in training or only at test time.

- reward or loss (block C — quoted from paper and code, weights and any mismatch):

Paper (Sec. 3, terms only — the rendered equations are lost in PDF extraction, only the prose definitions survive):
- r = r_goal + r_grasp, "r_goal is for motion objectives and r_grasp is for successful grasping."
- r_goal = r_dis + r_v + r_ω + r_m: "r_dis promotes approaching the target while avoiding non-graspable areas, and r_v, r_ω, and r_m reward aligning heading direction, wrist rotation, and midpoint, respectively," with weights "w_d+(i) and w_d-(i)" per link on the closest graspable/non-graspable point distance.
- r_grasp = r_c + r_f + r_reg (+ r_anatomy for MANO): "r_c assesses the contact between fingers and the object ... (r_c = w_c+‖c+‖₂ − w_c-‖c-‖₂)"; "r_f ... (r_f = w_f+·c+·min(f+, λw_o) − w_f-·c-·min(f-, λw_o))"; "r_reg penalizes excessive velocities ... (r_reg = −w_h‖u_h‖² − w_o‖u_o‖²)"; "If the hand model is MANO, we additionally apply the anatomy reward r_anatomy [46] on joint angles q."
- Table 9 weight values (phase 1 static-object / phase 2 moving-object, per the curriculum):
  w_d+ 0.3/0.3, w_d- 0.06/0.06, w_v 1.0/0.01, w_ω 1.0/0.01, w_m 10.0/10.0, w_c+ 1.0/1.0, w_c- 1.0/1.0, w_f+ 0.3/0.5, w_f- 0.15/0.25, w_h 0.001/0.001, w_o 0.0/0.1, w_anatomy 0.2/0.1, λ 5.0/5.0.

Code (`raisimGymTorch/raisimGymTorch/env/envs/ours_fixed/cfgs/cfg_reg.yaml` = phase 1, `ours_floating/cfgs/cfg_reg.yaml` = phase 2 — identified by matching coefficients below to Table 9's two columns):
- `affordance_contact_reward: coeff: 1.0` / `not_affordance_contact_reward: coeff: -1.0` — matches w_c+/w_c- = 1.0/1.0 in both phases.
- `affordance_impulse_reward` / `not_affordance_impulse_reward`: 0.3/-0.15 (fixed) and 0.5/-0.25 (floating) — matches w_f+/w_f- exactly for both phases (0.3/0.15 phase 1, 0.5/0.25 phase 2).
- `affordance_reward` / `not_affordance_reward`: 0.3/-0.06 in both cfgs — matches w_d+/w_d- (0.3/0.06, identical both phases).
- `direction_reward`: -1.0 (fixed) / -0.01 (floating) — matches w_v (1.0 phase 1, 0.01 phase 2).
- `center_reward`: -10.0 in both — matches w_m = 10.0.
- `anatomy_reward`: -0.2 (fixed) / -0.1 (floating) — matches w_anatomy (0.2/0.1).
- `wrist_vel_reward_`/`wrist_qvel_reward_`: -0.001/-0.0001 in both cfgs; `obj_vel_reward_`/`obj_qvel_reward_`: 0.0/0.0 (fixed) vs -1.5/-0.01 (floating).
- `torque: coeff: -0.0` in both (unused).

Mismatches: (1) the code splits the paper's single r_reg = −w_h‖u_h‖² − w_o‖u_o‖² into four separately-weighted terms (wrist vel, wrist qvel, obj vel, obj qvel); the object-velocity code coefficient in the floating cfg (-1.5) does not equal the paper's stated w_o = 0.1 for phase 2 — only obj_qvel (-0.01) is in the right range, so the code's velocity-regularization weighting cannot be reconciled 1:1 with Table 9's w_h/w_o. (2) No config field corresponds to a separate wrist-rotation weight w_ω distinct from `direction_reward`; either it is folded into `direction_reward` in the (unavailable) C++ reward code, or it is not exposed in this YAML at all — code/md does not contain `Environment.hpp` for `ours_fixed`/`ours_floating` (not present in the depth-3 file tree or the extracted Python signatures), so the actual reward computation cannot be verified beyond these coefficient tables.
- key trick(s): "objective-driven hand guidance" — the (target − current) differences in heading, wrist rotation, and midpoint are added directly as bias terms to the wrist's 6-DoF PD-controller target, not just left to the reward gradient (Sec. 3); a two-phase curriculum (static objects/high r_goal → moving objects/high r_grasp) to decouple objective-following from stable grasping (Sec. 3, "Curriculum").

## Contact / penetration handling (block D)
Not addressed as a reward term: the reward's contact terms (r_c, r_f) reward/punish contact with graspable vs. non-graspable surface points and their force magnitudes, not interpenetration depth. Interpenetration is judged only post hoc, subjectively: in the realism study (SupMat 9.3), 35 participants rated rendered motions 1–3 on "human likeness, naturalness, smoothness, and hand-object interpenetration," giving GraspXL 2.12 vs. HO3D 2.05 vs. DexYCB 2.45 (ground-truth). No numeric penetration metric is computed. Contact-solver friction: "we use the same friction coefficient in simulation for all objects" (SupMat 8.1) — the coefficient's numeric value is not stated.

## Evaluation
- metrics (exact definitions, Sec. 4.1 "Evaluation Protocol"): Midpoint Error — mean Euclidean distance between final and target midpoint, cm. Heading Error — mean geodesic distance between final and target heading direction, rad. Wrist Rotation Error — mean absolute error between final and target wrist rotation, rad. Contact Ratio — ratio of links contacted with the graspable part vs. the entire object. Grasping Success Rate — "a grasp is determined as a success if the object is lifted higher than 10cm and remains stable without falling until the sequence terminates."
- headline numbers: Table 2 (PartNet/ShapeNet method comparison, MANO hand): Ours 95.0%/81.0% success vs. SynH2R 82.3%/65.8% vs. PD baseline 26.5%/21.9%. Table 3 (Objaverse, 503,409 objects, three size bins): overall success 82.2% (Small 85.9, Medium 84.5, Large 79.0). Table 5 (hand generalization, PartNet/ShapeNet success): Allegro 95.3/83.4, Shadow 94.0/83.2, Faive 95.8/82.4, MANO 95.0/81.0. Table 4 (generated/reconstructed objects): DreamFusion-generated 88.4%, HOLD in-the-wild reconstructions 77.5%, YCB reconstructions 74.0%, YCB ground-truth 73.7%. Eval sample sizes: 25 random objective sets per PartNet object, 5 per ShapeNet object (Sec. 4.2), 25 per generated/reconstructed object (SupMat 8.2). Training-set-size ablation (SupMat Table 10): 58 vs. 500 training objects gives near-identical success (95.0/81.0 vs. 94.9/84.3), reported as evidence of data efficiency, not an improvement.
- baselines beaten: SynH2R [8] (re-implemented/adapted with added midpoint- and rotation-error optimization terms), SynH2R-PD (SynH2R references + plain PD tracking), and a naive PD baseline — all three re-run by the authors, not quoted from the original papers, since SynH2R itself did not report these objective-driven metrics.
- real robot? Not stated — all numbers are simulated in RaiSim; no physical robot trials reported.

## Limitations stated by the authors
No dedicated limitations section is present in papers/md/graspxl_2024.md (none of the top-level headings correspond to one). The closest self-critical statements are in Sec. 4.2: success rate drops on ShapeNet vs. PartNet, "caused by some objects that are too large or too heavy to be grasped," for all methods including the non-learned PD baseline; and Sec. 4.3 notes the Allegro hand has larger midpoint error / lower contact ratio "due to its larger size."

## Quotable claims (verbatim, with section)
- "our policy trained with 58 objects can robustly synthesize diverse grasping motions for more than 500k unseen objects with a success rate of 82.2%." (Abstract)
- "A grasp is determined as a success if the object is lifted higher than 10cm and remains stable without falling until the sequence terminates." (Sec. 4.1)
- "generating grasp pose references for the ShapeNet test set using the baselines requires approximately a week, whereas our method can directly perform realtime inference in simulation" (Sec. 4.2)
- Inference-speed numbers (SupMat 9.4): "we generate 100 sequences and calculate the average time consumption per sequence with our method, the baselines SynH2R-PD, and SynH2R [8], leading to 37.15, 37.17, and 0.14 seconds, respectively." NOTE: this ordering is inconsistent with the surrounding prose ("The most time consumption for SynH2R-PD and SynH2R are caused by the optimization-based ... procedure" and Sec. 4.2's claim that GraspXL is real-time while SynH2R takes ~1 week per test set) — the 0.14 s figure reads as if it belongs to GraspXL, not SynH2R, but the sentence's literal object order assigns it to SynH2R.
