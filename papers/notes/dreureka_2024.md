# dreureka_2024 — DrEureka: Language Model Guided Sim-To-Real Transfer (Ma, Liang, Wang, Wang, Zhu, Fan, Bastani, Jayaraman; RSS 2024)

sources: papers/md/dreureka_2024.md [5931e0b0] ; code/md/dreureka_2024.md [1d4e0070]

## One-line contribution
Extends Eureka's LLM reward search with a safety-instructed prompt, then adds a "reward-aware physics prior" (RAPP) — simulate the reward-only policy under swept single-parameter perturbations to bound a feasible domain-randomization (DR) range per parameter — which is handed to the LLM to propose full DR configurations, evaluated on quadruped locomotion, quadruped "globe walking" (novel task), and LEAP-hand cube rotation (Abstract; Sec. IV).

## Setting
- hand(s): LEAP hand (Shaw et al. [30]), 16 DoF across 3 fingers + thumb, low-cost anthropomorphic; no arm; single hand. Also quadruped (Unitree Go1, 12 DoF) for the two locomotion case studies — out of scope for this survey's hand focus but part of the same method (Sec. V).
- simulator / physics: NVIDIA Isaac Gym for all tasks (Sec. V, "Both robots... admit simulators in NVIDIA Isaac Gym"). Cube-rotation training/deployment code is the LEAP-hand authors' own (Shaw et al. [30]); not included in the released DrEureka repo (code/md has only `forward_locomotion/` and `globe_walking/` trees, no LEAP-hand directory).
- observation (cube rotation): "16 joint angles and proprioceptive history, encoded via GRU... does not have access to the position and pose of the cube" (Sec. V). Reward function code (Prompt 13) additionally uses `object_pos`, `object_angvel_finite_diff`, `object_linvel`, `leap_hand_dof_pos`, `init_pose_buf` as privileged reward inputs (not necessarily policy observations).
- action space: 16 target joint angles as PD position commands, deployed to a "PID controller running at 20 Hz" (App. D2).
- objects / data: single cube per episode; cube size domain-randomized (App. D2, "randomize... the size of the cube" following LeapHand training code); real cube measured at 0.046 kg (Prompt 8 comment).

## Method
- paradigm: RL, sim-trained with LLM-automated reward design (Eureka) + LLM-automated domain randomization (novel to this paper); algorithm: PPO (Sec. V, "the reinforcement learning algorithm is Proximal Policy Optimization [69]"), using the LEAP-hand authors' original training hyperparameters unmodified (Sec. V, "Adopting the evaluation protocol from Ma et al. [9], we use the original policy training hyperparameters... and do not modify or tune them").
- outer loop (Algorithm 1, "DrEureka Reward Design"): for N iterations, sample K reward-function candidates from the LLM given task description `l_task`, safety instruction `l_safety`, and environment code M; train a policy per candidate with RL; score each with fitness function F; feed the best candidate's reward code and score back to the LLM as a "Reflection" to produce the next iteration's prompt; keep the running best (R_DrEureka, π_initial). Hyperparameters from code/md `eureka/cfg/config.yaml`: `model: gpt-4-0125-preview`, `temperature: 1.0`, `iteration: 5`, `sample: 16` — i.e. N=5, K=16 (identical to the "original Eureka hyperparameters" the paper says it reuses, Sec. V).
- Reward-Aware Physics Prior (RAPP, Algorithm 2, Sec. IV-C): for each candidate DR parameter p, sweep search values r over a "general range," set only p=r (others at default), roll out π_initial, and check a per-task success criterion F(τ); the feasible range for p is [min, max] over values that pass. This produces per-parameter (valid range, RAPP search range) bounds, e.g. Table XIII for cube rotation: object mass RAPP range [0.01,1] kg, hand friction [0,10], dof stiffness [1,10], dof damping [0,0.5], hand restitution [0,1], dof friction [0,0.1], armature [0,0.01], object friction [0,10], object restitution [0,1].
- LLM DR generation (Sec. IV-D): the LLM is given all RAPP ranges and asked to (1) choose a subset of parameters to randomize and (2) pick a randomization range within the RAPP bounds, output as Python variable assignments with comments explaining each choice (Prompt 6, system prompt). Unlike prior auto-DR work that directly sets DR to the full feasible range, DrEureka uses RAPP only as a *prior context* for the LLM, which the paper shows outperforms using the raw RAPP range directly ("Prompt DR" ablation, worse than DrEureka in Table I). m independent DR configurations are sampled zero-shot (m=16 per `sample: 16`); a policy is trained per configuration and ALL are kept — "it is difficult to select the best DR configuration... we keep all m policies and report both the best and the average performance in the real world" (Sec. IV-D).
- fitness / success criteria (Table IV, App. A5, quoted): Forward Locomotion: `exp(-(v_x - v_x^t)^2/0.25)`; Cube Rotation: `clip(ω_z, -0.25, 0.25)`; Walking Globe: `1` (survival/height-based, constant per-step credit). "The success criteria is summed over all steps within an episode." This F is the *outer-loop* fitness used to rank reward candidates and to gate RAPP feasibility — separate from the reward function R being optimized by the inner RL.
- reward (quoted verbatim, cube rotation, App. B1 "Prompt 13" = code/md's would-be `eureka_reward.py` equivalent, not present in released repo but shown in the paper):
```
@torch.jit.script
def compute_reward(object_pos, object_angvel_finite_diff, object_linvel, leap_hand_dof_pos, init_pose_buf, reset_z_threshold):
    ang_vel_target = 0.25
    max_ang_vel_reward = 2.5
    linear_velocity_penalty_coefficient = -3.0
    angular_velocity_penalty_coefficient = -2.5
    fall_penalty = -5.0
    deviation_penalty_coefficient = -0.2
    ang_z_vel = object_angvel_finite_diff[:, 2]
    ang_z_vel_reward = torch.where(ang_z_vel > ang_vel_target,
        ang_vel_target + (1 - torch.exp(ang_vel_target - ang_z_vel)), ang_z_vel)
    ang_z_vel_reward = torch.clamp(ang_z_vel_reward, max=max_ang_vel_reward)
    lin_vel_penalty = linear_velocity_penalty_coefficient * torch.norm(object_linvel, dim=1)
    object_fall_penalty = torch.where(object_pos[:, 2] < reset_z_threshold, fall_penalty * ones, zeros)
    deviation_penalty = deviation_penalty_coefficient * torch.norm(leap_hand_dof_pos - init_pose_buf, dim=1)
    total_reward = ang_z_vel_reward + lin_vel_penalty + object_fall_penalty + deviation_penalty
```
Note `angular_velocity_penalty_coefficient` is defined but never used in the shown reward body — a residual/unused variable in the LLM-generated code, left as-is in the quote.
- reward (forward locomotion, quoted, App. B1 "Prompt 12", confirmed byte-identical in code/md `forward_locomotion/go1_gym/rewards/eureka_reward.py::compute_reward`): multiplicative product `velocity_reward * height_reward * orientation_reward * dof_limit_violations_reward * smoothness_reward`, each an `exp(-k * error)` term or a binary indicator; code adds an optional curriculum branch (`_reward_tracking_lin_vel`, `_reward_tracking_ang_vel`) not in the paper's printed prompt, gated by `using_curriculum` — a paper/code addition specific to the curriculum-trained baseline variant, confirmed present in the actual `EurekaReward.compute_reward` signature `compute_reward(self, using_curriculum=False)`.
- safety instruction (Sec. IV-B, Prompt 3, quoted for cube rotation): "the policy should be smooth and steady, and the fingers should be penalized for deviating far from their initial position... we would like the cube to rotate at around 0.25 radians per second; however, it's okay if it rotates faster." This natural-language instruction, not a fixed reward template, is what the LLM turns into the `deviation_penalty` and the `ang_vel_target=0.25` clamp above — the paper's central claim is that asking for safety in the prompt (rather than post-hoc adding a penalty term) lets the LLM balance term weights itself (Sec. IV-B).
- reward reflection (App. B3, quoted example on globe walking, not cube rotation — no cube-rotation reflection trace is shown in the parse): after training, the LLM receives per-500-epoch max/mean/min of task score, episode length, and each named reward component, plus fixed tips ("(1) If the task score is always near zero, then you must rewrite the entire reward function (2) If the values for a certain reward component are near identical throughout... (3) If some reward component's magnitude is significantly larger, then you must re-scale its value"). In the shown example this moved task-score mean from 115.54 to 407.71 across one iteration by rescaling `height_reward` (added an exp transform, ×2 scale) and `smooth_actions_reward` (×0.5 → later ×1.0 in final).

## Evaluation
- metrics: Cube rotation — total rotation (rad) over a fixed 20 s real-world trial, and time-to-fall (s) (Table II). Forward locomotion — forward velocity and meters traveled on a 5 m real track (Table I). Globe walking — time on ball, sim and real (Table III).
- headline numbers (Table II, cube rotation): Human-Designed [30] 3.24 ± 1.66 rad, 20.00 ± 0.00 s (never falls in the trial window); DrEureka Best 9.39 ± 4.15 rad, 20.00 ± 0.00 s; DrEureka Average (over all 16 DR-configuration policies) 4.67 ± 3.55 rad, 16.29 ± 6.28 s. Text: "the best policy from DrEureka significantly outperforms the baseline by nearly three times the rotation without dropping the cube" (Sec. VI-A) — matches the bib's "~300% more rotations" framing.
- eval protocol: "For every DR configuration, we train policies using 3 random seeds and report average as well as standard deviation across trials and seeds" (Sec. V) — this is stated for the general protocol; the cube-rotation table does not separately break down real-world trial count beyond this, and no explicit number of physical rollouts per seed is given for cube rotation (no per-trial video count stated in the parse — flag as under-specified for this task specifically, distinct from forward locomotion's explicit "5-meter track" single-run description).
- baselines beaten: Human-Designed (Shaw et al.'s original LEAP-hand reward + DR) is the only cube-rotation baseline; no plain-Eureka (reward-only, no DR) ablation is run for cube rotation — that ablation exists only for forward locomotion (Table I: Eureka alone gets 0.0 ± 0.00 m/s, "fails to walk").
- real robot? Yes — LEAP hand, real cube, but exact real-world trial count for cube rotation is not stated beyond the 3-seed/DR-configuration protocol quoted above; not video-only (numeric rotation and time-to-fall are reported per configuration), but the granularity (how many physical rollouts contribute to each mean/std) is not printed.

## Limitations stated by the authors (Sec. VIII)
- "Lack of visual inputs": state-based only, no vision integration.
- "Static domain randomization parameters": DR ranges are fixed after generation, not adapted during training (unlike some auto-DR curricula it compares against).
- "Lack of policy selection mechanism": no systematic way to pick the best of the 16 generated (reward, DR) policies without real-world evaluation of all of them.

## Notes for the survey
- What DrEureka adds over Eureka (2023): Eureka is the outer LLM-reward-evolution loop alone (Algorithm 1's inner Eureka background, Sec. IV-A, unchanged from the 2023 paper). DrEureka's contribution is entirely downstream of the reward: (1) a safety-instruction prompt in place of Eureka's bare task prompt, so the LLM itself balances safety/task terms instead of a human bolting on a penalty post hoc (Sec. IV-B); (2) RAPP, a policy-conditioned single-parameter sweep that bounds a per-parameter feasible range *without any real-world data*, purely by testing the reward-only policy under perturbed sim physics (Sec. IV-C); (3) using that RAPP range as a *prior fed to the LLM* rather than as the DR range itself — the paper's own "Prompt DR" ablation (using the raw RAPP bound as DR) underperforms DrEureka's LLM-mediated choice (Table I). Plain Eureka (reward-only, no DR) fails outright on the real robot for forward locomotion (0 m/s) — direct evidence that a sim-only reward is not sufficient for sim-to-real, motivating the whole DR pipeline.
- Feeds: the survey's reward-design comparison table (Eureka vs. DrEureka vs. hand-written); the DR section (LLM-proposed vs. classical CEM/BayRn, which DrEureka beats in Table I at 3h vs. 10-20h wall-clock); and the "how was the candidate selected" methodology box — DrEureka's answer is a hand-authored, task-specific scalar F(τ) (Table IV), not the training reward itself, consistent with Eureka's design.
- Caveat for citing the cube-rotation numbers: only one baseline (Human-Designed) and one task variant are tested for the hand; no ablations (No DR, No Prior, etc.) are run on cube rotation, only on forward locomotion — do not extend the ablation conclusions to the hand task without noting this gap.
- Contact/penetration handling: not addressed anywhere in this paper for cube rotation (no penetration metric, no contact reward term in Prompt 13); the only contact-adjacent term is the linear-velocity and fall penalties.
