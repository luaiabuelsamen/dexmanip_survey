# dexmimicgen_2024 — DexMimicGen: Automated Data Generation for Bimanual Dexterous Manipulation via Imitation Learning (Jiang, Xie, Lin et al., ICRA 2025 / arXiv 2024)

sources: papers/md/dexmimicgen_2024.md [96349aac / arxiv 2410.24185] ; code/md/dexmimicgen_2024.md [940e8a1b]

## One-line contribution
DexMimicGen extends MimicGen's single-arm data-generation-from-demonstrations pipeline to bimanual (and dexterous-hand) robots by adding a per-arm subtask taxonomy — parallel, coordination, and sequential subtasks — with asynchronous per-arm execution, synchronization, and ordering constraints, generating 21K simulated demonstrations from 60 human source demos across 9 tasks / 3 embodiments, and deploying a real-to-sim-to-real pipeline on a real humanoid can-sorting task (Abstract, §IV).

## Setting
- hand(s): three embodiments (§V): (1) bimanual Panda arms with parallel-jaw grippers (not multi-fingered); (2) bimanual Panda arms with dexterous hands (multi-fingered, exact hand model not named in the parsed text beyond "dexterous hands"); (3) GR-1 humanoid with dexterous hands. Real-world deployment uses a Fourier GR1 robot "equipped with two 6-DoF Inspire dexterous hands" (§VI-D) — multi-fingered. Arm: Panda arms (bimanual embodiments 1-2) or GR-1's arms (embodiment 3, torso-linked). Bimanual throughout.
- simulator / physics: RoboSuite built on MuJoCo for physics (§V). Panda-arm embodiments controlled via Operational Space Control (OSC) converting delta end-effector pose to joint torques; the GR-1 humanoid controlled via an Inverse Kinematics (IK) controller based on `mink`, translating global target end-effector poses to joint positions, chosen specifically "to deal with the complexity of the humanoid kinematic tree, where both arms are linked to a single torso" (§V). Finger control is direct joint position control on all embodiments with dexterous hands.
- observation: image-based visuomotor policies trained on the generated datasets (§VI-A); exact observation vector composition beyond "image-based" is not detailed in the parsed paper text; code confirms environments expose `use_camera_obs`/`use_object_obs` flags (constructor signature in `two_arm_can_sort.py`) but the concrete observation keys were not captured in the parsed code markdown.
- action space: per MimicGen's Assumption A1, inherited by DexMimicGen: "the action space A consists of the following components for each robot arm: a pose command for an end effector controller and an actuation command for the hand (1D open/close for parallel-jaw gripper, 6-D joint commands for dexterous hand)" (§III). Finger motion during data generation is generated by directly replaying the source demo's finger joint actions, "because the finger movement is always relative to the end-effector movement" (§IV-D) — i.e., finger trajectories are not independently retargeted/regenerated, only arm end-effector poses are transformed.
- objects / data: 9 simulation tasks (Threading, Piece Assembly, Transport, Box Cleanup/Packing, Drawer Cleanup, Tray Lift, Pouring, Coffee, Can Sorting) across the 3 embodiments (Fig. 4); also applied to BiGym (FlipCup, DishwasherLoadPlates, CupboardsCloseAll). Real-world: Can Sorting task with red/blue cups on the GR1 platform.

## Method
- paradigm: automated demonstration-generation-from-demonstrations (not RL, not end-to-end learned) feeding standard IL/BC policy training (BC-RNN, BC-RNN-GMM, Diffusion Policy) — a data-generation system paper, not a policy-architecture paper. IL formalized as BC maximizing "arg max_θ E_(s,o,a)~D [log π_θ(a|o)]" (§III).
- reward or loss: RL-style reward is not used for policy training (BC only); the environments do implement a sparse task-completion "reward" function used purely as the generation-time success filter, quoted from code (`two_arm_can_sort.py`, `TwoArmCanSortRandom.reward`): "The sparse reward only consists of the threading component... sparse completion reward: if self._check_success(): reward = 1.0" with an unused `reward_shaping` branch (`if self.reward_shaping: pass`) — confirms the paper's statement that DexMimicGen's "success check is used for filtering out failed demonstrations during the data generation phase" (Appendix IX) rather than for training a reward-driven policy. No BC loss formula beyond the log-likelihood objective is given.
- key trick(s): per-arm object-centric subtask segmentation with a 3-way taxonomy (parallel/coordination/sequential, §IV-A/B/C); asynchronous per-arm action-queue execution for parallel subtasks; for coordination subtasks, either a "Transform" scheme (apply a shared SE(3) transform derived from the reference object's pose to both arms' source segments) or a "Replay" scheme (execute the source trajectories unmodified) — Replay preferred by default for handover subtasks since it "ensures the trajectory remains within kinematic limits and is fully executable" (§IV-B); for sequential subtasks, an ordering-constraint mechanism makes the post-subtask arm wait for the pre-subtask arm to finish (§IV-C); real2sim2real digital twin pipeline using GroundingDINO-based RGB-D object pose estimation to synchronize simulated and real initial states before generating and executing each real-world demonstration (§VI-D).

## Contact / penetration handling
Explicitly addressed and explicitly NOT solved: "How does DexMimicGen handle collisions between the robots and objects? DexMimicGen does not explicitly handle collisions. Some failure cases during the data generation phase result from collisions between the generated trajectory and objects in the workspace. To mitigate this issue, we plan to extend DexMimicGen with motion planning modules from SkillMimicGen [79] for future work" (Appendix IX). So collisions are neither penalized nor measured — they simply manifest as generation failures, which are then filtered out by the binary success check (a demonstration is kept "only if the task is successful", §IV-D), not by any penetration metric. No two-hand collision-avoidance mechanism is described either, beyond the general MuJoCo contact/dynamics simulation itself.

## Coordination and embodiment (survey fields)
- two-hand coordination: neither "one policy over both hands" nor "leader-follower" in the RL/control sense — this is a data-generation system, and coordination is handled structurally by the subtask taxonomy: parallel subtasks let each arm run its own independent per-arm subtask queue asynchronously (Sec IV-A); coordination subtasks synchronize both arms' remaining-step counts so they finish together and apply either a shared Transform or a Replay of source trajectories to preserve the relative pose between end-effectors (§IV-B) — this IS an explicit relative-frame mechanism, applied at generation time rather than as a policy observation; sequential subtasks enforce an explicit ordering constraint (one arm's post-subtask must wait for the other's pre-subtask, §IV-C). The downstream trained policies (BC-RNN/BC-RNN-GMM/Diffusion Policy) are each a single policy over the full bimanual action space (both arms + both hands/grippers), i.e. one policy over both hands at the imitation-learning stage.
- torso: both fixed and mobile depending on embodiment — bimanual Panda-arm embodiments (grippers and dexterous hands) are on a fixed/table-mounted base; the GR-1 humanoid embodiment has "both arms... linked to a single torso" requiring the IK controller specifically to handle that kinematic coupling (§V), and the BiGym extension explicitly targets "bimanual mobile manipulation tasks" (§VI-B), i.e. a mobile humanoid setting.
- hand model/DoF each side: real-world hardware is Fourier GR1 with two 6-DoF Inspire dexterous hands (identical both sides, multi-fingered, §VI-D); the two simulated dexterous-hand embodiments (bimanual Panda + dexterous hands, and GR-1 + dexterous hands) use "dexterous hands" per MimicGen's assumption A1 with 6-D joint hand-actuation commands, exact make/model not further specified in the parsed paper text; the third simulated embodiment (bimanual Panda + parallel-jaw grippers) is explicitly NOT multi-fingered (1-D open/close gripper actuation).

## Evaluation
- metrics (exact definitions): task success rate from BC policies, reported as mean ± std over 3 seeds, "we run each experiment across 3 different seeds, and take the maximum policy success rate for each seed" (§VI-A) — i.e. each seed's reported number is that seed's best checkpoint success rate, then averaged across seeds. Real-world: success rate over "10 trials each for the red and blue cups" (20 total real trials per model, §VI-D).
- headline numbers: Table I (1000 DexMimicGen demos/task, 3 seeds) — Diffusion Policy is generally best: Piece Assembly 80.7±0.9% (vs. source-demo DP 3.3±0.9%), Threading 69.3±1.9% (vs. 1.3±0.9%), Transport 83.3±0.9% (vs. 52.7±7.7%), Drawer Cleanup 76.0±0.0% BCRNN 80.0±0.0% (vs. source 0.7±0.9%), Can Sorting 97.3±0.9% DP / 96.0±4.3% BCRNN (vs. source 0.7±0.9%). Data-scale study (Fig. 5): performance rises from 100->500->1000 demos but sometimes plateaus or drops from 1000->5000 (diminishing/negative returns on some tasks). Ablations: Replay vs Transform for handover coordination — Transport 63.3% (Replay) vs 46.0% (Transform); Can Sorting 97.3% vs 98.6% (comparable). Ordering constraints for sequential subtasks: Drawer Cleanup 50.7% (with constraint) vs 48.0% (without) vs 56.7% (same source demo for both arms); Pouring 88.7% vs 76.7% vs 79.3%. DemoNoise baseline comparison (Table III): DexMimicGen outperforms DemoNoise "by more than 58% across all tasks" (e.g. Piece Assembly 74.0±2.8% vs 12.7±3.4%; Tray Lift 75.3±7.5% vs 16.7±2.5%; Pouring 79.3±0.9% vs 26.7±2.5%). BiGym generation success rates: FlipCup 29.1%, DishwasherLoadPlates 43.6%, CupboardsCloseAll 76.4% (these are data-generation success rates, not policy success rates). Real-world Can Sorting: policy trained on 40 DexMimicGen demos reaches 90% success (18/20 trials) vs. 0% for a policy trained on the 4 raw source demos.
- baselines beaten: BC on raw source demos only (Table I "Source Demo DP" column); DemoNoise (replay-with-action-noise data generation, Table III); comparison across BC-RNN, BC-RNN-GMM, and Diffusion Policy architectures on the same generated data (Diffusion Policy generally best; BC-RNN-GMM "generally underperformed BC-RNN and Diffusion Policy, especially on tasks that involve dexterous hands," contrasting with the RoboMimic study's finding that a GMM head helps, §VI-C — flagged mismatch with prior literature).
- baselines beaten (real): the 4-source-demo BC policy (0% success) vs. the 40-DexMimicGen-demo policy (90% success), both Diffusion Policy, on real hardware.
- real robot? Yes for the Can Sorting deployment: Fourier GR1 + two 6-DoF Inspire hands, 10 trials each for red and blue cup (20 total), reported above. All other numbers (Tables I-III, Fig. 5) are simulation-only (RoboSuite/MuJoCo).

## Data-generation specifics (survey field: demos synthesized / success rate of generation)
- Source demos: "60 source human demos" total across the 9 sim tasks (Abstract); per-task breakdown (§VI-A): "ten source human demonstrations for each task with parallel-jaw grippers, but only five demonstrations for those involving dexterous hands due to the additional operator burden and time cost of collecting demonstrations for dexterous hands."
- Generated demos: "21K demos across these tasks" (Abstract); per-task generation target used for the main experiments is 1000 demonstrations per task (§VI-A: "DexMimicGen is subsequently used to generate 1000 demonstrations per task"); larger runs of up to 5000 demos/task were also generated for the dataset-size study (Fig. 5).
- Generation success rate: not given as a single aggregate number across the 9 core tasks in the parsed text (the paper reports downstream policy success rates instead, which conflates generation quality with policy learnability); the one place a generation-process success rate is explicitly reported is for the BiGym extension tasks — FlipCup 29.1%, DishwasherLoadPlates 43.6%, CupboardsCloseAll 76.4% (§VI-B) — these are "data generation success rates," i.e. the fraction of attempted generation rollouts that were kept as successful demonstrations.
- Real-world generation: 4 source human demonstrations for the real Can Sorting task, used to generate 40 successful demonstrations via the digital-twin pipeline (§VI-D) — an 4-to-40 (10x) real-to-sim-to-real scale-up, distinct from the sim-only 60-to-21,000 (350x) scale-up quoted above.

## Limitations stated by the authors
Collision handling is explicitly unsolved (quoted above, Appendix IX) with SkillMimicGen-style motion planning proposed as future work. Threading's success rate stays below 70% because "both the threading object and the hole are occluded from the third-person camera," proposed fix is visual RL for active perception (Appendix X). Finger-joint action generation is limited to local interpolation/replay of the source demo rather than broad distributional expansion (PCA visualization, Appendix X, Fig. 7), unlike end-effector pose actions which DexMimicGen "significantly expands."

## Quotable claims (verbatim, with section)
- "We generate 21K demos across these tasks from just 60 source human demos" (Abstract).
- "DexMimicGen does not explicitly handle collisions. Some failure cases during the data generation phase result from collisions between the generated trajectory and objects in the workspace" (Appendix IX).
- "we generate finger motion by replaying the finger joint actions in the source demo because the finger movement is always relative to the end-effector movement" (§IV-D).
- "The policy trained on DexMimicGen data achieves 90% success, while the model trained on the source data achieves 0%" (§VI-D).
