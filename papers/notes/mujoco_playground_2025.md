# mujoco_playground_2025 — MuJoCo Playground (Zakka et al., arXiv 2502.08844, 2025)

sources: papers/md/mujoco_playground_2025.md [sha256 1227d941] ; code/md/mujoco_playground_2025.md [commit 4057c147]

## One-line contribution
An open-source suite of GPU-native RL environments built on MJX (MuJoCo-on-JAX) spanning DM Control, locomotion (6 embodiments), and manipulation (Leap Hand, Franka+Robotiq, Aloha), integrating the Madrona batch renderer for on-device vision training, and demonstrating zero-shot sim-to-real transfer including contact-rich in-hand cube reorientation trained in 30 minutes on 2 RTX 4090s (Abstract, Sec. I).

## Setting
- hand(s): **LEAP Hand** [56] — the paper's only named dexterous hand, used for "contact-rich dexterous re-orientation of a block" (Sec. II-C) and real-world cube reorientation (Sec. IV-C1). No DoF count or vendor detail given in the paper text (cites [56] for the platform). Code additionally ships an **Aero Hand** (`mujoco_playground/_src/manipulation/aero_hand/`, docstring: "Base classes for TetherIA Aero Hand Open" — i.e. the TetherIA Aero Hand Open, a tendon-driven hand inferred from its tendon-length sensor observations) — this hand does **not** appear anywhere in the paper text; it is a code-only addition postdating or outside the paper's own reporting. Flag this paper-vs-code mismatch explicitly.
- arm: Franka Emika Panda (+ Robotiq gripper for non-prehensile block reorientation), Aloha bi-arm platform (peg insertion). single/bimanual: single-hand in-hand manipulation (Leap Hand); bimanual only for the non-dexterous Aloha peg-insertion task.
- simulator / physics: **MJX** ("MuJoCo XLA"), "a JAX-based branch of the MuJoCo physics engine that runs on GPU, enabling training directly on device" (Sec. I). Vision added via the **Madrona** batch renderer (GPU entity-component-system), integrated with MJX through low-level JAX primitives compatible with `jit`/`vmap` (Sec. III); two backends: "a software-based batch ray tracer written in CUDA (used for the experiments in this work) and a Vulkan-based rasterizer" (Sec. III).
- observation: LEAP Hand `CubeReorient` state observation is built from (code, `leap_hand/reorient.py::_get_obs`): noisy 16-dim hand joint angles, a rolled 16-step joint-position-error history, a rolled 3-step cube-position-error history, a rolled 6-step cube-orientation-error history (flattened rotation-matrix difference), and `last_act` (16) — concatenated into `state`; `privileged_state` additionally includes true joint pos/vel, fingertip positions, uncorrupted cube pos/orientation error, cube linear/angular velocity, perturbation direction, and applied external force on the cube. Cube pose observations are corrupted with configurable noise and, with probability `random_ori_injection_prob`, replaced entirely by a random pose (`m = level * bernoulli(...)`) to harden against tracking dropout.
- action space: LEAP Hand — joint targets (16-dim actuator space implied by `_hand_qids` size); Franka non-prehensile block task — "direct high-frequency torque control at 200 Hz, where the RL policy outputs motor torques for the arm's seven joints (with the gripper closed)" (Sec. IV-C2); Franka pixel pick-cube — reduced 3-dim Cartesian action (Y-move, Z-move, discrete jaw) via closed-form IK (Sec. IV-C3).
- objects / data: LEAP Hand task reorients "a 7 cm cube ... from random initial poses to new target orientations in SE(3)" (Sec. IV-C1-a); non-prehensile task moves "a yoga block from a random initial pose ... to a fixed goal pose" (Sec. IV-C2-a); pixel pick-cube task uses "a small 2x2x3 cm block" (Sec. IV-C3-a). Assets sourced from MuJoCo Menagerie: "Playground directly utilizes MuJoCo Menagerie [68] which offers a suite of robot assets and configurations tailored to run in MuJoCo" (Sec. II).

## Physics
- **Contact model**: MJX inherits MuJoCo's convex-contact family (not re-derived in this paper); per-environment MJX solver settings are tuned per DM Control task and explicitly parameterize **max contact points** and **max geom pairs** (Table III, Appendix A.1, exact per-env values below) because "JAX's requirement of static shapes at compile time" forces a fixed upper bound on simultaneous contacts (Sec. VI, Limitations).
- **Solver / iteration counts** (Table III, DM Control Suite ported to MJX; "solver iterations, line search iterations, as well as contact custom parameters for MJX" — exact per-env cells, verbatim): acrobot-swingup `iterations=2, ls_iterations=4`; ball-in-cup-catch `iterations=1, ls_iterations=4`; cartpole-balance `iterations=1, ls_iterations=4`; cheetah-run `iterations=4, ls_iterations=8, max_contact_points=6, max_geom_pairs=4`; finger-spin `iterations=2, ls_iterations=8, max_contact_points=4, max_geom_pairs=2, removed cylinder collision`; fish-upright `iterations=2, ls_iterations=6, disabled contacts`; hopper-stand `iterations=4, ls_iterations=8, max_contact_points=6, max_geom_pairs=2`; humanoid-stand `timestep=0.005, max_contact_points=8, max_geom_pairs=8`; pendulum-swingup `timestep=0.01, iterations=4, ls_iterations=8`; point_mass-easy `iterations=1, ls_iterations=4`; reacher-easy `timestep=0.005, iterations=1, ls_iterations=6`; swimmer-swimmer6 `timestep=0.003, iterations=4, ls_iterations=8, contype/conaffinity set to 0`; walker-stand `timestep=0.005, iterations=2, ls_iterations=5, max_contact_points=4, max_geom_pairs=4`. No per-env solver-family name (PGS/Newton/CG) is stated in the paper — only iteration counts and, for a handful of envs, an explicit physics timestep override.
- **Differentiable contacts**: not claimed or used by this paper. MJX is JAX-based (hence auto-differentiable in principle, and the Related Work section cites Brax and DiffTaichi as differentiable engines, Sec. V-a refs [13],[23]), but MuJoCo Playground trains exclusively with RL (PPO/SAC via Brax, plus a torch-based RSL-RL comparison, Sec. IV-C2) — the word "differentiable" is never applied to MJX itself in the paper text.
- **Default timestep / substeps**: no single global default is stated for the whole suite; per-task overrides appear only in Table III (0.003-0.01 s for several DM Control envs). The one explicit physics-timestep figure for a manipulation task: "At 20 Hz control with a 5ms physics timestep, the policy makes only one decision per 10 simulator sub-steps" (Sec. D.3, Franka pixel pick-cube environment) — i.e. **5 ms physics timestep, 10 substeps per 50 ms (20 Hz) control step**.
- **Friction model**: not specified quantitatively anywhere in the paper (no friction-coefficient values or cone-vs-pyramid statement); domain randomization is applied to "cube mass and friction" for the LEAP hand task (Sec. IV-C1-c) without giving ranges in the main text.
- **Penetration handling / exposure**: not discussed as a named metric or resolution mechanism; the paper's only interpenetration-adjacent statement is a real-world hardware failure mode, not a simulator quantity: "The most frequent failure occurs when the cube becomes wedged in the space present between the fingers and the palm of the LEAP hand ... we also observe accidental interlocking of the index and thumb, attributed to physical flex in the low-cost hardware ... more accurate collision geometries could mitigate these edge-case failures" (Sec. IV-C1-d) — i.e. collision-geometry fidelity (sim-to-real geometry mismatch), not a penetration-depth quantity, is named as the fix.
- **GPU or CPU**: GPU throughout for physics (MJX) and rendering (Madrona); RL training hardware spans "NVIDIA RTX 4090, A100, and H100 GPUs" in single- and multi-GPU topologies (Sec. IV-D).
- **Throughput** (exact figures/tables and hardware):
  - LeapCubeReorient wallclock scaling (Fig. 6, Sec. IV-D): "1x 4090 takes ~2080 s to train and 8x H100 takes ~670 s to train" (8192 num envs, same hyperparameters across topologies) — "GPUs with higher theoretical performance and larger topologies can reduce training time by a factor of 3x on a contact-rich task like in-hand reorientation."
  - Manipulation-suite PPO steps/sec on a single A100 GPU, 5 seeds, brax PPO (Table IX, exact): AlohaSinglePegInsertion 121119+/-2159; **LeapCubeReorient 76354+/-143**; **LeapCubeRotateZAxis 76602+/-179**; PandaOpenCabinet 136007+/-1553; PandaPickCube 140386+/-1707; PandaPickCubeCartesian 38015+/-5302; PandaPickCubeOrientation 140429+/-1604; PandaRobotiqPushCube 487341+/-4346.
  - Vision throughput via Madrona batch rendering, single-camera, on-device renderer (Fig. 7): "our Cartpole and Franka environments unroll at roughly 403,000 and 37,000 steps per second respectively" (resolution-swept 64-512 px); "our Franka physics are over 20x more costly than Cartpole's, resulting in the lower sensitivity of FPS to image resolution."
  - Pixel-training bottleneck breakdown, RTX 4090, averaged over 5 runs (Table X/XI, exact): CartpoleBalance FPS = env-step-only 1.37e6, +pixels 4.03e5, +inference 3.41e5, +training 3.13e4 (time/env-step 7.30e-7 -> 2.48e-6 -> 2.93e-6 -> 3.20e-5 s); PandaPickCubeCartesian FPS = 6.40e4 -> 3.69e4 -> 3.60e4 -> 1.56e4 (time/env-step 1.56e-5 -> 2.71e-5 -> 2.78e-5 -> 6.39e-5 s). Fractional time breakdown (Table XI): CartpoleBalance physics 0.02 / rendering 0.06 / inference 0.01 / policy-update 0.91; PandaPickCubeCartesian physics 0.24 / rendering 0.18 / inference 0.01 / policy-update 0.57 — "in the context of a PPO training loop, physics, rendering, and inference together only comprise 9% and 43% of the Cartpole and Franka total training times, respectively" (Sec. IV-D-1).
  - Cross-simulator batch-rendering comparison (Sec. D.2, Fig. 23-24): "we plot our results alongside those from IsaacLab [41] and Maniskill3 [60]; data for IsaacLab and Maniskill3 is obtained from [60]. This is only a rough comparison as we only take steps to ensure similar hardware and timestep size" — explicitly caveated as not a controlled benchmark; no numeric values survived parsing from the figures, only the qualitative claim that "our batch rendering is competitive with other state-of-the-art simulators" and that "Madrona's rendering speed improvements appear to be the primary driver of the measured speed-ups" over raw MJX physics gains.
- **Robot hands shipped as assets**: **LEAP Hand** (paper + code) and **TetherIA Aero Hand Open** (code only, not in paper text) — see Setting above for the paper-vs-code mismatch.

## Evaluation
- metrics: LEAP Hand in-hand reorientation — "number of consecutive successful rotations before failure," over 10 real-world trials (Table I, exact per-trial data: trials 1-10 = 3, 27, 8, 2, 15, 3, 4, 1(?), 3, 5 — note the OCR-flattened table has an ambiguous split around trials 7-8, "4<br>1" — flag before quoting per-trial values individually; median = 3.5, mean = 7.1, both cleanly stated). Non-prehensile block reorientation — success defined as "within 3 cm of the goal position and within 10 degrees of the desired orientation" (Sec. IV-C2-a), evaluated over 35 hardware trials (Table II): Real Success (%) median 100, mean 85.7 +/- 12.2 (95% CI); Position Error (cm) median 1.95, mean 5.28 +/- 3.26; Rotation Error (deg) median 1.72, mean 3.32 +/- 1.59. Pixel pick-cube — binary success over 12 real-world trials: "100% success rate" (Sec. IV-C3-d).
- headline numbers: LEAP Hand policy "trains within 30 min on two RTX 4090 GPUs" (Sec. IV-C1-c); non-prehensile block-reorientation policy "Training takes 10 minutes on 16x A100 devices" (Sec. IV-C2-c); pixel pick-cube "Training in simulation takes ten minutes on a single RTX 4090" (Sec. IV-C3-c). See Throughput above for the full per-env/per-hardware breakdown.
- baselines beaten: Brax PPO vs. RSL-RL PPO on Unitree Go1 joystick — "Both libraries are able to achieve successful rewards and gaits within similar wallclock times" (Sec. IV-D-2, Fig. 8) — not a "beats" claim, a parity claim.
- real robot? Yes, three separate deployments: (1) LEAP Hand cube reorientation, 10 trials, median 3.5 / mean 7.1 consecutive successful rotations before failure (Table I); (2) Franka Emika Panda + Robotiq, non-prehensile block reorientation, 35 trials, 85.7% mean success (Table II); (3) Franka Emika Panda, pixel-based pick-cube, 12 trials, 100% success (Sec. IV-C3-d). Also locomotion sim-to-real on Unitree Go1 (joystick, fall recovery, handstand), Berkeley Humanoid, Unitree G1, Booster T1 (Sec. II-B, IV-B) — no numeric trial counts given for these in the excerpted sections.

## Limitations stated by the authors
- "MuJoCo Playground inherits the limitations of MJX due to constraints imposed by JAX. First, just-in-time (JIT) compilation can be slow (1-3 minutes on Playground's tasks)." (Sec. VI)
- "Second, computation time related to contacts does not scale like the number of active contacts in the scene, but like the number of possible contacts in the scene. This is due to JAX's requirement of static shapes at compile time. This limitation can be overcome by using more flexible frameworks like Warp and Taichi. This upgrade is an active area of development." (Sec. VI) — this is the single most load-bearing "Physics block" limitation: contact cost in MJX is a function of *possible*, not active, contact pairs, directly explaining the per-env `max_contact_points`/`max_geom_pairs` tuning in Table III.
- "vision-based training using Madrona is still at an early stage" (Sec. VI); Madrona lacks "deformable materials, moving lights, and terrain height fields" as of this work (Sec. III).
- LEAP Hand hardware failure modes attributed to sim-to-real geometry gap: cube wedging between fingers/palm, and index-thumb interlocking "attributed to physical flex in the low-cost hardware," with "improved camera coverage and more accurate collision geometries" left as future work (Sec. IV-C1-d).
- Single-camera pose estimation for the LEAP hand: "occlusions can introduce observation noise, we leave multi-camera extensions to future work" (Sec. IV-C1-b).
- The Madrona-vs-IsaacLab/ManiSkill3 throughput comparison is explicitly caveated as uncontrolled: "a fully controlled performance benchmark is difficult due to the inherent differences between simulators" (Sec. D.2).
- Genesis (a peer open-source GPU engine) is noted as still limited: "sim-to-real results are still limited to a few locomotion policies" (Sec. V-a) — a limitation of a comparator, cited to contextualize MJX/Playground's relative maturity, not a self-criticism.

## Notes for the survey (which sections this feeds; contradictions with other notes)
- Physics-engine section: this is the clearest documented "MJX solver knob" data point in the whole batch — Table III's per-env iteration/line-search-iteration/max-contact-point/max-geom-pair overrides are directly quotable for a solver/iteration-count comparison table, and are unusually concrete for an RL-environment paper (most such papers, e.g. isaaclab_2025/orbit_2023, give none).
- Contact-cost/JAX static-shape limitation (Sec. VI) is the single most important caveat for anyone reasoning about MJX's suitability for scenes with many simultaneous or highly variable contact counts (e.g. bimanual/two-hand manipulation with unpredictable contact topology) — flag this prominently if the survey argues for MJX/Playground as a two-hand testbed.
- Paper-vs-code mismatch to flag explicitly: the paper's manipulation section (Sec. II-C, IV-C) discusses only the LEAP Hand; the shipped code (`aero_hand/`) adds a second, tendon-driven, TetherIA-branded hand with its own `RotateZAxis` task and near-identical reward structure to the LEAP-hand version — likely added to the repo after paper submission. Do not attribute Aero Hand results, DoF, or performance to this paper's own reported numbers.
- Reward-term structure for both hands (from code, `leap_hand/rotate_z.py` and `aero_hand/rotate_z.py::_get_reward`) is nearly identical: angvel reward = "Unconditionally maximize angvel in the z-direction" (`cube_angvel @ [0,0,1]`), plus costs for linear velocity, action rate, pose deviation, torques, and energy — useful for the survey's reward-term comparison table across "spin the cube as fast as possible" tasks; contrast with the `CubeReorient` task's `reward.tolerance`-based (soft-threshold) position/orientation rewards, a materially different reward design within the same codebase.
- Cross-simulator throughput claims (vs. IsaacLab, ManiSkill3) are explicitly non-rigorous per the authors themselves (Sec. D.2) — do not present the "competitive with state-of-the-art simulators" framing as a controlled benchmark result in the survey; it is a rough, same-team-caveated comparison using numbers borrowed from the ManiSkill3 paper, not independently reproduced here.
- Real-hardware sample sizes are small (10, 35, 12 trials) — appropriate for the survey's "count what you can rebuild" framing: these are genuine hardware numbers with explicit trial counts and confidence intervals (Tables I-II), unlike many pure-simulation papers in this batch.
