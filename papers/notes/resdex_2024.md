# resdex_2024 — Efficient Residual Learning with Mixture-of-Experts for Universal Dexterous Grasping (Huang et al., ICLR 2025)

sources: papers/md/resdex_2024.md [sha256 acda709b] ; code/md/resdex_2024.md [commit d40e36ae]

## One-line contribution
A residual multi-task RL policy plus a mixture-of-experts of "geometry-unaware" base
grasping policies reaches 88.8% success on 3,200 DexGraspNet objects with no
train/test generalization gap, in 12 GPU-hours on one RTX 4090 (Abstract; Sec 5.1 App. A.2).

## Setting
- hand: 5-fingered ShadowHand, 18 DoFs controlling 22 joints incl. 4 coupled joints; no arm (wrist itself is actuated); single-handed (Sec 3.1). Asset: `mjcf/open_ai_assets/hand/shadow_hand.xml` (`dexgrasp/cfg/shadow_hand_blind_grasp.yaml`).
- simulator/physics: IsaacGym (Makoviychuk et al., 2021), PhysX backend; `sim.substeps: 2`, `controlFrequencyInv: 1`, `num_position_iterations: 8`, `num_velocity_iterations: 0`, `contact_offset: 0.002`, `rest_offset: 0.0` (`dexgrasp/cfg/shadow_hand_blind_grasp.yaml`, sim block). Exact sim dt in seconds: not stated.
- observation (state-based teacher): proprioception **J**∈R^123 (wrist pos/orient, hand joint positions, fingertip states and fingertip-sensor forces) + object pose (pos R^3, quat R^4) + object code **c**∈R^64 from a pretrained PointNet (Sec 3.1). Base/geometry-unaware policy drops object code and quaternion, keeping only **J** and object 3D position **b_p** (Sec 4.1). Vision policy: **J** + object point cloud **p**∈R^(N×3), N=512 sampled points (Sec 3.1, Sec 5.1). Item-by-item build of the observation vector in code (`compute_full_state`) is not captured in code/md (only function signatures were extracted for that method, not the body).
- action space: target joint positions of the hand + 6D wrist force (Sec 3.1); `useRelativeControl: false`, `dofSpeedScale: 20.0`, `actionsMovingAverage: 1.0` (`shadow_hand_blind_grasp.yaml`).
- objects/data: DexGraspNet (Wang et al., 2023); training set 3,200 object instances; test sets 141 unseen objects in seen categories + 100 unseen objects in unseen categories = 241 held out (Sec 5.1; App. A.1). Grasp poses ("grasping proposals" g=(R,t,q)) come from the DexGraspNet dataset itself, not generated by this paper — ResDex only trains policies to reach them (Sec 3.1). Not stated whether these proposals are analytic/optimization-derived or learned within DexGraspNet (that detail lives in the cited DexGraspNet paper, not here).

## Method
- paradigm: RL (state-based teacher) + DAgger distillation (vision-based student); no diffusion/VLA component (Sec 3.2, 4.4).
- algorithm: PPO (Schulman et al., 2017) for all state-based training stages; DAgger (Ross et al., 2011) for vision distillation (App. A.1–A.2). Implementation base: repo says "based on UniDexGrasp" (README, Citation section); PPO/DAgger implementations live under `dexgrasp/algorithms/rl/`, not included in the captured code/md excerpt.
- residual structure: three-stage pipeline. (1) **Base/geometry-unaware policies** π_ψ^B(a|J, b_p, a_{t-1}): trained per object, one per k-means cluster center of PointNet-feature-clustered objects (Sec 4.1, 4.3–4.4). (2) **Residual/hyper-policy** π_φ^H(a_t^R, λ_t | J, b_p, b_q, c_ω, a_{t-1}): state-based, sees full privileged obs, outputs a residual action a_t^R and MoE mixing weights λ_t∈R^k. Final action a_t = normalized-weighted-sum_i(λ_t,i · a^B_t,i) + a_t^R (Sec 4.2–4.3). The combination equation, an unrendered image in the layout parse, reads in the OCR pass as `at = aR / t + / 1 / ∥λt∥ / k / i=1 / λt,iaB / t,i, / (4)` — i.e. Eq. 4, quoted with the OCR's own line breaks shown as ` / ` (recovered by OCR from papers/md/resdex_2024.ocr.md; OCR text is noisier than the layout parse, symbols may be imperfect — here the summation's Σ glyph is missing, leaving only its `k` / `i=1` bounds between the `1/∥λt∥` factor and the `λt,iaB t,i` summand). The surrounding sentence confirms the reading: "using a normalized weighted sum of base actions in addition to the residual action". Base policies are frozen while the hyper-policy trains (Sec 4.4). (3) **Vision-based student** π_θ^V(a|J, p, a_{t-1}): distilled from the hyper-policy teacher via DAgger (Sec 3.2, 4.4). This is residual learning on top of the base (geometry-unaware, per-cluster) policies, not on top of a classical controller.
- teacher→student distillation: state-based hyper-policy (privileged: object pose + PointNet object code c_ω) is the teacher; vision-based policy (point cloud only) is the student, trained online with DAgger (Sec 3.2, 4.4).
- domain randomization: listed in `task.randomization_params` of `shadow_hand_residual_grasp.yaml`/`shadow_hand_blind_grasp.yaml` but with `randomize: false` at the top level (so inactive by default in the released config): actions (gaussian additive, range [0,0.05], correlated [0,0.015]); hand DoF damping/stiffness (loguniform scaling, 0.3–3.0 / 0.75–1.5), DoF lower/upper (gaussian additive, [0,0.01]); hand tendon damping/stiffness (loguniform, same ranges); hand and object rigid-body mass (uniform scaling, 0.5–1.5); hand and object friction (uniform scaling, 0.7–1.3, 250 buckets); object scale (uniform, 0.95–1.05); observations (gaussian additive, [0,0.002]); gravity (gaussian additive, [0,0.4]). Paper text does not discuss domain randomization at all — this is a code-only finding, and it is disabled (`randomize: false`) in the shipped configs.

### C. Reward / objective (paper + code, verbatim where possible)
Paper (Sec 3.1, 4.1, 4.4, App. A.1): the base reward is r = r^task + r^proposal, where "r^proposal penalizes the distance to the grasping proposal, where α is a hyperparameter adjusting its weight." For geometry-unaware base policies this is replaced by a pose-only term: "we replace this term with a pose reward" using current hand joint positions q_t (Sec 4.1) — the actual formulas for r^proposal, r^pose, r^task, r^reach, r^lift, r^move and r^bonus were all images that did not survive PDF→markdown conversion, and **have since been recovered**; they are quoted verbatim in the "reward formulas (recovered)" block below (recovered by OCR from papers/md/resdex_2024.ocr.md; OCR text is noisier than the layout parse, symbols may be imperfect). Descriptive text and the two numeric thresholds already known from the layout parse are unchanged by the recovery: r^lift/r^move use indicator f1 = 1(Σ‖X_obj−X_finger‖₂ ≤ 0.6) + 1(‖X_obj−X_hand‖₂ ≤ 0.12); r^move additionally requires 1(‖q−X_joint‖₁ ≤ 6) (App. A.1). Hyper-policy training is two-stage: stage 1 reward = r^task + r^proposal (natural, dataset-guided poses); stage 2 drops r^proposal and drops the "approach" terms inside r^task, "focusing solely on terms related to object lifting and task completion" (Sec 4.4, App. A.1).

Two things the recovery settles that the prose alone did not. (a) The numeric coefficients are now visible: r^pose = −0.05 ∗ ‖q − Xjoint‖₁; r^reach = −1.0 ∗ ‖Xobj − Xhand‖₂ − 0.5 ∗ [Σ] ‖Xobj − Xfinger‖₂; r^lift = 0.1 + 0.1 ∗ az when f1 = 2; r^move = 0.9 − 2‖Xobj − Xtarget‖₂ when f2 = 3; r^bonus = 1/(1+10∗dobj) when dobj ≤ 0.05, else 0 in each case. (b) The stage-2 "loosening" is precisely a substitution of the gate, not of the value: stage 2 drops r^reach (r = rlift + rmove + rbonus) and r^move keeps its `0.9 − 2‖Xobj − Xtarget‖₂` value but fires on `f1 = 2` (the two-part lift condition) instead of `f2 = 3` (which additionally required the joint-pose term ‖q−Xjoint‖₁ ≤ 6). Stage 1's reward is still not written out anywhere in this paper — it is defined by reference, "exactly the same as the one proposed in UniDexGrasp(Xu et al., 2023)" — so that one term remains unverifiable from this PDF, OCR or not.

flag = (right_hand_finger_dist <= 0.6).int() + (right_hand_dist <= 0.12).int() + target_flag

hand_up = where(lowest >= lift_z, where(flag2==2, 0.1 + 0.1 * actions[:,2], 0), ...)  # flag2 == 2 term

The `else` (non-`goal_cond`, stage-2 "loosened") branch and the final `successes =` / reset logic are truncated in code/md for every one of the five task files (extraction cuts off mid-function), so the stage-2 code reward and the exact success-flag assignment could not be verified from code/md.

D metric (pose-quality, not a reward): D = −Σ_{t=1}^T r_t^proposal, "the higher the value of D, the less natural the grasping poses" (Sec 5.3, Table 5) — geometric, computed from the same proposal-distance term, not from a physical/contact quality check.

### E. Evaluation block (exact criteria)
Task: "grasp the object and lift its center to 20 cm above the center of the tabletop" (App. A.1); table 60 cm tall, object dropped from 10 cm above table, hand initialized 20 cm above the desktop. Episode length = 200 steps (App. A.2, Table 6/7; also `episodeLength: 200` in cfg). `successTolerance: 0.1` and `fallDistance: 0.4` appear in config as the tolerance/fall thresholds fed to `compute_hand_reward`, but the exact line computing the binary `successes` flag (and whether success requires holding the lift for some duration, vs. a single-step threshold) is in the truncated part of the reward function not captured by code/md — **not fully verifiable; treat "20 cm lift" plus `successTolerance=0.1` as the stated criterion, hold-duration unconfirmed.**
Eval episodes/seeds: Tables 1–2 report 3 random seeds (mean±std); Table 3 (vision policy) reports single numbers, no seed count stated. All numbers are simulation (IsaacGym), never real-robot — paper explicitly lists no real-robot deployment as a limitation (Sec 6).
Baselines: UniDexGrasp (Xu et al., 2023) and UniDexGrasp++ (Wan et al., 2023), both re-quoted (numbers identical across Tables 1–3 to their original papers, not re-run by the authors — not stated explicitly either way, but the same baseline numbers (79.4/74.3/70.8 etc.) appear in both Table 1 and Table 2, consistent with the baselines only being reported once and reused, suggesting quoted rather than re-run).
Grasp-quality check: **both**, but for different purposes — (a) task success is a physical/simulated check (object lifted 20 cm in IsaacGym physics, Sec 5.1/App. A.1); (b) "naturalness"/pose quality (Table 5, Fig. 3) is a purely geometric check via the D metric (distance to the dataset's annotated wrist pose/joint angles), not a contact or force-closure check.

## Evaluation (headline numbers)
- Table 1 (state-based, stage 1), k=4: Train 90.6±0.6%, Test unseen-obj-seen-cat 89.7±0.8%, Test unseen-cat 90.9±0.1%; beats UniDexGrasp++ (87.9/84.3/83.1) by 2.7/5.4/7.8 pts (Sec 5.2).
- Table 2 (state-based, stage 2), k=4 (best): Train 94.6±1.6%, Test seen-cat 94.4±1.7%, Test unseen-cat 95.4±1.0%; beats UniDexGrasp++ by 6.7/10.1/12.3 pts (Sec 5.2).
- Table 3 (vision, DAgger-distilled, k=4): Train 88.8%, Test seen-cat 88.5%, Test unseen-cat 87.2% — the abstract's "88.8%" is the vision-policy *training-set* number, not a held-out number (Table 3; Sec 5.2 confirms "outperforms UniDexGrasp++ by 3.4%, 8.9%, 10.5%").
- Table 4 (ablation, training set, stage-1 reward): MoE-only (no residual) k=1..6 → 61.4/71.1/79.4/80.3/72.1/81.6%; MoE+Res → 83.2/82.8/88.1/90.6/87.6/88.7% (residual learning adds 8–22 points depending on k).
- Table 5: pose-quality D on unseen-unseen-cat test set: k=1..6 → 223.6/174.5/194.3/176.3/204.6/176.1 (lower is better; not monotone in k).
- Training cost: base policy ≈20 min, hyper-policy ≈11 h (RTX 4090), vision distillation ≈16 h (A800) (App. A.2). Abstract's "12 hours" ≈ base+hyper-policy time on one GPU, excluding vision distillation.

## Limitations stated by the authors
(1) Task is grasping only, not functional grasping — "we have not yet considered the task as functional grasping" (Sec 6). (2) No real-robot deployment: "We have not deployed the vision-based policy on hardware. Future efforts should focus on this aspect and overcome the sim-to-real gap" (Sec 6).

## Quotable claims (verbatim, with section)
- "ResDex achieves state-of-the-art performance on the DexGraspNet dataset comprising 3,200 objects with an 88.8% success rate. It exhibits no generalization gap with unseen objects" (Abstract).
- "we propose training geometry-unaware base policies that only observe proprioception and the 3D positions of objects to infer the object location" (Sec 1).
- "The final control action for the robot is determined by a weighted sum of the base policies' actions and the residual action" (Sec 1).
- "Their learned vision-based policies exhibit a significant decrease of about 7% in success rates when tested on unseen objects, indicating limited generalization capabilities" [re: UniDexGrasp/UniDexGrasp++] (Sec 3.2).

Feeds the survey's residual-RL and MoE-for-multitask-grasping sections, and the "generalization gap" comparison table against UniDexGrasp/UniDexGrasp++ (same DexGraspNet split, so numbers are directly comparable). Contradicts nothing else logged so far, but flag internally: (a) the abstract's headline 88.8% is the *vision-policy training-set* number (Table 3), not a held-out generalization number — the true held-out vision numbers are 88.5%/87.2%; (b) `cfg/ppo/config.yaml` (`max_iterations: 2500`) and `cfg/residual/config.yaml` (`max_iterations: 5000`) do not match the paper's stated 5,000 (base) / 20,000 (hyper-policy) iterations (App. A.2) — which config each training script actually loads was not verifiable (shell scripts not captured), so log this as an open discrepancy, not a resolved one; (c) similarly `numEnvs: 4096` is the default in both `shadow_hand_blind_grasp.yaml` and `shadow_hand_residual_grasp.yaml`, vs. the paper's 11,000 envs for hyper-policy training — likely overridden at the command line, but unconfirmed. Grasp poses themselves are not generated by this paper (imported from DexGraspNet); if the survey needs "how is the grasp pose generated" for a pose-generation table, this entry should be marked "external dataset, see dexgraspnet_2023 note," not attributed to ResDex.
