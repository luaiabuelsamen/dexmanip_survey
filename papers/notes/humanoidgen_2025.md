# humanoidgen_2025 — HumanoidGen: Data Generation for Bimanual Dexterous Manipulation via LLM Reasoning (Jing, Yang, Ao et al., NeurIPS 2025 / arXiv 2025)

sources: papers/md/humanoidgen_2025.md [58b1c5eb / arxiv 2507.00833] ; no code

## One-line contribution
An LLM-driven, fully autonomous simulation data-generation framework for bimanual dexterous manipulation: spatially-annotated atomic hand operations (pinch, grasp, press, ...) are chained by an LLM planner into geometric point/axis constraints per arm, solved by a trajectory optimizer, with a Monte-Carlo-tree-search variant (STCR) to recover from LLM planning failures on long-horizon or under-annotated tasks, producing the 20-task HGen-Bench benchmark on a Unitree H1-2 + Inspire hands (§1, §2, §3).

## Setting
- hand(s): Inspire hands (multi-fingered) mounted on Unitree H1-2 arms — "7 DoFs for each arm and 6 DoFs for each hand, resulting in a 26-dimensional action space" (§3). Real-world experiments use "the same Inspire hands used in the simulation environment" on the same H1-2 (Appendix C.1). Bimanual, fixed torso relative to a tabletop workspace (humanoid standing at a table, not locomoting).
- simulator / physics: SAPIEN as the primary simulation engine for HGen-Bench data collection (§2 intro); automatic asset annotation additionally evaluated in ManiSkill3 ("the same simulation environment as our data generation framework", Appendix C.2 — note: this creates an internal inconsistency between SAPIEN, named in §2, and ManiSkill3, named in Appendix C.2, which is itself built on SAPIEN, so likely not a true contradiction but worth flagging as imprecise in the parsed text). No timestep, env-count, or GPU/wall-clock training figures are given because there is no RL/policy training inside the generation pipeline itself — generation is via constrained trajectory optimization, not learned control.
- observation: for the downstream trained policies (DP/DP3), "RGB and depth images from six camera views, located on both wrists, a first-person perspective, and three third-person views" plus joint states (§3, §5.3); DP3 additionally consumes point clouds derived from the depth images.
- action space: 26-dimensional per the H1-2 setup (7 DoF/arm x2 + 6 DoF/hand x2); at the generation layer, actions come from solving per-step goal-pose and path constraints (`C^goal`, `C^path`) via a constrained trajectory optimizer, not from a learned policy (§2.2).
- objects / data: HGen-Bench = 20 tabletop tasks across difficulty tiers (blocks, drawers, boxes, laptops, cups, bottles, plates — task descriptions fully enumerated in Appendix Table 10); scene diversity extended to "over 120 scenes" via room-level "Scene Scaling" using RoboCasa assets and a coordinate transform between original and new scenes (§2.3). Five additional harder tasks in Appendix C.3 (rotate safe knob, press toaster, open safe door, dual lift pot, blocks stack hard with barrier).

## Method
- paradigm: LLM-based code/constraint generation + classical constrained trajectory optimization (not RL, not IL for the generation step itself) to synthesize demonstrations; the demonstrations are then consumed by standard IL/BC methods (Diffusion Policy, 3D Diffusion Policy) for the policy-validity experiments (§5.3). MCTS (a custom Segment-Truncate-Combine-Resume, "STCR", variant) is used purely at LLM-planning test time to recover from reasoning failures, not as part of the trained policy.
- reward or loss: not applicable to the generation pipeline (no reward function — success is a binary per-task success criterion also LLM-generated, e.g. "all cubes being successfully placed inside the bowl" for cup pour, §2.1). Downstream DP/DP3 policies use their standard diffusion training objectives; no explicit loss formula is quoted or re-derived in this paper (it cites DP [43] and DP3 [44] rather than restating their losses).
- key trick(s): dynamic "action frames" F_act per hand — sets of key points/axes that grow when a rigid grasp is established (e.g. left-hand frame extends from {F_l} to {F_l, F_o} once object o is grasped), letting goal/path constraints be expressed as point coincidence, parallelism, or orthogonality relations (§2.2, "Relational Action Constraints"); two explicit collision-handling mechanisms (see below); STCR abstracts executed LLM code into a search tree by segmenting at execution granularity, truncating at the first failure, combining consistent-intent atomic steps into single tree-search units, and resuming from stored node state (§2.3).

## Contact / penetration handling
Explicitly and centrally addressed — this is one of the paper's two named technical contributions in §2.2 ("Collision Avoidance"), with two distinct mechanisms quoted verbatim:
- "Active Collision Avoidance. The LLM planner generates atomic operation scripts that proactively incorporate collision avoidance behavior... For example, in block stack, the left hand retracts from the stacking area to make space for the right hand" — i.e. explicit two-hand collision avoidance for bimanual coordination.
- "Dynamic Collision Management. The LLM planner dynamically manages collision checks to enable in-contact manipulation. Specifically, we maintain an object-ignoring list and let the LLM dynamically adjust it when generating scripts... For example, in the block storage task... the LLM adds the drawer to the list to ignore the contact between the robot hand and the drawer when pulling the drawer out. After that, the drawer is removed from the list, enabling subsequent collision avoidance." This is a binary include/exclude collision-checking mechanism for the motion planner, not a continuous interpenetration measurement or penalty — collision is either checked (avoided) or ignored (permitted for in-contact motion), with no quantified penetration depth or contact-force term anywhere in the paper. §5.1 attributes HumanoidGen's outperformance of RoboTwin specifically to this dynamic collision management in long-horizon/complex-collision task categories.

## Coordination and embodiment (survey fields)
- two-hand coordination: explicit per-arm, per-step task decomposition with named roles per step, not a single relative-frame RL policy — each planning step `S_i = (S_i^l, S_i^r)` has independent left/right components drawn from the same atomic-operation library `A^hand`, and coordination across hands is enforced structurally by the LLM's constraint chain (e.g. Fig. 3's block-storage example: left hand pulls the drawer while right hand simultaneously pinches a cube, then a handover step transfers the object between hands) rather than by a shared bimanual RL policy with relative-frame observations. There is no leader/follower asymmetry named as such, but tasks are explicitly grouped by "the number of arms used" (single-arm vs. bimanual) and by coordination complexity (§5.1, Fig. 5 categories: "Single arm, free motion space"; "Single arm, complex collision scenarios"; "Bimanual, free motion space"; "Bimanual, long-horizon, complex collision scenarios"). Downstream trained policies (DP/DP3) are each one policy over the full 26-dim two-arm/two-hand action space.
- torso: fixed relative to the workspace — a tabletop setup with the humanoid standing in front of a table (§3); no locomotion or mobile-base component is used in HGen-Bench, despite the humanoid embodiment.
- hand model/DoF each side: Inspire hands, 6 DoF each, identical on both sides, multi-fingered (not a parallel-jaw gripper) — used both in simulation and in the real-world transfer experiments (Appendix C.1).

## Evaluation
- metrics (exact definitions): "success rate in trajectory generation with randomized scene configurations" (§3) — the fraction of LLM-planned-and-executed rollouts in simulation that satisfy the LLM-generated success criterion; downstream policy evaluation reports success rate over "3 random seeds" (Table 2 caption) though the number of eval episodes per seed is not stated in the parsed text beyond "we evaluated DP3 and DP on 14 tasks... measuring success rates across different episodes" (§5.3, exact episode count per evaluation not given).
- headline numbers: §5.1 generation/execution comparison to RoboTwin (with dexterous-hand annotations added) — HumanoidGen achieves "an average success rate of over 50%" across 20 tasks, "most task types achieve a success rate above 75%" except some bimanual long-horizon tasks, and specifically outperforms RoboTwin on long-horizon/complex-collision tasks (close & open box, blocks stack easy & hard) while being comparable on single-arm and short-horizon bimanual tasks (Fig. 5, exact per-task numbers not tabulated in the parsed text — only described qualitatively with a bar chart). §5.2 MCTS ablation (Table 1, DeepSeek-R1): Block Stack Single non-MCTS 63.3±6.24% -> MCTS(N=2) 98.3±2.36%; Blocks Stack Easy non-MCTS 46.7±2.36% -> MCTS(N=3) 95.0±4.08%; Blocks Stack Hard non-MCTS 18.3±6.24% -> MCTS(N=12) 98.3±2.36%; Pyramid Stack non-MCTS 13.3±6.24% -> MCTS(N=12) 90.0±4.08%, with token consumption rising only modestly (e.g. Block Stack Single: 15.3K -> 19.3K tokens for a 26% token increase yielding a 55% success-rate improvement, and average tokens-per-successful-execution actually falling from 24.17K to 19.63K, ~20% reduction). MCTS also raised solution diversity: "Among the 20 success solutions, MCTS obtains ≥12 distinct plans, whereas non-MCTS only generated ≤5 distinct plans" (§5.2). §5.3 policy-validity (Table 2, 14 tasks, DP vs DP3, 20/50/100 demos, 3 seeds): e.g. Cup Pour Easy DP3 reaches 67.8±10.8% with just 20 demos; Open Box Hard DP rises from 11.1±19.1% (20 demos) to 100.0±0.0% (100 demos), eventually surpassing DP3 (98.3±3.3% at 100); Blocks Stack Easy and Blocks Stack Hard and Handover and Storage remain near 0% for both DP and DP3 even at 100 demos, flagged as genuinely hard long-horizon/bimanual tasks. Appendix C.1 real-world sim2real (Table 5): Dual Bottles Pick Easy — data-collection success rate 85%, ~16 s/trajectory, DP success 0% (5 real demos) -> 60% (25 real) -> 65% (100 sim + 5 real); Close Laptop Hard — 90% collection success, ~13 s/trajectory, DP 20% (5R) -> 70% (25R) -> 70% (100S+5R). Appendix C.3 (5 additional hard tasks): success rates 91.09% (rotate safe knob), 87.72% (press toaster), 95.24% (open safe door), 93.00% (dual lift pot), 73.00% (blocks stack hard with barrier, "over 60% of the workspace... blocked by obstacles"). Appendix C.2 automatic annotation: migration success 100% (cup rim), 90% (cup handle), 100% (bowl), 90% (drawer), 100% (laptop), each ~0.7-0.8s vs. 4-6s for manual annotation.
- baselines beaten: RoboTwin (modified by the authors to add dexterous-hand annotations, with LLM proactive dynamic collision management disabled "which reflects the default setup in RoboTwin", §5.1) for the generation/execution comparison; Non-MCTS direct LLM reasoning for the MCTS ablation.
- real robot? Yes for Appendix C.1 — Unitree H1-2 with Inspire hands and a head-mounted D435i depth camera, 2 tasks (Dual Bottles Pick Easy, Close Laptop Hard), 25 real-world trajectories collected per task via a real2sim2real pipeline (FoundationPose 6D pose estimation -> simulate/plan -> execute on real robot), evaluated with DP over 20 trials per condition (Table 5's "0/20", "12/20" etc. denominators confirm 20-trial real-world evaluation). All other results (§5.1-5.3, Appendix C.2-C.3) are simulation-only.

## Data-generation specifics (survey field: demos synthesized / success rate of generation)
- Simulation: 100 demonstration samples collected per task for the policy-validity study (§5.3: "We collected 100 data samples for each task using our method"), with ablations training on 20/50/100 demos per task (Table 2); this is generation from LLM+constraint-solver reasoning, not from a fixed number of human source demonstrations — HumanoidGen does not synthesize demonstrations from a small human-demo seed set the way DexMimicGen does; instead each demonstration is independently planned and executed by the LLM+solver pipeline, so there is no "N human demos -> M generated demos" ratio to quote for the main 20-task benchmark. Generation success rate is reported per-task-category rather than as one aggregate number: "over 50%" average, "above 75%" for most categories (§5.1); per-task numbers for the additional 5 hard tasks (73-95%, Appendix C.3) and for annotation migration (90-100%, Appendix C.2).
- Real-world: 25 real-world trajectories collected per task via the real2sim2real pipeline (Appendix C.1), with data-collection success rates of 85% (Dual Bottles Pick Easy) and 90% (Close Laptop Hard), and ~13-16 seconds per collected trajectory.

## Limitations stated by the authors
"human intervention has not been completely eliminated" — novel asset categories or manipulation primitives without prior spatial annotation still require manual annotation before a task can be generated (Appendix D). Framework cannot generate all task types: "due to the limitations of the ManiSkill3 physics engine, tasks involving deformable or fluid objects cannot be simulated," and because arm control relies on a low-level motion planner, "it is difficult to handle manipulation tasks with ambiguous or dynamic objectives, such as push-T or cloth flattening," which need continuous state adjustment rather than planning to a single target pose (Appendix D). Future work: broader physics-engine support (IsaacSim, MuJoCo), combining goal-conditioned motion planning with goal-agnostic pretrained atomic-operation models, and expanding HGen-Bench.

## Quotable claims (verbatim, with section)
- "We propose two solutions: (i) Active Collision Avoidance... (ii) Dynamic Collision Management. The LLM planner dynamically manages collision checks to enable in-contact manipulation. Specifically, we maintain an object-ignoring list and let the LLM dynamically adjust it" (§2.2).
- "HumanoidGen demonstrates superior performance across all dexterous manipulation tasks, achieving an average success rate of over 50%" (§5.1).
- "a 26% increase in token consumption led to a 55% improvement in the reasoning success rate" for MCTS on Block Stack Single (§5.2).
