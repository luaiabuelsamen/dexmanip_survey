# robohive_2023 — RoboHive: A Unified Framework for Robot Learning (Kumar et al., NeurIPS Datasets and Benchmarks 2023)

sources: papers/md/robohive_2023.md [85772195] ; code/md/robohive_2023.md [6c14798e]

## One-line contribution
A MuJoCo-based, Gym-API framework that consolidates the Adroit hand suite (door, hammer, pen, relocate), in-hand (baoding), MyoSuite, Franka kitchen, arms, TCDM tracking and locomotion suites under one robot class with sim/real backends, teleoperation, the RoboSet datasets, and visual-IL baselines; it explicitly separates a per-env `solved` criterion from the dense reward.

## Setting
- hand(s): Sec. 3.1 lists supported "Hands: Adroit [34], Shadow [33], Allegro [35], MPL [36], D'Hand [37], D'Manus [38]" and "Musculo-skeletal: MyoHand [44], MyoElbow [44]"; arms "Franka [31], Sawyer [37], Fetch [39]"; quadrupeds Spot Mini, MIT-Cheetah, D'Kitty; bipeds Darwin, Atlas. DoF counts are not stated in the paper or the code extract. The benchmarked dexterous results use the Adroit hand (Hand Manipulation Suite, "inspired by [51]" = DAPG; README: "Standard ADROIT benchmarks introduced in ... RSS2018"). single hand throughout; no bimanual suite.
- simulator / physics: "we build RoboHive on top of the now open-source MuJoCo physics engine [6]" (Sec. 3.1); `setup/env.yaml` pins `mujoco==2.3.3`, `mujoco-py<2.2,>=2.1`, `gym==0.13`. Timestep, frame_skip and solver settings are not stated in the paper; in code every env takes `frame_skip` through `MujocoEnv._setup(obs_keys, weighted_reward_keys, proprio_keys, visual_keys, reward_mode, frame_skip, normalize_act, obs_range, rwd_viz, device_id)` (`robohive/envs/env_base.py`) with defaults not in the extract. Supports "domain randomization, sensor noise, and delays" via a base config (Sec. 3.1). Throughput Table 1 (32 processes, 8 A100, random policy, TorchRL collectors, 3 seeds): Hand manipulation 8785+-665 samples/s state, 1713+-24 with 3 cameras at 244x244; Arm 7473+-1237 / 993+-63; Multi-task 4430+-6 / 346+-0.4; Myo 7366+-3509 / n/a. Table 3 per env: relocate-v1 9317.9963, door-v1 9124.0997, pen-v1 8871.5027, hammer-v1 7826.282 (state); the `_v2d` visual variants ~1680-1740.
- observation: "Sensors can include low-dimension states (simulation-only), proprioception, and cameras (RGBD)" with visual domain randomisation and pretrained encoders R3M / RRL / VC1 (Sec. 3.2; `robohive/envs/hands/__init__.py:register_visual_envs(env_name, encoder_type)`). Code obs dicts (from `get_reward_dict` usage): door `reach_err`, `door_pos`; hammer `palm_pos`, `obj_pos`, `tool_pos`, `target_pos`, `goal_pos`, `hand_vel`, `obj_vel`; pen `obj_err_pos`, `obj_rot`, `obj_des_rot`, `obj_pos`; relocate `palm_obj_err`, `palm_tar_err`, `obj_tar_err`, `obj_pos`. Exact `DEFAULT_OBS_KEYS` lists and dimensions are not in the extract.
- action space: "The robot class supports multiple control modalities such as position, velocity, and torque control" (Sec. 3.1); `normalize_act` flag in `MujocoEnv._setup`. Per-suite dimensions not stated.
- objects / data: RoboSet, Table 2: Real kitchen 28,700 trajs / 40 tasks / 4 cam / Human TeleOp; Bin Manipulation 70,000 / 4 / Script+Policy; Franka kitchen (sim) 600 / 4 / Human TeleOp and 75 / 5 / Expert; Adroit (sim) 25 / 4 / Human TeleOp (3 cam) and 75 / 4 / Expert Policy; D'Kitty 75 / 3 / Expert. ## Method
- paradigm: framework + baselines; RL via TorchRL and mjRL (NPG experts, Sec. 4.4/App. A.1), behaviour cloning on visual features (RRL, R3M, VC1) vs state and proprioceptive baselines (Sec. 4.4).
- reward: "RoboHive also explicitly decouples rewards and success criteria ... ships with an independent success criteria per environment that can be used for evaluations, as opposed to reporting rewards. We provide basic dense reward functions for all tasks" (Sec. 3.2). Every env returns an OrderedDict with optional keys, then must-keys `sparse`, `solved`, `done`; `dense = sum(wt * rwd_dict[key])` over `weighted_reward_keys` (`env_base.py`, `*_v1.py`). Task-family definitions (all in `robohive/envs/hands/`, identical in v0 and v1 except the weighted sum):
  - door: `('reach', -0.1*reach_dist), ('open', -0.1*(door_pos-1.57)**2), ('bonus', 2*(door_pos>0.2) + 8*(door_pos>1.0) + 10*(door_pos>1.35)), ('sparse', door_pos), ('solved', door_pos > 1.35), ('done', reach_dist > 1.0)` (`door_v0.py`, `door_v1.py`).
  - hammer: `('palm_obj', -0.1*palm_obj_dist), ('tool_target', -1.0*tool_target_dist), ('target_goal', -10.0*target_goal_dist), ('smooth', -1e-2*(hand_vel_mag+obj_vel_mag)), ('bonus', 2.0*lifted + 25.0*(target_goal_dist<0.020) + 75.0*(target_goal_dist<0.010)), ('sparse', -1.0*target_goal_dist), ('solved', target_goal_dist<0.010), ('done', palm_obj_dist > 1.0)`; `lifted = (obj_pos z > 0.04) * (tool_pos z > 0.04)` in v0 but `(obj_pos > 0.04) * (obj_pos > 0.04)` in v1 (tool height check lost) (`hammer_v0.py`, `hammer_v1.py`).
  - pen: `rot_align = cosine(obj_rot, obj_des_rot)`, `dropped = obj_pos z < 0.075`; `('pos_align', -1.0*pos_align), ('rot_align', 1.0*rot_align), ('drop', -5.0*dropped), ('bonus', 10.0*(rot_align>0.9)*(pos_align<0.075) + 50.0*(rot_align>0.95)*(pos_align<0.075)), ('sparse', -1.0*pos_align+rot_align), ('solved', (rot_align > 0.95)*(~dropped)), ('done', dropped)` (`pen_v0.py`, `pen_v1.py`).
  - relocate: `obj_lifted = obj_pos z > 0.04`; `('palm_obj', -0.1*palm_obj_dist), ('palm_tar', -0.5*palm_tar_dist*obj_lifted), ('obj_tar', -0.5*obj_tar_dist*obj_lifted), ('bonus', 1.0*obj_lifted + 10.0*(obj_tar_dist<0.1) + 20.0*(obj_tar_dist<0.05)), ('sparse', -1.0*obj_tar_dist), ('solved', obj_tar_dist<0.1), ('done', palm_obj_dist > 0.7)` (`relocate_v0.py`, `relocate_v1.py`); legacy `get_rewards_old` keeps the DAPG scalar form with `goal_achieved = ||obj-target|| < 0.1`.
  - baoding (in-hand, `baoding_v1.py`): `solved = (target1_dist < proximity_threshold)*(target2_dist < proximity_threshold)*(~is_fall)`, `done = is_fall` with `is_fall = object z < drop_height_threshold`; adds `wrist_angle = -||hand_pos*[5,0.5,1]||` and `act_reg` (thresholds not in extract).
  - TCDM tracking (`robohive/envs/tcdm/track.py`): `obj_reward = exp(-obj_err_scale*(obj_com_err + 0.1*obj_rot_err))`, `qpos_reward = exp(-qpos_err_scale*||hand_qpos_err||^2)`, `lift_bonus`, `penalty = check_termination`; `('sparse', 0), ('solved', 0)` - no success criterion is defined for tracking.
  - arms (`arms/pick_place_v0.py`, `push_base_v0.py`, `reach_base_v0.py`): `solved = target_dist < .050` / `reach_dist < .050`; claws `reorient_v0.py`: `solved = (reach_pos_dist<.050) and (reach_rot_dist<.1)`; multi-task kitchen (`multi_task_base_v1.py`): `solved = np.all(goal_dist < obj["dof_proximity"])`.
- key trick(s): unified robot class toggling sim/hardware "by simply modifying a single flag" (Sec. 1); teleop via keyboard, space mouse, VR, CyberGlove (Sec. 4.1); `evaluate_success(paths, logger, successful_steps)` in `env_base.py`.

## Evaluation
- metrics: per-env `solved` flag (definitions above); success rate over rollouts. App. A.3: "users are encouraged to perform 25 rollouts". Visual baselines averaged over "3 seeds x 3 camera angles x 25 trajectory rollouts" (Fig. 7, Fig. 8 captions).
- headline numbers: Figures 7 and 8 are bar charts of success rate (R3M50, RRL50, VC1-Large, Proprioceptive, State, Expert Policy) on Adroit Pen/Door/Hammer/Relocate (HMS, human data, 25 demos per task), Kitchen FK1-v4 (MicroOpen, Knob1On, Knob2Off, SdoorOpen, LdoorOpen; 100 human demos or 75 expert), and ROBEL D'Kitty Stand/Walk (75 expert demos). Numeric bar heights are not recoverable from the markdown (axis labels only). Text (Sec. 4.4): "a wide gap between state-of-the-art visual baselines and policy learned using the privileged state information"; locomotion visual baselines "perform worse ... than a proprioceptive-only baseline"; "solving tasks with few demonstrations (25 demonstrations in this suite for each task) using behavior cloning can be challenging (e.g., Pen and Relocate)". No RL success-rate table for the hand suite is in the paper; baselines are pointed to the website.
- baselines beaten: none claimed; the paper benchmarks representations, not a method.
- real robot? Sim2real deployment shown qualitatively for Franka and D'Kitty (Fig. 6, video); no success counts. Real kitchen dataset 28,700 teleop trajectories (Table 2).

## Limitations stated by the authors
Sec. 5: "(1) RoboHive provide trained agents only for a few algorithmic families ... (2) ... we hope that the community will help enrich the ecosystem over time, especially towards aerial and navigation suites. (3) RoboHive's robot class supports a diverse set of commonly used hardware but it's not representative. Manipulation hardware support outweighs locomotion, navigation, and aerial hardware support."

## Notes for the survey (which sections this feeds; contradictions with other notes)
- Feeds: the MuJoCo single-hand benchmark row (Adroit door/hammer/pen/relocate with their exact `solved` thresholds: door hinge > 1.35 rad, nail-goal < 1 cm, pen cosine > 0.95 and not dropped, object-target < 10 cm); the "success criterion vs reward" methodology paragraph; the replay-validation paragraph (their App. A.2 replays DAPG actions and checks final-state discrepancy - a replay-is-placement caveat applies: they validate state agreement, not contact physics).
- The Isaac Gym comparison (Sec. 2) is the counterpoint to isaacgym_2021: RoboHive claims MuJoCo has higher "physical realism"; no measurement supports either claim in these sources.
- Hammer v1 code drops the tool-height term from `lifted` relative to v0; a version-dependence to flag if hammer numbers are compared across papers.
- No hand DoF, timestep, control rate or obs dimension is stated anywhere in the two sources; take those from plappert_multigoal_2018 / DAPG notes, not from here.
- Bimanual: absent. TCDM tracking has no `solved` definition, so "success" on GRAB-tracking tasks in this framework is undefined.
