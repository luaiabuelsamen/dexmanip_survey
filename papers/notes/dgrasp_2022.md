# dgrasp_2022 — D-Grasp: Physically Plausible Dynamic Grasp Synthesis for Hand-Object Interactions (Christen et al., CVPR 2022)

sources: papers/md/dgrasp_2022.md [4f0b919b] ; papers/md/dgrasp_2022.ocr.md ; code/md/dgrasp_2022.md [8816d1ba]

## One-line contribution
A PPO policy on a simulated MANO hand in RaiSim that, from a single static grasp label, approaches an object, forms a stable grasp and carries it to a 6D target pose, with a second module controlling the wrist; 0.63 grasp success against 0.35 for the same labels under PD control on the DexYCB test split (Table 1), and it reports an interpenetration volume for the poses its own policy produced.

## Setting
- hand(s): a controllable hand model built from MANO [36]: "we create a controllable hand model and integrate information obtained from a statistical parametric hand model (i.e., MANO [36])", using "a unified hand model corresponding to the mean MANO shape" (Sec. 3.1). "The fingers are controlled via one actuator per joint for a total of 45 actuators, to which we add 6 DoF to control the global pose" (Sec. 3.1) = 51 DoF, matching the 51 that `artigrasp_2023` states for the same model. Code: `hand_model: "mano_mean.urdf"` (dgrasp/cfgs/cfg.yaml). No arm; the wrist floats, and Sec. A.2 names a full arm as future work ("one could extend our method to include a biomechanical model of a full arm").
- simulator / physics: RaiSim [19], chosen "since it allows modeling non-convex meshes and efficient parallel training" (Sec. B.1). "Simulation timestep 2.22e-3s", "Simulation steps per action 13" (Table 5) = 34.6 Hz control; code `simulation_dt: 0.00222`, `control_dt: 0.03` (33.3 Hz), `max_time: 4.0`, `num_threads: 60`. Training: "Each training cycle utilizes a single GPU and 100 CPU cores and takes up to 24-72 hours" (Sec. B.2).
- parallelism: "We create a parallelized training scheme with a worker per grasp label for data gathering (amounting to e.g. 376 parallel environments for DexYCB)", doubled to "400 workers with 2 workers for each label" for the GraspTTA and ContactOpt experiments (Sec. B.2). Table 5 gives batch size 376 for the same reason.
- observation (Sec. 3.1, 3.2.1): the state is `s = (q_h, q_h_dot, f, T_h, T_h_dot, T_o, T_o_dot)` — joint angles and velocities, "the forces between the hand and object f", wrist 6D pose and object 6D pose with their velocities. The policy does not see this directly: a feature layer phi(s, D) outputs object- and wrist-relative quantities plus goal components `G = [g_x | g_q | g_c]`, the distance to the label's target joint positions, the angular distance to its target rotations, and the target contact vector. Target contacts come from the label geometrically: "If the distance between any vertex v_i of a joint j and an object vertex v_o is below a small threshold epsilon (in our case 0.015m), we determine that the finger part should be in contact" (Sec. A.1).
- action space: residual PD targets. "The policy pi outputs actions a, which are residual actions that change a bias term q_b. For the finger joints, the bias term is equivalent to the current joint configuration q_b = q_h" (Sec. 3.1); wrist-guidance replaces the bias of the three translational DoF with the label's target position (Sec. 3.2.3). Code `finger_action_std: 0.015`, `rot_action_std: 0.01`.
- objects / data: DexYCB [5], "1000 sequences of object grasping, with 10 different subjects and 20 YCB objects [3]", left-handed sequences filtered out, random 75/25 train/test split over sequences and subjects (Sec. 4.1). Grasp labels from three sources: motion capture (DexYCB, the label being the timestep where object displacement first exceeds a threshold), a static grasp synthesiser (GraspTTA [20], 400/200 label split on DexYCB objects and 200/100 on HO3D), and an image-based estimator with offline optimisation (ContactOpt [13]) on HO3D (Sec. 4.1).

## Method
- paradigm: RL. "We train policies by using our own implementation of the widely used PPO algorithm [37]" (Sec. B.2). Table 5: 1e4 epochs, 1.2e6 steps per epoch, 195 environment steps for grasping and 300 for the full task, batch 376, 16 updates per epoch, gamma 0.996, lambda_GAE 0.95, clip 0.2, lr 5e-4, 2 x 128 hidden, entropy 0.0, Adam.
- the single label is a reward parameter, not a demonstration: "we propose a reward function that is parameterized by the grasp label to incentivize the fingers to reach contact points on the object" (Sec. 1), and the paper sets itself against demonstration-trained work explicitly — "While prior work investigates the control of dexterous hands by learning from full demonstration trajectories [12, 34], we address the generation of hand motion from only a single-frame grasp reference" (Sec. 1). No trajectory is imitated and no behaviour-cloning loss appears.
- hierarchy: a low-level grasping policy and a high-level motion synthesis module that "controls only the movement of the wrist, i.e., the first 6DoF" (Sec. 3.3). In the motion phase both act concurrently, and the motion module is analytic closed-loop control by default, recomputing the hand-object displacement "after every action" (Sec. 3.3); a learned variant (Ours+learned policy) is an ablation, not the method.
- reward (Sec. 3.2.2): four weighted groups, "a combination between position, angle, contact and regularization terms". The position reward is a weighted sum of distances between target and current 3D positions over every joint including the wrist; the pose reward is the L2 norm of the joint and wrist angular error; the contact reward is the sum of two terms, "the fraction of target contacts that the agent has achieved" and a term that "rewards the amount of force exerted on desired contact points, capped by a factor proportional to the object's weight m_o through a factor lambda"; the regulariser penalises "the hand's and object's linear and angular velocities". The equation images (Eqs. 3-8) were dropped by the layout parse; see the OCR file and the Notes section below.
- weights (Table 5): w_x -2.0, w_q -0.1, w_c 1.0, w_reg,h 0.5, w_reg,o 1.0, w_x,j 1.0, w_x,tip 4.0, lambda 5.0, alpha_x -2.0, alpha_q -0.25 (the last two weight the motion-synthesis reward, Sec. A.2).
- code: the reward body is C++ inside the RaiSim environment and is not in the parse, which carries Python signatures and yaml only. The coefficients in `raisimGymTorch/raisimGymTorch/env/envs/dgrasp/cfgs/cfg.yaml` are: pos_reward 2.0, pose_reward 0.1, contact_reward 1.0, impulse_reward 2.0, falling_reward 1.0, rel_obj_reward_ -1.0, body_vel_reward_ -0.5, body_qvel_reward_ -0.5, torque -0.0, and four terms at 0.0 (root_pos, root_pose, contact_pos, obj, obj_pose). Match: w_x (2.0), w_q (0.1), w_c (contact_reward 1.0). Differences: the paper's single contact weight w_c = 1.0 is two separately weighted coefficients in the config, contact_reward 1.0 and impulse_reward 2.0, which correspond to the contact reward's two stated parts; `falling_reward: 1.0` has no counterpart anywhere in the paper's reward description or in Table 5; the paper's one hand-regulariser weight w_reg,h = 0.5 appears as two velocity penalties (body_vel -0.5, body_qvel -0.5); and w_x,tip 4.0, w_x,j 1.0 and lambda 5.0 appear in no yaml, consistent with their living in the C++ that the parse does not reach. The same pattern was recorded for `artigrasp_2023`, which is built on this code base.
- version skew, stated by the authors: "In the latest commit, RaiSim was updated to the newest version (1.1.6). Training D-Grasp is more stable and faster now (see RaiSim changelog). To get an already existing code-base to run, it should be re-built from scratch since the simulation backbone and some of the wrapper files and functions have been updated." (README, "RaiSim Update"). The parsed commit is therefore not the one that produced the paper's numbers, and the authors say training behaviour changed with the update.
- every shipped config sets `num_envs: 21`, including the all-objects one (`pretrained_policies/all_objs/cfg.yaml`), against the paper's 376 parallel environments for DexYCB. The runner is launched with flags (`-ao`, `-nr`, `-itr`) and its body is a top-level script that the parse does not capture, so whether it overrides `num_envs` at launch is not visible here.
- key trick(s): wrist-guidance, biasing the global PD target with the label's target wrist position rather than the current position (Sec. 3.2.3, worth 0.58 -> 0.89 success in Table 4); the object-relative feature layer with explicit target-contact components (0.47 -> 0.89 without it); the contact reward, without which the task collapses to 0.0 success.

## Evaluation
- metrics (Sec. 4.2.1 and B.3, verbatim): "Success Rate: ... the rate of sequences which maintain a stable grasp, i.e., where the object does not slip and fall down for a period of a 5s window. We lower the surface in the simulation for this purpose." "Interpenetration: We calculate the amount of hand volume that penetrates the object. To do so, we use the original MANO mesh [36] and the high-resolution object mesh. Hence, there is no physical simulation involved when measuring interpenetration. To ensure a fair comparison against the static baseline, we choose the last time step of the grasping phase for our method and hence omit the approaching phase from the evaluation." "Simulated Distance: ... we compute the mean displacement between the object and the hand's wrist ... in mm per second ... for a maximum window of 5s or stop whenever the object falls." "Contact Ratio: ... the ratio between the target contacts g_c defined via the grasp label D and the contacts achieved in the physics simulation I[f > 0]." MPE and Geodesic are the motion-synthesis metrics, in mm and radians.
- interpenetration, the field this survey cares about: it is reported, in cubic centimetres, for the poses the trained policy produced, which makes this the corpus's one closed-loop policy to report the quantity for its own output. Two qualifications are the paper's own. First, it is not measured in the physics the policy ran in: "We note that our method achieves 0 interpenetration loss when evaluated in the physics simulation. In Tab. 1, however, we report interpenetration on the original MANO hand model and detailed object meshes. For computational efficiency during training, the hand model and the object meshes are simplified in the physics simulation (Section 3.1), limiting the performance of our model when evaluated in the original setting with regards to interpenetration" (Sec. 4.3). Second, it is one timestep, the last of the grasping phase, not the rollout (Sec. B.3 above).
- numbers (Interpenetration in cm^3): Table 2, generalisation to unseen objects, averaged over six test sets — Ours 1.74, GT+PD 4.41, GT+IK 9.08, with success 0.56 / 0.30 / 0.38. Table 1, per label source, train | test — DexYCB MC: Ours 1.75 | 1.77 against GT+PD 4.59 | 4.41 and GT+IK 9.23 | 9.74; GraspTTA on DexYCB objects: Ours 2.84 | 2.81 against 4.92 | 4.94; GraspTTA on HO3D objects: Ours 3.33 | 3.40 against 5.21 | 5.40; ContactOpt on HO3D images: Ours 2.67 | 2.08 against 14.94 | 14.00. Success on the same rows (test): 0.63, 0.73, 0.71, 0.81 for the method against 0.35, 0.24, 0.30, 0.60.
- Table 3, motion synthesis, 100 out-of-distribution target poses on six YCB objects: MPE 0.08 mm and geodesic 0.52 rad for the method against Flat-RL 0.55 / 1.66, Ours+static grasp 0.45 / 1.46, Ours+learned policy 0.30 / 0.92.
- Table 4, ablations on three objects: w/o ContactRew 0.0, w/o GoalSpace 0.28, w/o FeatLayer 0.47, w/o WristGuidance 0.58, full method 0.89 success.
- Table 6, all-object against per-object policies: PO 0.81 train / 0.42 test, AO 0.70 / 0.63.
- Tables 7-13 give per-object results for every condition and per-test-set results for the generalisation experiment, where "the success rate of our method on test set 1 ... reaches up to 0.83 ... only achieves a 0.33 success rate on the test set 6, which contains the complex objects '037 scissors' and '040 large marker'" (Sec. C).
- protocol: policies are trained and evaluated per label, with the success rate a rate over sequences; the generalisation experiment is "six different test sets of three objects each, which we leave out during training. We report the average performance over all test sets" (Table 2), so three unseen objects per policy and 18 across the splits. Seeds are not reported, and no confidence interval is given for any rate.
- baselines: GT+PD and GT+IK (the label replayed under PD control, with or without an IK de-noising step), GraspTTA [20]+PD, ContactOpt [13]+PD, Flat-RL (no hierarchy), Ours+static grasp (grasping policy frozen during motion), Ours+learned policy.
- real robot? No. The hand is a simulated MANO model and no hardware appears anywhere in the paper.

## Limitations stated by the authors
- "dynamics components such as friction of surfaces, inertia, or the center of mass are assumed to be known a priori, which is often not the case in real world settings" (Sec. 5).
- Thin objects fail: "our approach may struggle with thin objects which are difficult to grasp on a surface" (Sec. 4.3), and scissors and a large marker are the two worst objects in the per-object tables (Sec. C).
- Generalisation is "a proof of concept experiment", and the authors say "the method could be scaled to even larger train/test sets in the future" (Sec. 5).
- The approach depends on the quality of the reference: "while our approach can correct interpenetration and noisy poses to some degree, it is conditioned on the reference pose, and hence performs best when provided with grasp targets that roughly approximate a real human (i.e., physically plausible) grasp" (Sec. C).
- For the synthesised and image-based labels the hand is allowed through the table: "We place the object on a surface and allow the hand to approach from any direction, even penetrating the surface. We achieve this by disabling the collision response between the surface and the hand" (Sec. B.5).

## Quotable claims (verbatim, with section)
- "Interpenetration: We calculate the amount of hand volume that penetrates the object. To do so, we use the original MANO mesh [36] and the high-resolution object mesh. Hence, there is no physical simulation involved when measuring interpenetration." (Sec. B.3)
- "We note that our method achieves 0 interpenetration loss when evaluated in the physics simulation." (Sec. 4.3)
- "For computational efficiency during training, the hand model and the object meshes are simplified in the physics simulation, limiting the performance of our model when evaluated in the original setting with regards to interpenetration." (Sec. 4.3)
- "For the baselines, we occasionally observe a configuration that leads to high success rates despite noisy pose references. Specifically, if the interpenetration is large (e.g. GT-IK in Table 8 for '021 bleach cleanser' or '024 bowl'), the objects can become entangled within the hand mesh and will therefore not be able to fall down. Thus, the success rate metric should always be interpreted in combination with the other metrics." (Sec. C)
- "This ensures physical plausibility, e.g., there is no hand-object interpenetration and the fingers exert enough force on the object to hold it without slipping." (Sec. 1)
- "In practice, we found that approximating the collision bodies with primitive shapes (i.e., the simple objects and the hand meshes) led to an order of magnitude increase in training speed. This is because the simulation time increases roughly quadratically with the number of collision points." (Sec. B.1)
- "For training and evaluation, we therefore use the simplified meshes (except for the interpenetration metric, see Section B.3)." (Sec. B.1)

## Notes for the survey
- This is the corpus row behind section 7.2. It is the one closed-loop policy here that reports a penetration volume for poses its own policy produced, and the way it reports them is the finding: zero inside the physics, because the meshes the simulator used are decimated for speed, and a non-zero number from re-measuring one frame of the output against the original MANO mesh and the full-resolution object mesh with "no physical simulation involved". Both halves are the paper's own words, not an inference.
- Sec. C is the strongest source in the corpus for why a success rate needs a penetration number beside it: with a penetrating reference, "the objects can become entangled within the hand mesh and will therefore not be able to fall down", which raises the success rate of the baseline it is measuring. The survey's evaluation protocol asks for both quantities for this reason, and the reason is now citable rather than argued.
- The reward equations (Eqs. 3-8) are images in the PDF and absent from the layout parse; the prose descriptions in Sec. 3.2.2 and the weights in Table 5 are complete enough to compare against the shipped yaml, which is what the paper-against-code reading used. The OCR file is the fallback for the symbol-level form.
- Lineage: `artigrasp_2023` and the full-body grasping follow-up are built on this code base (the README links both), and ArtiGrasp's own note records the same reward-coefficient split against its paper's table. ArtiGrasp drops the metric entirely, "We omit the interpenetration metric since all of our baselines include a physics simulation which exhibits no interpenetration" (artigrasp Sec. 6.1), which is the position this paper's own appendix contradicts for the simplified-mesh case.
- Code needs a RaiSim licence (README), as ArtiGrasp's does.
