# pianomime_2024 — PianoMime: Learning a Generalist, Dexterous Piano Player from Internet Demonstrations (Qian et al., CoRL 2024)

sources: papers/md/pianomime_2024.md [51b8b57c] ; code/md/pianomime_2024.md [c4abefac]

## One-line contribution
Extracts fingertip trajectories + MIDI goal states from YouTube piano videos, trains per-song residual-RL "expert" policies against those trajectories, then distils all experts into a single hierarchical, generative-model generalist policy via BC (abstract; Section 3).

## Setting
- hand(s): "A Shadow Hand E3M5" (code/md `robopianist/models/hands/shadow_hand.py` class docstring). Bimanual (two Shadow Hands). Each hand action = "23 joint angles and one dimension for the sustain pedal" (paper §3.2, p.3); action space is R^{23×2+1}. Total action dim = 47 (Table 5: 46 target joint positions + 1 sustain pedal); paper states 47-dim vs. 45-dim in RoboPianist [11] because "the z-axis sliding joints fixed on both forearms are enabled" (§4, p.5).
- simulator / physics: ROBOPIANIST [11] environment on MuJoCo [26] (§4, p.5). Policy predicts target joint angles at 20 Hz, converted to torques by PD controllers at 500 Hz (§4, p.5). #envs / GPU / wall-clock training time: not stated.
- observation: song-specific agent (Table 4, Appendix C): Hand+Forearm Joint Positions (rad, 52), Hand+Forearm Joint Velocities (rad/s, 52), Piano Key Joint Positions (rad, 88), Piano Key Goal State (discrete, 88), Demonstrator Forearm+Fingertip Cartesian Positions (m, 36), Prior control input ũ solved by IK (rad, 52), Sustain Pedal state (discrete, 1). Generalist BC policy: proprioception s_t plus a lookahead goal window ǧ_t:t+L, with the goal state encoded through the pretrained SDF autoencoder into a 16-d latent (§3.3, Appendix E); low-level policy additionally takes the predicted fingertip trajectory (Appendix F).
- action space: song-specific = target joint positions (Table 5: 46) + sustain pedal (1), residual around an IK nominal behavior (§3.2). Generalist (Two-stage Diff/-res) predicts action/fingertip chunks of 4 timesteps (Appendix F) — not raw joint torques.
- objects / data: self-collected dataset of 60 songs from YouTube channel "PianoX," split into 431 clips of 30 s each (258K state-action pairs); 12 unseen clips held out for generalization testing (§4, "Dataset and Evaluation Metrics", p.5). ~40% of clips (110K state-action pairs) are run through RL and used to train the low-level policy; the full dataset trains the high-level policy (§4.2, p.6).

## Method
- paradigm: RL (per-song specialists) → BC/distillation (generalist), i.e. RL+demo followed by policy distillation (§3).
- **Target representation**: two extracted trajectories — human fingertip trajectory τ_x: T-step sequence of "two hands' 3D fingertip positions x ∈ R^{3×10} (10 fingers)", and piano state trajectory τ_ǧ: T-step sequence of "piano states ǧ ∈ B^88, represented with an 88-dimensional binary variable representing which keys should be pressed" (§3.2, p.3). Fingertip extraction: MediaPipe [20] on top-view video gives 2D hand skeleton every 0.05 s; a homography matrix (8-point algorithm on chosen piano keypoints) maps pixel to MuJoCo x-y coordinates; a heuristic snaps a fingertip's y-value to the pressed key's midpoint (searching the neighboring two keys if no direct hit); z is set to 0 for pressing fingertips and 2·h_key otherwise, since RGB video has no depth (§3.1, Appendix A). MIDI files (co-uploaded by the YouTube channel) supply the ground-truth piano-state trajectory.
- **A. Embodiment**: bimanual Shadow Hand E3M5 (code); no arm, forearm has enabled z-sliding dof (§4); MuJoCo/ROBOPIANIST; 20 Hz control / 500 Hz PD; #envs, GPU, training wall-clock: not stated (only inference: "approximately 15Hz on an RTX 4090 machine," §4.4 Limitations).
- **B. Learning (teacher/student = per-song specialist → generalist)**: N song-specific expert policies are each trained by residual RL against one song's τ_x, τ_ǧ (PPO [27] via Stable-Baselines3 [30], Algorithm 1). Rollouts from all N experts form dataset D = {(τ_s^i, τ_q^i, τ_x^i, τ_ǧ^i)}_{i=1}^N. A single generalist "π_θ(q_{t:t+L}, x_{t:t+L} | s_t, ǧ_{t:t+L})" is then trained with Behavioral Cloning on D to jointly output configuration-space action chunks q_{t:t+L} and fingertip-motion chunks x_{t:t+L} (§3.3, p.4). The best generalist variant (Two-stage Diff/-res) is hierarchical: a high-level DDPM policy maps the SDF-embedded goal window (10 steps) to a 4-step fingertip trajectory, and a low-level DDPM policy maps that fingertip trajectory (+goal, +proprioception) to a 4-step joint-action (or IK-residual) chunk — i.e. action chunking with chunk/horizon = 4 (Appendix F, §3.3). This is "distillation" only in the loose sense that the generalist is trained on rollout data harvested from the specialists, not on a matched-state teacher-action loss.
- **C. Reward / objective — quoted verbatim, paper vs. code**:
  - Paper (Table 3, Appendix C), reward r = r_ǧ + r_x:
    - "Key Press | 0.5·g(‖k_s−k_g‖²) + 0.5·(1−**1**[false positive]) | 2/3 | Press the right keys and only the right keys"
    - "Mimic | g(‖p_df−p_rf‖²) | 1/3 | Mimic the demonstrator's fingertip trajectory"
  - Code (`single_task/piano_with_shadow_hands_res.py::_set_rewards`): `CompositeReward(key_press_reward=..., sustain_reward=..., energy_reward=...)`, plus `fingering_reward` and `forearm_reward` added unless disabled. `CompositeReward.add(self, name, reward_fn)` takes no weight argument, so the paper's stated 2/3–1/3 weighting is not visible as an explicit multiplier in the composite sum.
    - `_compute_key_press_reward`: computes `rew = 0.5*rews.mean()` (correct-key term) `+ 0.5*(1 - piano.activation[off].any())` (no-false-positive term), matching the paper's formula, but then **returns `2*rew`** — the code doubles the paper's [0,1]-range formula rather than applying the stated 2/3 weight.
    - `_compute_energy_reward` computes `power = hand.observables.actuators_power(...)`, `rew -= energy_penalty_coef * sum(power)`, but the function **`return 0`** (hardcoded), i.e. the energy term is computed and discarded — disabled in code despite being listed as a RoboPianist-style term (§2 Related Work says RoboPianist's reward has "a fingering reward, a task reward, and an energy reward").
    - `_compute_fingering_reward` computes a tolerance-based finger-to-key distance reward but **`return 0.0`** (hardcoded; the computed `rews` line is commented out) — also disabled in code.
    - `_compute_forearm_reward`: "Reward for not colliding the forearms" → returns 0.5 if no forearm-forearm collision, else 0.0.
    - `_compute_sustain_reward`: `tolerance(goal_current[-1] - piano.sustain_activation[0], bounds=(0, _KEY_CLOSE_ENOUGH_TO_PRESSED), ...)`.
    - The paper's "Mimic" term is implemented separately, not inside this task class, by `single_task/wrappers/deep_mimic.py::DeepMimicWrapper._compute_end_effector_pos_mimic_reward`, added via `self.task._reward_fn.add("end_effector_pos_mimic", ...)`: computes per-fingertip `tolerance(‖target−current‖, bounds=(0, _FINGERTIP_CLOSE_ENOUGH), margin=_FINGERTIP_CLOSE_ENOUGH*5, sigmoid="gaussian")` averaged over both hands' 5 fingertips.
  - **Mismatch noted**: paper's Table 3 lists exactly two weighted terms (Key Press 2/3, Mimic 1/3); the actual environment code sums five terms (key press ×2, sustain, energy [dead, returns 0], fingering [dead, returns 0], forearm-collision) plus a wrapper-added mimic term, with no explicit weight arguments — the paper's simplified two-term/two-weight description does not match the composite reward actually summed at run time.
  - **BC-MSE baseline** (Appendix G, distinct from the main generalist): "We train a feedforward network to predict the robot action of next timestep conditioned on the binary representation of goal and proprioception state with MSE loss." No IL loss equation is given in the paper text for the main Two-stage Diff generalist (a display-equation block after "minimize the reconstruction loss:" in Appendix E, and after the IK objective in Appendix B, is not rendered in the extracted paper md) — the generalist's training objective is stated only as "optimized with DDPM [28]" (Appendix F), i.e. the standard diffusion denoising loss; the exact formula is not present in either source.
  - key trick(s): residual policy on top of a per-timestep IK solution (§3.2, "Residual policy architecture"); style-mimicking reward as an adjustable human-likeness knob (§4.1: removing it changes F1 by only +0.03 but increases robot/human fingertip discrepancy); SDF-embedded goal representation (Appendix E); hierarchical fingertip→joint decomposition; action chunking (execute predicted action sequences "in chunks," §3.3).

## D. Contact / penetration handling
Not addressed as a measured quantity. The only contact-related reward is `_compute_forearm_reward`, which gives 0.5 for *no* forearm-forearm collision (binary, not a penetration depth) between the two hands' root-body geoms (`collision_utils.has_collision`, `single_task/piano_with_shadow_hands_res.py`). The task also exposes a `disable_hand_collisions` flag and `_disable_collisions_between_hands()` method, i.e. inter-hand collisions can be turned off in the physics rather than penalized. No hand-object interpenetration metric or penalty is defined anywhere in paper or code manifest.

## E. Evaluation
- metrics: "We use the same evaluation metrics from RoboPianist [11], i.e., precision, recall, and F1 score" (§4, "Dataset and Evaluation Metrics," p.5) — inherited from RoboPianist, not redefined; no formula for precision/recall/F1 is restated in this paper's text.
- success criterion: none stated as a scalar threshold; performance is reported purely as continuous P/R/F1 over the played clip.
- eval episodes/seeds: song-specific PPO policies "tested using 3 different seeds" (Appendix D). Specialist comparison uses "10 clips with diverse levels of difficulty" (§4.1). Generalization test set = 12 held-out clips (§4, p.5) plus, separately, the 12-song "Etude-12" set from RoboPianist [11] (Appendix I).
- sim vs. real: all results are simulation (ROBOPIANIST/MuJoCo); no real-robot trials reported.
- baselines: **Robopianist [11]** (same RL method/reward, manually labeled fingering reward) and **open-loop IK** for song-specific policies (§4.1); for distillation, **Multi-task RL** (SAC), **BC-MSE**, **One-stage Diff**, **Two-stage BeT**, **Two-stage Diff w/o SDF** (§4.2, Appendix G) — all re-run by the authors, not quoted from other papers.

## Limitations stated by the authors (§4.4)
- Inference speed: "approximately 15Hz on an RTX 4090 machine," below real-time hardware demand.
- Out-of-distribution data: performance degrades on RoboPianist's mostly-classical dataset since PianoMime's training data is mostly modern songs.
- Acoustic experience: even at up to 56% F1 on unseen songs, accuracy is "still necessary" to improve for acoustic appeal/recognizability.

## F. Reproducibility
Code released (github.com/sNiper-Qian/pianomime, commit c4abefac). README documents dataset-preparation tutorial and checkpoint download (code/md README section). Config values for PPO (Table 6) and DDPM/BeT (Tables 7–8) are given in the paper appendices; the manifest exposes only function signatures for most training/dataset code (`multi_task/dataset.py`, `multi_task/network.py`, `multi_task/utils.py`) and full bodies only for reward/observable functions in the `robopianist`/`single_task` task and wrapper files, so the diffusion training loop and BC dataset construction cannot be verified line-by-line from code/md alone. Table 1 (distillation ablation) and Table 9/10 (per-song test results) are numeric outputs the released eval scripts (`single_task/eval_ppo.py`, `multi_task/eval_low_level.py`) appear built to reproduce, but no run logs/checkpoints were inspected here.

## Quotable claims (verbatim, with section)
- "We show that we are able to learn a policy with up to 56% F1 score on unseen songs." (Abstract)
- "The resulting policy demonstrates an impressive generalization capability, achieving an average F1-score of 70% on unseen songs." (§5 Conclusion) — **inconsistent with Table 1 / Table 9** (Two-stage Diff-res test F1 mean = 0.57) and with the abstract's 56%; no reconciling number found in either source.
- "our method consistently outperforms the Robopianist baseline for all 10 clips, achieving an average F1 score of 0.94 compared to the baseline's 0.75" (§4.1, p.5); IK-only baseline reaches "0.72" (§4.1).
- Table 1 (Train/Test, P/R/F1): Two-stage Diff-res is best overall, Test F1 = 0.57 (P 0.71, R 0.55); Multi-task RL has highest test precision (0.95) "because it barely presses any keys" (§4.2).
- Table 9 (own 12-song test set): Two-stage Diff-res mean F1 = 0.57 (P 0.71, R 0.55); Table 10 (Etude-12, out-of-distribution classical songs): Two-stage Diff-res mean F1 = 0.32 (P 0.43, R 0.30).
- "Figure 8 shows the F1 score of all 184 trained song-specific policies (descending order)" (Appendix H) — 184 specialists were trained in total, more than the 60 songs / 431 clips headline count, consistent with per-clip specialists.
