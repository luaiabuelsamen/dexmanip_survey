# Outreach note — pddm_2019

## Paper
**Deep Dynamics Models for Learning Dexterous Manipulation**
Nagabandi, Konolige, Levine, Kumar — CoRL 2019 (arXiv 1909.11652)
Code: https://github.com/google-research/pddm

## The claim

Table 2 states the observation dimension for the In-hand Reorientation task is 46. The released
`cube_env.py`'s own `_get_obs` construction sums to 39 by our count of its listed fields
(`robot_pos` 24 + `object_position` 3 + `object_orientation` 3 + `object_velp` 3 + `object_velr` 3
+ `desired_orientation` 3 = 39). Separately, Table 2's printed Baoding-balls reward formula is
`−5||objects_xyz − targets_xyz|| − 500·1(is_drop)`; the released `baoding_env.py` reward computes
an additional `-10*wrist_too_high` term, triggered when the wrist angle exceeds a 0.15 threshold,
that has no row in Table 2.

## Evidence

- **Code (obs-dim):** `code/md/pddm_2019.md`, `pddm/envs/cube/cube_env.py`, method `_get_obs`
  (file header at code/md line 650; the field list and its own inline dimension comments at
  code/md lines 570 and 746: `robot_pos` #24, `object_position` #3, `object_orientation` #3,
  `object_velp` #3, `object_velr` #3, `desired_orientation` #3, summing to 39).
- **Code (reward):** `code/md/pddm_2019.md`, `pddm/envs/baoding/baoding_env.py`, method
  `get_reward` (file header at code/md line 444; the wrist term at code/md lines 526–528:
  `wrist_too_high = zeros; wrist_too_high[wrist_angle>wrist_threshold] = 1;
  self.reward_dict['wrist_angle'] = -10 * wrist_too_high`).
- **Paper:** Table 2 (App. B), observation-dimension column and reward-formula column.
- **Commit:** `06b88cdbafa7fc35451b3feb3e01aa6726113f72` (`corpus/code_manifest.json`,
  google-research/pddm).
- **Note:** `papers/notes/pddm_2019.md`, "Setting" (obs-dim mismatch) and "Method — Reward / cost
  block" (wrist term).

Two things weigh in favor of a simple bookkeeping slip rather than anything substantive: the
Valve-Turning and In-hand-Reorientation reward formulas both match Table 2 exactly once the code is
read, and the obs-dim mismatch is arithmetic (a component count), not a change in what the planner
actually optimizes.
